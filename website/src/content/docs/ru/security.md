## Как сообщить об уязвимости

Если вы обнаружили уязвимость в системе безопасности Meridian:

1. **НЕ создавайте публичный issue**
2. Отправьте закрытый отчёт через [GitHub Security Advisories](https://github.com/getmeridian/meridian/security/advisories/new)
3. Опишите шаги для воспроизведения и потенциальные последствия

Мы стараемся отвечать в течение 48 часов и благодарим авторов отчётов в описании релиза с исправлением.

## Архитектура безопасности

- **Учётные данные**: хранятся в файле `~/.config/meridian/cluster.yml` с правами доступа `0600` в каталоге с правами `0700` (доступ только у владельца). Секреты никогда не передаются в shell-команды без экранирования через `shlex.quote()` и автоматически скрываются в выводе `meridian doctor`. Любая программа, запущенная от имени вашего пользователя, может прочитать эти файлы — это общее свойство всех локальных CLI-утилит (SSH-ключей, токенов облачных провайдеров и т. п.). При компрометации вашей учётной записи локальное шифрование файла не защитит от перехвата парольной фразы или активной SSH-сессии, поэтому следите за безопасностью своего компьютера.
- **Доступ к сервису управления**: сервис управления работает за обратным прокси nginx по секретному HTTPS-пути — поднимать SSH-туннель не требуется. Страницы подключения и ссылки на подписку обслуживаются по отдельному префиксу и никогда не раскрывают секретный путь управления. Токен администратора для CLI хранится в `~/.config/meridian/cluster.yml`, а для скриптов выпускаются отдельные токены с ограниченными правами, которые можно отозвать в любой момент.
- **Веб-консоль**: рассчитана на одного владельца с паролем и необязательным одноразовым кодом (TOTP); сеанс завершается через 30 минут бездействия и максимум через 12 часов с момента входа. Для выпуска API-токенов и изменения настроек конфиденциальности требуется повторно подтвердить пароль. Через консоль управляются только пользователи и настройки конфиденциальности — в ней нет управления серверами и никогда не хранятся SSH-ключи. Консоль не делает внешних запросов и защищена строгой политикой Content Security Policy (CSP).
- **Узлы**: агенты на серверах сами устанавливают исходящее HTTPS-соединение с сервисом управления, поэтому открывать входящие порты управления на узлах не нужно. Каждый узел регистрируется по одноразовому токену и получает клиентский сертификат от внутреннего удостоверяющего центра ваших серверов. Конфигурационные документы подписываются сервисом управления; агент проверяет криптографическую подпись и отвергает любые документы со старым номером ревизии.
- **Конфиденциальность**: ограничение числа устройств и посуточная история трафика по умолчанию выключены — сервис управления хранит только общий объём трафика за всё время и время последней активности. При необходимости можно включить учёт устройств по защищённым ключом отпечаткам, полное сохранение метаданных устройств или посуточную статистику с ограниченным сроком хранения. IP-адреса клиентов, логи подключений и пути запросов не сохраняются ни в одном из режимов. Подробный разбор того, какие данные окажутся на сервере в случае его изъятия, приведён в разделе [Конфиденциальность](/ru/privacy/).
- **Резервные копии**: снимки состояния шифруются с помощью [age](https://age-encryption.org/) для ключей каждого управляющего компьютера и для ключа восстановления, закрытая часть которого хранится только у вас. В снимки не включаются ключи подписи узлов, активные сеансы и пароль от веб-консоли: при восстановлении создаются новые ключи, поэтому компрометация старого сервера управления не позволит подделать команды для восстановленных серверов.
- **SSH**: вход по паролю отключается, а защита fail2ban включается по умолчанию (флаг `--no-harden` пропускает эти шаги и настройку файрвола на серверах, где работают сторонние службы).
- **Файрвол**: UFW блокирует все входящие соединения, кроме порта SSH и портов, необходимых для роли сервера: TCP/443 для прокси-трафика, TCP/80 на серверах, выпускающих сертификаты, UDP/443 при включённом Hysteria2 и рабочего порта на промежуточных серверах.
- **Зашифрованный DNS на выходных серверах**: выходные серверы разрешают доменные имена через DNS over HTTPS (одновременно к Cloudflare, Quad9 и Google по прямым IP-адресам), не обращаясь к DNS-резолверу хостинг-провайдера, поэтому запрашиваемые домены никогда не покидают сервер в открытом виде. Если все три резолвера недоступны, запросы по доменным именам завершаются ошибкой без отката на незашифрованный DNS; команда `meridian check` покажет, какой из резолверов не отвечает.
- **Фиксация версий и проверка целостности**: сервис управления устанавливает точную версию Meridian через пакетный менеджер uv с проверкой контрольной суммы; бинарный файл агента входит в пакет Meridian; архивы Xray, Realm и RealiTLScanner привязаны к конкретным версиям и проверяются по контрольным суммам SHA-256 перед запуском.
- **TLS**: выпуск и автоматическое продление сертификатов Let's Encrypt выполняются через [acme.sh](https://github.com/acmesh-official/acme.sh), а терминация TLS — силами nginx.

## Границы ответственности

Meridian отвечает за безопасную настройку и оркестрацию серверов, но **не** разрабатывает собственные криптографические протоколы. Криптографическая защита и сетевой стек опираются на проверенные проекты:

- [Xray-core](https://github.com/XTLS/Xray-core) — реализация протоколов VLESS+Reality, XHTTP, WSS и Hysteria2
- [age](https://age-encryption.org/) (через библиотеку pyrage) — шифрование резервных снимков
- [nginx](https://nginx.org/) — маршрутизация по TLS SNI и терминация HTTPS
- [acme.sh](https://github.com/acmesh-official/acme.sh) — выпуск и продление сертификатов Let's Encrypt
- [Realm](https://github.com/zhboner/realm) — перенаправление TCP-соединений на промежуточных серверах
