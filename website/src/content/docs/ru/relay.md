## Что решают промежуточные серверы

Когда IP выходного сервера заблокирован, пользователи теряют доступ. Промежуточный сервер даёт им точку входа с отечественным IP, которую сложнее заблокировать:

```
Клиент → Промежуточный сервер (отечественный IP) → Выходной сервер (за границей) → Internet
```

Цензоры видят трафик к отечественному IP. Промежуточный сервер пересылает необработанный TCP выходному серверу; шифрование сквозное, от клиента до выхода, поэтому промежуточный сервер никогда не видит трафик в открытом виде.

## Как работают промежуточные серверы

Промежуточный сервер запускает [Realm](https://github.com/zhboner/realm), маленький TCP-форвардер с нулевым копированием. Он слушает на порту 443 (настраивается) и пересылает трафик слушателю Reality выхода. Docker и панели на промежуточном сервере нет.

Промежуточные серверы несут трафик **Reality**. XHTTP, WSS и Hysteria2 работают на собственном адресе и домене выхода и остаются в той же подписке как запасные варианты.

## Развернуть промежуточный сервер

Сначала разверните выход, затем укажите на него промежуточный сервер:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10
```

Meridian добавляет промежуточный сервер в вашу топологию и применяет её:
1. Подготавливает промежуточный сервер (пакеты, BBR, защита SSH, файрвол, который открывает только SSH и порт промежуточного сервера)
2. Устанавливает Realm (версия-закреплена, SHA256-проверена) как сервис systemd
3. Указывает промежуточный сервер на слушатель Reality выхода
4. Публикует промежуточный сервер в подписке каждого клиента

### Флаги

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--exit/-e EXIT` | (требуется) | IP или имя выходного сервера |
| `--name NAME` | (авто) | Понятное имя промежуточного сервера (например `ru-moscow`) |
| `--port/-p PORT` | 443 | Порт слушания на промежуточном сервере |
| `--sni HOST` | цель выхода | Цель маскировки Reality для этого промежуточного сервера; пропустите, чтобы использовать цель выхода |
| `--user/-u USER` | root | SSH-пользователь на промежуточном сервере |
| `--ssh-port PORT` | 22 | SSH-порт на промежуточном сервере |
| `--yes/-y` | | Пропустить диалоги подтверждения |

### Пример со всеми вариантами

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-moscow \
  --port 443 --sni dl.google.com --user ubuntu --ssh-port 2222 --yes
```

## Как клиенты подключаются

Существующие клиенты получают промежуточный сервер при следующем обновлении подписки, и их страницы подключения перечисляют его. Новые клиенты получают его автоматически:

```bash
meridian client add alice   # промежуточный сервер включён
```

## Управление промежуточными серверами

```bash
meridian relay list                       # все промежуточные серверы
meridian relay list --exit 198.51.100.10  # промежуточные серверы одного выхода
```

Проверьте звенья промежуточного сервера — что каждый сервис Realm запущен, каждое звено достукивается до следующего, а публичный порт принимает соединения — и затем проверьте прохождение трафика по всему маршруту:

```bash
meridian check 203.0.113.10
meridian test
```

Команда `check` также измеряет каждый участок: с каждого звена она скачивает главную страницу сайта маскировки выхода через следующее звено с тем же SNI, который отправляют клиенты, и показывает время установки соединения, время до первого байта и объём полученных данных. Если передача замирает в районе 8–32 КБ, это характерный признак троттлинга на этом участке (выводится предупреждение); обычно помогает перенос промежуточного сервера к другому хостинг-провайдеру (в другую сеть или ASN). Если главная страница сайта маскировки меньше 32 КБ, результат такой проверки считается неопределённым, а не успешным.

Чтобы сменить SNI маскировки промежуточного сервера (например, если `meridian test --probe` показал, что текущий SNI заблокирован), замените его одной командой. Meridian проверит, что выходной сервер открывает новый сайт, покажет план и применит изменения; старое имя сразу перестанет работать, а приложения переключатся при следующем обновлении подписки (каждые 6 часов) или при ручном обновлении. Передайте SNI самого выхода, чтобы промежуточный сервер снова следовал за SNI выхода:

```bash
meridian relay sni 203.0.113.10 dl.google.com
```

Чтобы вывести промежуточный сервер из эксплуатации, удалите цепочки через него. Meridian показывает то, что будет удалено, запрашивает подтверждение и очищает сервис Realm, правила файрвола и опубликованные точки входа; существующие клиенты теряют промежуточный сервер при следующем обновлении подписки:

```bash
meridian relay remove 203.0.113.10
```

## Несколько промежуточных серверов

Присоедините несколько промежуточных серверов к одному выходу, например в разных городах или сетях:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-moscow
meridian relay add 203.0.113.11 --exit 198.51.100.10 --name ru-spb
```

Клиенты получают каждый промежуточный сервер в своей подписке. Для цепочек промежуточных серверов с более чем одним звеном используйте `meridian setup`.

## Белые списки мобильных операторов

Во время ограничений мобильного интернета в России операторы иногда пропускают трафик только к утверждённому списку сайтов и адресов. Ситуация отличается от оператора к оператору, от региона к региону и меняется со временем, а сами списки нигде официально не публикуются. Meridian не определяет и не отслеживает белые списки автоматически; ниже описано, что можно настроить сейчас и что проверяется вручную.

### Что сообщают администраторы

- **Сети ведут себя по-разному.** Одни проверяют только имя сервера (SNI) в начале TLS-соединения, другие — ещё и IP-адрес назначения. Там, где проверяется только имя, может пройти и прямое подключение Reality с разрешённым SNI. Там, где проверяется IP-адрес, первой точкой входа должен быть адрес из белого списка.
- **Обычно первой точкой входа служит российский облачный сервер.** В белый список попадает не вся сеть провайдера: часто одна подсеть хостинга проходит, а соседняя у того же провайдера — нет. Кроме того, провайдеры могут ограничивать регистрацию физлиц, лимитировать частоту пересоздания серверов или резать скорость.
- **Зарубежные адреса CDN в мобильных сетях при таких ограничениях обычно не работают.** Рассматривайте [режим домена](/ru/domain-mode/) через Cloudflare как резервный канал для домашнего интернета, а не как решение для белых списков.
- **Канал между промежуточным сервером и зарубежным выходом тоже может блокироваться.** Даже если пользователи достучались до промежуточного сервера внутри страны, сам он может потерять связь с зарубежным выходом.

### Промежуточный сервер на разрешённом адресе

Арендуйте небольшой сервер у российского провайдера, чья подсеть проходит в мобильной сети ваших пользователей. В сообществах ведут списки подходящих диапазонов, но надёжно проверить это можно только с мобильного интернета в момент действия ограничений. Добавьте сервер как промежуточный и задайте ему разрешённое имя:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-mobile --sni allowed.example.com
```

С флагом `--sni` это имя объявляется только в записи данного промежуточного сервера в подписке. Meridian поднимает для него отдельный порт на выходе (доступный только с последнего звена цепочки) и отдельный слушатель Reality (с теми же ключами), имитирующий указанное имя. В Reality направляется только это имя, а любые другие запросы пересылаются на настоящий сайт, поэтому любая проверка без вашего ключа увидит подлинный сертификат сайта, а не прокси. Собственная цель маскировки выхода и остальные записи в подписке не меняются. Выход должен открывать указанный сайт по TLS 1.3 с HTTP/2; позже имя можно сменить командой `meridian relay sni RELAY NEW_SNI`.

Затем проверьте промежуточный сервер и протестируйте подключение из целевой сети:

```bash
meridian check 203.0.113.10
meridian test
```

Запуск `meridian test` с вашего компьютера не покажет, что пропускает мобильный оператор в режиме белых списков — проверяйте на реальном телефоне в этой сети.

### Выбор SNI для выхода

Флаг `--sni` у `meridian deploy` и `meridian node add` задаёт сайт маскировки для прямого подключения Reality к выходу. Этот сайт должен открываться с выходного сервера по TLS 1.3, а `deploy` проверяет прохождение реального трафика и останавливается, если трафик не идёт. Перед развёртыванием кандидата можно проверить командой `meridian check IP --sni HOST`. В сети, где фильтруют только по SNI, разрешённое имя может пропустить и прямое подключение, но результат зависит от конкретного оператора — проверяйте на практике.

### Чего Meridian не делает

- Не определяет, входит ли IP промежуточного сервера в белый список оператора и действуют ли сейчас ограничения.
- Не настраивает проксирование через российские CDN. Режим домена рассчитан и протестирован для Cloudflare.
- Через промежуточный сервер идёт только Reality. XHTTP, WSS и Hysteria2 работают напрямую с выходом.
- Не строит туннели поверх сторонних сервисов звонков или мессенджеров.

## Устранение неполадок

### Конфликт портов

Другой сервис использует порт слушания на промежуточном сервере. Проверьте с `ss -tlnp sport = :443` и остановите его или выберите другой порт с `--port 8443`.

### Блокировка файрволом

Убедитесь, что порт промежуточного сервера открыт в файрволе вашего облачного провайдера или группе безопасности, а не только в UFW.

### Выход недостижим

Промежуточный сервер должен достичь порта Reality выхода. Запустите `meridian test` для сквозной проверки маршрута и `meridian check EXIT` для проверки самого выхода.

### Промежуточный сервер не работает

На промежуточном сервере выведите сервисы форвардера и прочитайте их логи. Промежуточные серверы используют нейтральные имена (модули `netfwd-*`, конфиги `/etc/netfwd/`), поэтому ничто на них не называет Meridian, Realm или промежуточный сервер:

```bash
systemctl list-units 'netfwd-*'
journalctl -u 'netfwd-*' --no-pager -n 20
```
