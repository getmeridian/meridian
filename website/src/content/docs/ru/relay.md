## Что решают ретрансляторы

Когда IP вашего exit-сервера блокируется, клиенты теряют доступ. Узел-ретранслятор даёт им отечественную точку входа, которую сложнее блокировать:

```
Клиент → Ретранслятор (отечественный IP) → Exit-сервер (за границей) → Интернет
```

Цензоры видят трафик на отечественный IP. Ретранслятор пересылает чистый TCP на exit-сервер — всё шифрование end-to-end между клиентом и exit-сервером. Ретранслятор никогда не видит открытый текст.

## Как работают ретрансляторы

Ретранслятор использует [Realm](https://github.com/zhboner/realm) — лёгкий TCP-forwarder с нулевым копированием (~5МБ бинарный файл Rust). Он слушает порт 443 (настраивается) и пересылает весь трафик на порт 443 exit-сервера. Нет Docker, нет VPN-ПО, нет управляющей панели.

Legacy Realm-ретрансляторы публикуют только **Reality**. Их выделенный SNI-маршрут завершается на Reality inbound выходного сервера, а HTTP-транспортам нужна собственная маршрутизация по host/path. Прямые XHTTP и WSS остаются резервными вариантами в той же подписке.

В V4 ретранслятор является цепочкой в `topology_intent`: каждый hop имеет сохранённую серверную идентичность, а entry hop может рекламироваться клиентам. Внутренние hop'ы не считаются проверенными только потому, что entry listener доступен.

## Развёртывание ретранслятора

Сначала разверните exit-сервер нормально. Затем разверните ретранслятор, указав на него:

```bash
meridian relay deploy RELAY_IP --exit EXIT_IP
```

В legacy-режиме provisioner:
1. Устанавливает требуемые пакеты и включает BBR
2. Настраивает firewall UFW (разрешение SSH + порт ретранслятора)
3. Загружает бинарный файл Realm (версия закреплена, SHA256-проверен)
4. Пишет конфиг Realm и запускает systemd-сервис
5. Проверяет связь ретранслятор → exit

### Флаги

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--exit/-e EXIT` | (требуется) | IP или имя exit-сервера |
| `--name NAME` | (авто) | Дружественное имя ретранслятора (например, `ru-moscow`) |
| `--port/-p PORT` | 443 | Порт прослушивания на ретрансляторе |
| `--sni HOST` | (авто) | Локальная для ретранслятора цель маскировки Reality |
| `--user/-u USER` | root | SSH-пользователь на ретрансляторе |
| `--ssh-port PORT` | 22 | SSH-порт сервера ретранслятора |
| `--yes/-y` | | Пропустить подтверждающие подсказки |

В legacy отсутствие `--sni` запускает RealiTLScanner на IPv4-сети ретранслятора. В V4 `--exit` должен однозначно указывать существующий exit из intent, команда добавляет цепочку и сразу применяет план, а пустой `--sni` наследует Reality-маршрут exit.

### Пример со всеми параметрами

```bash
meridian relay deploy 203.0.113.10 --exit 198.51.100.10 --name ru-moscow \
  --port 443 --sni www.microsoft.com --user ubuntu --ssh-port 2222 --yes
```

## Как подключаются клиенты

После развёртывания Meridian создаёт для ретранслятора записи хостов Remnawave. Они появляются у существующих клиентов при следующем обновлении подписки; прямые подключения остаются резервными.

Когда вы добавляете новых клиентов, URL-адреса ретранслятора включаются автоматически:

```bash
meridian client add alice   # хосты ретранслятора уже включены в подписку
```

## Управление ретрансляторами

```bash
meridian relay list                    # все ретрансляторы на всех exit-серверах
meridian relay list --exit 198.51.100.10     # ретрансляторы для конкретного exit
meridian relay check RELAY_IP          # проверки ретранслятора и панели
meridian relay remove RELAY_IP         # остановить сервис + удалить из конфига
```

`relay list` отображает и legacy-записи, и проекцию V4. `relay check` и `relay remove` предназначены только для legacy Realm-ретрансляторов. Для V4 они намеренно отклоняются: полную цепочку проверяйте `meridian test`, а удаление просматривайте в `meridian setup` и применяйте как изменение intent.

### Проверка здоровья

Для legacy `meridian relay check` тестирует путь ретранслятора и его регистрацию в панели:

| Проверка | Что тестируется |
|-------|---------------|
| SSH к ретранслятору | Можно ли подключиться к серверу ретранслятора? |
| Сервис Realm | Активен ли systemd-сервис? |
| Ретранслятор → exit TCP | Может ли ретранслятор достичь exit-сервера на порту 443? |
| Локально → ретранслятор TCP | Может ли ваша машина достичь ретранслятора на его порту прослушивания? |
| Хосты панели | Существуют и включены ли записи хостов ретранслятора в Remnawave? |

Код `0` означает здоровое состояние, `4` — завершённые проверки с проблемами, `3` — недоступность обязательных данных SSH или панели.

`meridian fleet status` проверяет публичный ретранслятор только TCP-подключением к listener. Это не доказательство прохождения proxy-трафика. Внутренние V4 hop'ы остаются `unknown`, поэтому флот может вернуть код `3`, пока end-to-end маршрут не проверен отдельно.

### Удаление ретранслятора

```bash
meridian relay remove RELAY_IP [--exit EXIT_IP] [--yes]
```

Legacy-команда останавливает и удаляет сервис Realm, binary и config, точное правило UFW, nginx routing на exit и Host-записи Remnawave. Запись в `cluster.yml` сохраняется как возможность повтора, пока вся удалённая очистка не завершится успешно. После обновления подписки у клиентов останутся только актуальные варианты подключения.

## Несколько ретрансляторов

Вы можете присоединить несколько ретрансляторов к одному exit-серверу — например, ретрансляторы в разных городах или ISP:

```bash
meridian relay deploy 203.0.113.10 --exit 198.51.100.10 --name ru-moscow
meridian relay deploy 203.0.113.11 --exit 198.51.100.10 --name ru-spb
```

Клиенты получают все варианты ретрансляторов в подписке.

## Решение проблем

### Конфликт портов

Другой сервис использует порт 443 на ретрансляторе. Проверьте с помощью `ss -tlnp sport = :443` и остановите конфликтующий сервис, или используйте другой порт с `--port 8443`.

### Блокирование firewall

Убедитесь, что порт 443 открыт на firewall облачного провайдера ретранслятора / группе безопасности, не только в UFW.

### Exit-сервер недостижим

Ретранслятор должен достигать exit-сервера на TCP/443. Для legacy запустите `meridian relay check`; для V4 используйте `meridian test`, поскольку отдельная проверка hop'а ещё не подтверждает канонический маршрут клиента.

### Сервис ретранслятора не запущен

Проверьте сервис Realm: `systemctl status meridian-relay`. Посмотрите логи: `journalctl -u meridian-relay --no-pager -n 20`.
