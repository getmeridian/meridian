## Команды

### meridian deploy

Развернуть один сервер и получить ссылку для обмена подключением. Сервер становится и контроль-планом (панель Remnawave), и выходом. Deploy строит ту же рассмотренную топологию, что и `meridian setup`, применяет её с контрольными точками, проверяет реальный трафик через доставленную подписку и выводит страницу подключения и URL подписки. Повторный запуск того же команды возобновляет прерванное развёртывание или переразворачивает, сохраняя пути, ключи и пользователей.

```
meridian deploy [SERVER] [flags]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--sni HOST` | (авто) | Цель маскировки. Без него сервер пытается `www.google.com`, `dl.google.com`, `www.cloudflare.com` и использует первый, который несёт трафик; переразворачивание сохраняет сохранённую цель. Явный `--sni` никогда не меняется |
| `--domain DOMAIN` | (нет) | Ваш домен для XHTTP и WSS (возврат CDN Cloudflare). Панель и страницы подключения остаются на IP-сертификате |
| `--hysteria2` | отключен | Также предлагать Hysteria2 на UDP/443. Требует `--domain`; QUIC дросселируется в некоторых регионах |
| `--fingerprint NAME` | chrome | Отпечаток TLS, который клиенты показывают на Reality, XHTTP и WSS (`chrome`, `firefox`, `safari`, `ios`, `android`, `edge`, `random`, `randomized`). Измените его, если ваш регион начнёт флагировать текущий; переразворачивание сохраняет сохранённое значение |
| `--client-name NAME` | default | Имя первого клиента |
| `--display-name NAME` | (нет) | Ярлык для страниц подключения |
| `--icon EMOJI_OR_URL` | (нет) | Значок страницы — эмодзи или URL изображения |
| `--color PALETTE` | ocean | Тема цвета страницы (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | сохранено, иначе root | SSH пользователь (не-root требует passwordless sudo) |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт |
| `--harden / --no-harden` | вкл | SSH только по ключу, fail2ban и брандмауэр UFW. `--no-harden` для серверов, общих с другими сервисами |
| `--warp / --no-warp` | выкл | Отправлять исходящий трафик через Cloudflare WARP |
| `--geo-block` / `--no-geo-block` | вкл | Блокировать российские домены и IP (`geosite:category-ru` + `geoip:ru`) на выходе. Xray JSON и Mihomo подписки уже отправляют их напрямую с устройства |
| `--yes` | | Пропустить диалоги подтверждения |
| `--json` | | Выдать окончательный результат развёртывания как конверт `meridian.output/v1` |
| `--events=jsonl` | | Потоком передавать типизированные события прогресса как JSONL на stderr |
| `--request FILE` | | Прочитать `deploy-request` JSON от файла; используйте `-` для stdin |
| `--dry-run` | | Компилировать и просмотреть развёртывание без SSH или локальных изменений |

Без IP, deploy запрашивает его. `local` развёртывает на машине, на которой вы находитесь. Deploy только переразворачивает сервер, который уже является выходом во вашем флоте; добавляйте другие серверы с помощью `meridian node add`. Изменения дополняющие: удаление уже развёрнутого (например, отпадение `--domain`) отклоняется.

**Поток машина/UI**: `meridian api workflow deploy --json` возвращает отрисовываемый контракт мастера. UI собирает эти поля, проверяет их против `deploy-request`, затем запускает `meridian deploy --request deploy.json --json --events=jsonl`. Машинные развёртывания неинтерактивны: запрос должен содержать `yes: true` после подтверждения пользователем. `--dry-run --json` возвращает `deploy-plan` под `data`, чтобы UI мог просмотреть режим, порты и сгенерированные пути перед открытием SSH.

### meridian setup

Настроить несколько серверов с возобновляемым пошаговым мастером: выходы, прозрачные цепи ретранслятора Realm, маршрутизирующие шлюзы с пулами отказоустойчивости и пользователи доступа.

```
meridian setup [--intent FILE|-] [--restart] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--intent FILE` | (нет) | Начать с проверки из полного документа JSON топологии; используйте `-` для stdin |
| `--restart` | | Отбросить сохранённый прогресс настройки перед запуском |
| `--yes`, `-y` | | Одобрить проверку и применить без запроса |

Мастер проходит по серверам, ролям, путям протокола, маршрутизации, доступу, проверке и применению. На любом запросе вы можете ввести `back`, `details`, `save` или `quit`. Прогресс сохраняется в `~/.meridian/setup.json` после каждого этапа, поэтому запуск `meridian setup` снова возобновляет; пароли и приватные ключи никогда не сохраняются там. `--intent` не заменяет существующий черновик, если `--restart` также не указан. Когда применение успешно, setup проверяет каждый узел и подписку и выводит страницу подключения каждого пользователя.

### meridian plan

Показать, что изменит `meridian apply`, сравнивая топологию в `~/.meridian/cluster.yml` с живыми серверами и панелью. Ничего не меняется.

```
meridian plan [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать план как конверт `meridian.output/v1` для CI и UI клиентов |

Вывод показывает хеш плана, подсчёты ресурсов по типам и любые ресурсы, которые нужно исправить или не удалось наблюдать. JSON `data` содержит `plan_hash`, `converged`, `resources[]`, `drifted_resources[]`, `observation_errors[]` и `state_changes[]`.

**Коды выхода**:
- `0` — сходится, нечего делать
- `1` — нечего планировать (нет флота, или неиспользуемое локальное состояние)
- `2` — ожидающие изменения (запустите `meridian apply`)
- `3` — требуемые доказательства (панель, SSH, локальное состояние) были недоступны

Не редактируйте топологию в `cluster.yml` вручную. Измените её с помощью `meridian setup`, `deploy`, `client add`, `node add` или `relay add`.

### meridian apply

Применить рассмотренную топологию в `cluster.yml` на ваши серверы. Apply показывает хеш плана и подсчёт ресурсов, просит подтверждение, затем применяет точный показанный план с контрольными точками. Прерванное применение возобновляется там, где остановилось.

```
meridian apply [--yes] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--yes`, `-y` | | Пропустить подтверждение |
| `--json` | | Выдать окончательный результат применения как конверт `meridian.output/v1` |

JSON `data` содержит `plan_hash`, `generation` и `actions[]` с `status: "converged" | "applied" | "failed" | "unknown" | "skipped"`. JSON режим никогда не спрашивает: без `--yes` возвращает `MERIDIAN_CONFIRMATION_REQUIRED` с хешем плана и выходит `2`. Неудавшийся ресурс выходит `3`; исправьте причину и снова запустите apply. Если локальное состояние не может быть сохранено после удалённых изменений, apply выходит `3` и говорит это; исправьте разрешения `~/.meridian`, затем запустите `plan` и `apply` снова.

Удаление пользователей или путей протокола применяется: удалённые ресурсы удаляются после того как всё, что осталось в плане, сходится, и `plan` выводит их первыми. Удаление выхода, ретранслятора или маршрутизирующего шлюза отказывается пока.

### meridian client

Управлять людьми, которые подключаются.

```
meridian client add NAME [NAME...] [--json]
meridian client show NAME [--repair-page] [--json]
meridian client list [--json]
meridian client enable NAME [--json]
meridian client disable NAME [--json]
meridian client remove NAME [--yes] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать результат как конверт `meridian.output/v1` (все команды client) |
| `--repair-page` | | Переопубликовать страницу подключения клиента (`client show`) |
| `--yes`, `-y` | | Подтвердить `client remove`; требуется с `--json` |

**`client add`** — добавляет одного или нескольких людей в топологию, применяет её и выводит страницу подключения и URL подписки каждого человека. Страница строится из их подлинной подписки, поэтому ретрансляторы и Hysteria2 появляются при наличии. Имена уже в топологии или уже в панели отклоняются. Если ссылка подписки клиента не может быть построена, клиент всё ещё добавляется и команда выходит `3`; отсутствующая страница подключения одна — это предупреждение (исправьте её с помощью `client show --repair-page`).

**`client show`** — выводит страницу подключения, URL подписки, статус, трафик и время последнего видения. `--repair-page` переопубликовывает отсутствующую страницу; если это не удаётся, ссылки всё ещё показаны с предупреждением и выходом `3`.

**`client list`** — выводит клиентов со статусом, трафиком, временем создания и последним временем видения. С `--json` возвращает подсчёты `data.summary` и `data.clients[]`.

**`client enable` / `client disable`** — возобновить или приостановить клиента немедленно. Отключение длится до следующего применения (включая переразворачивания и `client add`, `node add`, `relay add`), которое снова включает каждого объявленного клиента.

**`client remove`** — удаляет клиента из топологии, удаляет пользователя панели и его страницу подключения. Запрашивает подтверждение, если не дан `--yes`. Последний клиент не может быть удалён. Не удаляйте пользователей в панели напрямую; Meridian воссоздаёт любого клиента, который осталась в топологии, при следующем применении.

### meridian server

Управлять сохранёнными SSH серверами (`~/.meridian/servers.json`).

```
meridian server add [USER@]IP[:PORT]|local [--name NAME] [--user USER] [--ssh-port PORT]
meridian server list
meridian server remove NAME_OR_IP [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (нет) | Имя для отображения сервера |
| `--user/-u USER` | root | SSH пользователь |
| `--ssh-port PORT` | 22 | SSH порт |
| `--yes`, `-y` | | Пропустить подтверждение удаления (`server remove`) |

Имена и адреса должны быть уникальны; `server add` отклоняет коллизии вместо переориентирования существующего сервера. `server remove` удаляет только сохранённый профиль и отклоняет, пока сервер всё ещё имеет роль в вашей топологии.

### meridian node

Управлять серверами выхода. Первый сервер развёртывается с помощью `meridian deploy` (или `meridian setup`); добавляйте дополнительные выходы с помощью `meridian node add`.

```
meridian node add [USER@]IP[:PORT] [flags]
meridian node list [--json]
meridian node remove NAME_OR_IP [--yes] [--force]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (авто) | Дружественное имя для узла |
| `--user USER` | сохранено, иначе root | SSH пользователь на узле |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт на узле (`node add`) |
| `--sni HOST` | www.google.com | Цель маскировки Reality для этого узла |
| `--domain DOMAIN` | (нет) | Домен узла; добавляет пути XHTTP, WSS и Hysteria2 на него |
| `--harden / --no-harden` | вкл | Затвердевание ОС, SSH и брандмауэра. Серверы флота всегда его сохраняют; `--no-harden` отклоняется |
| `--yes` | | Пропустить диалоги подтверждения |
| `--force` | | `node remove`: также удалить цепи ретрансляторов, которые маршрутизируют к этому выходу |
| `--json` | | Выдать `node list` как конверт `meridian.output/v1` |

**`node add`** — подключается по SSH, добавляет сервер как выход в вашу топологию и применяет рассмотренный план (затвердевание, Docker, Xray, регистрация панели). Существующие клиенты получают новый выход при следующем обновлении подписки.

**`node list`** — выводит узлы с живым статусом панели, версией Xray и трафиком. Если статус панели недоступен, настроенные узлы показаны как `unknown` и команда выходит `3`.

**`node remove`** — удаляет выход или маршрутизирующий шлюз из вашей топологии. Выводит каждый ресурс, который будет удален (панель узла и профиль, контейнер узла, правила брандмауэра, опубликованные Hosts), запрашивает подтверждение и применяет именно это рассмотрение; сервер остается в сохраненных серверах. Отклоняется для контрольного сервера (используйте `meridian teardown`), пока ретрансляторы все еще маршрутизируют к выходу (удалите их сначала или передайте `--force`), пока маршрутизирующий шлюз входит в флот через него, и когда результат нарушит топологию (например пустой пул исходящих связей или исходящий выход по умолчанию). Правила маршрутизации, ограниченные удаленным шлюзом, удаляются с ним.

### meridian relay

Управлять ретрансляторами — TCP форвардерами Realm, которые дают пользователям внутреннюю точку входа на выход за границей. Ретрансляторы несут трафик Reality.

```
meridian relay add [USER@]RELAY_IP[:PORT] --exit EXIT [flags]
meridian relay list [--exit EXIT] [--json]
meridian relay remove RELAY [--exit EXIT] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--exit/-e EXIT` | (требуется для add) | IP или имя сервера выхода |
| `--name NAME` | (авто) | Дружественное имя для ретранслятора (например, "ru-moscow") |
| `--port/-p PORT` | 443 | Портслушания на сервере ретранслятора |
| `--sni HOST` | цель выхода | Цель маскировки Reality для этого ретранслятора; пропустите, чтобы использовать цель выхода |
| `--user/-u USER` | сохранено, иначе root | SSH пользователь на ретрансляторе |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт на сервере ретранслятора (`relay add`) |
| `--yes/-y` | | Пропустить диалоги подтверждения |
| `--json` | | Выдать `relay list` (`data.relays[]`) как конверт `meridian.output/v1` |

**`relay add`** — добавляет одноузловой ретранслятор в вашу топологию и применяет её. Клиенты получают его при следующем обновлении подписки. Для цепей с несколькими узлами используйте `meridian setup`.

**`relay remove`** — `RELAY` это IP ретранслятора или сохраненное имя, или ID цепи ретранслятора. Отбрасывает каждую цепь через этот сервер (сузить с `--exit`), выводит то, что будет удалено (Realm юниты, правила брандмауэра, слушатель со стороны выхода, опубликованные Hosts), подтверждает и применяет рассмотренное удаление. Серверы остаются в сохраненных серверах.

Для проверки хопов ретранслятора запустите `meridian check RELAY`.

### meridian fleet

Здоровье флота и инвентарь с живой панели.

```
meridian fleet status [--json]
meridian fleet inventory [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать результат как конверт `meridian.output/v1` |

**`fleet status`** — здоровье панели, биения сердца узла, слушатели ретранслятора и подсчёты клиентов. Отсутствующие или неактивные объявленные клиенты понижают здоровье. Достижимый слушатель ретранслятора только доказывает TCP, поэтому непроверенные маршруты ретранслятора сохраняют здоровье `unknown`; используйте `meridian test` для проверки полного пути. Выход `0` означает здоровый, `4` понижение и `3` неизвестный.

**`fleet inventory`** — ваши настроенные серверы, роли, узлы и ретрансляторы с живым статусом панели при достижимости. Никогда не выводит токен API панели или секретные пути. Если живой статус недоступен, настроенный инвентарь всё ещё показан с предупреждениями и команда выходит `3`. Используйте `plan --json` для решения, имеет ли apply работу.

### meridian check

Проверить здоровье сервера, или сможет ли новый сервер запустить Meridian. Что проверяется зависит от роли сервера в вашем флоте:

- **Ещё не в флоте** — проверки перед развёртыванием: достижимость цели маскировки и DNS, доступность и внешняя достижимость портов 443, DNS домена, ОС, диск и часы. Ничего не установлено; кратосрочный слушатель тестирует брандмауэр, когда порт 443 свободен. DNS использует собственный разрешитель сервера.
- **Контроль, выход или шлюз маршрутизации** — подключение панели, SSH (или локальный доступ), контейнеры (включая здоровье страницы подписки), все скомпилированные публичные и внутренние порты, TLS сертификаты и дисковое пространство.
- **Ретранслятор** — каждый хоп Realm на сервере: сервис активен и может достичь следующего хопа, и публичный вход цепи принимает TCP с вашей машины.

Без сервера, каждый сервер в флоте проверяется.

```
meridian check [SERVER] [--domain NAME] [--sni HOST] [--user USER]
               [--ssh-port PORT] [--ai] [--json]
```

`--domain` и `--sni` применяются к серверам, ещё не развёрнутым: проверяют, что домен разрешается на сервер и что конкретная цель маскировки достижима. `--user` и `--ssh-port` переопределяют сохранённого SSH пользователя и порт. `--ai` копирует готовый для AI диагностический запрос в буфер обмена. `--json` выводит один конверт `meridian.output/v1` с отчётом по сервёрам и областям.

Отсутствующие доказательства никогда не рассматриваются как успех. Выход `0` означает, что все проверки прошли, `4` означает найденные проблемы, `3` означает требуемые доказательства были недоступны, и `2` означает недопустимый ввод. Каждая неудача выводит её исправление. Используйте `meridian test` для передачи реального трафика через весь маршрут.

Старые команды `preflight`, `node check` и `relay check` всё ещё работают на этом релизе.

### meridian scan

Найти цели маскировки на собственной сети сервера, используя закреплённый выпуск RealiTLScanner. Meridian проверяет его SHA-256 контрольную сумму перед запуском и удаляет удалённое рабочее пространство после этого.

```
meridian scan [SERVER] [--user USER] [--ssh-port PORT]
```

RealiTLScanner сканирует IPv4 диапазоны; IPv6-только сервер выходит `3`. Выбор результата выводит команду для его использования — он не изменяет развёрнутую топологию. Пропуск выходит `0`, недопустимый выбор выходит `2`, нет подходящих целей выходит `4` и сканер или ошибки загрузки выходят `3`.

### meridian test

Протестировать доставленный прокси-трафик с вашего устройства. SSH не требуется.

Полный тест выбирает активного клиента, получает точный JSON Xray, который Remnawave доставляет им, и пропускает реальный трафик через автоматический возврат и через каждый путь целевого сервера. Первый запуск может потратить до 120 секунд на загрузку и проверку закреплённого времени выполнения Xray. Проверки трафика вращают независимых наблюдателей IP и сравнивают их с прямым запросом, поэтому отключение наблюдателя неубедительно вместо ложной неудачи. `MERIDIAN_CONNECT_TEST_URL` переопределяет наблюдателя для контролируемых окружений.

Отключение панели, HTTP `429` или HTTP `5xx` делает подписку недоступной, поэтому запуск выходит `3`. Любое другое отклонение подписки, такое как `400` или `422`, это завершённый отказ и выходит `4`.

```
meridian test [SERVER|DOMAIN] [--domain NAME] [--sni NAME]
              [--client NAME] [--basic] [--probe] [--timeout SECONDS] [--json]
```

`--client` тестирует конкретного активного клиента. `--basic` запускает только сетевые и TLS проверки без загрузки Xray и не может проверить пути только UDP; не может быть объединено с `--client` (выход `2`). `--timeout` (по умолчанию `5`, диапазон `1`–`30`) ограничивает каждую сетевую операцию, отдельно от первой загрузки Xray.

Выход `0` означает каждая проверка прошла, `4` означает тест нашёл проблемы и `3` означает требуемые доказательства были недоступны. `--json` выдаёт конверт `meridian.output/v1` с каждой проверкой и находкой.

#### Взгляд цензора: `meridian test --probe`

`--probe` смотрит на сервер так, как активный зондировщик, чтобы проверить, раскрывает ли развёртывание себя, вместо отправки трафика. Работает на любом IP или домене и применяет более строгие проверки, когда цель принадлежит вашей сохранённой топологии.

Проверки следуют реальному развёртыванию: публичное и внутреннее раскрытие портов, поведение HTTP/TLS, консистентность и маскировка SNI, обычные пути прокси и панели, улучшения WebSocket, обратный DNS, HTTP/2, устаревшие версии TLS и настроенные домены. `--sni` переопределяет SNI для общих TLS зондов. Слушатели только UDP сообщаются как нуждающиеся в полной `meridian test` вместо предположения. `--probe` не может быть объединён с `--basic`, `--client` или `--domain`. Коды выхода такие же как `test`; пропущенные проверки никогда не сообщаются как прохождения. Старая команда `meridian probe` всё ещё работает на этом релизе.

### meridian doctor

Собрать системные диагностики для отчётов об ошибках. Псевдоним: `meridian rage`.

```
meridian doctor [SERVER] [--sni HOST] [--user USER] [--ssh-port PORT] [--ai]
```

`--sni` выбирает цель маскировки для диагностики, `--user` и `--ssh-port` переопределяют сохранённого SSH пользователя и порт, и `--ai` копирует отредактированный, готовый к AI отчёт в буфер обмена вместо печати шаблона проблемы.

Doctor следует ролям сервера: сервер только ретранслятора не диагностируется как выход, и маршрутизирующие шлюзы помечены отдельно. Отсутствующие инструменты или потерянное SSH подключение делают отчёт неубедительным (выход `3`); уже собранные секции всё ещё показаны.

### meridian teardown

Удалить Meridian с сервера.

```
meridian teardown [SERVER] [--user USER] [--ssh-port PORT] [--yes]
```

При одиночном развёртывании сервера, teardown удаляет всё: панель, узел, конфигурацию nginx, сертификаты, ретрансляторы и правила брандмауэра на сервере (Docker и системные пакеты остаются), затем локальный `cluster.yml` и сохранённый профиль сервера. Также удаляет 3x-ui из Meridian 3.x. В многосерверном флоте, teardown отклоняет сервер, который всё ещё имеет роль в топологии.

`--yes` пропускает подтверждение; проверки ролей всё ещё запускаются первыми. Отклонение выходит `1`. Неизвестное имя сервера, или ноль или несколько возможных целей выходит `2` вместо запроса.

### meridian update

Обновить CLI на последний выпуск своей основной версии на PyPI. Новая основная версия только анонсируется; `--major` переходит на неё после прочтения вами заметок о выпуске. Бета-версия следует за более новыми бета-версиями своей основной версии, а затем стабильным выпуском. Meridian пытается uv, pipx и pip, и только сообщает успех, когда активная команда `meridian` показывает новую версию. Выход `0` означает уже текущий или обновлённый; `3` означает обновление или его проверка не удалась. Обновление CLI не изменяет ваши серверы.

```
meridian update [--major]
```

### meridian studio

Открыть Meridian Studio, экспериментальный браузерный UI, с его локальным Engine API. Сервер привязывается только к `127.0.0.1`.

```
meridian studio [--port PORT] [--assets-dir DIRECTORY] [--no-open]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--port PORT` | 0 | Локальный порт 0 по 65535; `0` выбирает свободный высокий порт |
| `--assets-dir DIRECTORY` | упакованные ресурсы | Использовать встроенный директорий ресурсов Studio вместо упакованной копии |
| `--no-open` | | Выводить локальный URL без открытия браузера |

Studio падает чётко, если порт занят или ресурсы отсутствуют. Явный директорий ресурсов должен содержать `studio/index.html`.

### meridian api

Проверить машиночитаемые контракты позади JSON вывода для скриптов и UI клиентов.

```
meridian api schemas [--json] [--include-schemas]
meridian api commands [--json] [--include-schemas]
meridian api schema NAME [--envelope|--json]
meridian api workflow NAME [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать каталог как конверт `meridian.output/v1` |
| `--include-schemas` | | Включить полные JSON Schemas (подразумевает JSON вывод) для `api schemas` или `api commands` |
| `--envelope`, `--json` | | Обернуть `api schema NAME` в конверт `meridian.output/v1` вместо вывода сырой схемы |

**`api schemas`** — выводит имена схем, такие как `output-envelope`, `deploy-request`, `deploy-result`, `deploy-plan`, `plan-envelope`, `apply-envelope`, `client-list-envelope`, `fleet-status-envelope` и `event`.

**`api commands`** — выводит контракты команд: argv, схемы конверта и данных, возможные статусы и результаты, значения кодов выхода, машинные флаги и `interrupt_behavior`. Ctrl-C выходит `130` без конверта JSON (`interrupt_behavior: "exit_130_without_envelope"`).

**`api schema NAME`** — выводит одну JSON Schema, например `meridian api schema output-envelope`.

**`api workflow NAME`** — выводит отрисовываемый UI поток работы, например `meridian api workflow deploy --json`.

## Глобальные параметры

Глобальные параметры идут перед командой, например `meridian --quiet doctor`. Параметры команд, такие как `test --json`, идут после неё.

| Флаг | Описание |
|------|-------------|
| `--version`, `-v` | Показать версию CLI и выйти |
| `--verbose` | Включить отладочное логирование |
| `--quiet`, `-q` | Подавить вывод прогресса |
| `--json` | Запросить конверт JSON из команды, которая его поддерживает; другие команды явно падают |
| `--install-completion` | Установить завершение оболочки для текущей оболочки |
| `--show-completion` | Выводить скрипт завершения для текущей оболочки |

JSON вывод использует конверт `meridian.output/v1` (`schema`, `command`, `operation_id`, `status`, `summary`, `data`, `warnings`, `errors`). Он поддерживается развёртыванием, планом, применением, тестом, зондом, всеми командами client, статусом/инвентарём флота, списками узла/ретранслятора и командами api. Секреты отредактированы перед выходом JSON из процесса. Запустите `meridian api commands --json` для открытия контрактов.

## Обычные параметры сервера

Они повторяются по командам; каждая команда принимает только параметры, указанные в её собственном разделе.

| Флаг | Использовано |
|------|---------|
| `SERVER` аргумент | deploy, check, scan, test, doctor, teardown, node add, relay add, server add |
| `--user`, `-u USER` | deploy, check, node add, relay add, server add, scan, doctor, teardown |
| `--ssh-port PORT` | deploy, check, node add, relay add, server add, scan, doctor, teardown |
| `--sni HOST` | deploy, check, node add, relay add, test, doctor |
| `--domain DOMAIN` | deploy, check, node add, test |

Команды client используют API панели напрямую и не принимают сервер. `test` запускается с вашего устройства и не использует SSH.

## Разрешение сервера

Сервер указывается первым, как в `ssh`: IP, сохранённое имя, `user@host:port` или `local` — запуск на текущей машине без SSH. `--user` и `--ssh-port` дополняют то, чего нет в цели, и не должны ей противоречить. Пустой пользователь или порт означают сохранённое значение, а если его нет — `root` и `22`. Без сервера Meridian использует локальный режим (при запуске на развёрнутом сервере) или единственный сохранённый сервер. Если кандидатов нет или их несколько, команда завершается с кодом `2`, а не задаёт вопрос. Старый флаг `--server NAME` по-прежнему работает.
