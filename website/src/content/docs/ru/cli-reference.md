## Команды

### meridian setup

Настроить полную топологию V4 с помощью возобновляемого пошагового мастера.

```
meridian setup [--intent FILE|-] [--restart] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|--------------|----------|
| `--intent FILE` | (нет) | Начать с проверки полного JSON-документа `SetupIntent`; `-` читает stdin |
| `--restart` | | Явно удалить сохранённый прогресс перед запуском |
| `--yes`, `-y` | | Одобрить проверенный план и применить его без дополнительного подтверждения |

Setup сохраняет контрольные точки без секретов в `~/.meridian/setup.json`, поэтому повторный запуск продолжает последний завершённый этап. Учётные данные и закрытые ключи в черновик не записываются. Существующий черновик не заменяется через `--intent` без `--restart`.

### meridian deploy

Развернуть прокси-сервер на VPS.

```
meridian deploy [IP] [flags]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--sni HOST` | www.microsoft.com | Сайт, который Reality маскирует |
| `--domain DOMAIN` | (нет) | Резервный домен Cloudflare CDN |
| `--client-name NAME` | default | Имя для первого клиента |
| `--display-name NAME` | (нет) | Ярлык для страниц подключения |
| `--icon EMOJI_OR_URL` | (нет) | Значок страницы — эмодзи или URL изображения |
| `--color PALETTE` | ocean | Цветовая палитра (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | root | SSH пользователь |
| `--harden / --no-harden` | включен | Защита SSH + файрвол |
| `--warp / --no-warp` | выключен | Маршрутизировать исходящий трафик через Cloudflare WARP |
| `--server NAME` | | Целевой сервер (имя или IP) |
| `--geo-block` / `--no-geo-block` | включен | Блокировать российские домены и IP (geosite:category-ru + geoip:ru) |
| `--ssh-port PORT` | 22 | SSH порт (если нестандартный) |
| `--yes` | | Пропустить подтверждающие диалоги |
| `--json` | | Выдать окончательный результат развёртывания в виде конверта `meridian.output/v1` |
| `--events=jsonl` | | Потоком выдавать типизированные события прогресса как JSONL на stderr |
| `--request FILE` | | Прочитать JSON-полезную нагрузку `deploy-request` из файла; используйте `-` для stdin |
| `--dry-run` | | Проверить и спланировать развёртывание без SSH или изменения панели |

**Поток машина/UI**: `meridian api workflow deploy --json` возвращает контракт отрисовки мастера. UI собирает эти поля, проверяет их против `deploy-request`, затем запускает `meridian deploy --request deploy.json --json --events=jsonl`. Машинные развёртывания неинтерактивны: запрос должен содержать `yes: true` после подтверждения пользователем. `--dry-run --json` возвращает `deploy-plan` в `data` чтобы UI мог просмотреть режим, порты и сгенерированные пути перед открытием SSH.

### meridian client

Управление ключами доступа клиента и данными подключения.

```
meridian client add NAME [NAME...]  [--json]
meridian client show NAME [--repair-page] [--json]
meridian client list [--json]
meridian client remove NAME [--yes] [--json]
meridian client enable NAME [--json]
meridian client disable NAME [--json]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--json` | | Выдать результат в виде конверта `meridian.output/v1` (для всех команд client) |
| `--yes`, `-y` | | Пропустить подтверждение удаления (применяется к `client remove`) |
| `--repair-page` | | Только в legacy-развёртывании явно пересоздать отсутствующую страницу подключения при `client show` |

**`client add`** — передайте несколько имён, чтобы добавить несколько клиентов сразу (например `meridian client add alice bob charlie`). С `--json` массив `data.clients[]` сохраняет все успешные создания, даже если последующее legacy-создание, выдача данных подключения или сохранение локального состояния завершились ошибкой. Уже выполненные удалённые изменения сохраняются, повторяемые ошибки попадают в `warnings[]`, а команда завершается с кодом `3` как в обычном, так и в JSON-режиме.

**`client list`** — с флагом `--json` возвращает подсчёты статуса `data.summary` и записи `data.clients[]` с именем пользователя, UUID, статусом, счётчиками трафика, временем создания и последним временем появления.

**`client show`** — с `--json` возвращает запись `data.client` и метаданные доступности `data.handoff.*`. Ссылка на страницу подключения выводится лишь при наличии подтверждения, что страница развёрнута на диске; в legacy-режиме `--repair-page` явно пересоздаёт пропавшую страницу. Если восстановить страницу не удалось, данные client и handoff всё равно возвращаются с предупреждением и кодом `3`. V4 не создаёт отдельную PWA-страницу и показывает канонический URL подписки панели.

**`client enable`** — возобновляет ранее приостановленного клиента, чтобы он снова мог подключаться. С флагом `--json` возвращает `data.client` с именем пользователя и статусом.

**`client disable`** — временно приостанавливает клиента. Его конфигурация остаётся целой, но он не может подключаться до повторного включения. С флагом `--json` возвращает `data.client` с именем пользователя и статусом.

**Владение V4** — `client add` добавляет пользователей в access intent и применяет обновлённый intent. `list` и `show` видят только объявленных пользователей, а `enable`/`disable` принимают только их. Отключение V4-клиента действует лишь до следующего `meridian apply`. `client remove` в V4 отклоняется, поскольку безопасное удаление управляемого пользователя ещё не реализовано; для немедленного временного отзыва используйте `client disable`. Частичный batch и PWA-страницы относятся к legacy-режиму.

**`client remove`** — если пользователь удалён из панели, но сохранить локальное состояние или полностью очистить legacy share-page не удалось, удаление возвращает типизированный частичный результат с кодом `3`. JSON сохраняет запись удалённого клиента в `data.client` и сообщает о незавершённых последующих действиях в `warnings[]`.

**Изменяющие команды в JSON-режиме** неинтерактивны. Для `client remove --json` обязателен `--yes`; без него Meridian возвращает типизированную ошибку подтверждения, а не открывает диалог.

### meridian server

Управление известными серверами.

```
meridian server add IP
meridian server list
meridian server remove NAME [--yes]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--name NAME` | (автоматически) | Отображаемое имя сервера |
| `--user/-u USER` | root | SSH-пользователь на сервере |
| `--ssh-port PORT` | 22 | SSH-порт сервера, если он нестандартный |
| `--yes`, `-y` | | Пропустить подтверждение удаления (для `server remove`) |

`server add` проверяет SSH до записи; имя, host и стабильный идентификатор должны быть уникальны, а существующий профиль нельзя незаметно переназначить другому host. `server remove` по умолчанию запрашивает подтверждение и удаляет только локальный профиль. Команда отказывается работать, пока профиль используется legacy-состоянием или V4 topology intent; сначала удалите роль сервера через setup/apply. Используйте `--yes` только для заранее проверенного неинтерактивного удаления.

### meridian node

Управление дополнительными выходными узлами в многоузловом флоте. Первый сервер (хост панели) развёртывается с помощью `meridian deploy`; последующие выходные узлы добавляются с помощью `meridian node add`.

```
meridian node add IP [flags]
meridian node list
meridian --json node list
meridian node remove IP [--yes] [--force]
meridian node check IP
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--user USER` | root | SSH пользователь на узле |
| `--ssh-port PORT` | 22 | SSH порт на узле (если нестандартный) |
| `--name NAME` | (автоматически, из IP) | Дружественное имя отображаемое в панели / подписке |
| `--domain DOMAIN` | (нет) | Домен для узла WSS/CDN резерва |
| `--sni HOST` | www.microsoft.com | Цель маскировки Reality для этого узла |
| `--harden / --no-harden` | включен | Защита ОС + SSH + файрвола для узла |
| `--yes` | | Пропустить подтверждение `node add` или `node remove` |
| `--force` | | При `node remove` сначала удалить зависимые ретрансляторы, затем узел |
| глобальный `--json` | | Разместите перед `node`, чтобы выдать `node list` в виде конверта `meridian.output/v1` |

**Legacy**: `meridian node add` подготавливает хост, регистрирует его через API панели и создаёт `reality`, `xhttp`, `hysteria2` и, при наличии домена, `wss`. Запись добавляется в `nodes[]` и синхронизируется с активным `desired_nodes[]`. `node remove` сначала останавливает контейнеры; при зависимых ретрансляторах команда отказывается работать, а `--force` сначала удаляет именно эти ретрансляторы.

**V4**: `node add` добавляет exit в `topology_intent` и применяет проверенный план. Усиление безопасности обязательно, поэтому `--no-harden` отклоняется. Без `--domain` объявляется только Reality-маршрут; домен добавляет TLS/WSS. `node remove` для управляемого V4-узла отклоняется: удалите роль exit или routing gateway в `meridian setup`, затем примените план.

**Проверки здоровья**: `meridian node check` проверяет панель, SSH, контейнеры, порты и TLS. Для V4 используются публичные порты, объявленные в настроенных протокольных путях, а не фиксированный порт 443. Код `0` означает здоровое состояние, `4` — завершённые проверки с проблемами, `3` — отсутствие обязательных данных. Отсутствующий инструмент проверки или потеря SSH-транспорта считаются недоступными данными, а не отрицательным результатом.

**JSON вывод**: `meridian --json node list` использует конверт `meridian.output/v1` с `data.nodes[]` содержащим ip, name, uuid, status, xray_version и traffic_bytes. Если статус панели недоступен, настроенные узлы сохраняются со статусом `unknown`; Meridian выдаёт предупреждение и завершает работу с кодом `3`.

### meridian fleet

Инспектировать и восстанавливать флот из активного REST API панели.

```
meridian fleet status [--json]
meridian fleet inventory [--json]
meridian fleet recover --legacy --panel-url URL [--api-token-file FILE]
                       [--profile NAME_OR_UUID] [--squad NAME_OR_UUID]
                       [--panel-node SELECTOR]
                       [--panel-server IP] [--user USER] [--ssh-port PORT] [--force]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--json` | | Выдать состояние флота как JSON (для скриптинга / CI) |
| `--panel-url URL` | требуется | Полный HTTPS URL панели, включая секретный путь |
| `--api-token-file FILE` | защищённый запрос или окружение | Прочитать токен из файла с режимом 600 вместо `MERIDIAN_API_TOKEN` или запроса |
| `--profile NAME_OR_UUID` | автоматически, если единственный | Выбрать точный legacy-профиль при наличии нескольких профилей |
| `--squad NAME_OR_UUID` | автоматически, если подходит одна | Выбрать точную legacy-группу доступа, когда все восстановленные входящие разрешают несколько групп |
| `--panel-node SELECTOR` | автоматически, если однозначно | Указать хост панели точным именем узла, UUID или адресом |
| `--panel-server IP` | IP из URL панели | Публичный SSH IPv4/IPv6 хоста Remnawave; обязателен, если URL панели использует домен |
| `--user`, `-u USER` | root | SSH-пользователь публичного сервера панели |
| `--ssh-port PORT` | 22 | SSH-порт публичного сервера панели, от 1 до 65535 |
| `--legacy` | требуется | Подтвердить, что целевая система — legacy-развёртывание с общим профилем |
| `--force` | | Создать резервную копию и заменить существующий локальный `cluster.yml` |

**`fleet status`** — показывает здоровье панели, heartbeat узлов, публичные relay-listener'ы, внутренние relay-hop'ы V4 и количество управляемых пользователей. Отсутствующие или неактивные объявленные пользователи V4 ухудшают здоровье и учитываются в `data.summary.missing_access_users` и `data.summary.nonactive_access_users`. Доступный listener ретранслятора является только TCP-свидетельством, поэтому любой не проверенный иным способом relay-маршрут сохраняет статус флота `unknown`; полную зашифрованную цепочку проверяет `meridian test`. Код выхода `0` означает полностью наблюдаемое здоровое состояние, `4` — деградацию, а `3` — unknown или unavailable.

**`fleet inventory`** — показывает настроенную панель, узлы, ретрансляторы, желаемую топологию и актуальный статус узлов панели, когда он доступен. Если актуальные данные панели недоступны, настроенный inventory сохраняется в результате, затронутые источники помечаются как `unavailable`, предупреждения объясняют пробелы, а команда завершается с кодом `3`, не отбрасывая частичные данные. Токен API панели и секретные пути URL не выводятся. Стабильный доступ к полям внутри `data` включает `data.sources.*`, `data.servers[].roles`, `data.summary.*`, `data.nodes[].desired`, `data.nodes[].protocols`, `data.relays[].exit_node_*` и `data.desired_nodes[].present`. Поля присутствия inventory не являются истиной о сходимости; для решений о drift и apply используйте `plan --json`.

**`fleet recover`** — импортирует из активной панели только один однозначный общий legacy-профиль. `--legacy` обязателен, а `--panel-url` должен содержать настоящий секретный путь, а не только корень сайта. Recovery доказывает access squad и panel node, читает share path по SSH, заново заполняет `servers.json` и отказывается от WSS metadata, если нельзя безопасно назначить ровно один допустимый домен. Для доменного URL панели требуется `--panel-server`. V4 intent из панели не восстанавливается; восстановите резервную копию или снова запустите `meridian setup`. Токен берётся из защищённого запроса, `MERIDIAN_API_TOKEN` или файла с режимом 600. Существующее локальное состояние заменяется только с `--force` и после создания резервной копии.

### meridian api

Инспектировать машинночитаемый контракт meridian-core используемый JSON выводом и будущими UI клиентами.

```
meridian api schemas [--json] [--include-schemas]
meridian api commands [--json] [--include-schemas]
meridian api schema NAME [--envelope|--json]
meridian api workflow NAME [--json]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--json` | | Выдать каталог схем как конверт `meridian.output/v1` |
| `--include-schemas` | | Включить полные JSON-схемы и автоматически выдать JSON-конверт для `api schemas` или `api commands` |
| `--envelope`, `--json` | | Оборачивать `api schema NAME` в конверт `meridian.output/v1` вместо выведения сырой JSON-схемы |

**`api schemas`** — выводит стабильные имена схем как `output-envelope`, `apply-envelope`, `client-list-envelope`, `client-show-envelope`, `deploy-envelope`, `deploy-command-data`, `deploy-request`, `deploy-workflow-answers`, `deploy-result`, `deploy-plan`, `workflow-plan`, `input-field`, `remote-target`, `command-spec`, `remote-command-result`, `plan-envelope`, `fleet-status-envelope`, `fleet-inventory-envelope`, `event`, `apply`, `plan-result`, `fleet-status` и `fleet-inventory`. Схемы конверта команды включают запись `commands` в каталог.

**`api commands`** — выводит контракты команд с `command`, `argv`, `envelope_schema`, `data_schema`, возможными `statuses`, структурированными `outcomes`, значениями выходных кодов, машинными флагами, стабильностью и `interrupt_behavior`. Поля `statuses` и `outcomes` описывают только завершённые JSON-конверты. Значение `interrupt_behavior: "exit_130_without_envelope"` означает, что Ctrl-C/SIGINT завершает процесс с кодом `130`, не гарантируя JSON в stdout. Используйте каталог перед подключением UI, чтобы выбрать схему данных команды для проверки конверта. `deploy` объявляет `--json`, `--events=jsonl`, `--request` и `--dry-run`.

**`api schema NAME`** — выводит одну JSON-схему. Пример: `meridian api schema output-envelope`.

**`api workflow NAME`** — выводит отрисовываемый UI план работы. Пример: `meridian api workflow deploy --json` возвращает разделы и поля мастера развёртывания.

### meridian studio

Открыть Meridian Studio и локальный Engine API. Сервер слушает только `127.0.0.1`.

```
meridian studio [--port PORT] [--assets-dir DIRECTORY] [--no-open]
```

| Флаг | По умолчанию | Описание |
|------|--------------|----------|
| `--port PORT` | 0 | Локальный порт от 0 до 65535; `0` выбирает свободный высокий порт |
| `--assets-dir DIRECTORY` | встроенные ресурсы | Использовать каталог собранных ресурсов Studio вместо ресурсов пакета |
| `--no-open` | | Вывести локальный URL, не открывая браузер |

Studio явно завершается ошибкой, если порт занят или встроенные/указанные ресурсы отсутствуют. Явный каталог ресурсов должен содержать `studio/index.html`.

### meridian relay

Управление узлами ретранслятора — легковесные TCP-маршрутизаторы, направляющие трафик через внутренний сервер на выходной сервер за границей.

```
meridian relay deploy RELAY_IP --exit EXIT [flags]
meridian relay list [--exit EXIT]
meridian --json relay list [--exit EXIT]
meridian relay remove RELAY_IP [--exit EXIT] [--yes]
meridian relay check RELAY_IP [--exit EXIT]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--exit/-e EXIT` | (требуется для deploy) | IP или имя выходного сервера |
| `--name NAME` | (автоматически) | Дружественное имя для ретранслятора (например, "ru-moscow") |
| `--port/-p PORT` | 443 | Порт прослушивания на сервере ретранслятора |
| `--sni HOST` | (автоматически) | Локальная для ретранслятора цель маскировки Reality |
| `--user/-u USER` | root | SSH пользователь на ретрансляторе |
| `--ssh-port PORT` | 22 | SSH порт на сервере ретранслятора (если нестандартный) |
| `--yes/-y` | | Пропустить подтверждающие диалоги |
| глобальный `--json` | | Разместите перед `relay`, чтобы выдать `relay list` в виде конверта `meridian.output/v1` |

**Legacy**: без `--sni` команда `relay deploy` выбирает локальную цель с помощью RealiTLScanner. Realm публикует только Reality, поскольку выделенный SNI-маршрут завершается на Reality inbound. `relay check` проверяет сервис, TCP-путь до exit, публичный listener и Host-записи панели; коды: `0` исправно, `4` проблема, `3` нет обязательных данных. Отсутствующий удалённый инструмент, тайм-аут команды или потеря SSH-транспорта дают код `3`, а не ложную проблему с кодом `4`. `relay remove` удаляет сервис, binary/config, точное правило UFW, routing на exit и Host-записи и сохраняет локальное состояние до полного успеха.

**V4**: `relay deploy` добавляет цепочку в intent и применяет её; `--exit` должен указывать существующий V4 exit, а пустой SNI наследует Reality-маршрут выхода. `relay check` и `relay remove` для управляемой цепочки отклоняются. Проверяйте весь маршрут через `meridian test`, а удаление цепочки выполняйте через проверку и apply в `meridian setup`.

**JSON вывод**: `meridian --json relay list` использует конверт `meridian.output/v1` с `data.relays[]`.

### meridian plan

Показать план примирения — что `meridian apply` сделает чтобы привести кластер в желаемое состояние объявленное в `cluster.yml`.

В V4 источником истины служит скомпилированный `topology_intent`, созданный setup. Человекочитаемый вывод показывает hash плана и количество скомпилированных ресурсов, затем требующие исправления ресурсы, недоступные наблюдения и изменения сохранённого состояния поколения. JSON содержит `plan_hash`, `resources[]` с желаемыми hash, `drifted_resources[]`, `observation_errors[]` и `state_changes[]`; универсальные символы действий Terraform в нём не используются.

В legacy желаемыми входами служат необязательные `desired_nodes`, `desired_relays`, `desired_clients` и `subscription_page`. Только legacy-plan выводит Terraform-подобную разницу действий: `+` для добавления, `-` для удаления и `~` для обновления.

```
meridian plan [--json]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--json` | | Выдать план как JSON конверт `meridian.output/v1` для CI/CD и UI клиентов. Такие же выходные коды; человеческий вывод плана подавляется |

**Выходные коды**:
- `0` — приведён в соответствие (изменений не требуется)
- `2` — изменения ожидаются (запустите `meridian apply` чтобы привести в соответствие)
- `3` — обязательные данные наблюдения недоступны, в том числе если SSH-проверка legacy-страницы подписки превысила время ожидания, потеряла соединение или не смогла запустить команду инспекции
- ошибки также используют ненулевые выходы; клиенты процесса должны рассматривать JSON `status` и `errors[].category` как авторитетные потому что `2` может также означать ошибку пользователя/конфигурации когда `status` это `failed`

**Форма legacy JSON** (режим `--json`):
```json

  "duration_ms": 128,
  "status": "changed",
  "exit_code": 2,
  "summary": {

    "changed": true,
    "counts": {"actions": 2, "adds": 1, "updates": 0, "replacements": 0, "removes": 1,
               "destructive": 1, "from_extras": 1}
  },
  "data": {
    "converged": false,
    "summary": "Plan: 1 to add, 1 to remove",
    "exit_code": 2,

В обоих контрактах plan значение `status` равно `no_changes` при сходимости и `changed`, когда apply должен внести изменения; ошибки наблюдения используют `failed` и код `3`. `data.exit_code` отражает выходной код процесса.

### meridian apply

Привести кластер в желаемое состояние, объявленное в `cluster.yml`. Legacy-apply выполняет план действий, показывает различия, запрашивает подтверждение и запускает действия в порядке зависимостей. V4 применяет проверенный граф скомпилированных ресурсов и сообщает hash плана, поколение и статус наблюдения каждого ресурса.

```
meridian apply [--yes] [--parallel N] [--prune-extras=ask|yes|no] [--json]
```

| Флаг | По умолчанию | Описание |
|------|--------------|---------|
| `--yes`, `-y` | | Пропустить подтверждающие диалоги |
| `--parallel N` | 4 | Только legacy: от 1 до 32 параллельных потоков подготовки узлов (каждый получает свою SSH-сессию и клиент панели) |
| `--prune-extras` | `ask` | Только legacy: обработка ресурсов, которые есть на панели, но отсутствуют в `cluster.yml`. `ask` спрашивает о каждом ресурсе (с `--yes` безопасно преобразуется в `no`); `yes` удаляет автоматически; `no` пропускает и выводит однострочное резюме |
| `--json` | | Выдать результат `meridian.output/v1` окончательного применения с статусом выполнения каждого действия |

V4 принимает `--yes` и `--json`. Нестандартные значения параметров только для legacy (`--parallel` кроме `4` или `--prune-extras` кроме `ask`) отклоняются до начала apply как ошибка пользователя с кодом `2`.

Во время apply V4 сохраняет локальные контрольные точки с данными о происхождении. Если не удалось сохранить контрольную точку или состояние сходимости, Meridian возвращает системную ошибку с кодом `3` и предупреждает, что удалённое состояние могло измениться. Исправьте сохранение локального состояния, затем повторно запустите `meridian plan` и `meridian apply`, чтобы наблюдать и согласовать результат.

Деструктивные действия (удаления, UPDATE_RELAY переподготовка) выводят предупреждение и требуют отдельное подтверждение. Ошибка в начале плана пропускает оставшиеся деструктивные действия — `cluster.yml` остаётся истинным.

В legacy-выводе `--json` поле `data.plan` содержит типизированный план, а `data.actions[]` — результаты выполнения со статусом `"succeeded" | "failed" | "skipped"`. V4 вместо этого возвращает скомпилированные действия со статусом `"converged" | "applied" | "failed" | "unknown" | "skipped"`. Режим JSON неинтерактивен: если изменения требуют подтверждения и `--yes` отсутствует, Meridian возвращает `MERIDIAN_CONFIRMATION_REQUIRED` с вычисленным планом или предварительными данными скомпилированного плана. Legacy-дрейф только на панели при `--prune-extras=ask` возвращает `MERIDIAN_DRIFT_DECISION_REQUIRED`; передайте `--prune-extras=no`, чтобы сохранить дрейф, или `--prune-extras=yes`, чтобы удалить его. Если legacy-действия выполнены, но последующее сохранение состояния не удалось, в том числе из-за одновременного изменения `cluster.yml`, конверт сохраняет результаты действий и возвращает код `3` с `MERIDIAN_STATE_SAVE_FAILED`. Контракт JSON сообщает о выполнении, но не делает деструктивные операции транзакционными. UI-клиенты должны проверить неудавшиеся и пропущенные действия и после устранения причины идемпотентно повторить запуск.

**Legacy-пример drift:** если `cluster.yml` содержит `desired_clients: ['alice']`, но панель также имеет `bob`, `meridian plan` показывает `- remove client: bob`. `--prune-extras=ask` требует явного решения; `--yes --prune-extras=yes` удаляет extra, а один `--yes` без решения пропускает его.

### meridian preflight

Предварительная проверка сервера. Тестирует SNI, порты, DNS, ОС, диск и часы без установки. DNS использует настроенный на сервере резолвер; Meridian не отправляет адрес сервера стороннему ASN-сервису. Код выхода `0` означает успех всех проверок, `4` — обнаруженные проблемы, `3` — недоступность обязательных данных.

```
meridian preflight [IP] [--domain NAME] [--sni HOST] [--user USER]
                   [--ai] [--server NAME]
```

`--domain` проверяет, что домен разрешается в адрес целевого сервера. `--sni` заменяет цель маскировки, `--user` — сохранённого SSH-пользователя, а `--ai` формирует готовый для AI диагностический запрос.

### meridian scan

Найти оптимальные цели SNI в сети сервера с помощью закреплённой версии RealiTLScanner. Перед запуском Meridian проверяет опубликованный SHA-256 и после сканирования удаляет изолированный рабочий каталог.

```
meridian scan [IP] [--user USER] [--server NAME]
```

RealiTLScanner поддерживает только IPv4; для цели только с IPv6 команда завершается как неопределённая с кодом `3`. Выбранная цель сохраняется только для отслеживаемого legacy-узла. В V4 Meridian показывает выбор, но не меняет проверенный intent; примените его через `meridian setup`. Пустой ответ возвращает `0`, недопустимый выбор — `2`, отсутствие кандидатов — `4`, ошибка сканера или загрузки — `3`.

### meridian test

Протестировать доступность прокси и проверить фактические подключения с устройства клиента. SSH не требуется.

Полная проверка детерминированно выбирает активного клиента, получает точный JSON подписки Xray от Remnawave и запускает automatic fallback и каждый поддерживаемый outbound выбранной цели. В V4 выбор ограничен пользователями из `topology_intent.access.users`: service users нельзя выбрать явно, и они не участвуют в fallback. Первый запуск может потратить до 120 секунд на загрузку и проверку закреплённого Xray runtime с GitHub. Проверки трафика чередуют независимые IP-observer'ы и сравнивают результат с прямым контрольным запросом, поэтому сбой observer'а не превращается в ложную ошибку протокола. В контролируемой среде observer можно переопределить через `MERIDIAN_CONNECT_TEST_URL`.

`--client` выбирает конкретного активного управляемого клиента. `--basic` ограничивает запуск наблюдениями сети/TLS и не может подтвердить трафик только по UDP. Параметры `--basic` и `--client NAME` несовместимы: их сочетание завершается ошибкой пользователя с кодом `2` до любого сетевого I/O. Значение `--timeout` по умолчанию равно `5` секундам, допустимый диапазон — от `1` до `30`; оно ограничивает каждую сетевую операцию отдельно от первой загрузки Xray.

Во время полной проверки ошибка транспорта панели, ответ HTTP `429` или HTTP `5xx` означает, что данные канонической подписки недоступны (`PANEL_UNAVAILABLE`); результат неопределённый и завершается с кодом `3`. Напротив, однозначное отклонение запроса подписки с не связанным с аутентификацией HTTP `4xx`, например `400` или `422`, но не `429`, является завершённым отрицательным результатом (`PANEL_REQUEST_FAILED`) и возвращает код `4`.

```
meridian test [IP|DOMAIN] [--server NAME] [--domain NAME] [--sni NAME]
              [--client NAME] [--basic] [--timeout SECONDS] [--json]
```

Код выхода `0` означает, что все обязательные проверки пройдены, `4` — что проверка завершена с отрицательными результатами, а `3` — что необходимые данные недоступны. `--json` выводит типизированный конверт `meridian.output/v1` со всеми проверками и результатами.

### meridian probe

Проверить сервер с точки зрения цензора — определить, можно ли обнаружить развёртывание. SSH не требуется. Команда работает с произвольными IP-адресами и доменами и автоматически применяет более строгие правила, если цель входит в сохранённую топологию Meridian.

Набор проверок определяется реальной схемой развёртывания: экспозиция публичных и внутренних портов, поведение HTTP/TLS, согласованность и маскировка SNI, типовые пути прокси и панели, переключения на WebSocket, обратный DNS, HTTP/2, устаревшие версии TLS, защищённые корневые пути и настроенные домены. `--sni` переопределяет обычное TLS SNI. Прослушиватели только на UDP не определяются по пустой датаграмме; для них probe сообщает, что нужна каноническая полная проверка соединения.

```
meridian probe [IP|DOMAIN] [--server NAME] [--sni NAME]
               [--timeout SECONDS] [--json]
```

Probe использует тот же контракт кодов выхода, что и `test`: `0` — проверка пройдена, `4` — завершена с отрицательными результатами, `3` — результат неопределённый. `--timeout` принимает 1–30 секунд и применяется к каждой операции; TARGET и `--server` взаимно исключаются. Неполные повторные наблюдения и разные сертификаты у доверенных CDN edge считаются неопределёнными, а не провалом; нарушение trust или hostname остаётся провалом. Пропущенные данные никогда не считаются успехом.

### meridian doctor

Собрать диагностику системы для отладки. Альтернатива: `meridian rage`.

```
meridian doctor [IP] [--sni HOST] [--user USER] [--ai] [--server NAME]
```

`--sni` выбирает диагностируемую цель маскировки, `--user` заменяет сохранённого SSH-пользователя, а `--ai` копирует готовый для AI отредактированный отчёт.

Doctor определяет разделы и порты прослушивания по ролям сервера и настроенным публичным портам V4. Отсутствующие инструменты проверки или потеря SSH-транспорта делают отчёт неполным и дают код `3`; уже собранные разделы всё равно выводятся.

### meridian teardown

Удалить прокси с сервера.

```
meridian teardown [IP] [--user USER] [--server NAME] [--yes]
```

`--yes` пропускает подтверждение разрушительной операции, а `--user` заменяет сохранённого SSH-пользователя. Выбор цели неинтерактивен: неизвестный `--server`, а также отсутствие или неоднозначность неявной цели завершаются с кодом `2` без запроса IP. Отказ от подтверждения даёт код `1`. В V4 teardown запрещён, пока сервер имеет роль control, exit, routing gateway, relay hop или активный workload: сначала удалите роль через setup и примените план. Хост панели нельзя удалить, пока остаются другие узлы или ретрансляторы. Цель-ретранслятор проходит полный relay cleanup, а серверный профиль удаляется только после успешной очистки.

### meridian update

Обновить CLI до последней версии из PyPI. Код `0` означает, что версия уже актуальна или успешно обновлена; `3` — что проверка версии или обновление завершились ошибкой.

```
meridian update
```

## Глобальные параметры

Глобальные параметры указываются до команды, например `meridian --quiet doctor`. Локальные параметры команды, такие как `test --json`, остаются после неё.

| Флаг | Описание |
|------|----------|
| `--version`, `-v` | Показать версию CLI и выйти |
| `--verbose` | Включить отладочные сообщения |
| `--quiet`, `-q` | Скрыть вывод прогресса |
| `--json` | Запросить типизированный JSON-конверт у поддерживаемой команды; неподдерживаемые команды явно завершаются ошибкой |
| `--install-completion` | Установить автодополнение для текущей оболочки |
| `--show-completion` | Вывести скрипт автодополнения для текущей оболочки |

Глобальный `--json` поддерживают deploy, plan, apply, test, probe, все client-команды, fleet status/inventory, node/relay list и API-команды. Для команд с локальным `--json` его также можно указать после команды. Стабильные машинные контракты перечисляет `meridian api commands --json`.

## Общие параметры сервера

Эти имена повторяются в серверных командах, но каждая команда принимает только параметры из своего раздела:

| Флаг | Команды |
|------|---------|
| `--server NAME` | deploy, preflight, scan, test, probe, doctor, teardown |
| `--user`, `-u USER` | deploy, node add/check, relay-команды, preflight, scan, doctor, teardown |
| `--sni HOST` | deploy, node add, relay deploy, preflight, test, probe, doctor |
| `--domain DOMAIN` | deploy, node add, preflight, test |

Client-команды работают с панелью кластера напрямую и не принимают `--server`. `test` и `probe` выполняются на клиентском устройстве и не используют SSH.

## Разрешение сервера

Команды с общим SSH-resolver используют такой приоритет:
1. Явный аргумент IP или ключевое слово `local` (deploy на этом сервере без SSH)
2. Флаг `--server NAME` (также принимает `--server local`)
3. Определение локального режима (запуск на самом сервере)
4. Автоматический выбор одного сервера (если сохранён только один)

При нуле или нескольких доступных серверах команды, включая `teardown`, завершаются с кодом `2` и требуют явного имени; общий resolver не открывает диалог. У `test` и `probe` отдельное внешнее разрешение: TARGET или `--server`, но не оба; затем local detection, затем единственный сохранённый профиль, а при нуле/нескольких профилях — ошибка.
