## Команды

### meridian deploy

Развернуть один сервер и получить ссылку для обмена подключением. Сервер становится и сервером управления (на нём работает сервис управления Meridian), и выходом. Deploy строит ту же одобренную топологию, что и `meridian setup`, применяет её с контрольными точками, проверяет реальный трафик через выпущенную подписку и выводит страницу подключения и URL подписки. Повторный запуск той же команды возобновляет прерванное развёртывание или обновляет существующее, сохраняя пути, ключи и пользователей. Первое развёртывание ваших серверов заканчивается тем, что один раз показывает ключ восстановления (см. [meridian backup](#meridian-backup)).

```
meridian deploy [SERVER] [flags]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--sni HOST` | (авто) | Цель маскировки. Без него первое развёртывание пробует сайты из собственной подсети сервера, затем `www.google.com`, `dl.google.com`, `www.cloudflare.com` и использует первый, который несёт трафик; переразворачивание сохраняет сохранённую цель. Явный `--sni` никогда не меняется |
| `--domain DOMAIN` | (нет) | Ваш домен: XHTTP переносится на него и добавляется WSS, оба через CDN Cloudflare (XHTTP работает и без домена, на IP). Сервис управления и страницы подключения остаются на IP-сертификате |
| `--self-steal` | выкл. | Маскировка под ваш собственный домен (`--sni`, иначе `--domain`), направленный на сервер записью только DNS: Meridian выпускает для него сертификат Let's Encrypt, а сервер сам отвечает на проверки стандартной страницей 404 nginx. Сначала deploy проверяет, куда резолвится имя: останавливается, если оно не резолвится, и предупреждает, если указывает в другое место. Переразворачивание сохраняет настройку; новый `--sni` без флага возвращает чужой сайт |
| `--hysteria2/--no-hysteria2` | вкл | Предлагать Hysteria2 на UDP/443, замаскированный salamander, как последний возврат. Использует сертификат домена или IP-сертификат без домена |
| `--fingerprint NAME` | chrome | Отпечаток TLS, который клиенты показывают на Reality, XHTTP и WSS (`chrome`, `firefox`, `safari`, `ios`, `android`, `edge`, `random`, `randomized`). Измените его, если ваш регион начнёт флагировать текущий; переразворачивание сохраняет сохранённое значение |
| `--client-name NAME` | default | Имя первого клиента |
| `--display-name NAME` | (нет) | Ярлык для страниц подключения |
| `--icon EMOJI_OR_URL` | (нет) | Значок страницы — эмодзи или URL изображения |
| `--color PALETTE` | ocean | Тема цвета страницы (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | сохранено, иначе root | SSH пользователь (не-root требует passwordless sudo) |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт |
| `--harden / --no-harden` | вкл | SSH только по ключу, fail2ban и файрвол UFW. `--no-harden` для серверов, общих с другими сервисами |
| `--warp / --no-warp` | выкл | Отправлять исходящий трафик через Cloudflare WARP |
| `--geo-block` / `--no-geo-block` | вкл | Блокировать российские домены и IP (`geosite:category-ru` + `geoip:ru`) на выходе. Xray JSON и Mihomo подписки уже отправляют их напрямую с устройства |
| `--country CC` | реестр адреса | Двухбуквенный код страны, который показывается в названиях подключений и в списке серверов консоли. Без него при первом развёртывании Meridian спрашивает региональный интернет-реестр адреса сервера (через RDAP bootstrap IANA, без гео-IP сервиса); при повторном развёртывании сохраняется прежняя страна |
| `--yes` | | Пропустить диалоги подтверждения |
| `--json` | | Выдать окончательный результат развёртывания как конверт `meridian.output/v1` |
| `--events=jsonl` | | Потоком передавать типизированные события прогресса как JSONL на stderr |
| `--request FILE` | | Прочитать `deploy-request` JSON от файла; используйте `-` для stdin |
| `--dry-run` | | Компилировать и просмотреть развёртывание без SSH или локальных изменений |

Без IP `deploy` запрашивает его. `local` разворачивает на машине, на которой вы находитесь. `deploy` повторно разворачивает только сервер, который уже является выходом среди ваших серверов; другие серверы добавляйте через `meridian node add`. Если ваши серверы ещё работают на панели Remnawave, `deploy` сначала предложит запустить [`meridian migrate`](#meridian-migrate). Повторный запуск с другими флагами обновляет этот выход (например, добавляет или убирает `--domain` либо `--no-hysteria2`), сохраняя остальные выходы, промежуточные серверы, шлюзы и клиентов.

**Поток машина/UI**: `meridian api workflow deploy --json` возвращает отрисовываемый контракт мастера. UI собирает эти поля, проверяет их против `deploy-request`, затем запускает `meridian deploy --request deploy.json --json --events=jsonl`. Машинные развёртывания неинтерактивны: запрос должен содержать `yes: true` после подтверждения пользователем. `--dry-run --json` возвращает `deploy-plan` под `data`, чтобы UI мог просмотреть режим, порты и сгенерированные пути перед открытием SSH.

### meridian setup

Возобновляемый пошаговый мастер для одного сервера или многих: выходы, промежуточные серверы Realm, маршрутизирующие шлюзы с пулами отказоустойчивости и пользователи. Он написан для людей, которые никогда не настраивали VPN: каждый вопрос использует настоящий термин (выход, промежуточный сервер, SNI) и объясняет его в одном простом предложении с безопасным стандартом, который вы можете принять, нажав Enter.

```
meridian setup [--intent FILE|-] [--restart] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--intent FILE` | (нет) | Начать с проверки из полного документа JSON топологии; используйте `-` для stdin |
| `--restart` | | Отбросить сохранённый прогресс настройки перед запуском |
| `--devices N\|default` | общий лимит | Лимит человека, 1–100 (`client add`, `client set`); `default` использует общий лимит |
| `--remove ID` | | Удалить одну регистрацию (`client devices`); устройство сможет зарегистрироваться при следующем обновлении |
| `--clear` | | Удалить все регистрации (`client devices`); нельзя вместе с `--remove` |
| `--yes`, `-y` | | Одобрить проверку и применить без запроса |

Первый вопрос — язык (English, Русский, فارسی, 中文), предвыбранный из вашего терминала и запомненный в `~/.config/meridian/preferences.json`; `--lang` или `MERIDIAN_LANG` пропускают его. Затем мастер проходит по серверам (IP, `user@IP:port` или `local` для этой машины), что делает каждый сервер, методы подключения, маршрутизация (спрашивается только если у вас есть шлюз маршрутизации: каждое правило отправляет подходящий трафик на выход или в пул, напрямую со шлюза или никуда), пользователи, сводка на простом языке и применение. Варианты выбора — это списки: перемещайтесь стрелками (или нажмите номер варианта), отмечайте пункты чек-листа клавишей Пробел, нажмите `?` для подробностей, Enter для подтверждения, Esc для возврата назад и Ctrl+C для выхода. Везде, где список предлагает «Другое», можно ввести собственное значение. В текстовых полях также можно ввести `back`, `details`, `save` или `quit` (или те же слова на вашем языке). Для сайта для маскировки мастер сначала сканирует собственную сеть выхода (около минуты) и показывает эти сайты раньше общеизвестных. Задайте `MERIDIAN_PLAIN_PROMPTS=1`, чтобы получить нумерованные запросы (они включаются автоматически, когда терминал не может отрисовать списки). Запуск `meridian` без команды в терминале, до того как существует VPN, предлагает запустить мастер. Прогресс сохраняется в `~/.config/meridian/setup.json` после каждого этапа, поэтому запуск `meridian setup` снова возобновляет; пароли и приватные ключи никогда не сохраняются там. `--intent` не заменяет существующий черновик, если `--restart` также не указан. Когда применение успешно, setup проверяет каждый узел и подписку и выводит страницу подключения каждого пользователя.

### meridian plan

Показать, что изменит `meridian apply`, сравнивая топологию в `~/.config/meridian/cluster.yml` с живыми серверами и сервисом управления. Ничего не меняется.

```
meridian plan [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать план как конверт `meridian.output/v1` для CI и UI клиентов |

Вывод показывает хеш плана, подсчёты ресурсов по типам и любые ресурсы, которые нужно исправить или не удалось наблюдать. JSON `data` содержит `plan_hash`, `converged`, `resources[]`, `drifted_resources[]`, `observation_errors[]` и `state_changes[]`.

**Коды выхода**:
- `0` — сходится, нечего делать
- `1` — нечего планировать (нет серверов, или неиспользуемое локальное состояние)
- `2` — ожидающие изменения (запустите `meridian apply`)
- `3` — необходимые данные (сервис управления, SSH, локальное состояние) были недоступны

Не редактируйте топологию в `cluster.yml` вручную. Измените её с помощью `meridian setup`, `deploy`, `client add`, `node add` или `relay add`.

### meridian apply

Применить одобренную топологию в `cluster.yml` на ваши серверы. Apply показывает хеш плана и подсчёт ресурсов, просит подтверждение, затем применяет точный показанный план с контрольными точками. Прерванное применение возобновляется там, где остановилось.

```
meridian apply [--yes] [--forget-unreachable] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--yes`, `-y` | | Пропустить подтверждение |
| `--forget-unreachable` | | Забыть развёрнутое на удаляемом сервере, если он не отвечает по SSH (заблокирован или удалён), вместо неудачной очистки; он обслуживает прежних пользователей, пока вы его не удалите |
| `--json` | | Выдать окончательный результат применения как конверт `meridian.output/v1` |

JSON `data` содержит `plan_hash`, `generation` и `actions[]` с `status: "converged" | "applied" | "failed" | "unknown" | "skipped"`. JSON режим никогда не спрашивает: без `--yes` возвращает `MERIDIAN_CONFIRMATION_REQUIRED` с хешем плана и выходит `2`. Неудавшийся ресурс выходит `3`; исправьте причину и снова запустите apply. Если локальное состояние не может быть сохранено после удалённых изменений, apply выходит `3` и говорит это; исправьте разрешения `~/.config/meridian`, затем запустите `plan` и `apply` снова.

Удаления тоже применяются: всё, что покинуло топологию (пользователи, пути протокола, выходы, промежуточные серверы, маршрутизирующие шлюзы), удаляется после того как всё, что осталось в плане, сходится, и `plan` выводит это первым. Сервер управления уходит только через `meridian teardown` или переезжает через `meridian restore`.

Каждое применение записывается в сервисе управления как ревизия (см. `meridian fleet history`) и на время работы держит там аренду, поэтому две машины никогда не применяют одновременно.

### meridian client

Управлять людьми, которые подключаются.

```
meridian client add NAME [NAME...] [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N|default] [--json]
meridian client show NAME [--repair-page] [--json]
meridian client usage NAME [--days N] [--json]
meridian client list [--attention] [--json]
meridian client set NAME [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N|default] [--json]
meridian client reset-traffic NAME [--json]
meridian client extend NAME --days N [--json]
meridian client devices NAME [--remove ID | --clear] [--json]
meridian client enable NAME [--json]
meridian client disable NAME [--json]
meridian client reissue NAME [--cut-off] [--yes] [--json]
meridian client remove NAME [--cut-off] [--yes] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--days N` | 30 | Дни UTC для `client usage` или `fleet usage`: 1–730, не больше сохранённого срока хранения |
| `--json` | | Выдать результат как конверт `meridian.output/v1` (все команды client) |
| `--attention` | выключен | `client list`: только люди, требующие внимания, с указанием причины |
| `--repair-page` | | Переопубликовать страницу подключения клиента (`client show`) |
| `--limit SIZE` | нет | Лимит трафика (`client add`, `client set`): `500MB`, `50GB`, `1.5TB`; `none` или `0` снимает его. Единицы двоичные (1 GB = 1024³ байт), как считает сервис управления |
| `--reset PERIOD` | never | Когда использованный трафик снова начинается с нуля: `day`, `week`, `month` или `never`, по календарным дням, неделям или месяцам |
| `--expires DATE` | never | Когда заканчивается доступ: `YYYY-MM-DD` (конец этого дня по UTC), время ISO вроде `2026-12-31T18:00:00+03:00` (время без смещения считается UTC) или `never`. Дата должна быть в будущем |
| `--yes`, `-y` | | Подтвердить `client reissue` или `client remove`; требуется с `--json` |

**`client add`** — добавляет одного или нескольких людей в топологию, применяет её и выводит страницу подключения и URL подписки каждого человека. Страница строится из их настоящей подписки, поэтому промежуточные серверы и Hysteria2 появляются, если они есть. Имена, которые уже есть в топологии или в сервисе управления, отклоняются. Имена могут быть на любом алфавите (`client add Биба 王小明`): страницы и вывод показывают их так, как они введены, а сервис управления, который принимает только латинские буквы, цифры, `.`, `-` и `_`, получает транслитерированное имя пользователя (`biba`, `wangxiaoming`). Другие команды `client` принимают любую из форм. Если ссылку подписки клиента собрать не удалось, клиент всё равно добавляется, а команда завершается с кодом `3`; если не хватает только страницы подключения, выводится предупреждение (восстановите её командой `client show --repair-page`). `--limit`, `--reset`, `--expires` и `--devices` входят в одобренный план и задаются вместе с каждой учётной записью в одной транзакции. Неудачное применение не выводит ссылок; завершите его командой `meridian apply`. Последующие применения сохраняют изменения оператора.

**`client show`** — выводит страницу подключения, URL подписки, статус, трафик относительно лимита с периодом сброса, срок доступа и время, когда клиент последний раз был в сети. `--repair-page` переопубликовывает отсутствующую страницу; если это не удаётся, ссылки всё ещё показаны с предупреждением и выходом `3`.

Первый учтённый трафик и последний узел с трафиком определяются по принятому приросту счётчиков (`first_traffic_at` и `last_traffic_node` в JSON). Время первого использования до обновления может быть неизвестно; это сводные данные без сеансов и адресов клиентов.

**`client list`** — выводит клиентов со статусом, трафиком, сроком доступа и временем, когда клиент последний раз был в сети, включая людей, добавленных в веб-консоли (`declared: false` в JSON). С `--json` возвращает подсчёты `data.summary` и `data.clients[]`.

`client list --attention` показывает только тех, чей доступ истекает в ближайшие семь дней (включая текущий момент), кто израсходовал не менее 80% лимита, или у кого нет трафика за всё время спустя более трёх дней после создания. Причина указана в отдельном столбце; JSON содержит `clients[].attention_reasons`, а сводка учитывает только показанных людей. Импортированный трафик без точной даты и сброс периода не делают пользователя неиспользованным.

`GET /api/attention` требует область `read` и доступен вошедшему владельцу. Ответ содержит `observed_at`, `thresholds`, `people[]` с именами и причинами и `nodes[]` с ID узлов и причинами. Учитываются недоступные или ещё не выходившие на связь агенты, ошибки применения конфигурации и состояние здоровья `degraded` или `unhealthy`. Параметры: `expiry_days` (1–30, по умолчанию 7), `quota_percent` (1–100, по умолчанию 80), `unused_days` (1–365, по умолчанию 3). Список вычисляется без сохранённых отметок, сеансов, адресов и данных устройств.

**`client set`** — меняет лимит трафика, период сброса или срок доступа клиента; меняется только то, что вы передали, и нужен хотя бы один флаг. Клиент, которого отключил лимит или срок (статус `limited` или `expired`), снова может подключиться, как только новые значения это позволяют. Изменения действуют сразу, и применения их не трогают. Неверное значение завершает команду с кодом `2` раньше, чем Meridian куда-либо подключится. С `--json` возвращает в `data.client` клиента таким, каким его теперь видит сервис управления, включая `traffic_limit_bytes`, `traffic_reset` и `expires_at` (пусто — бессрочно).

**`client reset-traffic`** — обнуляет использованный трафик клиента, как это сделал бы новый период; клиент, которого отключил лимит, снова может подключиться.

**`client extend`** — добавляет 1–3650 целых дней к текущему сроку доступа или к настоящему времени, если срок прошёл или не задан. Обязателен `--days N`. Расчёт и проверка ограничений проходят в одной транзакции сервиса, поэтому одновременные продления складываются. Истёкший доступ восстанавливается, но отключение оператором и лимит трафика продолжают действовать. JSON возвращает итоговые статус и срок в `data.client`.

**`client enable` / `client disable`** — возобновить или приостановить клиента немедленно. Отключённый клиент остаётся отключённым, пока вы не выполните `client enable`: применения (включая переразворачивание, `client add`, `node add` и `relay add`) статус клиента не меняют.

**`client reissue`** — заменяет ссылки клиента после утечки. Сервис управления выдаёт новый идентификатор подписки и новые ключи, поэтому старый URL подписки, страница подключения и ссылки перестают работать. Meridian сначала удаляет старую страницу, затем публикует новую и выводит новые ссылки. Статус, лимиты и срок действия остаются прежними. Запрашивает подтверждение, если не дан `--yes`, и отклоняет имена, которых нет среди ваших клиентов. Если новую страницу не удалось опубликовать, ссылки всё равно показываются с предупреждением и выходом `3` (исправьте с помощью `client show --repair-page`).

**`client remove`** — удаляет клиента из топологии, его учётную запись в сервисе управления и его страницу подключения. Запрашивает подтверждение, если не дан `--yes`. Последний клиент не может быть удалён. Людей, добавленных в веб-консоли, удаляют там.

**`client usage`** — показывает отправленные, полученные и общие байты по дням для любого человека в сервисе, включая добавленных в консоли. Историю нужно включить в [Конфиденциальности](/ru/privacy/); иначе команда выходит с `2` и подсказывает, как её включить. `client show` добавляет последние семь дней UTC, когда история включена (`data.usage` в JSON, `null` при выключенной). Пустой день означает отсутствие записанного трафика; прошлое использование не восстанавливается.

**`client devices`** — показывает количество в private и сведения об устройствах в full; off ничего не читает. `--json` возвращает `username`, `level`, `count`, действующий `limit`, `devices` и `removed`. `--remove ID` или `--clear` удаляет регистрации, не отзывая ключи; повторное удаление сообщает ноль изменений. Чтение и удаление регистраций доступны и для людей, добавленных в консоли. `client set --devices N` задаёт лимит; `--devices default` использует общий. См. [Лимит устройств](/ru/client-management/#лимит-устройств). Выпуск новой ссылки очищает все регистрации и сохраняет лимит.

Команды, меняющие данные человека в сервисе (`client enable`, `disable`, `set`, `reset-traffic` и удаление регистраций устройств), работают и для людей из консоли. Точное имя пользователя имеет приоритет; имя без учёта регистра или отображаемое имя должно указывать на одного человека. При неоднозначности используйте точное имя из `client list`. Удаление человека, перевыпуск ключей и публикация страницы остаются за клиентами из топологии.

Открытые сеансы VLESS могут продолжаться после отзыва ключей. **`--cut-off`** в `client remove` или `client reissue` ждёт, пока каждый затронутый сервер применит ревизию без старых ключей, затем сбрасывает нужные входы. Все их сеансы завершаются, включая сеансы других пользователей; они ненадолго переподключатся. Если API входа не сработает, перезапустится Xray и завершатся все его сеансы на этом сервере. Флаг включается явно и рекомендуется при утечке ссылки. JSON содержит результат каждого сервера в `data.cut_off`: `done`, `core_restart`, `failed` или `timed_out`. Ожидание длится до пяти минут; сбой завершает команду с кодом `4`, тайм-аут — `3`. Консоль предлагает тот же выбор при удалении человека, добавленного через неё.

### meridian privacy

Выберите, что хранит сервис управления. Ограничение устройств и ежедневная история по умолчанию выключены; применение конфигурации серверов не меняет настройки. Раскрываемые данные и последствия захвата сервера описаны в [Конфиденциальности](/ru/privacy/).

```bash
meridian privacy [--json]
meridian privacy show [--json]
meridian privacy set [--devices off|private|full] [--device-limit N] [--history off|daily] [--history-days N] [--yes] [--json]
```

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `--devices LEVEL` | без изменения | `off`, отпечатки с ключом `private` или подробные данные устройств `full` |
| `--device-limit N` | без изменения (сначала 3) | Лимит по умолчанию для людей без собственного: 1–100 |
| `--history LEVEL` | без изменения | `off`: суммарный трафик и последняя активность; `daily`: итоги людей и серверов по дням UTC |
| `--history-days N` | без изменения (сначала 90) | Хранить 7–730 дней UTC, включая сегодня |
| `--yes`, `-y` | | Пропустить подтверждение; обязательно для изменения в JSON |
| `--json` | | Выдать конверт `meridian.output/v1` |

Без подкоманды `privacy` работает как `privacy show`: настройки, раскрываемые данные и 50 последних изменений. `set` меняет только переданные параметры, объясняет хранение при повышении режима и удаление при понижении и спрашивает подтверждение. Те же значения ничего не меняют. JSON `data` содержит настройки и изменения; `set` также возвращает число удалённых записей в `deleted` и преобразованных в `rekeyed_devices`. Записываются имя токена, `owner` или `root`, время и значения до/после. После восстановления приватные записи устройств удаляются: ключ отпечатков никогда не входит в снимки.

### meridian server

Управлять сохранёнными SSH серверами (`~/.config/meridian/servers.json`).

```
meridian server add [USER@]IP[:PORT]|local [--name NAME] [--user USER] [--ssh-port PORT]
meridian server list
meridian server remove NAME_OR_IP [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (нет) | Имя для отображения сервера |
| `--user/-u USER` | root | SSH пользователь |
| `--ssh-port PORT` | 22 | SSH порт |
| `--yes`, `-y` | | Пропустить подтверждение удаления (`server remove`) |

`server add local` сохраняет машину, на которой вы находитесь; последующие команды выполняются на ней напрямую, а не по SSH. Имена и адреса должны быть уникальны; `server add` отклоняет коллизии вместо переназначения существующего сервера. `server remove` удаляет только сохранённый профиль и отказывает, пока сервер ещё выполняет роль в вашей топологии.

### meridian node

Управлять серверами выхода. Первый сервер развёртывается с помощью `meridian deploy` (или `meridian setup`); добавляйте дополнительные выходы с помощью `meridian node add`.

```
meridian node add [USER@]IP[:PORT] [flags]
meridian node list [--json]
meridian node remove NAME_OR_IP [--yes] [--force] [--forget-unreachable]
meridian node replace EXIT [USER@]NEW_IP[:PORT] [--name NAME] [--yes] [--forget-unreachable]
meridian node sni EXIT NEW_SNI [--self-steal] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (авто) | Дружественное имя для узла |
| `--user USER` | сохранено, иначе root | SSH пользователь на узле |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт на узле (`node add`, `node replace`) |
| `--sni HOST` | (авто) | Цель маскировки Reality для этого узла (без флага предпочитает сайт из собственной подсети узла, иначе `www.google.com`) |
| `--domain DOMAIN` | (нет) | Домен узла: XHTTP переносится на него и добавляется WSS, оба через CDN Cloudflare; Hysteria2 использует его сертификат |
| `--self-steal` | выкл. | `node add`: маскировка под ваш собственный домен (`--sni`, иначе `--domain`), направленный на узел. `node sni`: `NEW_SNI` — ваш собственный домен |
| `--country CC` | реестр адреса | Страна в названиях подключений; задайте её, если реестр ошибается (anycast или арендованные диапазоны) |
| `--harden / --no-harden` | вкл | Защита ОС, SSH и файрвола. На серверах в топологии она всегда включена; `--no-harden` отклоняется |
| `--yes` | | Пропустить диалоги подтверждения |
| `--forget-unreachable` | | `node remove`, `node replace`: Забыть развёрнутое на удаляемом сервере, если он не отвечает по SSH (заблокирован или удалён), вместо неудачной очистки; он обслуживает прежних пользователей, пока вы его не удалите |
| `--force` | | `node remove`: также удалить цепочки промежуточных серверов, которые маршрутизируют к этому выходу |
| `--json` | | Выдать `node list` как конверт `meridian.output/v1` |

**`node add`** — подключается по SSH, добавляет сервер как выход в вашу топологию и применяет одобренный план (защита ОС и SSH, агент узла и Xray, регистрация в сервисе управления). Существующие клиенты получают новый выход при следующем обновлении подписки.

**`node list`** — выводит узлы с актуальным статусом их агента, версией и трафиком. Если сервис управления недоступен, настроенные узлы показаны как `unknown`, и команда завершается с кодом `3`.

**`node remove`** — удаляет выход или маршрутизирующий шлюз из вашей топологии. Выводит все ресурсы, которые будут удалены (запись и документ узла, его агент и Xray, правила файрвола, клиентские точки подключения), запрашивает подтверждение и применяет этот одобренный план; сам сервер остаётся в списке сохранённых серверов. Команда отказывает для сервера управления (используйте `meridian teardown`), при наличии промежуточных серверов, направленных на этот выход (сначала удалите их или передайте `--force`), если через этот выход подключён маршрутизирующий шлюз, а также если удаление нарушит целостность топологии (например, оставит пустым пул выходов или удалит выход по умолчанию). Правила маршрутизации, привязанные к удаляемому шлюзу, удаляются вместе с ним.

**`node replace`** — переносит один выход на другой сервер. `EXIT` — это ID выхода или сохранённое имя либо IP его сервера; новый сервер задаётся так же, как в `node add` (подойдёт и сохранённое имя, и `local`), и сохраняется как при `server add`. Выход сохраняет свой ID, ключи Reality, пути протоколов, SNI, настройки WARP и геоблокировки, а также все промежуточные серверы, которые ведут на него: пользователи промежуточных серверов продолжают работать, а прямые подключения получают новый адрес при следующем обновлении подписки. Перед применением команда показывает, что будет развёрнуто на новом сервере и какие ресурсы будут удалены со старого (агент и Xray, файлы nginx, правила файрвола и сертификаты); запись в сохранённых серверах остаётся. Команда отказывает для сервера управления (его перенос изменил бы все URL подписок; если он потерян, используйте `meridian restore`) и для сервера, у которого уже есть роль.

**`node sni`** — задаёт Reality-пути выхода новый SNI маскировки. `EXIT` — ID выхода или сохранённое имя его сервера или IP. Отклоняет имена `apple.com` и `icloud.com` и `www.microsoft.com`, проверяет по SSH, что выход открывает новый сайт по TLS 1.3 с HTTP/2, показывает план изменений (промежуточные серверы, которые следуют SNI выхода; те, что сохраняют свой; шлюзы маршрутизации на этом пути; что будет удалено), подтверждает и применяет. Старое имя заменяется, а не остаётся рядом: приложения переключатся при следующем обновлении подписки (каждые 6 часов) или при ручном обновлении, а до этого не смогут подключиться через Reality. XHTTP, WSS и Hysteria2 не меняются. Используйте, когда `meridian test --probe` сообщает, что SNI маскировки заблокирован. С `--self-steal` `NEW_SNI` — ваш собственный домен: вместо проверки доступности команда проверяет, что имя резолвится в выход (останавливается, если не резолвится, и предупреждает, если указывает в другое место), а выход получает для него сертификат Let's Encrypt и сам отвечает на проверки.

### meridian relay

Управлять промежуточными серверами — TCP-форвардерами Realm, которые дают пользователям внутреннюю точку входа на выход за границей. Промежуточные серверы несут трафик Reality.

```
meridian relay add [USER@]RELAY_IP[:PORT] --exit EXIT [flags]
meridian relay list [--exit EXIT] [--json]
meridian relay remove RELAY [--exit EXIT] [--yes] [--forget-unreachable]
meridian relay sni RELAY NEW_SNI [--exit EXIT] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--exit/-e EXIT` | (требуется для add) | IP или имя сервера выхода |
| `--name NAME` | (авто) | Дружественное имя для промежуточного сервера (например, "ru-moscow") |
| `--port/-p PORT` | 443 | Порт слушания на промежуточном сервере |
| `--sni HOST` | цель выхода | Цель маскировки Reality для этого промежуточного сервера; пропустите, чтобы использовать цель выхода |
| `--user/-u USER` | сохранено, иначе root | SSH пользователь на промежуточном сервере |
| `--ssh-port PORT` | сохранено, иначе 22 | SSH порт на промежуточном сервере (`relay add`) |
| `--yes/-y` | | Пропустить диалоги подтверждения |
| `--forget-unreachable` | | `relay remove`: Забыть развёрнутое на удаляемом сервере, если он не отвечает по SSH (заблокирован или удалён), вместо неудачной очистки; он обслуживает прежних пользователей, пока вы его не удалите |
| `--json` | | Выдать `relay list` (`data.relays[]`) как конверт `meridian.output/v1` |

**`relay add`** — добавляет одноузловой промежуточный сервер в вашу топологию и применяет её. Клиенты получают его при следующем обновлении подписки. Для цепей с несколькими узлами используйте `meridian setup`.

**`relay remove`** — `RELAY` — это IP промежуточного сервера, сохранённое имя или ID цепочки. Удаляет каждую цепочку через этот сервер (можно сузить с `--exit`), выводит список удаляемых ресурсов (юниты Realm, правила файрвола, слушатель со стороны выхода, клиентские точки подключения), запрашивает подтверждение и применяет одобренное удаление. Серверы остаются в списке сохранённых.

**`relay sni`** — задаёт новый SNI маскировки цепочкам через сервер (или одной цепочке по ID; можно сузить с `--exit`). Отклоняет те же имена, что и `node sni`, проверяет, что выход открывает сайт (собственное имя промежуточного сервера обслуживает Reality-слушатель на выходе), показывает план изменений, подтверждает и применяет. SNI самого выхода снова привязывает промежуточный сервер к выходу. Приложения переключатся при следующем обновлении подписки.

Для проверки звеньев промежуточного сервера запустите `meridian check RELAY`.

### meridian route

Отправлять выбранные направления с выхода через Cloudflare WARP, напрямую или никуда, впереди исходящего по умолчанию выхода.

```
meridian route add EXIT VALUE... --via warp|direct|block [--name ID] [--json]
meridian route add EXIT --preset ai [--via warp|direct|block] [--name ID] [--json]
meridian route list [EXIT] [--json]
meridian route remove EXIT ROUTE [--yes] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--via ACTION` | `warp` с `--preset`, иначе обязателен для add | `warp`, `direct` или `block` |
| `--preset NAME` | | Готовый набор направлений вместо `VALUE`: `ai` (AI-сервисы) |
| `--name ID` | пресет или действие с номером | ID маршрута показанный через `route list` и используемый через `route remove` |
| `--yes/-y` | | Пропустить подтверждение удаления (требуется с `--json`) |
| `--json` | | Выдать конверт `meridian.output/v1` (`data.override` для add/remove, `data.exits[]` для list) |

`EXIT` это ID выхода, сохранённое имя сервера или IP. Каждый `VALUE` это домен (поддомены включены), `geosite:NAME` или `geoip:NAME`; один маршрут держит один вид.

**`route add`** — добавляет маршрут к выходу в вашу топологию и применяет его. Маршруты совпадают в порядке который они были добавлены. Маршрут `warp` на выходе без WARP настраивает WARP только для того маршрута; остальной трафик остаётся прямым.

**`route list`** — показывает каждый исходящий выход по умолчанию и его маршруты в порядке совпадения.

**`route remove`** — удаляет один маршрут и применяет изменение; его направления следуют исходящему по умолчанию выхода снова. WARP остаётся установленным на сервере но ничего не несёт пока маршрут или `--warp` не используется снова.

### meridian fleet

Здоровье серверов и инвентарь из живого сервиса управления, история применений, обновления и описание серверов в виде редактируемого файла.

```
meridian fleet status [--json]
meridian fleet inventory [--json]
meridian fleet history [--json]
meridian fleet events [--since ID] [--limit N] [--json]
meridian fleet usage [--days N] [--json]
meridian fleet upgrade [--tested] [--yes]
meridian fleet export [--json]
meridian fleet import FILE [--dry-run] [--yes] [--forget-unreachable] [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--since ID` | 0 | `fleet events`: события после этого номера |
| `--limit N` | 100 | `fleet events`: вернуть 1–2000 событий |
| `--days N` | 30 | Дни UTC для `client usage` или `fleet usage`: 1–730, не больше сохранённого срока хранения |
| `--json` | | Выдать результат как конверт `meridian.output/v1` (`status`, `inventory`, `history`, `export`, `import`) |
| `--tested` | | `fleet upgrade`: не обращаться к GitHub; Realm остаётся на протестированной версии или на той, до которой вы уже обновились |
| `--yes`, `-y` | | `fleet upgrade`, `fleet import`: пропустить подтверждение |
| `--dry-run` | | `fleet import`: показать изменения и проверку, ничего не применяя |
| `--forget-unreachable` | | `fleet import`: забыть развёрнутое на удаляемом сервере, чей SSH-порт не отвечает |

**`fleet status`** — состояние сервиса управления, последний отчёт каждого агента и применил ли он текущую конфигурацию, слушатели промежуточных серверов и число клиентов. Отсутствие объявленных клиентов помечает состояние как деградировавшее; отключённые, исчерпавшие лимит или просроченные клиенты учитываются в сводке, но не считаются сбоем. Доступный слушатель промежуточного сервера подтверждает только TCP-соединение, поэтому непроверенные маршруты через промежуточные серверы оставляют статус `unknown`; для полной сквозной проверки используйте `meridian test`. Код выхода `0` означает исправное состояние, `4` — есть проблемы, `3` — статус неизвестен.

Столбец `active` показывает число людей с приростом трафика в последнем отчёте; время его сбора указано ниже. Запоздавший старый отчёт не заменяет более свежие данные об активности. Итоги трафика узла сохраняются при смене эпох счётчиков; `traffic_counting_since` отмечает начало полного учёта, а до обновления восстанавливаются только сохранившиеся данные.

`GET /api/nodes/NODE` возвращает сохраняемый итог `traffic_bytes`, данные об активности в последнем отчёте и начало полного учёта; контракт доступен через `meridian api schema service-node-status`.

**`fleet inventory`** — настроенные серверы, роли, узлы и промежуточные серверы вместе с живым статусом, если сервис управления доступен. API-токены и секретные пути никогда не выводятся. Если живой статус недоступен, настроенный состав серверов всё равно выводится с предупреждениями, а команда завершается с кодом `3`. Чтобы проверить, требуется ли `apply`, используйте `plan --json`.

**`fleet history`** — каждое одобренное применение, которое записал сервис управления, от новых к старым: номер, время, автор (имя токена компьютера, `root` для собственного токена CLI, `owner` для консоли), статус (`proposed`, `approved`, `applied` или `failed`) и начало хеша плана. С `--json` возвращает `data.revisions[]`.

**`fleet events`** — локальные изменения пользователей, токенов и приватности, а также потеря связи с узлами и восстановление. События идут от старых к новым после `--since ID` (по умолчанию `0`). `--limit N` возвращает 1–2000 событий, по умолчанию 100. JSON содержит `data.events[]`, `next_cursor` и `has_more`; для продолжения передайте полученный номер. В каждой записи есть время UTC, вид события, автор (имя токена, `root`, `owner` или `system`), объект и краткие подробности: имена изменённых полей, область доступа токена или ID записи приватности. Учётные данные, тексты ошибок, адреса клиентов и сведения об устройствах не записываются. Хранятся не более 2 000 событий за последние 180 дней; они входят в снимки. `GET /api/events?after=ID&limit=N` требует область `read` и также доступен вошедшему владельцу.

**`fleet upgrade`** — обновляет ваши серверы одним одобренным применением. Сервис управления и каждый агент узла переходят на сборку, которая поставляется с этой версией Meridian, причём агент обновляется на месте и сохраняет идентичность узла; чтобы получить более новые сборки, сначала выполните `meridian update`. Промежуточные серверы переходят на новейший выпуск Realm, не дожидаясь обновления Meridian: последний релиз на GitHub в рамках протестированной мажорной версии записывается в `cluster.yml` вместе с опубликованной GitHub контрольной суммой sha256 для каждого архива, которую каждый промежуточный сервер проверяет перед установкой. Команда показывает, что работает на каждом сервере, с пометкой `current` или `upgrade`, а после вашего подтверждения применяет одобренный план и запускает `meridian check` на каждом сервере. Если какую-либо версию прочитать не удалось, команда завершается с кодом `3` до внесения изменений.

**`fleet export`** — выводит проверенную топологию ваших серверов как YAML-файл, который можно редактировать: выходные серверы и их методы подключения, промежуточные серверы, шлюзы, пулы выходов, правила маршрутизации, маршруты, клиентов и общие настройки. Серверы указаны по сохранённому имени (или адресу, если имени нет), а не по внутреннему ID; файл начинается с `schema: meridian.fleet/v1`. Ключи Reality, API-токены, ссылки клиентов и транспортные пути XHTTP и WSS остаются в Meridian и в файл не попадают. С `--json` тот же документ возвращается в `data.document`.

**`fleet import`** — читает отредактированный файл (или `-` для стандартного ввода) и показывает, что он меняет, по строке на изменение: `+` добавляет, `-` удаляет, `~` меняет поле (`~ exit-2 sni www.example.com -> www.example.org`). Затем перечисляет всё, что изменение удалит, и хеш проверки, спрашивает подтверждение и применяет ровно эту проверку, как `apply`. Для файла без правок выводится «Изменений нет». Клиент, удалённый из `access.users`, удаляется как через `client remove`: его ссылки перестают работать, а страница подключения удаляется. Добавленный клиент создаётся как через `client add` и получает страницу; ссылки покажет `client show NAME`. Новые камуфляжные SNI проходят те же проверки, что и в `node sni`. Импорт отказывает при другой `schema`, несохранённом сервере (сохраните его через `meridian server add`), транспортных путях в файле, изменении сервера управления, его домена или бэкенда, удалении или переименовании выходного сервера на сервере управления и переносе выходного сервера на другой сервер (используйте `node replace`). Ключи и учётные данные остаются как есть. Без терминала передайте `--yes`; `--dry-run` показывает изменения и проверку, ничего не применяя.

**`fleet usage`** — показывает байты каждого сервера по дням UTC, включая сохранённый трафик удалённых серверов. `--days N` выбирает 1–730 дней в пределах срока хранения. История должна быть включена; JSON возвращает общие итоги и `nodes[].daily` в `data`.

### meridian context

Позволяет держать на одном компьютере несколько независимых наборов серверов, например для семьи и для работы, и выбирать, с каким из них работают команды.

```
meridian context list [--json]
meridian context use NAME
meridian context rename OLD NEW
meridian context remove NAME [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | `context list`: вывести конверт `meridian.output/v1` |
| `--yes`, `-y` | | `context remove`: удалить контекст, в котором ещё есть серверы, без вопроса |

**`context list`** — все контексты с адресом управляющего сервера и числом выходных серверов, промежуточных серверов и шлюзов маршрутизации. Данные берутся только с этого компьютера; `*` отмечает текущий контекст:

```
  * default   198.51.100.10    2 exits, 1 relay
    family    198.51.100.40    1 exit
```

**`context use`** — делает NAME контекстом для всех следующих команд. `meridian deploy IP --context NAME` создаёт новый контекст, а `--context NAME` у любой команды позволяет один раз поработать с другим набором серверов.

**`context rename`** — переименовывает контекст; серверы не затрагиваются.

**`context remove`** — удаляет файлы контекста с этого компьютера и не обращается к серверам: они продолжают работать, но управлять ими отсюда будет нельзя. Текущий контекст удалить нельзя, а если в контексте ещё есть серверы, команда сначала спрашивает (`--yes` пропускает вопрос). Контекст `default` — это сам домашний каталог Meridian, поэтому его нельзя переименовать, а удалить можно, только когда ваши серверы перешли в другой контекст. Такая копия помечена в `context list` как замещённая и отказывается что-либо менять; удаление `default` тогда стирает только файлы этих серверов, а SSH-ключ и настройки остаются.

### meridian check

Проверить здоровье сервера, или сможет ли новый сервер запустить Meridian. Что проверяется зависит от роли сервера в вашей системе:

- **Ещё не в системе** — проверки перед развёртыванием: достижимость цели маскировки и DNS, доступность и внешняя достижимость портов 443, DNS домена, ОС, диск и часы. Ничего не установлено; кратосрочный слушатель тестирует файрвол, когда порт 443 свободен. DNS использует собственный разрешитель сервера.
- **Сервер управления, выход или шлюз маршрутизации** — сервис управления (отвечает, принадлежит этим серверам и работает в совместимой версии), агент каждого узла (в сети, применил текущую конфигурацию, текущая сборка), SSH (или локальный доступ), все скомпилированные публичные и внутренние порты, TLS-сертификаты и место на диске. При запуске с другой машины сервер управления также проходит проверку потока данных: скачивание ~50 КБ, которое выдаёт предупреждение, если передача замирает примерно после 16–24 КБ (троттлинг, измеренный из вашей сети).
- **Промежуточный сервер** — каждое звено Realm на сервере: сервис активен и может достучаться до следующего звена, а публичный вход цепочки принимает TCP с вашей машины.

Без сервера проверяется каждый сервер в системе.

```
meridian check [SERVER] [--domain NAME] [--sni HOST] [--user USER]
               [--ssh-port PORT] [--ai] [--json]
```

`--domain` и `--sni` применяются к серверам, ещё не развёрнутым: проверяют, что домен разрешается на сервер и что конкретная цель маскировки достижима. `--user` и `--ssh-port` переопределяют сохранённого SSH пользователя и порт. `--ai` копирует готовый для AI диагностический запрос в буфер обмена. `--json` выводит один конверт `meridian.output/v1` с отчётом по сервёрам и областям.

Отсутствующие доказательства никогда не рассматриваются как успех. Выход `0` означает, что все проверки прошли, `4` означает найденные проблемы, `3` означает требуемые доказательства были недоступны, и `2` означает недопустимый ввод. Каждая неудача выводит её исправление. Используйте `meridian test` для передачи реального трафика через весь маршрут.

### meridian scan

Найти цели маскировки на собственной сети сервера, используя закреплённый выпуск RealiTLScanner. Meridian проверяет его SHA-256 контрольную сумму перед запуском и удаляет удалённое рабочее пространство после этого.

```
meridian scan [SERVER] [--user USER] [--ssh-port PORT]
```

RealiTLScanner сканирует IPv4 диапазоны; IPv6-только сервер выходит `3`. Выбор результата выводит команду для его использования — он не изменяет развёрнутую топологию. Пропуск выходит `0`, недопустимый выбор выходит `2`, нет подходящих целей выходит `4` и сканер или ошибки загрузки выходят `3`.

### meridian test

Протестировать реальный VPN-трафик с вашего устройства. SSH не требуется.

Полный тест выбирает активного клиента, получает точный Xray JSON, который ему отдаёт сервис управления, и пропускает реальный трафик через группу автопереключения и через каждый маршрут целевого сервера. При первом запуске может потребоваться до 120 секунд на скачивание и проверку контрольной суммы закреплённой версии Xray. Проверки трафика чередуют независимые сервисы определения внешнего IP и сравнивают ответ через прокси с прямым запросом, поэтому сбой самого сервиса определения IP даёт неопределённый результат, а не ложную ошибку. Переменная `MERIDIAN_CONNECT_TEST_URL` позволяет задать свой URL проверки для изолированных окружений.

Для каждого маршрута выводится время до первого байта. Если маршрут не сработал, Meridian открывает обычное TCP-соединение к его порту, чтобы уточнить причину: **подключается, но трафик не проходит** (сервер отвечает, но прокси-сессия не передаёт данные — неверные ключи или обрыв соединения) либо **недоступен** (на порту никто не отвечает). С флагом `--json` поле `data.transports` перечисляет итог по каждому маршруту (`ok`, `no_traffic`, `unreachable`, `failed`, `egress_mismatch`, `inconclusive`, `invalid`) и `first_byte_ms`.

При недоступности сервиса управления, ответе HTTP `429` или `5xx` получить подписку нельзя, поэтому команда завершается с кодом `3`. Любой другой отказ при получении подписки (например, `400` или `422`) считается отрицательным результатом проверки и возвращает код `4`.

```
meridian test [SERVER|DOMAIN] [--domain NAME] [--sni NAME]
              [--client NAME] [--basic] [--probe] [--timeout SECONDS] [--json]
```

Без указания цели `test` проверяет сохранённый сервер, на котором запущен, или ваш единственный сохранённый сервер. Если их несколько, он по очереди проверяет каждую публичную точку входа ваших серверов (каждый выход, затем точку входа каждого промежуточного сервера) и завершается с худшим результатом; тогда `--json` возвращает по одному результату на сервер в `data.results`.

`--client` тестирует конкретного активного клиента. `--basic` запускает только сетевые и TLS-проверки без скачивания Xray и не проверяет маршруты, работающие только по UDP; его нельзя совмещать с `--client` (код выхода `2`). `--timeout` (по умолчанию `5`, диапазон `1`–`30`) ограничивает каждую сетевую операцию отдельно от первичной загрузки Xray.

Код выхода `0` означает, что все проверки прошли, `4` — тест выявил проблемы, `3` — не удалось собрать необходимые данные. `--json` выводит конверт `meridian.output/v1` со всеми проверками и результатами.

#### Взгляд цензора: `meridian test --probe`

`--probe` смотрит на сервер так, как это делает активный сканер цензора, проверяя, не выдаёт ли сервер себя, вместо отправки трафика. Работает с любым IP или доменом и применяет более строгие проверки, если цель входит в вашу сохранённую топологию.

Проверки соответствуют реальной конфигурации: открытые публичные и внутренние порты, поведение HTTP/TLS, согласованность SNI и маскировки, типичные пути прокси и панелей управления, апгрейды WebSocket, обратный DNS, HTTP/2, устаревшие версии TLS и настроенные домены. `--sni` переопределяет SNI для общих TLS-проверок. Для чисто UDP-портов сообщается, что требуется полный `meridian test`.

`--probe` также отвечает на вопрос «что блокируется?». Команда открывает TLS-соединение к серверу с его маскировочным SNI; если оно не проходит, повторяет попытку без SNI и открывает настоящий сайт маскировки напрямую, после чего сообщает, что именно выглядит заблокированным: **IP сервера** или **маскировочный SNI**. Если настоящий сайт тоже недоступен, результат считается неопределённым, а не ошибкой. При маскировке self-steal настоящий сайт — это сам сервер, поэтому независимого ориентира нет: когда ничего не проходит, результат остаётся неопределённым. На сервере управления команда также скачивает скрипт страницы подключения (~50 КБ) и проверяет, не замирает ли передача примерно после 16–24 КБ — именно так ведут себя иностранные IP под троттлингом. Если маршрут WSS идёт через CDN, та же проверка выполняется через CDN. Эти результаты имеют смысл только при запуске изнутри цензурируемой сети. `--probe` нельзя совмещать с `--basic`, `--client` или `--domain`. Коды выхода те же, что у `test`; пропущенные проверки никогда не засчитываются как успешные.

`meridian probe [SERVER|DOMAIN] [--sni NAME] [--timeout SECONDS] [--json]` — то же самое, что `meridian test IP --probe`.

### meridian doctor

Собрать системные диагностики для отчётов об ошибках.

```
meridian doctor [SERVER] [--sni HOST] [--user USER] [--ssh-port PORT] [--ai]
```

`--sni` выбирает цель маскировки для диагностики, `--user` и `--ssh-port` переопределяют сохранённого SSH пользователя и порт, и `--ai` копирует отредактированный, готовый к AI отчёт в буфер обмена вместо печати шаблона проблемы.

Doctor следует ролям сервера: сервер, который работает только как промежуточный, не диагностируется как выход, и маршрутизирующие шлюзы помечены отдельно. Отсутствующие инструменты или потерянное SSH подключение делают отчёт неубедительным (выход `3`); уже собранные секции всё ещё показаны.

### meridian logs

Показать последние журналы сервера в отредактированном виде, не входя на него.

```
meridian logs [SERVER] [--lines N] [--grep TEXT] [--component NAME]
              [--user USER] [--ssh-port PORT]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--lines`, `-n N` | `100` | Сколько строк показать из каждого журнала (`1`–`10000`) |
| `--grep`, `-g TEXT` | | Только строки с этим текстом; без учёта регистра, ищется буквально, а не как регулярное выражение |
| `--component`, `-c NAME` | все | Только `node`, `panel`, `nginx` или `relay`; повторите, чтобы выбрать несколько |

`logs` читает то, что запускают роли сервера: выходы и маршрутизирующие шлюзы показывают агента (`netagent`) и Xray (`netcore`) в компоненте `node`, сервер управления показывает сервис управления (`ctld`) в компоненте `panel`, оба показывают журнал ошибок nginx, а промежуточные серверы показывают журнал своих юнитов Realm. `--user` и `--ssh-port` переопределяют сохранённого SSH пользователя и порт.

В каждой строке секреты скрываются так же, как в `meridian doctor`: токены, пароли, ключи, UUID, идентификаторы подписок и секретные пути сервиса управления и страницы подключения заменяются на `[REDACTED]`, поэтому вывод безопасно вставлять в отчёт об ошибке. Строки печатаются простым текстом, управляющие символы терминала удалены.

Сервер без роли в системе или `--component`, который он не запускает, завершается с кодом `2` до подключения. Журнал, который не удалось прочитать (нет сервиса, потеряно SSH-подключение), показывается как недоступный, и команда завершается с кодом `3`.

### meridian panel

Показать адрес веб-консоли, а пока у неё нет владельца — одноразовую ссылку настройки.

```
meridian panel [--setup-link]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--setup-link` | | Вывести ссылку сброса, даже если у консоли есть владелец: она задаёт новый пароль, отключает код входа и завершает сеансы на всех устройствах |

Ссылка настройки работает один раз в течение 15 минут; откройте её, чтобы выбрать пароль владельца. Когда у консоли есть владелец, `panel` выводит адрес и включён ли код входа. Храните и адрес, и ссылку настройки как пароль. В консоли вы управляете людьми и API-токенами; серверы, ревизии и название подписки там только для чтения. См. [Веб-консоль](/ru/client-management/#веб-консоль).

### meridian teardown

Удалить Meridian с сервера.

```
meridian teardown [SERVER] [--user USER] [--ssh-port PORT] [--yes]
```

При одиночном развёртывании сервера teardown удаляет всё, что создал Meridian: сервис управления и его базу, агента и Xray, конфигурацию nginx, сертификаты, промежуточные серверы и правила файрвола на сервере, а затем локальный `cluster.yml` и сохранённый профиль сервера. Системные пакеты, настройки SSH и fail2ban остаются, а nginx продолжает работать, если он ещё обслуживает ваши собственные сайты. Также удаляет 3x-ui из Meridian 3.x. При нескольких серверах teardown отклоняет сервер, который всё ещё имеет роль в топологии.

`--yes` пропускает подтверждение; проверки ролей всё ещё запускаются первыми. Отклонение выходит `1`. Неизвестное имя сервера, или ноль или несколько возможных целей выходит `2` вместо запроса.

### meridian backup

Зашифрованные снимки состояния сервиса управления, компьютеры, которые их получают, и ключ восстановления.

```
meridian backup pull [--name NAME]
meridian backup recovery-key [--yes]
meridian backup devices
meridian backup revoke ID
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | имя этого компьютера | `backup pull`: имя, которое получает ключ этого компьютера при первой регистрации |
| `--yes`, `-y` | | `backup recovery-key`: заменить существующий ключ восстановления без вопроса |

После каждой команды, которая меняет ваши серверы, Meridian сохраняет свежий снимок сервиса управления в `snapshots/` рядом с `cluster.yml` (хранятся несколько последних). Снимок содержит пользователей, лимиты, трафик, ревизии, API-токены и копию `cluster.yml` и `servers.json` этого компьютера, поэтому из него можно восстановить серверы на компьютере, где больше ничего нет. Он зашифрован для ключа каждого зарегистрированного компьютера и для ключа восстановления и никогда не содержит ключей подписи, сеансов и пароля консоли. Неудачное сохранение выдаёт предупреждение и никогда не роняет команду, которая его вызвала.

**`backup pull`** — сохраняет снимок сейчас. Первый `pull` на компьютере создаёт его ключ (`device.key`, доступный только вам) и регистрирует его в сервисе управления.

**`backup recovery-key`** — создаёт ключ восстановления ваших серверов или, спросив, заменяет существующий, и показывает его один раз. Meridian хранит только его открытую часть, поэтому запишите или распечатайте его и храните офлайн. Первое развёртывание уже показывает такой ключ. Недоступно с `--json`.

**`backup devices`** — выводит компьютеры, для ключей которых шифруются снимки, с их ID и временем регистрации, а также есть ли у ваших серверов ключ восстановления.

**`backup revoke`** — перестаёт шифровать новые снимки для ключа одного компьютера, например потерянного ноутбука. Снимки, которые у него уже есть, по-прежнему читаются его ключом; отзовите его до того, как он получит новый.

### meridian restore

Восстановить потерянный или изъятый сервер управления на другом сервере из снимка.

```
meridian restore --to SERVER [--snapshot FILE] [--recovery-key] [--force]
                 [--name NAME] [--user USER] [--ssh-port PORT] [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--to SERVER` | (обязателен) | Новый сервер управления: IP, `user@IP:port` или сохранённое имя |
| `--snapshot FILE` | последний сохранённый | Снимок для восстановления |
| `--recovery-key` | | Открыть снимок ключом восстановления вместо ключа этого компьютера; ключ спрашивается (скрыто) или читается одной строкой из стандартного ввода |
| `--force` | | Восстановить, даже если старый сервис управления ещё отвечает |
| `--name NAME` | (нет) | Имя для нового сервера |
| `--user/-u USER` | root | Пользователь SSH на новом сервере |
| `--ssh-port PORT` | 22 | Порт SSH на новом сервере |
| `--yes`, `-y` | | Пропустить подтверждение |

Restore открывает снимок, показывает, что собирается сделать, и спрашивает подтверждение. Затем устанавливает сервис управления на новый сервер из снимка, переносит в вашей топологии сервер управления (и выход старого сервера, если он был) на новый адрес и выполняет обычное одобренное применение. Восстановленный сервис получает новый удостоверяющий центр, новые ключи подписи и новый API-токен, поэтому каждый агент регистрируется заново, а изъятый сервер не может подписать ничего, что примут ваши узлы. Пользователи сохраняют учётные записи, лимиты и трафик. Владелец консоли задаёт новый пароль по ссылке из `meridian panel`.

Если сервер управления работает по голому IP, его адрес входит в каждый URL подписки, поэтому все ссылки меняются: проверка об этом предупреждает, а в конце выводится новая ссылка каждого клиента. С доменом ссылки остаются прежними, как только его DNS-запись указывает на новый сервер; проверка называет эти записи.

Restore отказывается работать, пока старый сервер управления отвечает, потому что два сервиса управления разделили бы ваши серверы; `--force` это обходит, например если старый сервер изъят. Команда предупреждает, если `--snapshot` указывает на файл старше последнего сохранённого: старый снимок вернёт токены, компьютеры и людей, которых вы с тех пор удалили. Остановившийся restore можно запустить снова, и он продолжит с места остановки.

На компьютере без ваших серверов передайте файл снимка и `--recovery-key`: сначала восстанавливается копия файлов конфигурации из самого снимка. Если копия на этом компьютере старше, чем в снимке, restore помещает серверы в новый контекст и после проверки, где это названо, забирает их у старого контекста; тот помечается как заменённый и отказывается вносить изменения, пока вы не удалите его командой `meridian context remove`.

### meridian migrate

Перевести серверы, работающие на панели Remnawave, на сервис управления Meridian на месте, сохранив все ссылки.

```
meridian migrate [--yes]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--yes`, `-y` | | Пропустить подтверждение |

Сначала migrate показывает план перехода: какие клиенты переносятся, что о клиенте сохранить не удастся и какие данные панели не сохранит никто (учётная запись администратора и API-токены панели, история трафика по дням, регистрации устройств HWID, плагины панели и правила ответов, которые задавал не Meridian, передача IP-адресов клиентов (она обслуживала лимиты панели по IP для каждого пользователя), а также страница подписки Remnawave; собственные страницы подключения Meridian остаются). После вашего подтверждения команда:

1. Делает резервную копию базы панели — в `backups/` на вашем компьютере и в `/var/backups/meridian-migration/` на сервере управления, вместе с файлами конфигурации
2. Устанавливает сервис управления рядом с панелью и импортирует каждого клиента с теми же ключами, идентификатором подписки, статусом, лимитами, сроком действия и трафиком
3. Останавливает панель (её данные сохраняются) и удаляет контейнер каждого узла
4. Применяет конфигурацию: на каждом выходе появляется агент, зарегистрированный в сервисе управления
5. Проверяет, что ссылка подписки каждого клиента осталась точно такой же
6. Удаляет Remnawave

Отката нет: путь назад — резервная копия. Каждый шаг сохраняется, поэтому остановившийся переход продолжается при повторном запуске, а завершённый ничего не делает. Если проверка ссылок не прошла, Remnawave остаётся на месте (остановленным), и команда завершается с ошибкой. Без терминала передайте `--yes`, иначе migrate остановится после показа плана. `meridian deploy` предлагает переход, если находит серверы на Remnawave.

### meridian update

Обновить CLI на последний выпуск своей основной версии на PyPI. Новая основная версия только анонсируется; `--major` переходит на неё после прочтения вами заметок о выпуске. Бета-версия следует за более новыми бета-версиями своей основной версии, а затем стабильным выпуском. Meridian пытается uv, pipx и pip, и только сообщает успех, когда активная команда `meridian` показывает новую версию. Выход `0` означает уже текущий или обновлённый; `3` означает обновление или его проверка не удалась. Обновление CLI не изменяет ваши серверы.

```
meridian update [--major]
```

### meridian studio

Открыть Meridian Studio, экспериментальный браузерный UI, с его локальным Engine API. Сервер привязывается только к `127.0.0.1`.

```
meridian studio [--port PORT] [--assets-dir DIRECTORY] [--no-open]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--port PORT` | 7391 | Локальный порт от 0 до 65535; `0` выбирает любой свободный порт |
| `--assets-dir DIRECTORY` | упакованные ресурсы | Использовать встроенный директорий ресурсов Studio вместо упакованной копии |
| `--no-open` | | Выводить локальный URL без открытия браузера |

Studio выводит и открывает адрес вида `http://127.0.0.1:7391/studio/#k=…`. Часть после `#k=` — это ключ, который меняется при каждом запуске: пользоваться Engine может только вкладка браузера, открытая по этому адресу, поэтому другие программы и другие пользователи на этом же компьютере не смогут. Держите адрес в тайне. После перезапуска Studio откройте новый адрес, который он выведет.

Без `--port` Studio использует порт 7391 или, если он занят, следующий свободный порт до 7400. Так черновик, который браузер сохраняет для Studio, остаётся на месте и при следующем запуске. Если явно указанный `--port` занят, Studio завершается с понятной ошибкой; то же происходит, если нет ресурсов. Явно указанный каталог ресурсов должен содержать `studio/index.html`.

### meridian serve

Запустить сервис управления. Meridian устанавливает его на сервер управления как модуль systemd `ctld`, который запускает эту команду; вручную её запускать не нужно.

```
meridian serve [--config FILE]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--config FILE` | `/etc/ctld/config.json` | Конфигурация сервиса, которую пишет Meridian |

Сервис слушает `127.0.0.1:3000` за nginx и хранит состояние в одном файле SQLite в `/var/lib/ctld/`. Он не записывает запросы, поэтому идентификаторы подписок и секретные пути никогда не попадают в журнал. `meridian logs SERVER -c panel` показывает его журнал.

### meridian api

Проверить машиночитаемые контракты позади JSON вывода для скриптов и UI клиентов.

```
meridian api schemas [--json] [--include-schemas]
meridian api commands [--json] [--include-schemas]
meridian api schema NAME [--envelope|--json]
meridian api workflow NAME [--json]
```

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Выдать каталог как конверт `meridian.output/v1` |
| `--include-schemas` | | Включить полные JSON Schemas (подразумевает JSON вывод) для `api schemas` или `api commands` |
| `--envelope`, `--json` | | Обернуть `api schema NAME` в конверт `meridian.output/v1` вместо вывода сырой схемы |

**`api schemas`** — выводит имена схем, такие как `output-envelope`, `deploy-request`, `deploy-result`, `deploy-plan`, `plan-envelope`, `apply-envelope`, `client-list-envelope`, `fleet-status-envelope` и `event`.

**`api commands`** — выводит контракты команд: argv, схемы конверта и данных, возможные статусы и результаты, значения кодов выхода, все опции, которые принимает команда (`machine_flags`), и `interrupt_behavior`. Аргументы, опции и описания читаются из самого CLI. Ctrl-C выходит `130` без конверта JSON (`interrupt_behavior: "exit_130_without_envelope"`).

**`api schema NAME`** — выводит одну JSON Schema, например `meridian api schema output-envelope`.

**`api workflow NAME`** — выводит отрисовываемый UI поток работы, например `meridian api workflow deploy --json`.

### meridian help

Рассказать об Meridian ИИ-агенту или показать справку по одной команде.

```
meridian help [agents | COMMAND...]
```

**`meridian help agents`** выводит руководство в формате Markdown для ИИ-агентов: что делает Meridian, как связаны ваши серверы и их одобренная топология, где хранится состояние, правила безопасной работы с CLI (неинтерактивные флаги, конверты JSON, план перед применением, подтверждение перед удалением, ссылки как секреты), коды выхода и типовые задачи. Вывод всегда в чистом Markdown, так что агент может прочитать его из канала.

**`meridian help COMMAND`** показывает ту же справку, что и `meridian COMMAND --help`, например `meridian help node add`. Без аргументов выводит справку верхнего уровня. Неизвестная тема завершается с кодом `2`.

## Глобальные параметры

Глобальные параметры идут перед командой, например `meridian --quiet doctor`. Параметры команд, такие как `test --json`, идут после неё.

| Флаг | Описание |
|------|-------------|
| `--version`, `-v` | Показать версию CLI и выйти |
| `--verbose` | Включить отладочное логирование |
| `--quiet`, `-q` | Подавить вывод прогресса |
| `--context NAME` | Работать с другим набором серверов ([meridian context](#meridian-context)); по умолчанию `MERIDIAN_CONTEXT`, иначе текущий контекст. Можно указывать и после команды: `meridian deploy 203.0.113.5 --context work` |
| `--lang CODE` | Язык для мастера setup: `en`, `ru`, `fa` или `zh` (по умолчанию: сохранённый выбор, иначе спрашивается) |
| `--json` | Запросить конверт JSON из команды, которая его поддерживает; другие команды явно падают |
| `--install-completion` | Установить завершение оболочки для текущей оболочки |
| `--show-completion` | Выводить скрипт завершения для текущей оболочки |

JSON-вывод использует конверт `meridian.output/v1` (`schema`, `command`, `operation_id`, `status`, `summary`, `data`, `warnings`, `errors`). Его поддерживает каждая команда, у которой указан флаг `--json`: `deploy`, `plan`, `apply`, `check`, `test`, `probe`, все команды `client` и `route`, `fleet status`/`inventory`/`history`/`export`/`import`, `node`/`relay list` и команды `api`. Глобальный `--json` и собственный `--json` команды взаимозаменяемы. Секреты скрываются до вывода JSON из процесса. Запустите `meridian api commands --json`, чтобы посмотреть список контрактов.

## Обычные параметры сервера

Они повторяются по командам; каждая команда принимает только параметры, указанные в её собственном разделе.

| Флаг | Использовано |
|------|---------|
| `SERVER` аргумент | deploy, check, scan, test, doctor, logs, teardown, node add, relay add, server add |
| `--user`, `-u USER` | deploy, check, node add, relay add, server add, scan, doctor, logs, teardown, restore |
| `--ssh-port PORT` | deploy, check, node add, relay add, server add, scan, doctor, logs, teardown, restore |
| `--sni HOST` | deploy, check, node add, relay add, test, doctor |
| `--domain DOMAIN` | deploy, check, node add, test |
| `--self-steal` | deploy, node add, node sni |

Команды client используют API сервиса управления напрямую и не принимают сервер. `test` запускается с вашего устройства и не использует SSH.

## Разрешение сервера

Сервер указывается первым, как в `ssh`: IP, сохранённое имя, `user@host:port` или `local` — запуск на текущей машине без SSH. `--user` и `--ssh-port` дополняют то, чего нет в цели, и не должны ей противоречить. Пустой пользователь или порт означают сохранённое значение, а если его нет — `root` и `22`. Без сервера Meridian использует локальный режим (при запуске на развёрнутом сервере) или единственный сохранённый сервер. Если кандидатов нет или их несколько, команда завершается с кодом `2`, а не задаёт вопрос.
