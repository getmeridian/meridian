## Команды

### meridian deploy

Разворачивает один сервер и выдаёт готовую ссылку для подключения. Этот сервер становится одновременно сервером управления (на нём работает сервис управления Meridian) и выходным сервером. Команда `deploy` формирует такую же проверенную топологию, что и `meridian setup`, применяет её с сохранением контрольных точек, проверяет прохождение реального трафика через выпущенную подписку и выводит ссылки на страницу подключения и подписку. Повторный запуск той же команды продолжает прерванную установку или обновляет существующую конфигурацию, сохраняя секретные пути, ключи и пользователей. В конце первого развёртывания ваших серверов один раз выводится ключ восстановления (см. [`meridian backup`](#meridian-backup)).

```
meridian deploy [SERVER] [flags]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--sni HOST` | (auto) | Сайт для маскировки (SNI). Если не указан, при первом развёртывании проверяются сайты из собственной подсети сервера, затем `www.google.com`, `dl.google.com` и `www.cloudflare.com`, и выбирается первый сайт, через который успешно проходит трафик; при повторном запуске сохраняется ранее выбранный сайт. Явно заданный `--sni` автоматически не заменяется |
| `--domain DOMAIN` | (нет) | Ваш домен: переносит XHTTP на домен и добавляет WSS — оба способа работают через CDN Cloudflare (без домена XHTTP работает по IP-адресу). Сервис управления и страницы подключения остаются на IP-сертификате |
| `--self-steal` | выкл. | Маскировка под ваш собственный домен (`--sni` или `--domain`), направленный на сервер записью в режиме «только DNS»: Meridian выпускает для него сертификат Let's Encrypt, и при внешних проверках сервер сам отвечает стандартной страницей 404 nginx. Перед установкой `deploy` проверяет DNS-запись домена: останавливается, если имя не разрешается, и предупреждает, если оно ведёт на другой адрес. При повторном запуске настройка сохраняется; указание нового `--sni` без этого флага возвращает маскировку под сторонний сайт |
| `--hysteria2/--no-hysteria2` | вкл. | Включает Hysteria2 на порту UDP/443 с обфускацией salamander в качестве резервного способа подключения. Использует сертификат домена или IP-сертификат |
| `--fingerprint NAME` | chrome | TLS-отпечаток клиента для подключений Reality, XHTTP и WSS (`chrome`, `firefox`, `safari`, `ios`, `android`, `edge`, `random`, `randomized`). Смените его, если провайдеры в вашем регионе начнут блокировать текущий отпечаток; при повторном запуске сохранённое значение не сбрасывается |
| `--client-name NAME` | default | Имя первого клиента |
| `--display-name NAME` | (нет) | Название VPN на страницах подключения |
| `--icon EMOJI_OR_URL` | (нет) | Значок страницы — эмодзи или ссылка на картинку |
| `--color PALETTE` | ocean | Цветовая тема страницы подключения (`ocean`, `sunset`, `forest`, `lavender`, `rose`, `slate`) |
| `--user USER` | сохранённый, иначе root | Пользователь SSH (для пользователя не `root` нужен `sudo` без пароля) |
| `--ssh-port PORT` | сохранённый, иначе 22 | Порт SSH |
| `--harden / --no-harden` | вкл. | Вход по SSH только по ключу, fail2ban и файрвол UFW. Флаг `--no-harden` оставляет эти настройки без изменений, если на сервере работают другие службы |
| `--warp / --no-warp` | выкл. | Направлять исходящий трафик выходного сервера через Cloudflare WARP |
| `--geo-block` / `--no-geo-block` | вкл. | Блокировать российские домены и IP-адреса (`geosite:category-ru` + `geoip:ru`) на выходном сервере. В профилях Xray JSON и Mihomo такой трафик и так направляется напрямую с устройства |
| `--country CC` | по реестру IP | Двухбуквенный код страны для названий подключений и списка серверов в веб-панели. Если не задан, при первом развёртывании страна определяется по региональному интернет-реестру (через RDAP bootstrap IANA без сторонних сервисов геолокации); при повторном запуске сохранённый код не меняется |
| `--yes` | | Пропустить запросы подтверждения |
| `--json` | | Вывести итоговый результат в JSON-конверте `meridian.output/v1` |
| `--events=jsonl` | | Передавать поток типизированных событий выполнения в формате JSONL в `stderr` |
| `--request FILE` | | Прочитать параметры развёртывания (`deploy-request`) из JSON-файла; укажите `-` для чтения из `stdin` |
| `--dry-run` | | Сформировать и показать план развёртывания без подключения по SSH и без изменения локальных файлов |

Если IP-адрес не указан, `deploy` запросит его интерактивно. Цель `local` разворачивает Meridian прямо на текущем сервере без SSH. Команда `deploy` обновляет только тот сервер, который уже числится выходным в вашей конфигурации; для добавления дополнительных серверов используйте `meridian node add`. Если ваши серверы ещё работают под управлением панели Remnawave, `deploy` сначала предложит выполнить переход с помощью [`meridian migrate`](#meridian-migrate). Повторный запуск с другими параметрами обновляет настройки этого выходного сервера (например, включает или отключает `--domain` либо `--no-hysteria2`), не затрагивая остальные выходные и промежуточные серверы, шлюзы маршрутизации и клиентов.

**Автоматизация и запуск из UI**: команда `meridian api workflow deploy --json` возвращает машиночитаемое описание полей мастера. Графический интерфейс собирает ответы, проверяет их по схеме `deploy-request` и запускает `meridian deploy --request deploy.json --json --events=jsonl`. Неинтерактивный запуск требует явного поля `yes: true` в запросе после подтверждения пользователем. Запуск с `--dry-run --json` возвращает объект `deploy-plan` в поле `data`, позволяя показать режим работы, порты и сгенерированные пути ещё до подключения по SSH.

### meridian setup

Пошаговый мастер настройки с поддержкой сохранения черновика — как для одного сервера, так и для сложной топологии с несколькими выходными серверами, промежуточными серверами Realm и шлюзами маршрутизации. Мастер рассчитан даже на тех, кто впервые настраивает собственный VPN: каждый вопрос использует точные термины (выходной сервер, промежуточный сервер, SNI), кратко поясняет их простыми словами и предлагает безопасное значение по умолчанию, которое можно принять нажатием Enter.

```
meridian setup [--intent FILE|-] [--restart] [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--intent FILE` | (нет) | Перейти сразу к проверке плана из готового JSON-документа топологии; укажите `-` для чтения из `stdin` |
| `--restart` | | Сбросить сохранённый черновик и начать настройку заново |
| `--yes`, `-y` | | Подтвердить план и применить изменения без дополнительных вопросов |

Первый шаг мастера — выбор языка интерфейса (English, Русский, فارسی, 中文): по умолчанию предлагается язык вашей системы, а выбор сохраняется в `~/.config/meridian/preferences.json` (флаг `--lang` или переменная `MERIDIAN_LANG` пропускают этот вопрос). Далее мастер последовательно спрашивает адреса серверов (IP, `user@IP:port` или `local` для текущего компьютера), роль каждого сервера, способы подключения, правила маршрутизации (только если выбран шлюз маршрутизации: каждое правило направляет трафик на выходной сервер, в пул выходов, напрямую со шлюза или блокирует его), список первых пользователей, показывает понятную сводку плана и применяет настройки. В списках выбора перемещайтесь стрелками (или нажимайте цифру нужного пункта), отмечайте строки пробелом, нажимайте `?` для подробной справки, Enter для подтверждения, Esc для возврата на шаг назад и Ctrl+C для сохранения черновика и выхода. В пунктах «Другое (ввести вручную)» можно указать собственное значение, а в текстовых полях также работают команды `назад`, `подробнее`, `сохранить` и `выйти` (или `back`, `details`, `save`, `quit`). При выборе сайта для маскировки мастер сначала сканирует подсеть самого выходного сервера (это занимает около минуты) и ставит найденные соседние сайты в начало списка перед стандартными доменами. Переменная `MERIDIAN_PLAIN_PROMPTS=1` переключает мастер в режим простых нумерованных вопросов (он также включается автоматически в терминалах без поддержки интерактивных списков). Если запустить `meridian` без аргументов, когда VPN ещё не настроен, CLI сам предложит открыть мастер. Прогресс сохраняется после каждого шага в `~/.config/meridian/setup.json` (пароли и закрытые ключи туда никогда не записываются), поэтому повторный запуск `meridian setup` продолжает с места остановки. Флаг `--intent` не перезаписывает незаконченный черновик, если не передан `--restart`. После успешного применения мастер проверяет работу всех узлов и подписок и выводит ссылки на страницы подключения.

### meridian plan

Показывает, какие изменения внесёт `meridian apply`, сверяя желаемую топологию из `~/.config/meridian/cluster.yml` с текущим состоянием серверов и сервиса управления. На самих серверах ничего не меняется.

```
meridian plan [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Вывести план в JSON-конверте `meridian.output/v1` для CI и графических интерфейсов |

Команда выводит хеш плана, количество ресурсов каждого типа, а также список ресурсов, которые требуют настройки или состояние которых не удалось проверить. В режиме `--json` поле `data` содержит `plan_hash`, `converged`, `resources[]`, `drifted_resources[]`, `observation_errors[]` и `state_changes[]`.

**Коды возврата**:
- `0` — все ресурсы соответствуют плану, изменений не требуется
- `1` — планировать нечего (серверы ещё не настроены или локальные файлы конфигурации повреждены)
- `2` — есть неприменённые изменения (выполните `meridian apply`)
- `3` — не удалось получить данные для проверки (недоступен сервис управления, SSH или локальные файлы)

Не редактируйте `cluster.yml` вручную: вносите изменения командами `meridian setup`, `deploy`, `client add`, `node add`, `relay add` или через `fleet export` / `fleet import`.

### meridian apply

Применяет проверенную топологию из `cluster.yml` к вашим серверам. Команда показывает хеш плана и количество затрагиваемых ресурсов, запрашивает подтверждение и пошагово выполняет именно этот план с сохранением контрольных точек. Если выполнение прервётся, повторный запуск продолжит с последнего незавершённого шага.

```
meridian apply [--yes] [--forget-unreachable] [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--yes`, `-y` | | Применить план без интерактивного подтверждения |
| `--forget-unreachable` | | Не останавливаться при ошибке очистки удаляемого сервера, если он не отвечает по SSH (заблокирован или уже удалён у хостера), и удалить его ресурсы из локального состояния; сам сервер продолжит работать со старыми настройками, пока вы не удалите VPS |
| `--json` | | Вывести результат применения в JSON-конверте `meridian.output/v1` |

В режиме `--json` поле `data` содержит `plan_hash`, `generation` и список `actions[]` со статусами `"converged" | "applied" | "failed" | "unknown" | "skipped"`. В режиме JSON интерактивные вопросы не задаются: без флага `--yes` команда возвращает ошибку `MERIDIAN_CONFIRMATION_REQUIRED` с хешем плана и завершается с кодом `2`. Если какой-либо шаг завершился ошибкой, возвращается код `3` — устраните причину и снова запустите `meridian apply`. Если изменения на серверах прошли, но сохранить локальное состояние не удалось, команда также вернёт код `3` с предупреждением: исправьте права доступа к `~/.config/meridian`, после чего выполните `plan` и `apply`.

Удаление ресурсов тоже проходит через `apply`: все объекты, исключённые из топологии (пользователи, способы подключения, выходные и промежуточные серверы, шлюзы маршрутизации), очищаются после того, как успешно настроены все актуальные ресурсы плана (в выводе `plan` удаляемые ресурсы показываются отдельно). Сам сервер управления можно удалить только командой `meridian teardown` либо перенести на новый адрес командой `meridian restore`.

Каждое применение фиксируется в сервисе управления как новая ревизия (см. `meridian fleet history`) и на время работы удерживает блокировку, чтобы два компьютера не могли менять конфигурацию одновременно.

### meridian client

Параметры ниже доступны в `client add` и `client set`. Начальные настройки применяются только при создании аккаунта; последующие применения не отменяют изменений оператора. `client show` возвращает типизированные поля и рассчитанный сервером `schedule` в JSON. `client set --dry-run` возвращает `data.schedule_preview` и `applied: false`; для сохранения расписания в JSON нужен `--yes`. `client extend --days N` добавляет дни к ожидающему сроку с первого использования, не активируя аккаунт; после активации продлевает дату окончания и начинает новую серию автопродлений.

| Параметр | Значение |
| --- | --- |
| `--reset-day N\|default` | День сброса от 1 до 31; default — день создания |
| `--duration DAYS\|none` | От 1 до 3650 дней с первого трафика; none убирает длительность |
| `--renew-days DAYS` | Продлевать каждые 1–3650 дней UTC |
| `--renew-months MONTHS` | Продлевать каждые 1–120 календарных месяцев |
| `--renewals N\|unlimited` | От 1 до 10000 продлений; unlimited снимает лимит |
| `--no-renew` | Выключить автопродление |
| `--dry-run` | Рассчитать даты без сохранения |
| `--yes` | Подтвердить изменение расписания |

`--devices unlimited` (или `0`) снимает с пользователя ограничение числа устройств. `--devices default` возвращает общий лимит из настроек серверов. В панели это два отдельных варианта. В API `device_limit: 0` означает отсутствие лимита, а `null` — общий лимит. Настройки конфиденциальности сохраняют силу. При миграции с Remnawave персональные лимиты, включая ноль, сохраняются; записи об устройствах не переносятся.

Управление доступом пользователей.

```
meridian client add NAME [NAME...] [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N\|default] [--json]
meridian client show NAME [--connections] [--json]
meridian client preview NAME --user-agent UA [--accept TYPE] [--suffix SUFFIX] [--json]
meridian client usage NAME [--days N] [--json]
meridian client list [--attention] [--tag TAG|none] [--json]
meridian client set NAME [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N\|default] [--note TEXT] [--tag TAG|none] [--language en|ru|fa|zh|default] [--json]
meridian client reset-traffic NAME [--json]
meridian client extend NAME --days N [--json]
meridian client devices NAME [--remove ID | --clear] [--json]
meridian client enable NAME [--json]
meridian client disable NAME [--json]
meridian client reissue NAME [--cut-off] [--yes] [--json]
meridian client remove NAME [--cut-off] [--yes] [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--days N` | 30 | Число дней UTC для `client usage` и `fleet usage` (1–730, но не больше настроенного срока хранения истории) |
| `--json` | | Вывести результат в JSON-конверте `meridian.output/v1` (доступно во всех подкомандах `client`) |
| `--attention` | выкл. | В `client list`: показать только пользователей, требующих внимания, с колонкой причины |
| `--limit SIZE` | нет | Лимит трафика (`client add`, `client set`): например, `500MB`, `50GB`, `1.5TB`; значения `none` и `0` убирают лимит. Единицы двоичные (1 GB = 1024³ байт), как считает сервис управления |
| `--reset PERIOD` | never | Период сброса счётчика трафика: `day` (каждый день), `week` (каждую неделю), `month` (каждый месяц) или `never` (без сброса) |
| `--expires DATE` | never | Срок окончания доступа: дата `YYYY-MM-DD` (конец указанного дня по UTC), точное время в формате ISO (например, `2026-12-31T18:00:00+03:00`; время без часового пояса считается UTC) или `never` (бессрочно). Дата должна быть в будущем |
| `--yes`, `-y` | | Подтвердить `client reissue` или `client remove` (обязателен при использовании `--json`) |

**`client add`** — добавляет одного или нескольких человек в топологию, применяет изменения и выводит для каждого страницу подключения и ссылку на подписку. Страница строится на основе реальной подписки пользователя и автоматически включает промежуточные серверы и Hysteria2, если они настроены. Имена, которые уже заняты в топологии или в сервисе управления, отклоняются. Имя можно указать на любом языке (`client add Биба 王小明`): на страницах и в выводе CLI сохранится исходное написание, а в сервисе управления (где допустимы только латинские буквы, цифры, `.`, `-` и `_`) будет создан транслитерированный логин (`biba`, `wangxiaoming`). Остальные команды `client` принимают оба варианта имени. Если сформировать ссылку подписки не удалось, пользователь всё равно добавляется, но команда завершается с кодом `3`. Параметры `--limit`, `--reset`, `--expires` и `--devices` включаются в проверяемый план и применяются при создании аккаунта в одной транзакции. Если применение плана завершилось ошибкой, ссылки не выводятся — доведите установку до конца командой `meridian apply`. Последующие вызовы `apply` не затирают изменения, внесённые оператором.

**`client show`** — выводит адрес страницы подключения, ссылку на подписку, статус, расход и лимит трафика с периодом сброса, срок доступа и время последней активности. **Для каждого пользователя ссылка на подписку одновременно является адресом его страницы подключения.**

С флагом `--connections` дополнительно выводятся название, протокол и URI каждого отдельного подключения в порядке следования в подписке, а также прямые ссылки на профили Xray JSON, Mihomo и sing-box. В режиме `--json` эти данные возвращаются в поле `data.connections` (ключи доступа раскрываются только в выводе этой команды). Не публикуйте эти ссылки и QR-коды в открытых логах или отчётах об ошибках.

Время первого трафика и последний узел, передававший трафик пользователя, определяются по принятым отчётам узлов (`first_traffic_at` и `last_traffic_node` в JSON). Для старого трафика, перенесённого при миграции, точное время первой активности может быть неизвестно; учитываются только сводные счётчики байтов без сохранения сессий и IP-адресов клиентов.

**`client list`** — выводит таблицу всех клиентов со статусом, расходом трафика, сроком доступа и временем последней активности, включая пользователей, добавленных через веб-панель (в JSON у них `declared: false`). С флагом `--json` возвращает сводные счётчики `data.summary` и массив `data.clients[]`.

Флаг `client list --attention` оставляет в списке только тех пользователей, у которых срок доступа истекает в ближайшие 7 дней (включая текущий момент), израсходовано 80 % и более от лимита трафика либо с момента создания прошло более 3 суток без единого байта трафика. В таблице появляется колонка «Причина», а в JSON — массив `clients[].attention_reasons` (сводка `summary` считается по отфильтрованному списку). Перенесённый при миграции трафик и обнулённые в новом периоде счётчики всё равно учитываются как признак того, что аккаунтом уже пользовались. Отдельная причина **Давно нет трафика** (`stopped`) отмечает тех, кто уже пользовался сервисом, но больше трёх суток не передавал трафик. **Ещё не пользовался** (`unused`) остаётся отдельной причиной. Параметр API `stopped_days` задаёт независимый порог от 1 до 365 суток, по умолчанию 3; границы и значение по умолчанию для `unused_days` не меняются. Сброс периода не стирает эти данные, а дневную историю включать не нужно. Если у перенесённого трафика неизвестно время последней активности, причина `stopped` не назначается наугад.

Запрос `GET /api/attention` доступен с правом `read` или в сеансе владельца веб-панели. Он возвращает `observed_at`, пороги `thresholds`, список пользователей `people[]` и список узлов `nodes[]` с причинами предупреждений. Для узлов отмечаются потеря связи с агентом, ошибки применения конфигурации и нездоровое состояние служб (`degraded` / `unhealthy`). Необязательные параметры запроса: `expiry_days` (1–30, по умолчанию 7), `quota_percent` (1–100, по умолчанию 80) и `unused_days` (1–365, по умолчанию 3). Предупреждения вычисляются на лету без хранения дополнительных флагов, сессий, IP-адресов или данных об устройствах.

**`client set`** — изменяет лимит трафика, период сброса, срок доступа, лимит устройств, заметку, метку или язык подписки (меняются только явно указанные параметры; требуется хотя бы один флаг). Если доступ пользователя был приостановлен из-за исчерпания лимита (`limited`) или истечения срока (`expired`), после увеличения лимита или продления даты доступ восстанавливается сразу же. Изменения вступают в силу немедленно и не сбрасываются при `apply`. При некорректном значении параметра команда завершается с кодом `2` ещё до обращения к серверу. С флагом `--json` обновлённая карточка пользователя возвращается в `data.client`, включая поля `traffic_limit_bytes`, `traffic_reset` и `expires_at` (пустая строка означает бессрочный доступ).

**`client reset-traffic`** — обнуляет счётчик использованного трафика за текущий период; если клиент был заблокирован по лимиту (`limited`), доступ сразу восстанавливается.

**`client extend`** — прибавляет от 1 до 3650 целых дней к текущему сроку доступа или к текущему моменту (смотря что наступит позже; если срок не был задан, отсчёт идёт от текущего момента). Флаг `--days N` обязателен. Расчёт новой даты и обновление статуса выполняются в одной транзакции, поэтому одновременные запросы не теряют дни. Если доступ был приостановлен из-за истёкшего срока, он сразу возобновляется (при этом ручное отключение через `disable` и превышение лимита трафика остаются в силе). В JSON итоговый статус и срок доступа возвращаются в `data.client`.

**`client enable` / `client disable`** — немедленно включает или приостанавливает доступ клиента. Ручное отключение сохраняется до вызова `client enable`: команды `apply`, `deploy`, `client add`, `node add` и `relay add` статус клиента не затрагивают.

**`client reissue`** — перевыпускает ссылки клиента при утечке. Сервис управления создаёт новый идентификатор подписки и новые ключи доступа, после чего прежний адрес подписки, старая страница подключения и старые ключи сразу перестают работать. Команда выводит новую ссылку на подписку (она же открывает новую страницу подключения). Статус, лимиты и срок доступа сохраняются, а список зарегистрированных устройств очищается. Без флага `--yes` запрашивается подтверждение; команда работает только для клиентов, объявленных в локальной конфигурации.

**`client remove`** — удаляет клиента из топологии и из базы сервиса управления, закрывая его подписку и страницу подключения. Без флага `--yes` запрашивает подтверждение. Единственного оставшегося клиента удалить нельзя. Пользователей, созданных в веб-панели, удаляют через веб-панель.

**`client usage`** — выводит посуточный объём отправленного, полученного и общего трафика по дням UTC для любого пользователя (включая созданных в веб-панели). Для работы команды в разделе [Конфиденциальность](/ru/privacy/) должна быть включена посуточная история трафика — иначе команда завершится с кодом `2` и подскажет команду для включения учёта. Когда история включена, `client show` также добавляет сводку за последние 7 дней UTC (в JSON — поле `data.usage`, либо `null`, если история выключена). Нулевые дни означают отсутствие трафика; задним числом история не заполняется.

**`client devices`** — показывает количество устройств в режиме `private` или подробный список устройств в режиме `full` (в режиме `off` данные об устройствах не хранятся). С флагом `--json` возвращает `username`, `level`, `count`, действующий `limit`, список `devices` и число удалённых записей `removed`. Флаги `--remove ID` и `--clear` сбрасывают зарегистрированные устройства без перевыпуска ключей доступа (повторное удаление уже сброшенной записи возвращает 0). Просмотр и сброс устройств работают в том числе для пользователей, добавленных через веб-панель. Задать индивидуальный лимит можно через `client set --devices N`, а вернуть общий лимит — через `--devices default` (см. [Лимит устройств](/ru/client-management/#лимит-устройств)). Команда `client reissue` очищает список устройств, сохраняя установленный лимит.

Команды, изменяющие оперативные параметры в сервисе управления (`client enable`, `disable`, `set`, `reset-traffic` и сброс устройств в `client devices`), работают и для пользователей, добавленных через веб-панель. Точное совпадение логина имеет приоритет; поиск без учёта регистра или по отображаемому имени срабатывает, если подходящий пользователь только один (при совпадении нескольких укажите точный логин из `client list`). Удаление аккаунта, перевыпуск ключей и обновление файлов страницы подключения через CLI относятся только к клиентам из локальной топологии.

Активные сессии VLESS могут продолжаться некоторое время после отзыва ключей. Флаг **`--cut-off`** в командах `client remove` и `client reissue` дожидается применения ревизии без старых ключей на каждом затронутом узле, после чего принудительно сбрасывает затронутые входы Xray. Все открытые соединения на этих входах разрываются (включая сессии других пользователей — их приложения переподключатся через секунду). Если сбросить вход точечно через API не удалось, узел перезапускает Xray целиком. Флаг включается явно и рекомендуется при утечке ссылки. В JSON результат по каждому узлу возвращается в `data.cut_off`: `done`, `core_restart`, `failed` или `timed_out`. Время ожидания ответа узлов — до 5 минут; при ошибке сброса возвращается код `4`, при тайм-ауте — `3`. Такая же опция доступна и в веб-панели.

Личная заметка и метка: команда `client set NAME --note TEXT --tag TAG` обновляет только переданные поля. Заметка вмещает до 500 символов обычного текста (переносы строк допустимы), а `--note ""` очищает её. Метка состоит из 1–16 латинских букв, цифр или символов подчёркивания и сохраняется заглавными буквами; `--tag none` удаляет метку. Оба поля отображаются в `client show`, а `client list --tag TAG` фильтрует список по метке (`--tag none` выбирает пользователей без метки). Чтение и запись требуют прав `people` или `admin`. Эти же поля редактируются в веб-панели, сохраняются при `apply` и включаются в зашифрованные резервные снимки — см. [Личные заметки и метки](/ru/client-management/#личные-заметки-и-метки).

Команда `client preview NAME --user-agent UA [--accept TYPE] [--suffix SUFFIX]` показывает, какой формат подписки получит приложение и какие подключения будут опущены, не раскрывая ключей доступа. Длина `User-Agent` ограничена 512 символами Unicode, `Accept` — 256 символами (оба без переносов строк; значения нигде не сохраняются). Флаг `--suffix` принудительно выбирает один из суффиксов формата URL. В JSON возвращается схема `subscription-preview`; в API за это отвечает метод `POST /api/subscription/preview` (требует права `read`).

### meridian privacy

Управление тем, какие данные хранит сервис управления. Ограничение числа устройств и посуточная история трафика по умолчанию выключены; применение конфигурации (`apply`) эти настройки никогда не меняет. Подробное описание каждого режима и того, какие данные окажутся на сервере в случае его изъятия, приведено в разделе [Конфиденциальность](/ru/privacy/).

```bash
meridian privacy [--json]
meridian privacy show [--json]
meridian privacy set [--devices off|private|full] [--device-limit N] [--history off|daily] [--history-days N] [--yes] [--json]
```

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `--devices LEVEL` | без изменений | Учёт устройств: `off` (выключен), `private` (защищённые ключом отпечатки) или `full` (подробные сведения об устройствах) |
| `--device-limit N` | без изменений (изначально 3) | Общий лимит устройств на человека по умолчанию: 1–100 |
| `--history LEVEL` | без изменений | История трафика: `off` (только общий счётчик за всё время и время последней активности) или `daily` (суточные итоги по людям и серверам в UTC) |
| `--history-days N` | без изменений (изначально 90) | Срок хранения посуточной истории: 7–730 дней UTC, включая сегодняшний день |
| `--yes`, `-y` | | Пропустить подтверждение (обязателен при изменении настроек с `--json`) |
| `--json` | | Вывести результат в JSON-конверте `meridian.output/v1` |

Вызов `meridian privacy` без подкоманды равнозначен `privacy show`: выводятся текущие настройки, памятка о хранимых данных и последние 50 записей журнала аудита. Команда `set` меняет только переданные параметры, перед сохранением объясняет, какие данные начнут собираться или будут удалены, и запрашивает подтверждение (повторная передача уже действующих значений ничего не меняет). В режиме `--json` поле `data` содержит текущие настройки и журнал изменений, а при вызове `set` — также количество удалённых записей (`deleted`) и пересчитанных отпечатков (`rekeyed_devices`). В журнале аудита фиксируются автор (`owner`, `root` или имя токена), время в UTC и старые/новые значения. После восстановления сервера управления из снимка приватные записи об устройствах очищаются, так как секретный ключ для расчёта отпечатков в резервные снимки не включается.

### meridian server

Управление списком сохранённых SSH-серверов (`~/.config/meridian/servers.json`).

```
meridian server add [USER@]IP[:PORT]|local [--name NAME] [--user USER] [--ssh-port PORT]
meridian server list [--json]
meridian server set NAME [--allowance SIZE] [--reset-day DAY] [--provider TEXT] [--pay-on DATE] [--pay-every month|year|none] [--dry-run] [--yes] [--json]
meridian server remove NAME_OR_IP [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (нет) | Короткое понятное имя сервера |
| `--user/-u USER` | root | Пользователь SSH |
| `--ssh-port PORT` | 22 | Порт SSH |
| `--yes`, `-y` | | Пропустить подтверждение при удалении (`server remove`) |

Команда `server add local` регистрирует текущую машину для локального выполнения команд без SSH. Имена и адреса серверов должны быть уникальными: при совпадении `server add` вернёт ошибку, а не перезапишет существующий сервер. Команда `server remove` удаляет только запись из локального списка и не позволит удалить сервер, пока за ним числится какая-либо роль в топологии.

**Месячные лимиты трафика и даты оплаты** хранятся в проверяемой топологии для выходных и промежуточных серверов, шлюзов маршрутизации и сервера управления. В `server set NAME` можно указать сохранённое имя сервера, ID профиля или IP-адрес. Неуказанные параметры сохраняют прежние значения, а вызов без флагов изменений выводит текущие сведения. Команда `server list --json` возвращает список серверов вместе с полем `metadata` и вычисленной датой следующего платежа.

| Параметр сервера | По умолчанию | Описание |
|---|---|---|
| `--allowance SIZE` | не задан | Месячный лимит трафика хостинга (например, `20TB` или `50GiB`); `none` убирает лимит. Обозначения GB/TB соответствуют двоичным GiB/TiB, как и в клиентских лимитах |
| `--reset-day DAY` | 1 | День ежемесячного сброса в 00:00 UTC (1–31); в коротких месяцах сброс происходит в последний день месяца |
| `--provider TEXT` | пусто | Название хостинг-провайдера (одна строка обычного текста до 80 символов; `none` очищает поле) |
| `--pay-on DATE` | не задана | Дата оплаты в формате `YYYY-MM-DD` (допускается и прошедшая дата для разового платежа); `none` очищает дату и периодичность |
| `--pay-every PERIOD` | none | Периодичность оплаты: `month` (раз в месяц), `year` (раз в год) или `none` (разовый платёж); для регулярных платежей требуется дата в `--pay-on` |
| `--dry-run` | | Показать план изменения сведений о сервере без применения |
| `--yes`, `-y` | | Применить проверенные изменения без подтверждения (обязателен с `--json` или без интерактивного терминала) |
| `--json` | | Вывести результат `server list` или `server set` в конверте `meridian.output/v1` |

```bash
meridian server set edge --allowance 20TB --reset-day 15 --provider "Пример провайдера" --pay-on 2026-11-15 --pay-every month --dry-run --json
meridian server set edge --allowance 20TB --reset-day 15 --yes
meridian server set edge --allowance none --pay-on none --yes
```

При включении месячного лимита или смене дня сброса отсчёт трафика начинается с момента получения этих настроек сервисом управления (расход за более раннюю часть текущего расчётного периода неизвестен). Изменение только самого объёма лимита, названия провайдера или даты оплаты накопленный за период счётчик не сбрасывает. Даты ежемесячных и ежегодных платежей при чтении автоматически сдвигаются вперёд после наступления даты по UTC с сохранением исходного числа месяца (с поправкой на короткие месяцы и високосные годы); разовые платежи после наступления даты помечаются как просроченные. Команда `fleet export` выгружает эти сведения в секцию `server_metadata` по сохранённым именам серверов, а `fleet import` проверяет и применяет их наравне с остальной топологией. При снятии с сервера последней роли его метаданные удаляются; при переносе выходного сервера они остаются привязанными к физическому серверу. Лимиты трафика хостинга и напоминания об оплате носят справочный характер и никогда не блокируют пользовательский трафик.

### meridian node

Управление выходными серверами. Первый сервер разворачивается командой `meridian deploy` (или через `meridian setup`), а дополнительные выходные серверы добавляются командой `meridian node add`.

```
meridian node add [USER@]IP[:PORT] [flags]
meridian node list [--json]
meridian node restart NAME [--core|--all] [--yes] [--json]
meridian node remove NAME_OR_IP [--yes] [--force] [--forget-unreachable]
meridian node replace EXIT [USER@]NEW_IP[:PORT] [--name NAME] [--yes] [--forget-unreachable]
meridian node sni EXIT NEW_SNI [--self-steal] [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | (auto) | Понятное имя для узла |
| `--user USER` | сохранённый, иначе root | Пользователь SSH на узле |
| `--ssh-port PORT` | сохранённый, иначе 22 | Порт SSH на узле (`node add`, `node replace`) |
| `--sni HOST` | (auto) | Сайт маскировки Reality для этого узла (если не указан, подбирается сайт из подсети самого узла, иначе `www.google.com`) |
| `--domain DOMAIN` | (нет) | Домен выходного сервера: переносит XHTTP на домен и добавляет WSS через CDN Cloudflare; Hysteria2 использует сертификат этого домена |
| `--self-steal` | выкл. | В `node add`: маскировка под ваш собственный домен (`--sni` или `--domain`), направленный на этот узел. В `node sni`: указывает, что `NEW_SNI` — ваш собственный домен |
| `--country CC` | по реестру IP | Двухбуквенный код страны для названий подключений (укажите вручную, если реестр определяет страну неверно для anycast- или арендованных подсетей) |
| `--harden / --no-harden` | вкл. | Защита ОС, SSH и файрвола. Для серверов в составе топологии защита обязательна; флаг `--no-harden` отклоняется |
| `--yes` | | Пропустить запросы подтверждения |
| `--forget-unreachable` | | В `node remove` и `node replace`: не прерывать очистку, если удаляемый сервер не отвечает по SSH (заблокирован или уже удалён), и убрать его из локальной конфигурации |
| `--force` | | В `node remove`: заодно удалить цепочки промежуточных серверов, ведущие на этот выходной сервер |
| `--json` | | Вывести результат `node list` или `node restart` в конверте `meridian.output/v1` |

**`node add`** — подключается к серверу по SSH, добавляет его в топологию как выходной сервер и применяет проверенный план (защита системы, установка агента узла и Xray, привязка к сервису управления). Приложения пользователей получат новый выходной сервер при следующем обновлении подписки.

**`node list`** — выводит список узлов со статусом связи агента, версией и расходом трафика. Если сервис управления недоступен, узлы отображаются со статусом `unknown`, а команда завершается с кодом `3`.

**`node restart`** — отправляет подписанную команду агенту узла и ждёт подтверждения запуска служб. По умолчанию и с флагом `--core` перезапускается только ядро Xray (`netcore`); с флагом `--all` поочерёдно перезапускаются все управляемые службы узла. На время перезапуска активные соединения через этот узел кратковременно прерываются. Флаги `--core` и `--all` взаимоисключающие; при использовании `--json` обязателен `--yes`. В JSON список команд и результат по каждому узлу (`done`, `failed` или `timed_out`) возвращаются в `data.nodes[]`. При ошибке перезапуска команда возвращает код `4`, а при превышении пятиминутного ожидания — код `3`. В разделе «Серверы» веб-панели есть аналогичная кнопка **«Перезапустить Xray»**.

**`node remove`** — удаляет выходной сервер или шлюз маршрутизации из топологии. Команда выводит полный перечень удаляемых ресурсов (запись и документ узла, службы агента и Xray, правила файрвола, точки подключения клиентов), запрашивает подтверждение и выполняет очистку; сам сервер остаётся в локальном списке `servers.json`. Команда не позволит удалить сервер управления (для этого предназначена `meridian teardown`), выходной сервер, к которому привязаны промежуточные серверы (сначала удалите их или укажите `--force`), выход, через который подключён шлюз маршрутизации, а также сервер, удаление которого нарушит целостность топологии (например, оставит пустым пул выходов или удалит маршрут по умолчанию). Правила маршрутизации удаляемого шлюза удаляются вместе с ним.

**`node replace`** — переносит выходной сервер на другой VPS. В качестве `EXIT` указывается ID выхода, сохранённое имя сервера или его IP-адрес; адрес нового сервера задаётся так же, как в `node add` (можно указать сохранённое имя или `local`). Выходной сервер сохраняет свой ID, ключи Reality, пути протоколов, SNI, настройки WARP и геоблокировки, а также все промежуточные серверы, которые перенаправляют на него трафик: маршруты через промежуточные серверы продолжат работать сразу, а прямые подключения обновят IP-адрес при следующем обновлении подписки. Перед выполнением команда показывает план развёртывания на новом сервере и список очищаемых ресурсов на старом (агент и Xray, конфигурация nginx, правила файрвола и сертификаты). Заменить таким способом сервер управления нельзя (это изменило бы ссылки подписок всех пользователей; при потере сервера управления используйте `meridian restore`), как и выбрать целевой сервер, который уже занят другой ролью.

**`node sni`** — меняет сайт маскировки (SNI) для Reality на выбранном выходном сервере (`EXIT` — ID выхода, имя сервера или IP). Команда не допускает домены `apple.com`, `icloud.com` и `www.microsoft.com`, проверяет по SSH, что выходной сервер успешно подключается к новому сайту по TLS 1.3 и HTTP/2, показывает план изменений (какие промежуточные серверы переключатся вслед за выходом, какие сохранят собственный SNI, какие шлюзы обновятся и какие старые ресурсы будут удалены), запрашивает подтверждение и применяет настройки. Прежний SNI заменяется новым: приложения перейдут на него при следующем автоматическом (раз в 6 часов) или ручном обновлении подписки, а до этого момента подключения Reality со старым SNI работать не будут (XHTTP, WSS и Hysteria2 при этом не затрагиваются). Используйте эту команду, если `meridian test --probe` показал блокировку текущего SNI. С флагом `--self-steal` аргумент `NEW_SNI` считается вашим собственным доменом: вместо внешней проверки команда убеждается, что DNS-запись домена ведёт на этот выходной сервер, выпускает для него сертификат Let's Encrypt и настраивает сервер отвечать на проверочные запросы самостоятельно.


### meridian relay

Управление промежуточными серверами — TCP-форвардерами Realm, которые создают точку входа внутри страны и перенаправляют трафик на выходной сервер за рубежом. Через промежуточные серверы передаётся трафик Reality.

```
meridian relay add [USER@]RELAY_IP[:PORT] --exit EXIT [flags]
meridian relay list [--exit EXIT] [--json]
meridian relay remove RELAY [--exit EXIT] [--yes] [--forget-unreachable]
meridian relay sni RELAY NEW_SNI [--exit EXIT] [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--exit/-e EXIT` | (обязателен для add) | IP-адрес или имя выходного сервера |
| `--name NAME` | (auto) | Понятное имя промежуточного сервера (например, `ru-moscow`) |
| `--port/-p PORT` | 443 | Порт приёма входящих соединений на промежуточном сервере |
| `--sni HOST` | SNI выходного сервера | Отдельный сайт маскировки Reality для этого промежуточного сервера; если не указан, используется SNI выходного сервера |
| `--user/-u USER` | сохранённый, иначе root | Пользователь SSH на промежуточном сервере |
| `--ssh-port PORT` | сохранённый, иначе 22 | Порт SSH на промежуточном сервере (`relay add`) |
| `--yes/-y` | | Пропустить запросы подтверждения |
| `--forget-unreachable` | | В `relay remove`: не останавливаться при ошибке очистки удаляемого сервера, если он не отвечает по SSH |
| `--json` | | Вывести результат `relay list` (`data.relays[]`) в конверте `meridian.output/v1` |

**`relay add`** — добавляет одиночный промежуточный сервер в топологию и сразу применяет изменения. Приложения пользователей получат новый маршрут при следующем обновлении подписки. Для построения цепочек из нескольких промежуточных серверов используйте мастер `meridian setup`.

**`relay remove`** — удаляет маршруты через указанный промежуточный сервер (`RELAY` — IP-адрес, сохранённое имя сервера или ID цепочки; область удаления можно ограничить конкретным выходом через `--exit`). Команда показывает список удаляемых ресурсов (службы Realm, правила файрвола, порт приёма на выходном сервере и точки подключения в подписках), запрашивает подтверждение и применяет изменения. Сами серверы остаются в локальном списке `servers.json`.

**`relay sni`** — назначает отдельный сайт маскировки (SNI) для маршрутов через промежуточный сервер (или для одной цепочки по её ID; можно уточнить выходом через `--exit`). Команда проверяет те же ограничения доменов, что и `node sni`, убеждается, что выходной сервер может подключиться к выбранному сайту (так как дополнительный порт приёма Reality с этим SNI поднимается на самом выходном сервере), показывает план изменений и применяет его после подтверждения. Если передать тот же SNI, что используется на выходном сервере, промежуточный сервер снова начнёт следовать за SNI выхода. Приложения подхватят новый SNI при следующем обновлении подписки.

Проверить работоспособность всех звеньев промежуточного сервера можно командой `meridian check RELAY`.

### meridian route

Направляет трафик к выбранным сайтам или странам с выходного сервера через Cloudflare WARP, напрямую с IP-адреса сервера или блокирует его — с приоритетом над основным режимом работы этого выходного сервера.

```
meridian route add EXIT VALUE... --via warp|direct|block [--name ID] [--json]
meridian route add EXIT --preset ai [--via warp|direct|block] [--name ID] [--json]
meridian route list [EXIT] [--json]
meridian route remove EXIT ROUTE [--yes] [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--via ACTION` | `warp` с `--preset`, иначе обязателен для add | Действие для совпавшего трафика: `warp` (через WARP), `direct` (напрямую) или `block` (блокировать) |
| `--preset NAME` | | Использовать готовый набор доменов вместо списка `VALUE`: `ai` (популярные ИИ-сервисы) |
| `--name ID` | имя пресета или действия с номером | Идентификатор правила, отображаемый в `route list` и используемый в `route remove` |
| `--yes/-y` | | Пропустить подтверждение при удалении (обязателен с `--json`) |
| `--json` | | Вывести результат в конверте `meridian.output/v1` (`data.override` для add/remove, `data.exits[]` для list) |

В качестве `EXIT` указывается ID выходного сервера, сохранённое имя сервера или его IP-адрес. Каждое значение `VALUE` — это домен (включая все его поддомены), категория `geosite:NAME` или список `geoip:NAME` (в рамках одного правила все значения должны быть одного типа).

**`route add`** — добавляет правило маршрутизации для выходного сервера в топологию и применяет изменения. Правила проверяются в порядке их добавления. Если добавить правило `--via warp` на выходной сервер, где глобальный WARP выключен, Meridian установит и поднимет WARP только для трафика этого правила, а весь остальной трафик по-прежнему будет выходить напрямую с IP сервера.

**`route list`** — показывает режим выхода по умолчанию и список правил в порядке их проверки для каждого выходного сервера.

**`route remove`** — удаляет одно правило и применяет изменения, после чего трафик к этим ресурсам снова подчиняется общему режиму выходного сервера. Сама служба WARP остаётся установленной на сервере, но не используется, пока не будет добавлено новое правило или включён флаг `--warp`.

### meridian fleet

Сводное состояние и состав серверов по данным сервиса управления, история ревизий, обновление серверных компонентов и работа с конфигурацией в виде текстового YAML-файла.

```
meridian fleet status [--json]
meridian fleet inventory [--json]
meridian fleet history [--json]
meridian fleet events [--since ID] [--limit N] [--json]
meridian fleet usage [--days N] [--json]
meridian fleet routing [ru-split|full] [--dry-run] [--yes] [--json]
meridian fleet contact [--text TEXT] [--link LINK|none] [--dry-run] [--yes] [--json]
meridian fleet notice show [--for NAME] [--json]
meridian fleet notice set TEXT [--until WHEN] [--for NAME] [--yes] [--json]
meridian fleet notice clear [--yes] [--json]
meridian fleet language [auto|en|ru|fa|zh] [--yes] [--json]
meridian fleet upgrade [--tested] [--yes]
meridian fleet export [--json]
meridian fleet import FILE [--dry-run] [--yes] [--forget-unreachable] [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--since ID` | 0 | В `fleet events`: вернуть события после указанного курсора |
| `--limit N` | 100 | В `fleet events`: вернуть от 1 до 2000 событий |
| `--days N` | 30 | Число дней UTC для `client usage` и `fleet usage` (1–730, но не больше настроенного срока хранения истории) |
| `--json` | | Вывести результат в конверте `meridian.output/v1` (`status`, `inventory`, `history`, `routing`, `export`, `import`, `usage`) |
| `--tested` | | В `fleet upgrade`: не обращаться к GitHub; оставить Realm на протестированной версии из пакета или на той, до которой он уже был обновлён |
| `--yes`, `-y` | | В `fleet upgrade`, `fleet routing`, `fleet import`: применить изменения без подтверждения |
| `--dry-run` | | В `fleet routing`, `fleet import`: показать изменения и план проверки без применения |
| `--forget-unreachable` | | В `fleet import`: не прерывать очистку удаляемого сервера, если его порт SSH не отвечает |

**`fleet status`** — показывает состояние сервиса управления, время последнего отчёта каждого агента и статус применения текущей ревизии, доступность портов промежуточных серверов и сводку по клиентам. Отсутствие в базе клиентов, объявленных в топологии, понижает статус до `degraded`; отключённые клиенты и клиенты с исчерпанным лимитом или истёкшим сроком учитываются в таблице, но ошибкой не считаются. Открытый TCP-порт на промежуточном сервере подтверждает только работу форвардера, поэтому без сквозной проверки трафика маршруты через промежуточные серверы имеют статус `unknown` (для полной проверки используйте `meridian test`). Код возврата `0` означает полную исправность, `4` — обнаружены проблемы (`degraded`), `3` — статус не удалось определить (`unknown`).

Колонка `active` показывает число пользователей, у которых в последнем отчёте узла был зафиксирован прирост трафика (время отчёта выводится строкой ниже). Запоздавший старый отчёт не перезаписывает более свежие данные об активности. Суммарные счётчики байтов узла сохраняются при перезапусках и смене эпох; поле `traffic_counting_since` отмечает момент начала непрерывного учёта (для старых серверов до миграции переносятся только сохранённые исторические итоги).

Запрос `GET /api/nodes/NODE` возвращает накопленный объём `traffic_bytes`, окно последнего отчёта об активности и время начала учёта (схема доступна по команде `meridian api schema service-node-status`).

**`fleet inventory`** — выводит список настроенных серверов, их ролей, узлов и промежуточных серверов, дополняя его актуальным статусом из сервиса управления. Секретные пути и API-токены никогда не выводятся. Если сервис управления недоступен, команда всё равно покажет локальный состав серверов с предупреждением и завершится с кодом `3`. Чтобы программно проверить, требуется ли запуск `apply`, используйте `meridian plan --json`.

**`fleet history`** — выводит список всех ревизий, зафиксированных в сервисе управления (сначала новые): номер ревизии, время, автора (название токена компьютера, `root` для локального токена CLI или `owner` для веб-панели), статус (`proposed`, `approved`, `applied` или `failed`) и префикс хеша плана. С флагом `--json` возвращает массив `data.revisions[]`.

**`fleet events`** — выводит локальный журнал событий жизненного цикла (создание и изменение пользователей, токенов, настроек конфиденциальности, а также потеря и восстановление связи с узлами) в хронологическом порядке после курсора `--since ID` (по умолчанию `0`). Флаг `--limit N` ограничивает выборку (1–2000, по умолчанию 100). В JSON возвращаются `data.events[]`, `next_cursor` и `has_more` — передайте `next_cursor` в следующий вызов `--since`, чтобы дочитать ленту. Каждая запись содержит время в UTC, тип события, автора (`root`, `owner`, `system` или имя токена), затрагиваемый объект и краткие метаданные (список изменённых полей, права токена или номер записи аудита конфиденциальности). Ключи доступа, сырые тексты ошибок, IP-адреса клиентов и данные об устройствах в журнал не пишутся. Сервис хранит до 2000 последних событий за последние 180 дней и включает их в резервные снимки. В API за это отвечает метод `GET /api/events?after=ID&limit=N` (доступен с правом `read` и в сеансе владельца).

**`fleet upgrade`** — обновляет серверные компоненты одним проверенным применением плана. Сервис управления и агенты всех узлов обновляются до версии, встроенной в ваш установленный пакет Meridian (агенты обновляются на месте без сброса ключей и привязки; чтобы получить свежие сборки, сначала обновите сам CLI командой `meridian update`). Промежуточные серверы обновляются до последнего релиза Realm в рамках протестированной мажорной ветки прямо с GitHub: номер версии и официальная контрольная сумма SHA-256 сохраняются в `cluster.yml` и проверяются на каждом промежуточном сервере перед установкой. Команда показывает текущие и целевые версии по каждому серверу (`current` или `upgrade`), запрашивает подтверждение, применяет план и в конце запускает `meridian check` на всех серверах. Если определить версию на каком-либо сервере не удалось, команда завершится с кодом `3`, ничего не меняя.

**`fleet routing`** — показывает текущий режим маршрутизации на устройствах пользователей и поясняет оба доступных варианта. Режим `ru-split` (по умолчанию) направляет трафик к российским доменам, российским IP-адресам и локальным сетям напрямую, а остальной интернет-трафик — через VPN. Режим `full` направляет через VPN весь интернет-трафик, включая российские ресурсы, оставляя прямыми только обращения к локальной сети. В обоих режимах блокируется QUIC (UDP/443) и (в профилях Xray JSON) по возможности выводится напрямую трафик к пирам BitTorrent, чтобы снизить риск жалоб правообладателей на выходные серверы. Если передать название режима, команда обновит топологию, покажет план изменений, запросит подтверждение и применит его. Без интерактивного терминала или с флагом `--json` требуется `--yes`; флаг `--dry-run` показывает план без применения. В JSON возвращаются `data.client_routing`, `choices[]` и данные плана/применения. Приложения получают обновлённые правила при следующем автоматическом или ручном обновлении подписки. В веб-панели эта настройка отображается в режиме чтения. Серверная геоблокировка на выходных серверах настраивается отдельно, а простые ссылки формата Base64 правил маршрутизации не содержат — подробнее см. [Маршрутизация на устройствах](/ru/split-routing/).

**`fleet export`** — выгружает проверенную топологию ваших серверов в виде редактируемого YAML-файла: выходные серверы и их способы подключения, промежуточные серверы, шлюзы маршрутизации, пулы выходов, правила маршрутизации, клиентов и общие настройки. Серверы записываются по их сохранённым именам (или по адресу, если имя не задано), а не по внутренним идентификаторам; файл начинается со строки `schema: meridian.fleet/v1`. Секретные ключи Reality, API-токены, ссылки подписок и пути транспорта XHTTP/WSS остаются внутри Meridian и в файл не попадают. С флагом `--json` тот же документ возвращается в поле `data.document`.

**`fleet import`** — читает отредактированный YAML-файл (или поток стандартного ввода при указании `-`) и построчно показывает изменения: `+` — добавление, `-` — удаление, `~` — изменение поля (например, `~ exit-2 sni www.example.com -> www.example.org`). Затем команда выводит список удаляемых ресурсов и хеш плана, запрашивает подтверждение и применяет изменения так же, как `meridian apply`. Если файл полностью совпадает с текущей топологией, выводится сообщение об отсутствии изменений. Удаление пользователя из списка `access.users` работает аналогично `client remove` (его подписка и страница подключения перестают открываться), а добавление нового имени создаёт клиента как при `client add` (посмотреть его ссылки можно командой `client show NAME`). Новые домены маскировки (SNI) проходят те же проверки доступности, что и в `node sni`. Импорт отклоняет файлы с другой версией `schema`, неизвестные серверы (сначала добавьте их через `meridian server add`), попытки вручную задать пути транспорта, изменение сервера управления, его домена или бэкенда, удаление или переименование выходного сервера на сервере управления, а также перенос выходного сервера на другой хост (для этого используйте `node replace`). Ключи и учётные данные существующих клиентов сохраняются. Без интерактивного терминала передайте `--yes`; для предварительной проверки без применения используйте `--dry-run`.

**`fleet usage`** — выводит посуточный расход трафика по каждому серверу в днях UTC, включая сохранённую историю уже удалённых узлов. Флаг `--days N` задаёт глубину выборки (1–730 дней в пределах срока хранения). Требует включённой посуточной истории трафика; в JSON возвращает общие итоги и массив `nodes[].daily` в поле `data`.

**`fleet contact`** — показывает или обновляет публичные контактные данные владельца. Флаг `--text TEXT` задаёт строку подсказки (до 120 символов обычного текста), а `--link LINK` — ссылку для связи со схемой `https:`, `tg:` или `mailto:`. Неуказанные поля не меняются; `--text ""` и `--link none` очищают соответствующие значения. Флаг `--dry-run` показывает план изменений без сохранения; в режиме `--json` или без терминала для записи требуется `--yes`. В JSON возвращаются `data.owner_contact`, план проверки и результат применения. В веб-панели контакт отображается в режиме чтения, а при экспорте и импорте переносится в секции `delivery.owner_contact`. На страницах подключения и поддержки отображаются текст подсказки и кнопка связи, а приложения используют ссылку для кнопки поддержки — см. [Контакт владельца](/ru/client-management/#контакт-владельца-на-страницах-подключения).
**Лимиты трафика и оплата серверов** — команда `fleet status` и раздел «Серверы» в веб-панели показывают приблизительный расход трафика за текущий расчётный период, провайдера, день сброса, дату следующего платежа и предупреждения. В расходе учитывается принятый пользовательский трафик (отправка + загрузка) без накладных расходов протоколов, системных загрузок самого сервера и транзитного трафика промежуточных серверов. Отчёты агентов относятся к тому расчётному периоду по UTC, в котором они были получены сервисом управления. Для промежуточных серверов и выделенного сервера управления без агента отображается пометка **не измеряется**. В веб-панели также приводится подсказка команды `meridian server set NAME` для изменения этих сведений.

Запрос `GET /api/servers` доступен с правом `read` и возвращает схему `server-usage`: метаданные сервера, границы расчётного периода по UTC, учтённые байты, дату начала учёта, дату следующего платежа и признак охвата измерениями. В `GET /api/attention` добавляется массив `servers[]` с предупреждениями `allowance_near` (от 80 % лимита), `allowance_exceeded` (от 100 %), `payment_due` (до оплаты 7 дней и менее) и `payment_overdue` (просроченный разовый платёж). Пороги `allowance_percent` и `allowance_exceeded_percent` в параметрах запроса настраиваются в диапазоне 1–100 (первый не больше второго), а `payment_days` — от 1 до 30. Предупреждения об оплате и лимитах поднимают флаг `summary.needs_attention`, но не влияют на оценку технического здоровья служб и код возврата `fleet status`.

Общее сообщение для пользователей хранится в сервисе управления. Команда `fleet notice set` перед сохранением показывает готовый текст после подстановки переменных: `--until WHEN` задаёт срок окончания показа, `--for NAME` подставляет в предпросмотр данные конкретного клиента, а в режиме `--json` требуется `--yes`. Команда `fleet notice show` выводит текущее сообщение, а `fleet notice clear` удаляет его после подтверждения — см. [Управление клиентами](/ru/client-management/).

Язык по умолчанию `auto` подстраивает страницы подключения и поддержки под язык браузера пользователя, оставляя статусные строки в приложениях на английском. Явный выбор `en`, `ru`, `fa` или `zh` задаёт язык по умолчанию и для страниц, и для строк в приложениях. Команда `fleet language` показывает текущую настройку, а `fleet language CODE --yes --json` сохраняет новую. Персональный язык задаётся через `client set NAME --language CODE` (значение `--language default` возвращает общую настройку). Выбор языка на самой странице подключения имеет наивысший приоритет. Коды статусов в API всегда остаются на английском, а сами настройки языка сохраняются при `apply` и в резервных снимках.

### meridian context

Позволяет управлять с одного компьютера несколькими независимыми наборами серверов (например, отдельным VPN для семьи и отдельным для работы) и переключаться между ними.

```
meridian context list [--json]
meridian context use NAME
meridian context rename OLD NEW
meridian context remove NAME [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | В `context list`: вывести результат в конверте `meridian.output/v1` |
| `--yes`, `-y` | | В `context remove`: удалить контекст, в котором ещё числятся серверы, без подтверждения |

**`context list`** — выводит все локальные контексты с адресом сервера управления и количеством выходных серверов, промежуточных серверов и шлюзов маршрутизации (данные читаются только с этого компьютера; звёздочкой `*` отмечен активный контекст):

```
  * default   198.51.100.10    2 exits, 1 relay
    family    198.51.100.40    1 exit
```

**`context use`** — делает указанный контекст активным для всех последующих команд. Команда `meridian deploy IP --context NAME` создаёт новый контекст при развёртывании, а глобальный флаг `--context NAME` позволяет выполнить одну команду в другом контексте без переключения по умолчанию.

**`context rename`** — переименовывает локальный контекст, не затрагивая работающие серверы.

**`context remove`** — удаляет локальные файлы контекста с этого компьютера без обращения к серверам: сами серверы продолжают работать, но управлять ими с этого компьютера вы больше не сможете. Активный контекст удалить нельзя; если в удаляемом контексте числятся серверы, команда запросит подтверждение (`--yes` пропускает запрос). Контекст `default` соответствует корневому каталогу настроек Meridian, поэтому его нельзя переименовать, а очистить можно только после того, как его серверы были перенесены в новый контекст при восстановлении (`restore`). В этом случае старый контекст помечается в `context list` как заменённый (`superseded`) и блокируется от изменений, а его удаление очищает только файлы серверов, сохраняя общий SSH-ключ и пользовательские предпочтения (`preferences.json`).

### meridian check

Проверяет состояние уже работающего сервера или пригодность нового VPS для установки Meridian. Набор проверок зависит от роли сервера в вашей топологии:

- **Новый сервер (ещё не в топологии)** — предварительная проверка перед установкой: доступность сайта маскировки (SNI) и работа DNS, свободен ли порт 443 и доступен ли он извне, разрешается ли доменное имя в IP сервера, поддерживается ли версия ОС, достаточно ли места на диске и точны ли системные часы. На сервер ничего не устанавливается: если порт 443 свободен, для проверки внешнего файрвола на несколько секунд запускается временный слушатель. DNS-запросы выполняются через системный резолвер самого сервера.
- **Сервер управления, выходной сервер или шлюз маршрутизации** — проверка сервиса управления (отвечает ли он, принадлежит ли этой топологии и совместима ли версия), агента каждого узла (на связи ли он, применил ли актуальную ревизию и совпадает ли версия сборки), доступа по SSH (или локального доступа), всех публичных и внутренних портов, TLS-сертификатов и свободного места на диске. При запуске с другого компьютера для сервера управления дополнительно проверяется передача данных: скачивается тестовый фрагмент ~50 КБ и отслеживается, не замирает ли соединение после 16–24 КБ (характерный признак ограничения скорости со стороны ТСПУ в вашей сети).
- **Промежуточный сервер** — проверка каждого звена Realm на сервере: запущена ли системная служба, проходит ли соединение до следующего звена и принимает ли входной порт цепочки TCP-соединения с вашего компьютера.

Если сервер не указан, поочерёдно проверяются все серверы вашей топологии.

```
meridian check [SERVER] [--domain NAME] [--sni HOST] [--user USER]
               [--ssh-port PORT] [--ai] [--json]
```

Флаги `--domain` и `--sni` используются при предварительной проверке нового сервера: они проверяют, что указанный домен ведёт на IP-адрес сервера, а выбранный сайт маскировки доступен с него по TLS 1.3 и HTTP/2. Флаги `--user` и `--ssh-port` переопределяют пользователя и порт SSH. Флаг `--ai` копирует в буфер обмена готовый диагностический запрос для ИИ-ассистента. Флаг `--json` выводит единый конверт `meridian.output/v1` с отчётами по каждому серверу и области проверки.

Недоступность данных для проверки никогда не засчитывается как успех. Код возврата `0` означает, что все проверки пройдены, `4` — обнаружены неполадки, `3` — не удалось получить данные для проверки, `2` — ошибка во входных параметрах. Для каждой найденной проблемы выводится рекомендация по исправлению. Чтобы проверить реальное прохождение трафика через VPN-туннель, используйте `meridian test`.

### meridian scan

Ищет подходящие сайты для маскировки (SNI) в собственной подсети сервера с помощью закреплённой версии утилиты RealiTLScanner. Перед запуском Meridian проверяет контрольную сумму SHA-256 исполняемого файла, а по завершении удаляет временные файлы с сервера.

```
meridian scan [SERVER] [--user USER] [--ssh-port PORT]
```

RealiTLScanner сканирует диапазоны IPv4, поэтому на сервере только с IPv6 команда завершится с кодом `3`. Когда вы выбираете найденный домен из списка, `scan` выводит готовую команду для его применения, но сам ничего не меняет на работающих серверах. При отказе от выбора возвращается код `0`, при некорректном вводе — `2`, если подходящих сайтов не найдено — `4`, а при ошибке загрузки или запуска сканера — `3`.

### meridian test

Проверяет прохождение реального VPN-трафика с вашего текущего устройства. Доступ по SSH не требуется.

Полный тест выбирает активного клиента, запрашивает у сервиса управления его реальный профиль Xray JSON и пропускает тестовый трафик сначала через группу автовыбора, а затем через каждый способ подключения целевого сервера. При первом запуске может потребоваться до 120 секунд на загрузку и проверку контрольной суммы закреплённой сборки Xray. Для проверки выхода в интернет поочерёдно используются независимые сервисы определения внешнего IP-адреса, а их ответ сравнивается с прямым запросом без VPN — поэтому сбой стороннего сервиса даёт неопределённый результат (`inconclusive`), а не ложную ошибку. Переменная окружения `MERIDIAN_CONNECT_TEST_URL` позволяет задать собственный проверочный URL для изолированных сред.

Для каждого способа подключения выводится время получения первого байта (TTFB). Если трафик по маршруту не прошёл, Meridian пробует установить обычное TCP-соединение с портом сервера, чтобы точнее назвать причину: **порт отвечает, но трафик не проходит** (сервер принимает соединение, но VPN-туннель не работает — например, из-за неверных ключей или обрыва сессии цензором) либо **сервер недоступен** (порт не отвечает совсем). С флагом `--json` поле `data.transports` содержит статус каждого маршрута (`ok`, `no_traffic`, `unreachable`, `failed`, `egress_mismatch`, `inconclusive`, `invalid`) и задержку `first_byte_ms`.

Если сервис управления недоступен либо вернул HTTP `429` или `5xx`, получить подписку невозможно, и команда завершается с кодом `3`. Любой другой отказ при загрузке подписки (например, HTTP `400` или `422`) считается отрицательным результатом теста и возвращает код `4`.

```
meridian test [SERVER|DOMAIN] [--domain NAME] [--sni NAME]
              [--client NAME] [--basic] [--probe] [--timeout SECONDS] [--json]
```

Если цель не указана, `test` проверяет сервер, на котором запущен локально, либо ваш единственный сохранённый сервер. Если серверов несколько, команда по очереди проверяет каждую публичную точку входа (сначала выходные серверы, затем входы промежуточных серверов) и возвращает наихудший код результата; в режиме `--json` отчёты по всем серверам собираются в массив `data.results`.

Флаг `--client` выбирает конкретного активного клиента для проверки. Флаг `--basic` выполняет только быстрые сетевые и TLS-проверки без скачивания Xray (он не может проверить чисто UDP-протоколы вроде Hysteria2 и несовместим с `--client`, код возврата `2`). Флаг `--timeout` (по умолчанию `5` с, допустимо от `1` до `30`) задаёт тайм-аут отдельных сетевых операций (не влияет на первичную загрузку Xray).

Код возврата `0` означает успешное прохождение всех проверок, `4` — обнаружены проблемы со связью, `3` — не удалось получить данные для проверки. С флагом `--json` полный отчёт выводится в конверте `meridian.output/v1`.

#### Взгляд цензора: `meridian test --probe`

Режим `--probe` не передаёт пользовательский трафик, а исследует сервер извне так, как это делают автоматические сканеры цензоров (active probers), проверяя, не выдаёт ли сервер в себе VPN. Команда работает с любым IP-адресом или доменом, а если сервер входит в вашу сохранённую топологию, применяет дополнительные строгие проверки.

Проверяются реальные параметры развёртывания: открытые публичные и внутренние порты, ответы по HTTP и TLS, совпадение сертификата и поведения с сайтом маскировки (SNI), доступность типичных путей прокси и панелей управления, реакция на заголовки WebSocket, обратная запись DNS (PTR), поддержка HTTP/2, отказ от устаревших версий TLS и настроенные домены. Флаг `--sni` позволяет явно указать домен маскировки при проверке стороннего адреса. Для UDP-портов без TCP-ответа выводится подсказка запустить полный `meridian test`.

Кроме того, `--probe` помогает понять, **что именно заблокировано**. Команда устанавливает TLS-соединение с вашим сервером, передавая его маскировочный SNI; если соединение не устанавливается, она пробует подключиться к серверу без SNI, а также напрямую к настоящему сайту маскировки, после чего делает вывод, заблокирован ли **IP-адрес сервера** или **сам домен маскировки (SNI)**. Если настоящий сайт тоже не открывается из вашей сети, результат помечается как неопределённый (`inconclusive`), чтобы избежать ложных выводов. При маскировке под собственный домен (`self-steal`) настоящим сайтом выступает сам сервер, поэтому независимое сравнение невозможно и при полной недоступности результат также остаётся неопределённым. Для сервера управления дополнительно скачивается скрипт страницы подключения (~50 КБ) и проверяется, не замирает ли передача после 16–24 КБ (типичный почерк фильтрации зарубежных хостингов по порогу объёма). Если настроен маршрут WSS через CDN, аналогичная проверка скачивания выполняется и через CDN. Все эти проверки блокировок имеют смысл только при запуске изнутри сети, где наблюдается проблема. Флаг `--probe` несовместим с `--basic`, `--client` и `--domain`. Коды возврата совпадают с обычным `test`; пропущенные проверки никогда не помечаются как успешные.

Команда `meridian probe [SERVER|DOMAIN] [--sni NAME] [--timeout SECONDS] [--json]` — короткий псевдоним для `meridian test IP --probe`.

### meridian doctor

Собирает подробный диагностический отчёт о сервере для обращения за помощью или сообщения об ошибке.

```
meridian doctor [SERVER] [--sni HOST] [--user USER] [--ssh-port PORT] [--ai]
```

Флаг `--sni` указывает сайт маскировки для проверки, `--user` и `--ssh-port` переопределяют сохранённые параметры SSH, а `--ai` копирует в буфер обмена очищенный от секретов отчёт с готовым промптом для ИИ-ассистента вместо вывода шаблона для GitHub Issues.

Набор проверок в `doctor` учитывает роль сервера: промежуточный сервер не проверяется как выходной, а шлюзы маршрутизации помечаются отдельно. Если на сервере отсутствуют системные утилиты или оборвалось соединение по SSH, отчёт считается неполным (код возврата `3`), но уже собранные разделы всё равно выводятся.

### meridian logs

Показывает последние строки системных журналов сервера с автоматическим скрытием секретов — без необходимости заходить на сервер вручную по SSH.

```
meridian logs [SERVER] [--lines N] [--grep TEXT] [--component NAME]
              [--user USER] [--ssh-port PORT]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--lines`, `-n N` | `100` | Количество последних строк из каждого журнала (`1`–`10000`) |
| `--grep`, `-g TEXT` | | Показывать только строки, содержащие указанную подстроку (поиск без учёта регистра, как обычный текст, а не регулярное выражение) |
| `--component`, `-c NAME` | все | Выбрать только нужный компонент: `node`, `panel`, `nginx` или `relay` (флаг можно указать несколько раз) |

Команда `logs` собирает журналы тех служб, которые соответствуют роли сервера: на выходных серверах и шлюзах маршрутизации компонент `node` выводит логи агента (`netagent`) и Xray (`netcore`), на сервере управления компонент `panel` выводит лог сервиса управления (`ctld`), на обоих также читается журнал ошибок `nginx`, а на промежуточных серверах компонент `relay` показывает логи служб Realm. Флаги `--user` и `--ssh-port` переопределяют сохранённые настройки SSH.

Каждая строка проходит ту же очистку секретов, что и в `meridian doctor`: токены, пароли, приватные ключи, UUID, идентификаторы подписок и секретные пути сервиса управления и страниц подключения заменяются меткой `[REDACTED]`, поэтому вывод безопасно публиковать в отчётах об ошибках. Управляющие последовательности терминала из текста удаляются.

Если у сервера нет роли в топологии или запрошен `--component`, который на нём не используется, команда сразу завершится с кодом `2` без подключения по SSH. Если прочитать какой-либо журнал не удалось (служба не найдена или прервалось SSH-соединение), он помечается как недоступный, а команда возвращает код `3`.

### meridian panel

Выводит адрес веб-панели, а если пароль владельца ещё не задан — одноразовую ссылку для первоначальной настройки.

```
meridian panel [--setup-link]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--setup-link` | | Сгенерировать одноразовую ссылку для сброса пароля, даже если у панели уже есть владелец (после перехода по ней задаётся новый пароль, отключается двухфакторный код и завершаются сеансы на всех устройствах) |

Одноразовая ссылка настройки действует 15 минут — откройте её в браузере, чтобы задать пароль владельца. Когда пароль уже установлен, `panel` выводит постоянный адрес панели и показывает, включён ли двухфакторный код для входа. Храните и постоянный адрес панели (он содержит секретный путь), и ссылку настройки так же надёжно, как пароли. В веб-панели удобно управлять пользователями, общими сообщениями, языком, конфиденциальностью и API-токенами, а список серверов, история ревизий и параметры топологии отображаются в режиме чтения — подробнее см. [Веб-панель](/ru/client-management/#веб-панель).

### meridian teardown

Полностью удаляет Meridian с сервера.

```
meridian teardown [SERVER] [--user USER] [--ssh-port PORT] [--yes]
```

При развёртывании из одного сервера `teardown` удаляет всё, что создал Meridian: сервис управления и его базу данных, агент узла и Xray, конфигурационные файлы nginx, сертификаты, службы промежуточных серверов и правила файрвола на самом сервере, а затем очищает локальный файл `cluster.yml` и удаляет профиль сервера из `servers.json`. Базовые системные пакеты, защита SSH и fail2ban остаются на месте, а nginx продолжает работать, если он обслуживает другие ваши сайты. Команда также умеет удалять панель 3x-ui, оставшуюся от Meridian 3.x. Если у вас несколько серверов, `teardown` не позволит очистить сервер, за которым ещё числится роль в топологии (сначала выведите его из топологии через `node remove` или `relay remove`).

Флаг `--yes` пропускает запрос подтверждения (проверка ролей всё равно выполняется). При отказе от подтверждения команда возвращает код `1`. Если указано неизвестное имя сервера либо подходящий сервер не удалось выбрать однозначно, возвращается код `2` без интерактивного вопроса.

### meridian backup

Управление зашифрованными резервными снимками сервиса управления, списком доверенных компьютеров и ключом восстановления.

```
meridian backup pull [--name NAME]
meridian backup recovery-key [--yes]
meridian backup devices
meridian backup revoke ID
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--name NAME` | имя этого компьютера (`hostname`) | В `backup pull`: понятное имя для ключа этого компьютера при первой регистрации |
| `--yes`, `-y` | | В `backup recovery-key`: заменить существующий ключ восстановления без дополнительного подтверждения |

После каждой команды, меняющей состояние серверов или пользователей, Meridian автоматически скачивает свежий резервный снимок сервиса управления в каталог `snapshots/` рядом с `cluster.yml` (хранятся несколько последних снимков). Снимок включает базу пользователей, лимиты, счётчики трафика, историю ревизий, API-токены, а также копию локальных файлов `cluster.yml` и `servers.json` — благодаря этому из одного файла снимка можно полностью восстановить управление на новом компьютере. Каждый снимок зашифрован открытыми ключами всех зарегистрированных компьютеров и ключом восстановления; закрытые ключи подписи сервиса управления, браузерные сессии и хеш пароля веб-панели в снимок никогда не включаются. Если скачать снимок после команды не удалось, выводится предупреждение, но сама команда ошибкой не завершается.

**`backup pull`** — принудительно скачивает и сохраняет свежий снимок прямо сейчас. При первом вызове на новом компьютере создаётся его закрытый ключ (`device.key`, с правами чтения только для вашего пользователя ОС), а открытая часть регистрируется в сервисе управления.

**`backup recovery-key`** — создаёт ключ восстановления (или заменяет существующий после подтверждения) и выводит его на экран ровно один раз. Meridian хранит на сервере только открытый ключ, поэтому обязательно запишите или распечатайте секретную строку и храните её офлайн отдельно от компьютера. При самом первом развёртывании серверов такой ключ уже создаётся и показывается автоматически. Команда недоступна в режиме `--json`.

**`backup devices`** — выводит список компьютеров, для ключей которых шифруются резервные снимки, с их идентификаторами и датами регистрации, а также показывает, настроен ли ключ восстановления.

**`backup revoke`** — отзывает ключ указанного компьютера (например, при потере ноутбука), чтобы новые снимки больше не шифровались для него. Снимки, которые уже были сохранены на том компьютере ранее, останутся читаемыми его локальным ключом, поэтому отзывайте потерянное устройство как можно раньше.

### meridian restore

Восстанавливает утерянный, заблокированный или изъятый сервер управления на новом VPS из зашифрованного резервного снимка.

```
meridian restore --to SERVER [--snapshot FILE] [--recovery-key] [--force]
                 [--name NAME] [--user USER] [--ssh-port PORT] [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--to SERVER` | (обязателен) | Адрес нового сервера управления: IP, `user@IP:port` или имя сохранённого сервера |
| `--snapshot FILE` | самый свежий снимок | Путь к файлу снимка для восстановления |
| `--recovery-key` | | Расшифровать снимок ключом восстановления вместо локального ключа компьютера (ключ вводится в скрытом поле или передаётся одной строкой в `stdin`) |
| `--force` | | Выполнить восстановление на новый сервер, даже если старый сервис управления всё ещё отвечает по сети |
| `--name NAME` | (нет) | Короткое имя для нового сервера |
| `--user/-u USER` | root | Пользователь SSH на новом сервере |
| `--ssh-port PORT` | 22 | Порт SSH на новом сервере |
| `--yes`, `-y` | | Пропустить интерактивное подтверждение |

Команда `restore` расшифровывает снимок, показывает подробный план восстановления и запрашивает подтверждение. Затем она разворачивает сервис управления с базой из снимка на новом сервере, переключает в топологии адрес сервера управления (а также выходной сервер, если он работал на том же хосте) на новый IP-адрес и выполняет стандартное применение конфигурации (`apply`). Восстановленный сервис управления создаёт новый корневой центр сертификации, новые ключи подписи документов и новый административный токен — поэтому агенты на всех остальных серверах проходят повторную привязку по SSH, а старый (например, изъятый) сервер теряет техническую возможность отдавать команды вашим узлам. Все учётные записи пользователей, лимиты и счётчики трафика полностью сохраняются. Чтобы снова войти в веб-панель, получите новую ссылку настройки командой `meridian panel`.

Если сервер управления работал без домена (по IP-адресу), этот IP входил во все ссылки подписок — поэтому после переезда на новый IP ссылки всех пользователей изменятся (команда заранее предупредит об этом в плане, а в конце выведет новые ссылки для каждого клиента). Если для панели использовался собственный домен, ссылки пользователей останутся прежними — достаточно перенаправить DNS-запись домена на новый IP-адрес (нужные записи будут перечислены в плане).

По умолчанию `restore` отказывается запускаться, если прежний сервер управления ещё выходит на связь, чтобы два активных сервиса управления не рассинхронизировали узлы; флаг `--force` снимает это ограничение (например, если доступ к старому серверу утрачен или он скомпрометирован). Если через `--snapshot` выбран не самый свежий файл, команда предупредит, что откат к старому снимку восстановит в том числе токены, компьютеры и пользователей, удалённых после его создания. Прерванное восстановление можно безопасно запустить повторно — оно продолжит с места остановки.

Если вы восстанавливаете систему на новом компьютере, где нет локальных файлов конфигурации, укажите путь к файлу снимка и флаг `--recovery-key`: сначала из снимка будут извлечены файлы `cluster.yml` и `servers.json`. Если же на компьютере уже есть более старая копия этой конфигурации, чем в снимке, `restore` развернёт восстановленную конфигурацию в новом контексте и переведёт серверы под его управление, а старый контекст пометит в `context list` как заменённый (`superseded`) и заблокирует от изменений до тех пор, пока вы не удалите его командой `meridian context remove`.

### meridian migrate

Переводит серверы, развёрнутые на ранних выпусках с панелью Remnawave, на встроенный сервис управления Meridian — прямо на месте и с сохранением всех существующих ссылок подписок.

```
meridian migrate [--yes]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--yes`, `-y` | | Выполнить переход без интерактивного подтверждения |

Перед началом работы `migrate` выводит подробный план перехода: список переносимых клиентов, возможные замечания по отдельным полям, а также перечень специфичных для Remnawave данных, которые не используются в новой архитектуре (учётная запись администратора и API-токены самой панели, внутренняя посуточная статистика панели, привязки устройств по HWID, сторонние плагины и правила ответов, проброс клиентских IP-адресов и встроенная страница подписки Remnawave; собственные страницы подключения Meridian полностью сохраняются). После вашего подтверждения команда пошагово:

1. Сохраняет полную резервную копию базы данных панели и файлов конфигурации на вашем компьютере (`backups/`) и на самом сервере управления (`/var/backups/meridian-migration/`)
2. Устанавливает сервис управления Meridian рядом с панелью и переносит всех клиентов с сохранением их ключей, идентификаторов подписок, статусов, лимитов трафика, сроков доступа и накопленного расхода
3. Останавливает контейнеры панели (сохраняя её данные на диске) и удаляет Docker-контейнеры узлов
4. Применяет обновлённую топологию: на каждый выходной сервер устанавливается агент `netagent` и привязывается к сервису управления
5. Сверяет ссылки подписок всех клиентов, убеждаясь, что ни один адрес не изменился
6. Удаляет контейнеры Remnawave

Автоматического отката назад нет — при необходимости вернуться к прежней схеме позволяет сохранённая на первом шаге резервная копия. Каждый этап фиксируется в контрольной точке: если процесс прервётся, повторный запуск `meridian migrate` продолжит с места остановки, а на уже переведённых серверах ничего менять не станет. Если на пятом шаге обнаружится расхождение в ссылках, удаление Remnawave отменяется (панель остаётся остановленной на диске), а команда завершается с ошибкой. При запуске без интерактивного терминала передайте `--yes`. Команда `meridian deploy` сама предложит запустить `migrate`, если обнаружит на сервере панель Remnawave.

### meridian update

Обновляет сам пакет CLI до последнего выпуска текущей мажорной версии на PyPI. Если вышла новая мажорная версия, команда только сообщит о ней; чтобы перейти на новую мажорную ветку после ознакомления со списком изменений, укажите флаг `--major`. Если у вас установлена бета-версия, команда обновляет её до более свежих бета-выпусков и затем до стабильного релиза этой же мажорной ветки. Meridian автоматически пробует `uv`, `pipx` и `pip` и сообщает об успехе только после проверки того, что вызываемая команда `meridian` действительно обновилась. Код возврата `0` означает, что установлена актуальная версия или обновление прошло успешно; `3` — не удалось выполнить или проверить обновление. Обновление CLI не затрагивает работающие серверы (для их обновления используйте `meridian fleet upgrade`).

```
meridian update [--major]
```

### meridian serve

Запускает серверный процесс сервиса управления. Meridian автоматически настраивает его на сервере управления как системную службу systemd `ctld` — запускать эту команду вручную не нужно.

```
meridian serve [--config FILE]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--config FILE` | `/etc/ctld/config.json` | Путь к файлу конфигурации сервиса (создаётся автоматически) |

Сервис принимает соединения на `127.0.0.1:3000` за обратным прокси nginx и хранит все данные в одном файле SQLite в каталоге `/var/lib/ctld/`. HTTP-запросы в системный журнал не записываются, поэтому идентификаторы подписок и секретные пути никогда не попадают в логи. Посмотреть журнал работы службы можно командой `meridian logs SERVER -c panel`.

### meridian api

Выводит машиночитаемые JSON-схемы и контракты команд CLI для интеграции со скриптами и графическими интерфейсами.

```
meridian api schemas [--json] [--include-schemas]
meridian api commands [--json] [--include-schemas]
meridian api schema NAME [--envelope|--json]
meridian api workflow NAME [--json]
```

| Параметр | По умолчанию | Описание |
|------|---------|-------------|
| `--json` | | Вывести каталог в конверте `meridian.output/v1` |
| `--include-schemas` | | Включить полные тексты JSON Schema в вывод `api schemas` или `api commands` (автоматически включает формат JSON) |
| `--envelope`, `--json` | | Обернуть вывод `api schema NAME` в конверт `meridian.output/v1` вместо печати чистой схемы |

**`api schemas`** — перечисляет доступные имена схем, такие как `output-envelope`, `deploy-request`, `deploy-result`, `deploy-plan`, `plan-envelope`, `apply-envelope`, `client-list-envelope`, `fleet-status-envelope` и `event`.

**`api commands`** — выводит машиночитаемые контракты всех команд CLI: аргументы (`argv`), схемы конверта и поля `data`, возможные статусы, значения кодов возврата, список поддерживаемых флагов (`machine_flags`) и поведение при прерывании (`interrupt_behavior`). Метаданные формируются напрямую из дерева команд CLI. Нажатие Ctrl+C завершает процесс с кодом `130` без вывода JSON-конверта (`interrupt_behavior: "exit_130_without_envelope"`).

**`api schema NAME`** — выводит конкретную схему JSON Schema, например: `meridian api schema output-envelope`.

**`api workflow NAME`** — выводит описание пошагового сценария для построения UI, например: `meridian api workflow deploy --json`.

### meridian help

Выводит руководство по Meridian для ИИ-агентов или встроенную справку по отдельной команде.

```
meridian help [agents | COMMAND...]
```

**`meridian help agents`** выводит полное руководство в формате Markdown, предназначенное для ИИ-агентов: назначение Meridian, устройство проверяемой топологии и сервиса управления, расположение файлов состояния, правила безопасного вызова команд (неинтерактивные флаги, JSON-конверты, проверка `plan` перед `apply`, подтверждение удаления, обращение со ссылками как с секретами), коды возврата и примеры типовых операций. Текст всегда выводится в чистом Markdown без оформления терминала, чтобы агент мог прочитать его напрямую через пайп.

**`meridian help COMMAND`** выводит ту же справку, что и `meridian COMMAND --help` (например, `meridian help node add`). Без аргументов показывается общая справка верхнего уровня. При указании неизвестного раздела возвращается код `2`.

## Глобальные параметры

Глобальные параметры указываются перед именем команды (например, `meridian --quiet doctor`), а параметры конкретной команды — после неё (например, `meridian test --json`).

| Параметр | Описание |
|------|-------------|
| `--version`, `-v` | Показать версию CLI и завершиться |
| `--verbose` | Включить подробный отладочный вывод |
| `--quiet`, `-q` | Скрыть промежуточные сообщения о ходе выполнения |
| `--context NAME` | Выполнить команду для другого набора серверов ([`meridian context`](#meridian-context)); по умолчанию берётся из `MERIDIAN_CONTEXT`, иначе используется активный контекст. Этот флаг можно указывать и после имени команды: `meridian deploy 203.0.113.5 --context work` |
| `--lang CODE` | Язык интерфейса мастера `setup`: `en`, `ru`, `fa` или `zh` (по умолчанию используется сохранённый выбор, иначе мастер спросит при запуске) |
| `--json` | Запросить ответ в JSON-конверте у команды, которая поддерживает JSON-вывод (для остальных команд вернёт явную ошибку) |
| `--install-completion` | Установить автодополнение команд для вашей текущей оболочки терминала |
| `--show-completion` | Вывести скрипт автодополнения для текущей оболочки |

Все команды с поддержкой `--json` возвращают единый конверт `meridian.output/v1` (поля `schema`, `command`, `operation_id`, `status`, `summary`, `data`, `warnings`, `errors`). В их число входят `deploy`, `plan`, `apply`, `check`, `test`, `probe`, все подкоманды `client` и `route`, команды `fleet status`/`inventory`/`history`/`events`/`usage`/`routing`/`contact`/`notice`/`language`/`export`/`import`, `node list`/`restart`, `relay list`, `server list`/`set`, `privacy`, `context list` и `api`. Глобальный флаг `--json` и локальный `--json` у подкоманды работают одинаково. Все секретные значения автоматически вырезаются перед формированием JSON. Полный каталог контрактов доступен по команде `meridian api commands --json`.

## Общие параметры подключения к серверам

Эти параметры одинаково называются в разных командах (каждая команда принимает только те из них, которые перечислены в её собственном разделе):

| Параметр | В каких командах используется |
|------|---------|
| Аргумент `SERVER` | `deploy`, `check`, `scan`, `test`, `doctor`, `logs`, `teardown`, `node add`, `relay add`, `server add` |
| `--user`, `-u USER` | `deploy`, `check`, `node add`, `relay add`, `server add`, `scan`, `doctor`, `logs`, `teardown`, `restore` |
| `--ssh-port PORT` | `deploy`, `check`, `node add`, `relay add`, `server add`, `scan`, `doctor`, `logs`, `teardown`, `restore` |
| `--sni HOST` | `deploy`, `check`, `node add`, `relay add`, `test`, `doctor` |
| `--domain DOMAIN` | `deploy`, `check`, `node add`, `test` |
| `--self-steal` | `deploy`, `node add`, `node sni` |

Команды группы `meridian client` обращаются напрямую к API сервиса управления и адрес SSH-сервера не принимают. Команда `meridian test` проверяет соединение непосредственно с вашего устройства и также не использует SSH.

## Как указывается целевой сервер

Целевой сервер передаётся первым аргументом в привычном для `ssh` формате: IP-адрес, имя сохранённого сервера, строка `user@host:port` или ключевое слово `local` для выполнения прямо на текущей машине без SSH. Флаги `--user` и `--ssh-port` дополняют недостающие параметры, но не должны противоречить данным, явно указанным в строке `user@host:port`. Если пользователь или порт не заданы ни в аргументе, ни во флагах, используются значения из сохранённого профиля сервера, а при их отсутствии — `root` и порт `22`. Если сервер не указан вовсе, Meridian выбирает локальный режим (когда команда запущена на самом развёрнутом сервере) либо единственный сохранённый сервер. Если сохранённых серверов нет или их несколько, команда не задаёт интерактивных вопросов и сразу завершается с кодом `2`.
