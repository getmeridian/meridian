В этом руководстве разобраны все возможности и флаги команды `meridian deploy`. Если вы настраиваете сервер впервые, рекомендуем сначала прочитать краткое руководство [С чего начать](/ru/getting-started/).

## Базовое развёртывание

```
meridian deploy 198.51.100.10
```

При запуске на одном сервере этот VPS становится одновременно сервером управления (на нём работает сервис управления Meridian) и выходным сервером, через который проходит пользовательский трафик. Команда `deploy` формирует такую же проверенную топологию, что и пошаговый мастер [`meridian setup`](/ru/cli-reference/#meridian-setup), и применяет её с сохранением контрольных точек. Прежде чем вывести сообщение о готовности, Meridian проверяет реальное прохождение трафика через созданную подписку.

Если запустить `meridian deploy` без IP-адреса, команда попросит ввести его. Чтобы пропустить интерактивные запросы подтверждения, добавьте флаг `--yes`:

```
meridian deploy 198.51.100.10 --client-name alice --yes
```

## Серверы только с паролем

Для управления серверами Meridian использует SSH-ключи. Однако многие хостинг-провайдеры при создании VPS присылают только пароль от пользователя `root`. Если сервер отклоняет ваши SSH-ключи, но разрешает вход по паролю, интерактивная команда `meridian deploy` предложит настроить ключ автоматически:

```
→ This server accepts only a password. Create a key for Meridian and install it now? [y/N]
```

Ответьте `y` и введите пароль (символы при вводе не отображаются). Meridian сгенерирует отдельный ключ в файле `~/.config/meridian/ssh/meridian_ed25519`, добавит его в `authorized_keys` на сервере, проверит вход по ключу, сохранит привязку в профиле сервера и продолжит установку. Введённый пароль используется только один раз и нигде не сохраняется. Отпечаток ключа самого сервера (host key) проверяется заранее. Точно так же работает добавление нового сервера в мастере `meridian setup`.

При запуске без интерактивного терминала, с флагом `--yes` или `--json` Meridian не запрашивает пароль, а выводит подсказку для ручной установки ключа:

```
ssh-copy-id root@198.51.100.10
```

После завершения развёртывания вход на сервер по паролю отключается для безопасности, а все дальнейшие команды Meridian автоматически используют сохранённый SSH-ключ.

## Все параметры `meridian deploy`

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--sni HOST` | (автоматически) | Сайт для маскировки (SNI). Если не указан, при первом развёртывании сканируется собственная подсеть сервера, а затем по очереди проверяются `www.google.com`, `dl.google.com` и `www.cloudflare.com` |
| `--domain DOMAIN` | (нет) | Ваш домен: переносит на него XHTTP и добавляет WSS (оба способа могут работать через CDN Cloudflare) |
| `--self-steal` | выкл. | Маскировка под ваш собственный домен (`--sni` или `--domain`), направленный на этот сервер (см. [Ваш собственный домен](#ваш-собственный-домен-self-steal)) |
| `--hysteria2/--no-hysteria2` | вкл. | Включить протокол Hysteria2 на порту UDP/443 как резервный способ для нестабильных сетей |
| `--client-name NAME` | default | Имя первого клиента |
| `--display-name NAME` | (нет) | Заголовок на страницах подключения и название подписки (например, «VPN Алисы») |
| `--icon EMOJI_OR_URL` | (нет) | Значок для страницы подключения — эмодзи или ссылка на изображение |
| `--color PALETTE` | ocean | Цветовая тема страницы подключения (`ocean`, `sunset`, `forest`, `lavender`, `rose`, `slate`) |
| `--user USER` | root | Пользователь SSH (для пользователя не `root` требуется беспарольный `sudo`) |
| `--ssh-port PORT` | 22 | Порт SSH, если он отличается от 22 |
| `--harden / --no-harden` | вкл. | Базовая защита сервера: вход по SSH только по ключу, fail2ban и файрвол UFW. Используйте `--no-harden`, если на сервере уже работают сторонние службы |
| `--warp / --no-warp` | выкл. | Направлять весь исходящий трафик сервера через Cloudflare WARP |
| `--geo-block / --no-geo-block` | вкл. | Блокировать обращения к российским доменам и IP-адресам на стороне выходного сервера |
| `--country CC` | определяется автоматически | Двухбуквенный код страны в названиях подключений (например, `DE`). По умолчанию определяется через региональный интернет-реестр (RDAP); укажите вручную, если страна определилась неточно |
| `--yes` | | Пропустить запросы подтверждения |

Служебные флаги для автоматизации и UI (`--json`, `--events`, `--request`, `--dry-run`) подробно описаны в [справочнике CLI](/ru/cli-reference/#meridian-deploy).

## Выбор цели маскировки

Цель маскировки (SNI) — это доменное имя настоящего сайта, под которое маскируется ваш сервер при работе по протоколу Reality. В стандартном режиме это **не** ваш собственный домен, а сторонний сайт с поддержкой TLS 1.3 и HTTP/2: при любой внешней проверке сервер предъявляет подлинный сертификат этого сайта. О том, как использовать для маскировки собственный домен, рассказано ниже в разделе [Ваш собственный домен](#ваш-собственный-домен-self-steal).

Лучше всего для маскировки подходит сайт, расположенный в той же сети (подсети хостинга), что и ваш VPS. Системы анализа трафика видят запрашиваемый SNI одновременно с IP-адресом вашего сервера: когда DNS выбранного сайта действительно ведёт в ту же подсеть, соединение выглядит максимально естественно.

Если флаг `--sni` не указан, при первом развёртывании Meridian сканирует соседние IP-адреса сервера (это занимает около минуты) и отбирает домены, чьи DNS-записи ведут в эту же подсеть и которые поддерживают TLS 1.3 и HTTP/2. Если подходящих соседей не нашлось, проверяются `www.google.com`, `dl.google.com` и `www.cloudflare.com`, после чего выбирается первый сайт, через который успешно проходит реальный трафик. Точно так же подбирается SNI при добавлении новых серверов через `meridian node add`. Если же вы явно указали сайт через `--sni`, Meridian не станет заменять его автоматически: если трафик через него не пройдёт, команда остановится и сообщит об ошибке. При повторном запуске `deploy` на уже настроенном сервере выбранный ранее SNI сохраняется.

Посмотреть список подходящих сайтов в подсети вашего сервера вручную можно командой:

```
meridian scan 198.51.100.10
```

Она запускает на сервере проверенную по контрольной сумме сборку RealiTLScanner и выводит найденные поблизости домены, после чего вы можете развернуть сервер с выбранным вариантом:

```
meridian deploy 198.51.100.10 --sni dl.google.com
```

Проверить конкретный домен перед установкой можно командой `meridian check 198.51.100.10 --sni HOST`. Не используйте `apple.com`, `icloud.com` (они работают только в собственных сетях Apple) и `www.microsoft.com` (слишком большая цепочка сертификатов для Reality).

### Как сменить сайт маскировки позже

Если проверка `meridian test --probe` показала, что текущий SNI маскировки попал под блокировку, смените его без полной переустановки сервера. Meridian проверит, что выходной сервер успешно открывает новый сайт по TLS 1.3 с HTTP/2, покажет план изменений и применит его. Старый SNI заменяется сразу; клиентские приложения подхватят новое значение при следующем автоматическом обновлении подписки (раз в 6 часов) или после ручного нажатия «Обновить» в приложении. Для смены SNI на промежуточном сервере используйте команду `meridian relay sni RELAY NEW_SNI`.

```
meridian node sni 198.51.100.10 www.cloudflare.com
```

### Ваш собственный домен (self-steal)

Вместо маскировки под чужой сайт сервер может использовать доменное имя, которое принадлежит вам. Направьте A-запись вашего домена на IP-адрес сервера в режиме «только DNS» (серое облако в Cloudflare, без проксирования) и запустите развёртывание с флагом `--self-steal`:

```
meridian deploy 198.51.100.10 --sni www.example.com --self-steal
```

Meridian выпустит для этого домена настоящий сертификат Let's Encrypt и настроит nginx так, чтобы на любые запросы без ключа Reality (или с неизвестным SNI) сервер отвечал этим сертификатом и стандартной страницей `404 Not Found` от nginx — точно так же, как любой обычный веб-сервер, на котором ещё не размещён сайт. В этом режиме доменное имя в DNS, IP-адрес сервера и TLS-сертификат полностью согласованы между собой, а работа маскировки не зависит от доступности сторонних сайтов.

Перед применением настроек Meridian проверяет с сервера, куда указывает DNS-запись домена: если имя ещё не разрешается в DNS, команда остановится, а если указывает на чужой адрес (например, на прокси Cloudflare) — выведет предупреждение.

Если указать `--domain` и `--self-steal` без отдельного `--sni`, один и тот же домен будет использоваться и для Reality, и для XHTTP/WSS. Однако учитывайте, что при включении оранжевого облака (проксирования Cloudflare) домен начинает разрешаться в IP-адреса Cloudflare, поэтому для одновременного использования `self-steal` и CDN Cloudflare лучше завести два разных поддомена: один без проксирования для `--sni --self-steal`, а второй с проксированием для `--domain`. Флаг `--self-steal` поддерживается также в командах `meridian node add` и `meridian node sni`.

### Чем отличаются `--sni` и `--domain`

- **Сайт для маскировки (`--sni`)** — сторонний сайт с TLS 1.3, под который маскируется протокол Reality (либо ваш собственный не проксируемый через CDN домен при использовании `--self-steal`).
- **Домен сервера (`--domain`)** — ваш собственный домен, направленный на сервер: на него переносится XHTTP и добавляется маршрут WSS, которые могут работать через CDN Cloudflare (см. [Режим домена](/ru/domain-mode/)).

## Протокол Hysteria2

```
meridian deploy 198.51.100.10 --no-hysteria2
```

По умолчанию на каждом выходном сервере включается Hysteria2 на порту UDP/443 (с сертификатом домена или IP-сертификатом сервера). Пакеты Hysteria2 маскируются обфускацией salamander, чтобы системы фильтрации не распознавали в них стандартный протокол QUIC. Этот маршрут выручает на загруженных каналах с потерей пакетов; в сетях, где оператор блокирует UDP, приложения автоматически переключаются на TCP-маршруты. Отключить Hysteria2 можно флагом `--no-hysteria2`. Через промежуточные серверы трафик Hysteria2 не передаётся.

## Оформление страницы подключения

Вы можете задать понятное название, значок и цветовую схему для страниц подключения, чтобы ваши близкие сразу видели, чей это VPN:

```
meridian deploy 198.51.100.10 --display-name "Alice's VPN" --icon 🚀 --color sunset
```

- **`--display-name`** — заголовок на странице подключения и название профиля в приложениях
- **`--icon`** — эмодзи или ссылка на картинку в шапке страницы
- **`--color`** — цветовая палитра: `ocean` (по умолчанию), `sunset`, `forest`, `lavender`, `rose`, `slate`

Настройки оформления сохраняются в `cluster.yml` и применяются ко всем пользовательским страницам.

## Повторное развёртывание и изменение параметров

При повторном запуске `meridian deploy` на уже настроенном сервере все ключи, пути и учётные записи пользователей сохраняются, поэтому существующие ссылки продолжают работать без перерывов. Повторный запуск без флага `--sni` оставляет ранее выбранный сайт маскировки.

В конце каждого развёртывания Meridian выводит в терминале полную команду для повторного запуска с вашими текущими параметрами. Запустив её с изменёнными флагами (например, добавив или убрав `--domain` или `--no-hysteria2`), вы обновите конфигурацию выходного сервера на месте.

Команда `meridian deploy` обновляет только тот сервер, который уже является выходным в вашей конфигурации. Чтобы добавить к существующему серверу второй выходной сервер, используйте команду `meridian node add NEW_IP`. Если же ваши серверы были развёрнуты на ранней бета-версии Meridian 4 с панелью Remnawave, `deploy` сначала предложит перевести их на встроенный сервис управления (см. [Переход с Remnawave](#переход-с-remnawave)).

## Редактирование конфигурации через YAML-файл

Чтобы внести сразу несколько изменений или хранить описание инфраструктуры в Git-репозитории, экспортируйте конфигурацию в файл, отредактируйте её и импортируйте обратно:

```bash
meridian fleet export > fleet.yml
$EDITOR fleet.yml
meridian fleet import fleet.yml
```

Перед применением `fleet import` наглядно покажет все изменения и попросит подтверждения:

```
  + client carol
  ~ exit-2 sni www.example.com -> www.example.org
  → Применить? [y/N]
```

В экспортируемом файле серверы именуются по их сохранённым именам, а секретные ключи, токены и ссылки в него не включаются — такой файл безопасно хранить в системе контроля версий. Все упомянутые в файле серверы должны быть предварительно добавлены в локальный реестр (`meridian server add`). Полный список правил и ограничений импорта приведён в описании [`fleet import`](/ru/cli-reference/#meridian-fleet).

## Предварительная проверка сервера

Чтобы проверить новый VPS перед установкой, выполните:

```
meridian check 198.51.100.10
```

Команда проверит доступность сайта маскировки, порт 443, видимость порта извне, DNS-запись домена (если указан `--domain`), версию ОС, свободное место на диске и точность системных часов, ничего не устанавливая на сервер.

## Развёртывание через пользователя без прав `root`

```
meridian deploy 198.51.100.10 --user ubuntu
```

Все административные команды на сервере будут выполняться через `sudo` (у указанного пользователя должен быть настроен `sudo` без запроса пароля).

## Локальное развёртывание на самом сервере

Если вы запустили Meridian непосредственно на самом VPS под пользователем `root`:

```
meridian deploy local
```

В этом режиме команды выполняются локально без SSH (аналогично работают `check local`, `scan local` и `doctor local`). Тем не менее мы рекомендуем управлять серверами со своего компьютера: тогда ключи управления не хранятся на VPS, а команда `meridian test` может проверять доступность сервера из вашей реальной сети.

## Cloudflare WARP

Режим WARP направляет исходящий трафик выходного сервера через сеть Cloudflare, благодаря чему целевые сайты видят IP-адрес Cloudflare, а не адрес вашего хостинг-провайдера:

```
meridian deploy 198.51.100.10 --warp
```

**Когда это полезно:** если нужные сайты блокируют IP-диапазоны дата-центров или предъявляют бесконечные капчи.

**Когда включать не стоит:** большинство сайтов отлично работают напрямую, а дополнительное звено (VPS → Cloudflare → сайт) немного увеличивает пинг.

При включении этого режима Meridian устанавливает официальный клиент `cloudflare-warp` в режиме локального SOCKS5-прокси (`127.0.0.1:40000`) и направляет через него исходящий трафик Xray. Регистрация аккаунта в Cloudflare не требуется.

### Точечный маршрут через WARP только для отдельных сайтов

Вместо того чтобы заворачивать в WARP вообще весь трафик сервера, можно направить через него только выбранные домены — при добавлении первого такого правила Meridian сам установит и запустит WARP на указанном выходном сервере:

```
meridian route add exit-1 --via warp chatgpt.com netflix.com
meridian route add exit-1 --via block geosite:category-ads-all
meridian route list
meridian route remove exit-1 warp
```

В правилах можно указывать доменные имена (включая все поддомены), категории `geosite:NAME` или списки `geoip:NAME`; одно правило объединяет значения одного типа. На сервере, где WARP включён по умолчанию для всего трафика, правило с `--via direct` делает обратное — пускает указанные сайты напрямую с IP-адреса сервера в обход WARP. Серверные правила проверяются по порядку добавления до стандартного выхода и до серверной геоблокировки. Подробнее о том, как они сочетаются с клиентской маршрутизацией и шлюзами, см. в разделе [Маршрутизация на устройствах](/ru/split-routing/#через-шлюз-маршрутизации).

### Готовый набор правил для ИИ-сервисов (`--preset ai`)

Сервисы искусственного интеллекта (ChatGPT, Claude, Gemini, Cursor и др.) часто блокируют IP-адреса хостинг-провайдеров, а при резкой смене страны выхода или кратковременной утечке российского IP могут разлогинить или заблокировать учётную запись. Одна команда направляет трафик всех основных ИИ-сервисов через Cloudflare WARP:

```
meridian route add exit-1 --preset ai
```

Пресет создаёт правило с именем `ai`, охватывающее списки `geosite:category-ai-!cn`, `anthropic`, `openai`, `cursor` и `google-gemini` (при необходимости можно указать `--via direct`, чтобы закрепить их за прямым IP выходного сервера). Поскольку узлы WARP выходят в интернет в стране самого VPS, при работе с ИИ-сервисами рекомендуется держать выходной сервер в одной поддерживаемой стране. Учитывайте, что серверное правило срабатывает только для трафика, вошедшего в VPN-туннель (например, на macOS после пробуждения из сна некоторые приложения могут в первую секунду отправить запрос мимо туннеля). Если сервисы Google продолжают определять ваш аккаунт как российский, подайте заявку на смену страны в справочном центре аккаунта Google.

## Геоблокировка на стороне сервера

По умолчанию выходной сервер блокирует передачу трафика через VPN к российским доменам (`geosite:category-ru`) и российским IP-адресам (`geoip:ru`). Это гарантирует, что IP-адрес вашего зарубежного VPS не попадёт в журналы российских ресурсов, даже если на устройстве пользователя не сработала раздельная маршрутизация.

Если вашим пользователям необходимо открывать российские сайты именно через зарубежный сервер, отключите серверную геоблокировку флагом:

```
meridian deploy 198.51.100.10 --no-geo-block
```

О том, как открывать российские сайты напрямую без отключения защиты сервера, рассказано в разделе [Маршрутизация на устройствах](/ru/split-routing/).

## Конфиденциальность и IP-адреса клиентов

Сервис управления никогда не сохраняет IP-адреса подключающихся клиентов и не ведёт логов посещаемых сайтов. По умолчанию хранятся только общий счётчик трафика за всё время и время последней активности; дополнительные возможности ограничения числа устройств и посуточной статистики описаны в разделе [Конфиденциальность](/ru/privacy/).

## Подключение промежуточного сервера

После развёртывания выходного сервера за рубежом вы можете добавить к нему промежуточный сервер (relay) внутри страны, чтобы сохранить доступ при блокировке зарубежных IP-адресов. Подробнее см. [Промежуточные серверы](/ru/relay/):

```
meridian relay add 203.0.113.10 --exit 198.51.100.10
```

## Веб-консоль

В состав сервиса управления входит встроенная веб-консоль для владельца сервера. Она расположена по отдельному секретному пути, который никогда не раскрывается в ссылках пользователей. Команда `meridian panel` выводит адрес консоли, а до первой регистрации владельца — одноразовую ссылку для создания пароля:

```
  Meridian console
  URL         https://198.51.100.10/<secret-path>/
  Setup link  https://198.51.100.10/<secret-path>/#setup=…
              Works once, for 15 minutes. Open it to choose the owner's password.
```

После установки пароля в настройках консоли можно подключить двухфакторную защиту одноразовыми кодами (TOTP) из приложения-аутентификатора. В веб-консоли удобно добавлять пользователей, делиться ссылками и QR-кодами, настраивать лимиты трафика, сроки доступа и сервисные сообщения, а также выпускать API-токены. Состав серверов, история ревизий и название подписки отображаются в консоли в режиме чтения вместе с подсказками команд CLI для их изменения. Подробнее см. [Веб-консоль](/ru/client-management/#веб-консоль).

Храните полный адрес консоли в секрете. Если вы забыли пароль или потеряли доступ к приложению-аутентификатору, выполните на своём компьютере команду `meridian panel --setup-link` — она сгенерирует одноразовую ссылку для установки нового пароля и сброса TOTP.

## Резервные копии

В самом конце первого развёртывания Meridian один раз выводит в терминале **ключ восстановления**:

```
  Recovery key (shown once; Meridian keeps no copy)

    AGE-SECRET-KEY-1…

  Write it down or print it, and keep it offline, away from this computer.
```

Запишите или распечатайте этот ключ и храните его отдельно от компьютера. После каждого изменения конфигурации Meridian автоматически скачивает на ваш компьютер зашифрованный снимок состояния сервиса управления (`~/.config/meridian/snapshots/`), который можно расшифровать либо ключом вашего компьютера (`device.key`), либо ключом восстановления. Если сервер управления когда-нибудь будет утерян или заблокирован, команда [`meridian restore`](/ru/recovery/#сервер-управления-потерян) полностью восстановит его на новом VPS из последнего снимка.

## Обновление серверных компонентов

Сервис управления (`ctld`) и агент узла (`netagent`) поставляются внутри пакета Meridian. После обновления CLI командой `meridian update` выполните `meridian fleet upgrade`: команда покажет план обновления и обновит сервис управления и агенты на всех узлах без сброса ключей и настроек, а также обновит бинарные файлы Realm на промежуточных серверах до актуального проверенного релиза. Обычный запуск `meridian apply` также автоматически подтягивает сервис управления и агенты узлов до версии установленного у вас CLI.

## Переход с Remnawave

Если ваши серверы были развёрнуты ранними выпусками Meridian 4 на базе панели Remnawave, команда `meridian migrate` переведёт их на встроенный сервис управления прямо на работающих серверах:

```
meridian migrate
```

Команда сохранит резервную копию базы данных панели (на вашем компьютере и на самом сервере управления), перенесёт всех пользователей вместе с их ключами, статусами, лимитами трафика, сроками действия и накопленным расходом, заменит Docker-контейнеры узлов легковесным агентом `netagent` и перед удалением Remnawave проверит, что все ссылки подписок остались неизменными. Для ваших пользователей переход пройдёт совершенно незаметно — менять ссылки в приложениях не придётся. Специфичные только для Remnawave данные (старые привязки HWID, суточная история панели и настройки плагинов) в новую базу не переносятся, а проброс клиентских IP-адресов отключается; полный список изменений выводится перед подтверждением. Если процесс прервётся, просто запустите `meridian migrate` повторно. Подробнее см. [`meridian migrate`](/ru/cli-reference/#meridian-migrate).
