В этом руководстве описаны все параметры команды `meridian deploy`. Если вы разворачиваете сервер впервые, начните с раздела [С чего начать](/ru/getting-started/).

## Базовое развёртывание

```
meridian deploy 198.51.100.10
```

Один сервер становится одновременно сервером управления (на нём работает сервис управления Meridian) и выходом, через который идёт трафик. Meridian строит ту же одобренную топологию, что и [`meridian setup`](/ru/cli-reference/#meridian-setup), и применяет её с контрольными точками. Прежде чем вывести «Done», он проверяет прохождение реального трафика через выпущенную подписку.

Если запустить `meridian deploy` без IP-адреса, команда спросит его. Добавьте `--yes`, чтобы пропустить подтверждения:

```
meridian deploy 198.51.100.10 --client-name alice --yes
```

## Серверы только с паролем

Meridian входит по SSH-ключам. Многие VPS-провайдеры выдают только пароль root, поэтому когда сервер отклоняет ваши ключи, но принимает пароль, интерактивный `meridian deploy` спрашивает:

```
→ This server accepts only a password. Create a key for Meridian and install it now? [y/N]
```

Ответьте `y` и введите пароль (он скрыт). Meridian создаёт собственный ключ в `~/.config/meridian/ssh/meridian_ed25519`, добавляет его в `authorized_keys` сервера, проверяет, что вход по нему работает, сохраняет его в профиле сервера и продолжает работу. Пароль используется для этой одной команды и никогда не сохраняется и не попадает в журнал. Ключ хоста проверяется первым, поэтому пароль уходит только на сервер, отпечаток которого вы приняли. `meridian setup` предлагает то же самое при добавлении сервера.

Без терминала, с `--yes` или с `--json` Meridian никогда не задаёт вопросов: вместо этого он останавливается и выводит команду для ручного выполнения. Один раз установите собственный ключ и запустите снова:

```
ssh-copy-id root@198.51.100.10
```

Защита сервера отключает вход по паролю после развёртывания, поэтому сохраните ключ: последующие команды используют его автоматически.

## Все флаги

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--sni HOST` | (авто) | Цель маскировки. Без этого флага развёртывание сначала ищет сайт в собственной подсети сервера, а затем пробует `www.google.com`, `dl.google.com`, `www.cloudflare.com` |
| `--domain DOMAIN` | (нет) | Ваш домен: XHTTP переносится на него и добавляется WSS, оба через CDN Cloudflare |
| `--self-steal` | выкл. | Маскировка под ваш собственный домен (`--sni`, иначе `--domain`) вместо чужого сайта (см. [Ваш собственный домен](#ваш-собственный-домен-self-steal)) |
| `--hysteria2/--no-hysteria2` | вкл. | Предлагать Hysteria2 на UDP/443 как последний резервный вариант |
| `--client-name NAME` | default | Имя первого клиента |
| `--display-name NAME` | (нет) | Название на страницах подключения (например, «VPN Алисы») |
| `--icon EMOJI_OR_URL` | (нет) | Значок страницы — эмодзи или URL изображения |
| `--color PALETTE` | ocean | Цветовая тема страницы (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | root | Пользователь SSH (не-root пользователям нужен `sudo` без пароля) |
| `--ssh-port PORT` | 22 | Порт SSH, если отличается от 22 |
| `--harden / --no-harden` | вкл. | Вход по SSH только по ключу, fail2ban и файрвол UFW. Используйте `--no-harden`, если на сервере работают другие сервисы |
| `--warp / --no-warp` | выкл. | Направлять исходящий трафик через Cloudflare WARP |
| `--geo-block / --no-geo-block` | вкл. | Блокировать российские домены и IP на сервере |
| `--country CC` | определяется | Страна в названиях подключений, например `DE`. Meridian определяет её по реестру адресов; укажите вручную, если определилась неверно |
| `--yes` | | Пропустить запросы подтверждения |

Флаги для скриптов и UI (`--json`, `--events`, `--request`, `--dry-run`) описаны в [справочнике CLI](/ru/cli-reference/#meridian-deploy).

## Выбор цели маскировки

Цель маскировки (SNI) — это веб-сайт, под который маскируется ваш сервер. Обычно это **не** ваш домен, а настоящий чужой сайт с TLS 1.3, и любой, кто проверяет ваш сервер, видит подлинный сертификат этого сайта. Как использовать собственный домен, см. [Ваш собственный домен](#ваш-собственный-домен-self-steal).

Лучшая цель находится рядом с вашим сервером. Цензор видит SNI вместе с IP вашего сервера; когда DNS сайта действительно указывает в ту же сеть, такая пара выглядит как обычный трафик, а известный зарубежный сайт на адресе VPS бросается в глаза.

Без `--sni` первое развёртывание сканирует собственную подсеть сервера в поисках таких сайтов (около минуты) и оставляет те, чей DNS указывает в эту подсеть и которые проходят проверку Reality на TLS 1.3 и HTTP/2. Затем в запасе идут `www.google.com`, `dl.google.com` и `www.cloudflare.com`. Используется первая цель, через которую проходит реальный трафик. `meridian node add` выбирает соседа так же. Цель, которую вы передаёте с `--sni`, никогда не меняется; если трафик не проходит, развёртывание останавливается и сообщает вам. Переразворачивание сохраняет сохранённую цель.

Чтобы увидеть кандидатов самостоятельно, отсканируйте IPv4-окрестность сервера:

```
meridian scan 198.51.100.10
```

Сканирование запускает закреплённую, проверенную по контрольной сумме версию RealiTLScanner на сервере и выводит домены сертификатов, которые оно нашло поблизости. Затем развёртывайте с вашей выбранной целью:

```
meridian deploy 198.51.100.10 --sni dl.google.com
```

Для проверки одной цели вручную запустите `meridian check 198.51.100.10 --sni HOST`. Избегайте `apple.com` и `icloud.com` — их сети не соответствуют VPS провайдерам.

### Смена цели позже

Когда `meridian test --probe` сообщает, что SNI маскировки заблокирован, переключите выход на другую цель без повторного развёртывания. Meridian отклоняет `apple.com`, `icloud.com` и `www.microsoft.com` (его сертификат слишком велик для Reality), проверяет, что выход открывает новый сайт по TLS 1.3 с HTTP/2, показывает план изменений и применяет его. Старое имя заменяется сразу, а не остаётся рядом, потому что Reality-слушатель имитирует ровно один сайт. Приложения переключатся при следующем обновлении подписки (каждые 6 часов) или когда пользователь обновит подписку. Для промежуточного сервера используйте `meridian relay sni RELAY NEW_SNI`.

```
meridian node sni 198.51.100.10 www.cloudflare.com
```

### Ваш собственный домен (self-steal)

Вместо чужого сайта сервер может маскироваться под ваш собственный домен. Направьте на сервер A-запись только DNS (серое облако в Cloudflare, без проксирования) и разверните с `--self-steal`:

```
meridian deploy 198.51.100.10 --sni www.example.com --self-steal
```

Meridian выпускает для этого имени сертификат Let's Encrypt и отдаёт его с самого сервера. Проверка без ключа Reality или с любым незнакомым SNI получает этот сертификат и стандартную страницу 404 nginx — как у любого сервера nginx, на котором ещё ничего не опубликовано. Имя резолвится в этот сервер, сертификат подлинный, поэтому несоответствия не видно, и нет чужого сайта, который может упасть, сменить сертификат или попасть под блокировку сам по себе.

Перед изменениями Meridian проверяет с сервера, куда указывает имя. Он останавливается, если имя не резолвится (Let's Encrypt не сможет выпустить сертификат), и предупреждает, если оно указывает в другое место, например на прокси Cloudflare.

С `--domain` и без `--sni` домен выполняет обе роли: Reality маскируется под него, а XHTTP и WSS продолжают работать за ним. Но домен, проксируемый через Cloudflare, резолвится в адреса Cloudflare, поэтому для self-steal вместе с CDN используйте два имени: без проксирования для `--sni` и проксируемое для `--domain`. `meridian node add` и `meridian node sni` тоже принимают `--self-steal`. Промежуточные серверы со своим SNI по-прежнему маскируются под чужой сайт.

### Цель маскировки против домена

- **Цель маскировки** (`--sni`) — популярный веб-сайт, которым вы **не** владеете и под который маскируется Reality; или, с `--self-steal`, ваше собственное имя, указывающее на этот сервер.
- **Домен** (`--domain`) — домен, которым вы **владеете**, указывающий на ваш сервер. XHTTP и Hysteria2 переходят на него, и он добавляет путь WSS через CDN Cloudflare. См. [Domain mode](/ru/domain-mode/).

## Hysteria2

```
meridian deploy 198.51.100.10 --no-hysteria2
```

Каждое развёртывание включает Hysteria2 на UDP/443 с сертификатом вашего домена или IP-сертификатом сервера, если домена нет. Трафик Hysteria2 обёрнут в обфускацию salamander, поэтому цензоры видят случайные UDP-пакеты, а не QUIC. Это помогает на нестабильных каналах и при большой задержке; там, где UDP заблокирован, приложения переключаются на TCP-методы, идущие перед ним в подписке. `--no-hysteria2` отключает его. Через промежуточные серверы Hysteria2 не проходит.

## Оформление страницы

Персонализируйте страницы подключения, чтобы получатели видели, кто настроил для них VPN:

```
meridian deploy 198.51.100.10 --display-name "Alice's VPN" --icon 🚀 --color sunset
```

- **`--display-name`** — отображается в шапке и заголовке страницы
- **`--icon`** — эмодзи или URL изображения в верхней части страницы
- **`--color`** — цветовая палитра: `ocean` (по умолчанию), `sunset`, `forest`, `lavender`, `rose`, `slate`

Оформление сохраняется в `cluster.yml` и применяется ко всем страницам подключения.

## Повторное развёртывание

Чтобы обновить конфигурацию сервера, запустите ту же команду ещё раз. Meridian сохраняет пути, ключи и пользователей, поэтому выданные ранее ссылки продолжают работать. Повторное развёртывание без `--sni` оставляет прежний сайт маскировки.

В конце каждого развёртывания Meridian выводит готовую команду для повторного запуска с вашими текущими параметрами. Если запустить её с другими флагами, конфигурация сервера обновится: например, добавление или удаление `--domain` либо `--no-hysteria2` добавит или уберёт соответствующие маршруты.

`meridian deploy` повторно разворачивает только тот сервер, который уже является выходом среди ваших серверов. Чтобы добавить ещё один сервер, используйте `meridian node add NEW_IP`. Если ваши серверы ещё работают на панели Remnawave, deploy сначала предложит перевести их на сервис управления (см. [Переход с Remnawave](#переход-с-remnawave)).

## Правка серверов через файл

Чтобы изменить сразу несколько вещей или хранить схему ваших серверов в системе контроля версий, выгрузите её, отредактируйте и загрузите обратно:

```bash
meridian fleet export > fleet.yml
$EDITOR fleet.yml
meridian fleet import fleet.yml
```

Импорт показывает каждое изменение до того, как что-либо произойдёт:

```
  + client carol
  ~ exit-2 sni www.example.com -> www.example.org
  → Применить? [y/N]
```

Файл называет серверы сохранёнными именами и не содержит ключей, учётных данных, ссылок и транспортных путей, поэтому его можно хранить в репозитории. Серверы, которые он называет, нужно сначала сохранить (`meridian server add`). Что импорт отклоняет, описано в [`fleet import`](/ru/cli-reference/#meridian-fleet).

## Предварительная проверка

Не уверены, подходит ли сервер?

```
meridian check 198.51.100.10
```

Команда проверяет сайт маскировки, свободен ли порт 443 и доступен ли он снаружи, DNS домена (если указан), ОС, место на диске и точность системных часов — без установки каких-либо пакетов.

## Развёртывание от имени обычного пользователя

```
meridian deploy 198.51.100.10 --user ubuntu
```

Команды выполняются через `sudo`, поэтому пользователю нужен `sudo` без пароля.

## Локальное развёртывание

Если вы вошли на сам сервер под `root`:

```
meridian deploy local
```

В этом режиме SSH не используется. Так же работают `check local`, `scan local` и `doctor local`, а после развёртывания последующие команды на этом сервере тоже выполняются локально. Тем не менее рекомендуется запускать Meridian со своего компьютера, поскольку для `meridian test` нужна проверка снаружи.

## Cloudflare WARP

WARP направляет исходящий трафик вашего сервера через сеть Cloudflare, поэтому сайты видят адрес Cloudflare вместо IP вашего VPS.

```
meridian deploy 198.51.100.10 --warp
```

**Когда WARP полезен:** если сайты блокируют диапазоны IP дата-центров или вы хотите скрыть адрес VPS от целевых сайтов.

**Когда он не нужен:** большинство сайтов отлично открываются и без него, а лишний узел (VPS → Cloudflare → сайт) добавляет небольшую задержку.

Meridian устанавливает клиент `cloudflare-warp` в прокси-режиме (SOCKS5 на `127.0.0.1:40000`) и направляет через него исходящий трафик Xray. Входящие подключения при этом не меняются. WARP бесплатен и не требует аккаунта Cloudflare.

### WARP только для выбранных сайтов

Чтобы пустить через WARP только отдельные сайты, а остальной трафик отправлять напрямую, добавьте правило маршрутизации на выходе вместо включения WARP для всего трафика. При первом таком правиле Meridian сам установит и настроит WARP на выходе:

```
meridian route add exit-1 --via warp chatgpt.com netflix.com
meridian route add exit-1 --via block geosite:category-ads-all
meridian route list
meridian route remove exit-1 warp
```

В качестве значений можно указывать домены (включая поддомены), списки `geosite:NAME` или `geoip:NAME` из стандартных баз v2fly; в одном правиле используется один тип значений. `--via direct` делает обратное на выходе с включённым WARP: выбранные направления идут мимо WARP. Правила проверяются в порядке добавления — до маршрута по умолчанию и до геоблокировки. Эти правила работают на сервере независимо от клиентских правил, которые пускают российские сайты напрямую с устройства пользователя, и от правил шлюза маршрутизации, которые могут выпускать трафик напрямую со шлюза внутри страны ([Раздельная маршрутизация](/ru/split-routing/#через-шлюз-маршрутизации)).

### AI-сервисы

AI-сервисы (ChatGPT, Claude, Gemini, Cursor и другие) отказывают части хостинговых адресов, а сессия, чей адрес прыгает между странами или на миг показывает домашнее подключение из России, может закончиться выходом из аккаунта или его блокировкой. Одно правило отправляет их все через WARP:

```
meridian route add exit-1 --preset ai
```

Пресет — это одно правило с именем `ai`, в которое входят `geosite:category-ai-!cn`, `anthropic`, `openai`, `cursor` и `google-gemini`; добавьте `--via direct`, чтобы оставить их на собственном адресе выхода. WARP выходит в интернет в регионе выхода, поэтому держите пользователей AI-сервисов на выходах в одной стране. Серверное правило не поймает трафик, который устройство отправляет мимо VPN: на macOS Happ может на мгновение пустить трафик напрямую после открытия крышки. Если сервисы Google всё равно считают, что вы в России, запрос на смену страны аккаунта в справке Google Аккаунта обычно помогает за несколько часов.

## Геоблокировка

По умолчанию сервер блокирует обращение через VPN к российским доменам (`geosite:category-ru`) и российским диапазонам IP (`geoip:ru`). Это не даёт IP-адресу вашего VPS светиться в логах российских сервисов и снижает риск блокировки.

Отключите её, если вашим пользователям нужно открывать российские сайты через Meridian:

```
meridian deploy 198.51.100.10 --no-geo-block
```

О том, как открывать российские сайты напрямую, не отключая геоблокировку, читайте в разделе [Раздельная маршрутизация](/ru/split-routing/).

## Адреса клиентов

Сервис управления никогда не хранит IP-адреса клиентов или журналы подключений. Каждое TCP-соединение попадает к Xray через nginx на сервере. По умолчанию сохраняются суммарный трафик за всё время и последняя активность; [Конфиденциальность](/ru/privacy/) позволяет включить ежедневную историю и ограничение устройств с объяснением раскрываемых данных.

## Добавление промежуточного сервера

После запуска выхода добавьте промежуточный сервер у российского провайдера, чтобы у пользователей осталась точка входа, если зарубежный IP заблокируют. См. [Промежуточные серверы](/ru/relay/).

```
meridian relay add 203.0.113.10 --exit 198.51.100.10
```

## Веб-консоль

Вместе с сервисом управления работает веб-консоль для одного владельца — для вас. Она находится на случайном секретном пути, отдельно от пути страниц подключения, поэтому ссылки, которыми вы делитесь, никогда её не раскрывают. `meridian panel` выводит её адрес, а пока у консоли нет владельца — ещё и одноразовую ссылку настройки:

```
  Meridian console
  URL         https://198.51.100.10/<secret-path>/
  Setup link  https://198.51.100.10/<secret-path>/#setup=…
              Works once, for 15 minutes. Open it to choose the owner's password.
```

Выбрав пароль, можно включить код входа из приложения-аутентификатора. В консоли вы добавляете людей, делитесь их ссылками и QR-кодами, задаёте лимиты и сроки действия и создаёте API-токены; серверы, ревизии и название подписки показаны только для чтения, вместе с командой `meridian`, которая их меняет. См. [Веб-консоль](/ru/client-management/#веб-консоль).

Храните адрес консоли как пароль. Если вы потеряли пароль или аутентификатор, `meridian panel --setup-link` выведет ссылку сброса: она задаёт новый пароль, отключает код входа и завершает сеансы на всех устройствах.

## Резервные копии

В конце первого развёртывания Meridian один раз показывает ключ восстановления:

```
  Recovery key (shown once; Meridian keeps no copy)

    AGE-SECRET-KEY-1…

  Write it down or print it, and keep it offline, away from this computer.
```

Храните его офлайн, отдельно от компьютеров, которые управляют вашими серверами. После каждого изменения Meridian сохраняет на вашем компьютере зашифрованный снимок сервиса управления, который можно прочитать ключом вашего компьютера или ключом восстановления. Если сервер управления когда-нибудь пропадёт, [`meridian restore`](/ru/recovery/#сервер-управления-потерян) восстановит его на новом сервере из свежего снимка.

## Обновления

Сервис управления и агент узла поставляются вместе с Meridian. После `meridian update` выполните `meridian fleet upgrade`: команда покажет, что изменится, затем переведёт сервис управления на новую версию и обновит каждого агента на месте, сохранив идентичность узлов. Заодно она переводит промежуточные серверы на новейший выпуск Realm, не дожидаясь обновления Meridian. Любой `meridian apply` тоже подтягивает сервис управления и агентов до установленной версии Meridian.

## Переход с Remnawave

Серверы, развёрнутые более ранним выпуском Meridian 4, работают на панели Remnawave. `meridian migrate` переводит их на сервис управления на месте, на тех же серверах:

```
meridian migrate
```

Команда делает резервную копию базы панели (на ваш компьютер и на сервер управления), переносит каждого клиента с его ключами, статусом, лимитами, сроком действия и трафиком, заменяет контейнер каждого узла агентом и, прежде чем удалить Remnawave, проверяет, что ни одна ссылка подписки не изменилась. Клиенты сохраняют свои ссылки и ничего не замечают. Данные, которые были только в панели — списки устройств HWID, история трафика по дням, настройки плагинов, — не переносятся, а передача IP-адресов клиентов (она обслуживала лимиты панели по IP) отключается; проверка перед запуском перечисляет их. Переход можно продолжить: если он остановился, снова запустите `meridian migrate`. См. [`meridian migrate`](/ru/cli-reference/#meridian-migrate).
