## Предварительные требования

Вам понадобятся:
- **VPS** на Debian или Ubuntu (с доступом по SSH ключу под root)
- **Терминал** на вашем локальном компьютере (macOS, Linux или [WSL в Windows](/docs/ru/wsl/))

## Установить CLI

```
curl -sSf https://getmeridian.org/install.sh | bash
```

Это установит команду `meridian` через [uv](https://docs.astral.sh/uv/) (предпочтительно) или pipx.

Можно запустить на своём компьютере или прямо на VPS. Рекомендуется локальная машина — с неё можно выполнить `meridian test` извне, и учётные данные останутся на вашем устройстве.

## Развернуть

Для новой управляемой топологии V4 используйте `meridian setup`: intent становится авторитетным графом серверов, маршрутов и access users. Команда `meridian deploy` ниже сохраняет быстрый legacy-путь развёртывания одного хоста.

```
meridian deploy
```

Интерактивный мастер спросит ваш IP-адрес сервера, SSH пользователя и цель маскировки (SNI). Для всего предусмотрены умные значения по умолчанию.

Или укажите всё заранее:

```
meridian deploy 198.51.100.10 --sni www.microsoft.com
```

Если вы запускаете команду прямо на VPS под root, SSH пропускается:

```
meridian deploy local
```

## Что происходит

1. **Устанавливает Docker** и развёртывает Xray под управлением панели Remnawave
2. **Генерирует x25519 пару ключей** — уникальные ключи для аутентификации Reality
3. **Укрепляет защиту сервера** — брандмауэр UFW, вход по SSH только с ключом, управление перегрузкой BBR
4. **Конфигурирует VLESS+Reality** на порту 443 — выдаёт себя за настоящий TLS сервер
5. **Включает транспорт XHTTP** — дополнительный слой скрытности, маршрутизируется через nginx
6. **В legacy развёртывает PWA-страницу** с QR-кодами; V4 передаёт канонический URL подписки без отдельной страницы

## Где что лежит

Meridian подключается к VPS по SSH (или работает прямо на нём через `deploy local`). После развёртывания состояние кэшируется локально:

| Что | Где |
|------|-------|
| Топология, токен панели и ключи | `~/.meridian/cluster.yml` на вашей машине |
| SSH-профили серверов | `~/.meridian/servers.json` на вашей машине |
| Прокси-сервисы | Docker, Xray, nginx на VPS |

`meridian client add alice` в legacy создаёт пользователя панели, а в V4 добавляет его в access intent и применяет план. Большинство операций используют API Remnawave; SSH нужен только для работы с legacy PWA-страницами. Если серверов несколько, указывайте `--server NAME` только для команд, которые работают с сервером.

## Подключиться

Legacy deploy выводит URL подписки и, после успешной загрузки, ссылку на PWA-страницу. V4 setup всегда выдаёт канонический URL подписки и не заявляет о наличии legacy PWA-страницы.

Установите одно из этих приложений, затем отсканируйте QR-код или нажмите «Открыть в приложении»:

| Платформа | Приложение |
|----------|-----|
| iOS | [v2RayTun](https://apps.apple.com/app/v2raytun/id6476628951) |
| Android | [v2rayNG](https://github.com/2dust/v2rayNG/releases/latest) |
| Windows | [v2rayN](https://github.com/2dust/v2rayN/releases/latest) |
| Все платформы | [Hiddify](https://github.com/hiddify/hiddify-app/releases/latest) |

## Добавить ещё пользователей

```
meridian client add alice
```

Каждый клиент получает собственный доступ и подписку. `client list` в V4 показывает только объявленных access users. `client remove alice` поддерживается в legacy; V4 пока отклоняет безопасное удаление управляемого пользователя, поэтому для немедленного временного отзыва используйте `client disable alice` (до следующего `meridian apply`).

## Управление серверами

Когда вы управляете несколькими VPS:

```
meridian server list                # просмотр всех серверов
meridian server add 198.51.100.11  # добавить существующий сервер
meridian server remove finland     # удалить из реестра
```

Флаг `--server` позволяет указать конкретный сервер для команд, которые работают с ним напрямую: `meridian doctor --server finland`.

## Декларативный процесс

V4 хранит проверенную модель флота в `topology_intent` файла `cluster.yml`. Создавайте или изменяйте её через `meridian setup`; intent описывает control plane, выходные узлы, цепочки маршрутизации, пути протоколов и пользователей доступа. Команда `plan` показывает будущие изменения скомпилированных ресурсов, а `apply` приводит их к нужному состоянию.

```
meridian plan                      # показать изменения скомпилированных ресурсов
meridian apply --yes               # применить проверенную топологию
```

`meridian plan` завершается с кодом `0`, когда кластер сошёлся, и с кодом `2`, когда ожидаются изменения, поэтому его можно использовать в CI. Для типизированного плана запускайте `meridian plan --json`, а для итога исполнения в process- или UI-клиенте — `meridian apply --json --yes`. Обе команды используют конверт `meridian.output/v1`. Все опции описаны в [справочнике CLI](/docs/ru/cli-reference/#meridian-plan).

Legacy-кластеры по-прежнему поддерживают необязательное согласование `desired_nodes`, `desired_relays` и `desired_clients`. Эти поля не являются источником истины для V4. Аннотированный пример состояния смотрите в [`cluster.example.yml`](https://github.com/getmeridian/meridian/blob/v4/cluster.example.yml).
