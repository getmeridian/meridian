## Какую команду выбрать для диагностики

```
ПЕРЕД УСТАНОВКОЙ               → meridian check IP
  «Подойдёт ли этот сервер для установки Meridian?»
  Проверяет: доступность сайта маскировки (SNI), порт 443, DNS, ОС и место на диске.

ПОСЛЕ УСТАНОВКИ: ВСЁ ЛИ В НОРМЕ? → meridian check
  «Исправны ли сервис управления, агенты, промежуточные серверы, порты и сертификаты?»
  Проверяет каждый сервер по его роли через SSH.

НЕ РАБОТАЕТ ПОДКЛЮЧЕНИЕ        → meridian test IP
  «Проходит ли трафик через VPN из моей текущей сети?»
  Проверяет: порты приёма, TLS/SNI, выдачу подписки и реальное прохождение трафика через каждый протокол.
  SSH не требуется — запускается прямо с клиентского компьютера.

ПРОВЕРКА ГЛАЗАМИ ЦЕНЗОРА       → meridian test IP --probe
  «Не выдаёт ли сервер признаки прокси или панели управления при внешнем сканировании?»
  Проверяет: открытые порты, ответы TLS/HTTP, секретные пути, SNI и совпадение DNS.
  SSH не требуется — запускается с клиентского компьютера.

СБОР ПОЛНОГО ОТЧЁТА ДЛЯ ОТЛАДКИ → meridian doctor IP
  «Собрать всю техническую информацию для разбора проблемы.»
  Собирает: версию ОС, статус служб Meridian, логи агента и nginx, порты, правила файрвола, SNI и DNS.
```

Добавьте флаг `--ai` к командам `check` или `doctor`, чтобы скопировать в буфер обмена готовый диагностический запрос для ИИ-ассистента.

## Не подключается совсем

### Порт 443 недоступен

**Возможные причины:**
1. Внешний файрвол облачного провайдера (Security Group) блокирует входящие соединения на порт 443
2. Интернет-провайдер пользователя заблокировал IP-адрес сервера
3. Сервер выключен или службы VPN остановлены
4. Файрвол UFW на самом сервере блокирует порт 443

**Что сделать:**
1. Проверьте панель управления хостинга — убедитесь, что входящие соединения на порт 443 (TCP и UDP) разрешены
2. Проверьте подключение из другой сети (например, с мобильного интернета вместо домашнего Wi-Fi)
3. Подключитесь к серверу по SSH и проверьте службы: `systemctl status ctld netagent netcore nginx` и `ss -tlnp sport = :443`
4. Проверьте статус UFW: `ufw status` — порт `443/tcp` должен быть в состоянии `ALLOW`

### Ошибка рукопожатия TLS (TLS handshake)

**Возможные причины:**
1. Служба Xray (`netcore`) не запущена
2. Порт 443 перехвачен сторонней службой
3. С самого сервера не открывается выбранный сайт маскировки (SNI)

**Что сделать:**
1. Проверьте логи узла: `meridian logs IP -c node -n 20`
2. Убедитесь, что порт 443 слушает именно nginx: `ss -tlnp sport = :443`
3. Проверьте доступность сайта маскировки с сервера: `meridian check IP --sni HOST`

### Не работает подключение через домен

**Возможные причины:**
1. A-запись домена не указывает на IP-адрес сервера
2. Служба nginx остановлена или не удалось выпустить TLS-сертификат
3. Ошибка в конфигурации маршрутизации nginx

**Что сделать:**
1. Проверьте разрешение имени в DNS: `dig +short yourdomain.com @8.8.8.8`
2. Проверьте состояние nginx: `systemctl status nginx`
3. Проверьте конфигурационные файлы nginx: `ls /etc/nginx/stream.d/ /etc/nginx/sites-enabled/` (файлы Meridian начинаются с `meridian-v4-`) и выполните `nginx -t`

## Соединение обрывается через несколько секунд

**Возможные причины:**
1. Проблемы с размером пакета (MTU) на маршруте
2. Провайдер принудительно сбрасывает длительные TLS-сессии к зарубежным IP

**Что сделать:**
1. Проверьте работу из другой сети
2. Переключитесь на маршрут XHTTP, WSS (в режиме домена) или через промежуточный сервер (`via relay`)

## Ошибки при развёртывании (`deploy` / `apply`)

### «No traffic passes through it»

Сервер был настроен, но контрольная прокачка трафика через указанный во флаге `--sni` сайт маскировки не прошла. Подберите другой сайт из собственной подсети сервера с помощью `meridian scan IP` и запустите `deploy` с новым значением `--sni` (без явного `--sni` Meridian автоматически перебирает найденные в подсети сайты, а затем `www.google.com`, `dl.google.com` и `www.cloudflare.com`).

### «The server cannot reach any Reality camouflage target»

С сервера не проходит исходящее соединение по HTTPS (TLS 1.3) к стандартным сайтам маскировки. Проверьте правила исходящего файрвола у хостинг-провайдера или укажите заведомо доступный с этого сервера сайт через `--sni`.

### Установка прервалась на полпути

Все шаги развёртывания и применения плана сохраняют контрольные точки. Устраните причину сбоя и запустите ту же команду повторно — уже выполненные шаги будут пропущены.

### Конфликт на порту 443

Порт 443 уже занят другой программой (например, предустановленным Apache или сторонней конфигурацией nginx). Остановите лишнюю службу или используйте чистый образ ОС. Команда `meridian check IP` подскажет, какой именно процесс занимает порт.

### Остановка при переходе с панели Remnawave

Команда `meridian migrate` сохраняет контрольную точку после каждого этапа. Устраните причину ошибки и запустите `meridian migrate` снова — миграция продолжится с места остановки. Перед началом переноса база данных панели сохраняется в `~/.config/meridian/backups/` на вашем компьютере и в `/var/backups/meridian-migration/` на сервере управления. Если финальная сверка пользовательских ссылок не совпадёт, контейнер Remnawave останется на сервере (в остановленном виде) — в этом случае [создайте issue](https://github.com/getmeridian/meridian/issues) и приложите вывод `meridian doctor`.

### Ошибки подключения по SSH

Проверьте вход по SSH вручную: `ssh root@SERVER_IP`. Если вы подключаетесь не под `root`, передайте имя пользователя флагом `--user`. Если сервер принимает только пароль, запустите `meridian deploy` в интерактивном терминале (без `--yes`), чтобы Meridian сам сгенерировал и установил SSH-ключ (см. [Серверы только с паролем](/ru/deploy/#серверы-только-с-паролем)), либо один раз скопируйте свой ключ командой `ssh-copy-id root@SERVER_IP`.

### Агент узла не выходит на связь или не применяет настройки

Посмотрите логи агента (`netagent`) и Xray (`netcore`) командой `meridian logs IP -c node -n 50`. Две самые частые причины: конфликт внутренних портов на хосте либо отсутствие связи от выходного сервера к серверу управления по порту TCP 443.

**Решение:** запустите `meridian check IP`, выполните предложенные рекомендации, а затем запустите `meridian apply` — команда перевыпустит регистрацию агента, если его удостоверение было утеряно, и обновит бинарный файл при несовпадении версий. Текущий статус всех агентов отображается в `meridian fleet status` и на вкладке **Серверы** в веб-консоли.

### Недостаточно свободного места на диске

Для установки требуется не менее 2 ГБ свободного места. Очистите системные журналы и кэш пакетов на сервере: `journalctl --vacuum-time=1d`, `apt-get clean` и проверьте объём каталога `/var/log/`.

### Не выпускается сертификат для домена (режим домена)

Сертификат Let's Encrypt для домена может быть выпущен только тогда, когда A-запись домена указывает прямо на IP-адрес сервера (серое облако «DNS only» в Cloudflare на время первого развёртывания). Обновите DNS-запись, подождите 5–15 минут и повторите команду. Предварительно проверить DNS можно командой `meridian check IP --domain DOMAIN`.

## Раньше всё работало, а теперь перестало

**Самая частая причина:** IP-адрес сервера попал под блокировку. Запустите `meridian test IP` из сети, где пропала связь: команда покажет, на каком именно этапе возникает сбой (доступность TCP, рукопожатие TLS/SNI, получение подписки или передача трафика).

Способы быстрого восстановления работы (добавление нового выходного сервера, перенос узла, подключение промежуточного сервера или CDN Cloudflare) подробно описаны в разделе [Восстановление при блокировке IP](/ru/recovery/).

Другие возможные причины:
- После перезагрузки VPS одна из служб не поднялась → выполните `meridian plan` и `meridian apply` (или перезапустите службы вручную: `systemctl restart ctld netagent nginx`)
- На сервере закончилось место на диске → проверьте `df -h /` и очистите логи `journalctl --vacuum-time=1d`
- Сервер управления безвозвратно утерян → восстановите его на новом IP из резервного снимка командой `meridian restore` ([Сервер управления потерян](/ru/recovery/#сервер-управления-потерян))
- VPN подключается и открывает ресурсы по IP-адресу, но не открывает сайты по доменным именам → с выходного сервера недоступны все три зашифрованных DNS-резолвера (Cloudflare, Quad9, Google). Запустите `meridian check`, посмотрите блок **Encrypted DNS** и откройте исходящий порт TCP 443 к указанным адресам в файрволе хостинг-провайдера

## Низкая скорость соединения

1. Выберите локацию сервера географически ближе к пользователям (для европейской части России обычно лучше всего подходят Финляндия, Швеция, Нидерланды и Германия)
2. Проверьте загрузку процессора и канала на самом VPS (`htop`, `uptime`)
3. Попробуйте переключиться между маршрутами Reality, Hysteria2 и XHTTP/WSS
4. Убедитесь, что на сервере активен алгоритм BBR: `sysctl net.ipv4.tcp_congestion_control`

**Не запускайте** на том же сервере незамаскированные протоколы (OpenVPN, стандартный WireGuard) — они быстро привлекают внимание систем DPI ко всему IP-адресу.

## Диагностика с помощью ИИ

```
meridian doctor --ai
```

Команда собирает полную диагностическую сводку (автоматически удаляя из неё все пароли, токены и секретные пути) и копирует в буфер обмена готовый промпт для вставки в ChatGPT или Claude.

Чтобы собрать чистый отчёт для публикации в [GitHub Issues](https://github.com/getmeridian/meridian/issues), выполните:

```
meridian doctor
```

## Не работает промежуточный сервер

Типовые неполадки промежуточных серверов (занятый порт, закрытый внешний файрвол, отсутствие связи с выходным сервером) разобраны в разделе [Промежуточные серверы — Устранение неполадок](/ru/relay/#устранение-неполадок).

## Расшифровка проверок `meridian check` (перед установкой)

| Проверка | Что проверяется | Что делать при ошибке |
|-------|--------------|-------------|
| Camouflage target | Доступен ли сайт маскировки с сервера по TLS 1.3? | Проверьте исходящий доступ с VPS или выберите другой сайт через `--sni` |
| Camouflage target DNS | Разрешается ли домен сайта маскировки через системный DNS сервера? | Проверьте настройки DNS на VPS или укажите другой сайт маскировки |
| Port 443 | Свободен ли порт 443 (или занят самим Meridian)? | Остановите сторонний веб-сервер на порту 443 или используйте чистую ОС |
| Port 443 from outside | Проходят ли входящие соединения на порт 443 из интернета? | Откройте входящий порт 443/TCP в панели управления облачного провайдера |
| Domain DNS | Указывает ли A-запись домена на IP-адрес сервера? | Исправьте A-запись в настройках DNS и отключите проксирование на время выпуска сертификата |
| Server OS | Установлена ли поддерживаемая ОС (Debian / Ubuntu)? | Переустановите образ сервера на актуальный Debian или Ubuntu |
| Disk space | Свободно ли хотя бы 2 ГБ на диске? | Освободите место на диске |
| Clock sync | Расхождение времени между вашим компьютером и сервером меньше 1 минуты? | Включите синхронизацию времени по NTP на сервере и автоматическое время на устройстве |

## Расшифровка разделов отчёта `meridian doctor`

| Раздел | На что смотреть |
|---------|-----------------|
| Local Machine | Версия ОС и окружения на вашем компьютере |
| Server | Версия ОС на VPS, время работы с последней перезагрузки (`uptime`), свободная память и место на диске |
| Services | Работают ли службы `ctld` (сервис управления), `netagent` (агент узла) и `netcore` (Xray) |
| Exit node Logs | Ошибки запуска агента и Xray, проблемы с портами или чтением сертификатов |
| Listening Ports | На порту 443/TCP должен находиться процесс `nginx` |
| Firewall (UFW) | Для порта `443/tcp` (и `443/udp` при Hysteria2) должно быть активно правило `ALLOW` |
| Camouflage Target | Статус `CONNECTED` и валидная цепочка сертификатов TLS |
| Domain DNS | Домен должен разрешаться в IP-адрес вашего сервера |

## Расшифровка проверок `meridian test`

| Проверка | Успешно (`PASS`) | Ошибка или пропуск |
|-------|------|-----------------|
| TCP reachability | Все публичные TCP-порты принимают соединения | Блокировка со стороны провайдера, закрытый внешний файрвол или остановленный сервер |
| TLS/SNI camouflage | Сервер возвращает ожидаемый сертификат сайта маскировки | Ошибка маршрутизации SNI в nginx, проблема с сертификатом или подмена ответа на пути |
| Domain root | Корневой адрес домена возвращает защищённый ответ `403`/`404` | Ошибка DNS/nginx или посторонний сайт на домене |
| Subscription | Сервис управления выдал корректный профиль Xray JSON для активного клиента | Нет активных клиентов или сервис управления недоступен |
| Automatic fallback | Группа автоматического выбора успешно провела тестовый трафик | Сбой маршрутизации, ключей или всех точек входа |
| Protocol checks | Каждый отдельный протокол (Reality, XHTTP, WSS, Hysteria2) провёл реальный трафик | Блокировка конкретного протокола/порта (например, UDP для Hysteria2) или ошибка службы |

Полный прогон `meridian test` чередует независимые сервисы проверки внешнего IP-адреса и сверяет их с прямым запросом без прокси: если проверочные сервисы недоступны ни напрямую, ни через туннель, команда возвращает код `3` (недостаточно данных), а не ложную ошибку работы VPN. При необходимости свой проверочный URL можно задать через переменную `MERIDIAN_CONNECT_TEST_URL`.

При самом первом запуске `meridian test` может потребоваться до 120 секунд на загрузку и проверку контрольной суммы локального ядра Xray с GitHub (последующие запуски используют локальный кэш). Флаг `--timeout` (по умолчанию `5` с, допустимо `1`–`30` с) задаёт тайм-аут для каждой отдельной сетевой операции. Код возврата `0` означает полное прохождение всех проверок, `4` — обнаруженные ошибки, `3` — невозможность завершить проверку из-за нехватки внешних данных. Облегчённый режим `--basic` проверяет только сеть и TLS без запуска Xray и не тестирует UDP-протокол Hysteria2.

Если `meridian test` с вашего устройства проходит полностью, но приложение всё равно не подключается: обновите подписку (или заново отсканируйте QR-код), проверьте автоматическую синхронизацию времени на устройстве и убедитесь, что используете одно из рекомендуемых приложений (Happ, FlClashX, Clash Mi или Throne на компьютере).
