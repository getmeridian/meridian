## Суть задачи

По умолчанию Meridian включает **геоблокировку на выходном сервере**: сервер блокирует обращения через VPN к российским доменам (`geosite:category-ru`) и российским IP-адресам (`geoip:ru`). Это защищает IP-адрес вашего зарубежного VPS от попадания в логи российских сервисов, по которым сервер могут вычислить и заблокировать.

Однако если направлять на такой сервер вообще весь трафик устройства, российские сайты и приложения перестанут открываться при включённом VPN — пользователям пришлось бы постоянно выключать VPN для входа в банки, Госуслуги, Яндекс и другие внутренние сервисы.

## Решение: раздельная маршрутизация на самом устройстве

При раздельной маршрутизации приложение на устройстве пользователя отправляет запросы к российским ресурсам **напрямую** через обычного провайдера, а весь остальной трафик — через VPN-туннель:

```
Российские сайты → Устройство → Напрямую → Интернет (местный провайдер)
Остальной трафик → Устройство → VPN-туннель → VPS → Интернет
```

В результате вы получаете оба преимущества:
- **Защиту VPS** — серверная геоблокировка остаётся включённой как страховка
- **Бесперебойную работу российских сайтов** — трафик к ним идёт напрямую, минуя VPN

## Как это устроено в Meridian

По умолчанию для подписок задан режим **`ru-split`**. Профили Xray JSON, Mihomo и Stash направляют напрямую:

- адреса частных и локальных сетей (`geosite:private`, `geoip:private`)
- домены в зонах `.ru`, `.su` и `.рф`, а также список `geosite:category-ru`
- российские диапазоны IP-адресов (`geoip:ru`)

В профилях sing-box этот же режим реализован встроенными правилами для локальных подсетей и доменных зон `.ru`, `.su` и `.рф` (внешние базы geosite/geoip sing-box не скачивает, поэтому обращения к российским сервисам на международных доменах или по прямому IP могут идти через туннель).

В обоих режимах после правил прямого доступа блокируется протокол QUIC (UDP 443), чтобы приложения переходили на TCP. Кроме того, в обоих режимах в профилях **Xray JSON сохраняется правило прямого доступа для трафика BitTorrent** — это снижает риск жалоб правообладателей (abuse) хостинг-провайдеру вашего выходного сервера. Правило распознаёт стандартные рукопожатия BitTorrent (шифрованные пиры и трафик UDP DHT/uTP могут по-прежнему попадать в туннель). В форматах Mihomo, Stash и sing-box фильтрация по протоколу BitTorrent не поддерживается.

### Выбор режима маршрутизации

| Режим | Поведение на устройстве пользователя |
|--------|-----------------------|
| `ru-split` (по умолчанию) | Локальные сети и российские сайты/IP открываются напрямую; весь остальной трафик идёт через VPN |
| `full` | Весь интернет-трафик, включая российские ресурсы, идёт через VPN; локальные сети остаются прямыми |

```bash
meridian fleet routing
meridian fleet routing full --dry-run
meridian fleet routing full --yes
meridian fleet routing ru-split --yes
```

Запуск команды без аргументов выводит текущий режим и краткую справку по обоим вариантам. При смене режима команда обновляет топологию, показывает план изменений и после подтверждения применяет его. При запуске без терминала или с флагом `--json` укажите `--yes`; сочетание `--dry-run --json` вернёт план проверки без применения. Приложения пользователей получат новые правила при следующем плановом обновлении подписки (по умолчанию раз в 6 часов, задаётся в `delivery.update_interval_hours`) или сразу после ручного обновления подписки. Пошаговый мастер настройки использует `ru-split` по умолчанию.

При экспорте и импорте конфигурации (`fleet export` / `fleet import`) явный режим сохраняется в поле `delivery.client_routing: full`. Стандартное значение `ru-split` в файл не записывается (если удалить это поле из экспортированного файла, вернётся режим `ru-split`). В веб-панели текущий режим отображается в разделе «Настройки» вместе с командой CLI для его смены.

Обычные текстовые списки ссылок Base64 не содержат правил маршрутизации — в приложениях, использующих только Base64, раздельное туннелирование настраивается внутри самого приложения. Приложение Hiddify получает профиль в формате sing-box и применяет встроенные в него правила.

### Как соотносятся клиентские и серверные правила

Сервис управления формирует все профили подписок на основе единого списка правил и выбранного в топологии режима. Клиентская маршрутизация настраивается командой [`meridian fleet routing`](/ru/cli-reference/#meridian-fleet). Команда [`meridian route`](/ru/cli-reference/#meridian-route) управляет маршрутизацией исходящего трафика на самих выходных серверах, а правила для [шлюза маршрутизации](#через-шлюз-маршрутизации) задаются отдельно на уровне топологии.

## Как взаимодействуют клиентский и серверный уровни

| Уровень | Что делает | От чего защищает |
|-------|-------------|-----------------|
| **Геоблокировка на выходном сервере** | Отбрасывает трафик к российским ресурсам на сервере | От попадания IP-адреса вашего VPS в логи российских сервисов |
| **Раздельная маршрутизация на устройстве** | Направляет российский трафик напрямую с устройства | От поломки российских сайтов и лишней нагрузки на VPS |

В режиме `ru-split` запросы к российским ресурсам уходят напрямую с устройства и вообще не попадают на выходной сервер. Если же приложение не поддерживает правила маршрутизации (например, при импорте ссылок Base64), сработает серверная геоблокировка на выходном сервере.

Переключение в режим `full` меняет правила только на устройствах пользователей. Если вам нужно, чтобы российские сайты действительно открывались через зарубежный выходной сервер, необходимо также отключить на этом сервере геоблокировку при развёртывании (`--no-geo-block`). Смена клиентского режима сама по себе серверную геоблокировку не отключает.

## Через шлюз маршрутизации

Шлюз маршрутизации (настраивается через `meridian setup`) — это сервер с Xray, стоящий перед вашими выходными серверами и распределяющий трафик по правилам. Каждое правило может направить трафик на конкретный выходной сервер, в пул выходных серверов, **напрямую со шлюза** или заблокировать его. Если такой шлюз расположен в России, правило прямого выхода позволяет открывать российские сайты с российского IP-адреса самого шлюза — даже в тех клиентских приложениях, которые не поддерживают клиентские правила маршрутизации:

Чтобы трафик к российским ресурсам доходил до правил шлюза, для клиентской маршрутизации следует выбрать режим `full` (в режиме `ru-split` он уйдёт напрямую ещё на самом устройстве).

```
Российские сайты → Устройство → Шлюз (в России) → Интернет
Остальной трафик → Устройство → Шлюз → Выходной сервер (за рубежом) → Интернет
```

На шаге настройки маршрутизации в `meridian setup` добавьте правила для доменных зон `ru, su, рф`, списка сайтов `category-ru` (российские сервисы на международных доменах) и страны `RU` (российские IP-диапазоны для подключений напрямую по IP), выбирая для каждого из них действие **напрямую со шлюза**. Правила по доменам и спискам `geosite` проверяют имя хоста без DNS-запроса, а правило по стране `geoip` предварительно разрешает доменное имя в IP-адрес на самом шлюзе. В файле топологии прямому выходу соответствует `"action": "direct"` без поля `target_ref`, доменным зонам — `"match": "domain"`, а спискам сайтов — `"match": "geosite"`. Правила проверяются сверху вниз до первого совпадения.

Поскольку такой трафик покидает сеть прямо со шлюза и не доходит до зарубежного выходного сервера, геоблокировку на выходном сервере можно оставить включённой. Учитывайте, однако, что в отличие от промежуточного сервера (relay), шлюз сам обращается к целевым сайтам: российские ресурсы будут видеть IP-адрес шлюза, а возможные претензии к трафику пойдут хостинг-провайдеру шлюза (см. [Выбор хостинга](/ru/hosting/)).

## Особенности работы DNS

В профилях Xray JSON доменные имена, не совпавшие с правилами прямого доступа, разрешаются через VPN-туннель, поэтому DNS-запросы к зарубежным сайтам не видны местному интернет-провайдеру. В профилях Mihomo при режиме `ru-split` проверка российских IP-диапазонов применяется только к соединениям, установленным напрямую по IP-адресу, чтобы не вызывать локальных DNS-запросов для остальных доменов. Если в используемом приложении есть отдельная настройка защиты от утечек DNS (DNS leak protection), рекомендуем включить её.


## Именованные политики и DNS

Добавьте `delivery.delivery_policies` в экспортированный файл конфигурации и проверьте изменения через `meridian fleet import`. У каждой политики есть `id`, встроенная основа `preset` (`full` или `ru-split`), упорядоченные `rules` и необязательный раздел `dns`. Укажите имя в `delivery.default_policy` или выберите его командами `meridian fleet routing work --dry-run` и `meridian fleet routing work --yes`. Встроенные политики заменить нельзя. Для существующих конфигураций подписки обоих режимов остаются прежними.

Пример раздела `delivery`:

```json
{
  "delivery_policies": [{
    "id": "work",
    "preset": "full",
    "rules": [{
      "match": {"kind": "domain_suffix", "values": ["example.test"]},
      "action": {"kind": "block"}
    }],
    "dns": {
      "resolvers": [{"transport": "doh", "address": "198.51.100.53", "path": "/dns-query"}],
      "fake_ip": false
    }
  }],
  "default_policy": "work"
}
```

Здесь указан адрес из диапазона для документации — замените его адресом своего DNS-сервера. Словарь `profile_policies` связывает имена профилей доступа, включая `default`, с политиками. Профиль без записи использует общую политику. Если у пользователя несколько профилей с собственной политикой, все они должны выбирать одну и ту же. Выбор встроенного режима через `fleet routing` сбрасывает именованную политику по умолчанию. Удаление необязательных полей возвращает прежнее поведение встроенного режима.

Правила проверяют суффикс домена, точное доменное имя, фрагмент имени в ASCII, списки `geosite`/`geoip` из закреплённого набора данных, сети CIDR, порты назначения или TCP/UDP. Значения `match.kind`: `domain_suffix`, `domain_full`, `domain_keyword`, `geosite`, `geoip`, `cidr`, `port`, `network`. Порт задаётся объектом, например `{"start": 8443, "end": 8445}`; без `end` выбирается один порт. Для совпадения достаточно одного значения в списке. Необязательные условия `network` и `ports` дополнительно ограничивают всё правило. Сначала обходятся локальные сети, затем проверяются ваши правила в указанном порядке, после них — остальные правила встроенного режима. Действует первое совпадение.

Действия: `{"kind":"proxy"}` — через VPN, `{"kind":"direct"}` — напрямую, `{"kind":"block"}` — блокировать, `{"kind":"exit","exit":"west"}` — через объявленный выходной сервер. Группы выходного сервера включают только доступные пользователю подключения. Если в выданном профиле нужного сервера нет, подходящий трафик блокируется; другой сервер не подставляется. Отдельные профили Xray и группы альтернативных TLS-отпечатков сохраняют изоляцию. Распознавание BitTorrent остаётся приблизительным и доступно только в Xray.

Для DNS задаются `transport: doh | dot | plain`, одноадресный IP в `address` и необязательный `port` (по умолчанию 443, 853 или 53). У DoH есть ограниченный `path`, у обычного DNS — `protocol: udp | tcp`. Сертификат шифрованного DNS-сервера должен быть действителен для его IP. Доменные адреса, требующие начального DNS-запроса, учётные данные, произвольные шаблоны и регулярные выражения не принимаются. Xray поддерживает DoH и обычный DNS, но пропускает DoT и fake-IP; Mihomo и sing-box поддерживают все три транспорта и fake-IP; Stash сохраняет свой режим DNS и пропускает fake-IP. Base64 не передаёт маршрутизацию или DNS. Неподдерживаемый DNS-транспорт не заменяется менее защищённым.

В политике может быть до 128 правил, до 64 значений в доменном/IP-условии и до четырёх DNS-серверов; в каталоге — до 64 политик. Политика должна занимать не более 64 КиБ, весь каталог — не более 256 КиБ. Имена геосписков проверяются по закреплённым файлам, уже установленным в приложениях. Политики не добавляют загрузку удалённых наборов правил; sing-box пропускает geosite и geoip, кроме частных адресов. После применения изменений обновите подписку.


### Личная настройка маршрутизации

`meridian client routing person` показывает действующую политику. Проверьте личную настройку командой `meridian client routing person work --dry-run --json`, затем сохраните её через `meridian client routing person work --yes --json`. Команда `meridian client routing person --inherit --yes` сбрасывает личный выбор. Карточка пользователя в веб-панели использует ту же проверку сервиса и хранит черновик только в памяти. Личная настройка имеет приоритет над профилем доступа, а профиль — над общими настройками серверов. Применение конфигурации и перевыпуск данных подключения её сохраняют; зашифрованные снимки её включают, удаление пользователя — удаляет. Выбор меняет выдачу подписки при обновлении в приложении, без изменения аккаунта или прав доступа к узлам.

Для чтения нужны `people.read` и `people.private`, для назначения — ещё и `people.delivery`. Право `delivery.read` открывает проверенный каталог. Выданные токены сохраняют прежние зафиксированные права; для назначения выдайте токен с новым правом. Без приватного доступа настройка скрыта; подписки, события и проверенная конфигурация её не содержат. Предварительная проверка ничего не записывает. Подтверждение требует `review_hash`; после изменения личного выбора, профилей или каталога нужна новая проверка.

| Операция | Назначение |
| --- | --- |
| `GET /api/delivery-policies` | Проверенный каталог и настройки профилей; `delivery.read` |
| `GET /api/users/{username}/delivery-policy` | Личный выбор и действующая политика; `people.read` и `people.private` |
| `PUT /api/users/{username}/delivery-policy` | `{ "policy": "work", "confirm": false }` проверяет выбор; подтвердите с `review_hash`; нужны `people.delivery`, `people.read`, `people.private`. Явный `policy: null` включает наследование. |


## Предварительная проверка и объяснение маршрута

`meridian client preview person --suffix singbox --json` и предварительная проверка подписки в веб-панели показывают действующую политику, источник выбора, порядок правил и DNS для каждого формата, а также пропущенные возможности и причины. Необязательное поле адреса назначения объясняет выбранный формат. Для Xray отдельно указаны индивидуальные профили и группы отпечатков без нужного выходного сервера. Нумерация правил общая для всех форматов: сначала обход локальных сетей, затем ваши правила, после них — остальные правила встроенного режима. Один такой номер может соответствовать нескольким записям в конфигурации приложения.

```bash
meridian fleet routing set work --dry-run --json
meridian fleet routing explain chat.example.test:443 --person person --format singbox --json
meridian fleet routing explain 198.51.100.10 --format xray-json --port 443 --network tcp --protocol other --json
```

`fleet routing explain` читает применённые настройки сервиса и необязательный личный выбор пользователя. Результат указывает первое совпавшее правило и действие, например: «Трафик идёт через выходной сервер west: сработало правило 2». Без `--person` проверяется общая политика. `--format` выбирает Xray JSON, Mihomo/Clash, Stash, sing-box или Base64. Если не указано иное, предполагаются TCP и обычный трафик; `--protocol bittorrent` задаёт условный результат распознавания протокола. Запросы к DNS и сети, проверка доступности не выполняются. Если для более раннего правила нужен неизвестный порт или отсутствующие в кэше закреплённые геоданные, результат остаётся неопределённым. То же относится к имени, для которого правило Xray требует уже полученный IP. Выбор в приложении и доступность серверов могут изменить конкретное подключение автоматической группы.

| Формат / приложения | Условия назначения | DNS | fake-IP | Через выходной сервер | BitTorrent |
| --- | --- | --- | --- | --- | --- |
| Приложения Xray JSON | Все восемь типов | DoH, обычный | Не передаётся | В пределах выданного профиля | Приблизительное распознавание |
| Mihomo / Clash Meta | Все восемь | DoH, DoT, обычный | Да | Только основные подключения | Не передаётся |
| Stash | Все восемь | DoH, DoT, обычный | Собственный режим; заданный fake-IP не передаётся | Только основные подключения | Не передаётся |
| sing-box / Hiddify | Домены, CIDR, порты, TCP/UDP, частные IP | DoH, DoT, обычный | Да | Только поддерживаемые подключения | Не передаётся |
| Приложения с Base64-ссылками | Правил нет | Настроек нет | Нет | Правилами не выбирается | Нет |

Сервис читает геоданные только из уже сохранённых архивов Xray, проверенных по закреплённому хешу Meridian. Объяснение не запускает загрузку. Приложения не получают удалённых наборов правил. Xray отправляет запросы к заданным публичным DNS через автоматическую группу, сохраняя прямое обращение к локальным DNS; остальные клиенты используют представимые настройки DNS. Неподдерживаемый транспорт не заменяется обычным DNS. Содержимое прежних режимов и ответы эталонных запросов для конфигураций по умолчанию не меняются.

`POST /api/delivery-policies/explain` принимает `destination`, необязательный `person`, `format`, `port`, `network`, `protocol`. Нужно право `delivery.explain`, а при указании пользователя — ещё и `people.read` с `people.private`. Для подробностей политики или объяснения адреса в проверке подписки нужен приватный доступ; остальные права открывают только прежние метаданные. В `/info` страницы подключения может появиться `user.deliveryCapabilities`: названия форматов, признаки поддержки и коды пропущенных возможностей. Имена политик, личные настройки, профили, адреса назначения и данные подключений туда не входят. Страница хранит эти свежие сведения только в памяти.
