## سرور واسطه چه مشکلی را حل می‌کند

وقتی IP سرور خروجی مسدود می‌شود، کاربران دیگر به آن دسترسی ندارند. سرور واسطه یک نقطهٔ ورود داخلی فراهم می‌کند که معمولاً مسدود کردن آن دشوارتر است:

```
کاربر → سرور واسطه (IP داخلی) → سرور خروجی (خارج از کشور) → اینترنت
```

فیلترکننده اتصال به یک IP داخلی را می‌بیند. واسطه جریان خام TCP را به خروجی هدایت می‌کند؛ رمزنگاری از دستگاه کاربر تا خروجی سرتاسری است و واسطه محتوای رمزگشایی‌شده را نمی‌بیند.

## سرور واسطه چگونه کار می‌کند

سرور واسطه [Realm](https://github.com/zhboner/realm) را اجرا می‌کند؛ یک هدایت‌کنندهٔ سبک TCP که داده را بدون کپی اضافی در حافظه منتقل می‌کند. روی پورت 443، یا پورت انتخابی شما، اتصال می‌پذیرد و آن را به ورودی Reality خروجی می‌فرستد. اجزای دیگر Meridian، یعنی عامل گره و سرویس کنترل، روی سروری که فقط نقش واسطه دارد اجرا نمی‌شوند. Meridian آن را با SSH مدیریت می‌کند.

واسطه فقط ترافیک **Reality** را عبور می‌دهد. XHTTP، WSS و Hysteria2 روی آدرس و دامنهٔ خود خروجی باقی می‌مانند و در همان اشتراک به‌عنوان مسیرهای جایگزین ارائه می‌شوند.

## استقرار سرور واسطه

ابتدا خروجی را مستقر کنید، سپس واسطه را به آن متصل کنید:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10
```

Meridian واسطه را به توپولوژی اضافه می‌کند و تغییرات را اعمال می‌کند:

1. سرور را آماده می‌کند: بسته‌ها، BBR، ایمن‌سازی SSH و فایروالی که فقط SSH و پورت واسطه را باز می‌گذارد.
2. نسخهٔ ثابت Realm را پس از بررسی SHA-256 به‌صورت سرویس systemd نصب می‌کند.
3. هدایت ترافیک به ورودی Reality خروجی را تنظیم می‌کند.
4. مسیر واسطه را در اشتراک همهٔ کاربران قرار می‌دهد.

### گزینه‌ها

| گزینه | پیش‌فرض | توضیح |
|-------|---------|-------|
| `--exit/-e EXIT` | الزامی | IP یا نام سرور خروجی |
| `--name NAME` | خودکار | نام قابل تشخیص برای واسطه، مانند `ru-moscow` |
| `--port/-p PORT` | 443 | پورت پذیرش اتصال روی سرور واسطه |
| `--sni HOST` | هدف خروجی | سایت استتار Reality این واسطه؛ اگر وارد نشود، هدف خروجی استفاده می‌شود. |
| `--user/-u USER` | root | کاربر SSH روی واسطه |
| `--ssh-port PORT` | 22 | پورت SSH روی واسطه |
| `--yes/-y` | | رد شدن از پرسش‌های تأیید |

### نمونه با همهٔ گزینه‌ها

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-moscow \
  --port 443 --sni dl.google.com --user ubuntu --ssh-port 2222 --yes
```

## کاربران چگونه متصل می‌شوند

کاربران فعلی در تازه‌سازی بعدی اشتراک مسیر واسطه را دریافت می‌کنند و صفحهٔ اتصالشان هم آن را نمایش می‌دهد. کاربران جدید آن را خودکار دریافت می‌کنند:

```bash
meridian client add guest   # مسیر واسطه در اشتراک قرار می‌گیرد
```

## مدیریت سرورهای واسطه

```bash
meridian relay list                       # همهٔ واسطه‌ها
meridian relay list --exit 198.51.100.10  # واسطه‌های یک خروجی
```

اجزای مسیر را بررسی کنید: سرویس‌های Realm باید فعال باشند، هر گام به گام بعدی برسد و ورودی عمومی اتصال بپذیرد. سپس عبور ترافیک واقعی از کل مسیر را آزمایش کنید:

```bash
meridian check 203.0.113.10
meridian test
```

این بررسی هر بخش مسیر را هم اندازه می‌گیرد: از هر گام، صفحهٔ سایت استتار خروجی را از طریق گام بعدی و با همان SNI کاربران دریافت می‌کند و زمان اتصال، زمان رسیدن نخستین بایت و حجم دریافتی را گزارش می‌دهد. توقف انتقال در حدود 8 تا 32 کیلوبایت نشانهٔ محدودسازی همان بخش است و به‌صورت هشدار گزارش می‌شود؛ معمولاً با انتخاب میزبان واسطه در شبکه یا ASN دیگری رفع می‌شود. اگر صفحهٔ اصلی سایت کمتر از 32 کیلوبایت باشد، نتیجهٔ بررسی آن بخش نامشخص است و موفق تلقی نمی‌شود.

اگر `meridian test --probe` مسدود بودن SNI واسطه را گزارش کرد، آن را در همان سرور تغییر دهید. Meridian دسترسی خروجی به سایت جدید را بررسی می‌کند، تغییر را برای بازبینی نشان می‌دهد و اعمال می‌کند. نام قدیمی بلافاصله از کار می‌افتد و برنامه‌ها در تازه‌سازی بعدی اشتراک، هر 6 ساعت، یا پس از تازه‌سازی دستی به نام جدید می‌روند. برای استفادهٔ دوباره از هدف خروجی، SNI خود خروجی را وارد کنید:

```bash
meridian relay sni 203.0.113.10 dl.google.com
```

برای کنار گذاشتن واسطه، زنجیره‌هایی را که از آن عبور می‌کنند حذف کنید. Meridian موارد حذف را نشان می‌دهد، تأیید می‌خواهد و سرویس Realm، قواعد فایروال و ورودی‌های منتشرشده را پاک می‌کند. کاربران در تازه‌سازی بعدی اشتراک این مسیر را از دست می‌دهند:

```bash
meridian relay remove 203.0.113.10
```

## چند سرور واسطه

می‌توانید چند واسطه، مثلاً در شهرها یا شبکه‌های مختلف، به یک خروجی متصل کنید:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-moscow
meridian relay add 203.0.113.11 --exit 198.51.100.10 --name ru-spb
```

همهٔ آن‌ها در اشتراک کاربران قرار می‌گیرند. برای زنجیره‌ای با چند گام واسطه از `meridian setup` استفاده کنید.

## فهرست سفید در شبکه‌های موبایل

در برخی محدودیت‌های اینترنت موبایل روسیه، اپراتورها فقط سایت‌ها و آدرس‌های مجاز را عبور می‌دهند. وضعیت به اپراتور، منطقه و زمان بستگی دارد و اپراتورها فهرست خود را منتشر نمی‌کنند. Meridian این فهرست‌ها را تشخیص نمی‌دهد و دنبال نمی‌کند؛ تنظیمات و بررسی‌های زیر بر عهدهٔ شماست.

### تجربه‌های گزارش‌شده

- **شبکه‌ها یکسان نیستند.** برخی فقط نام سایت در SNI را بررسی می‌کنند و برخی IP مقصد را هم می‌سنجند. در حالت اول، Reality مستقیم با یک نام مجاز ممکن است کار کند؛ در حالت دوم، آدرس گام اول هم باید مجاز باشد.
- **آدرس‌های ابر داخلی معمولاً نقطهٔ ورود هستند.** همهٔ آدرس‌های یک میزبان مجاز نیستند: یک زیرشبکه ممکن است باز باشد و زیرشبکهٔ دیگر همان شرکت بسته. میزبان‌ها ممکن است حساب‌های شخصی، دفعات ساخت دوبارهٔ سرور یا پهنای باند را هم محدود کنند.
- **آدرس‌های CDN خارجی معمولاً در شبکه‌های موبایل مجاز نیستند.** [حالت دامنه](/fa/domain-mode/) از طریق Cloudflare را مسیر جایگزین اینترنت خانگی در نظر بگیرید؛ برای عبور از فهرست سفید روی آن حساب نکنید.
- **مسیر واسطه به خروجی هم ممکن است قطع شود.** دسترسی کاربر به واسطه تضمین نمی‌کند که واسطه به خروجی خارجی برسد.

### سایت‌های روی CDNهای روسی

سایت‌های پشت بعضی CDNهای روسی وضعیت فهرست سفید آن CDN را به ارث می‌برند. گزارش‌های اکتبر 2026 شامل **Beeline، EdgeCenter، Beget، Timeweb و Yandex** هستند. سایتی در این شبکه‌ها می‌تواند نام مجازی برای SNI واسطه باشد. همان سایت را هنگام فعال بودن محدودیت‌ها آزمایش کنید؛ نتیجه به اپراتور، منطقه و زیرشبکه بستگی دارد.

SNI مجاز در شبکه‌ای کمک می‌کند که نام را بررسی می‌کند. اگر IP مقصد هم بررسی شود، آدرس واسطه نیز باید مجاز باشد. استفاده از نام یک سایت روی CDN، Realm را پشت آن CDN قرار نمی‌دهد و IP دلخواه یک VPS را مجاز نمی‌کند.

### فهرست‌های سفید عمومی

جامعهٔ کاربران فهرست‌های `WHITE-SNI-RU` و `WHITE-CIDR-RU` را در [igareck/vpn-configs-for-russia](https://github.com/igareck/vpn-configs-for-russia) نگهداری می‌کند. آن‌ها گزینه‌هایی برای آزمایش هستند و فهرست رسمی اپراتور محسوب نمی‌شوند. این پیوند را خودتان باز می‌کنید؛ Meridian این فهرست‌ها را بارگیری نمی‌کند و به سرویس فهرست سفید متصل نمی‌شود.

### واسطه روی یک آدرس مجاز

سرور کوچکی نزد میزبان داخلی بگیرید که آدرسش در شبکه‌های موبایل کاربران باز باشد؛ [انتخاب میزبانی](/fa/hosting/) را ببینید. تنها آزمایش در همان شبکهٔ موبایل هنگام فعال بودن محدودیت‌ها دسترسی را ثابت می‌کند. سپس واسطه را با یک نام مجاز اضافه کنید:

```bash
meridian relay add 203.0.113.10 --exit 198.51.100.10 --name ru-mobile --sni allowed.example.com
```

با `--sni`، فقط ورودی این واسطه در اشتراک آن نام را اعلام می‌کند. Meridian روی خروجی یک ورودی اختصاصی، قابل دسترسی فقط از آخرین گام زنجیره، و یک ورودی Reality با همان کلیدها برای تقلید سایت می‌سازد. نام انتخابی به Reality هدایت می‌شود و بقیهٔ اتصال‌ها به سایت واقعی می‌روند؛ بنابراین آزمونگر بدون کلید معتبر گواهی واقعی سایت را می‌بیند. هدف استتار خود خروجی و ورودی‌های دیگر تغییر نمی‌کنند. خروجی باید سایت را با TLS 1.3 و HTTP/2 باز کند؛ بعداً می‌توانید نام را با `meridian relay sni RELAY NEW_SNI` تغییر دهید.

سپس واسطه را بررسی و اتصال را در شبکهٔ مورد نظر آزمایش کنید:

```bash
meridian check 203.0.113.10
meridian test
```

آزمایش از کامپیوتر خودتان نمی‌گوید یک شبکهٔ موبایل در حالت فهرست سفید چه چیزی را عبور می‌دهد. روی دستگاهی واقعی در همان شبکه آزمایش کنید.

### انتخاب SNI خروجی

گزینهٔ `--sni` در `meridian deploy` و `meridian node add` هدف استتار مسیر مستقیم Reality خروجی را تعیین می‌کند. خروجی باید سایت را با TLS 1.3 باز کند؛ استقرار عبور ترافیک واقعی را بررسی می‌کند و اگر ترافیک نگذرد متوقف می‌شود. پیش از استقرار از `meridian check IP --sni HOST` استفاده کنید. در شبکه‌ای که فقط نام را می‌سنجد، SNI مجاز ممکن است مسیر مستقیم را باز کند، اما باید هر نام را در شبکهٔ اپراتور آزمایش کنید.

### کارهایی که Meridian انجام نمی‌دهد

- تشخیص عضویت IP واسطه در فهرست یک اپراتور یا فعال بودن محدودیت‌ها.
- راه‌اندازی واسطه‌سازی از طریق CDN داخلی؛ حالت دامنه برای Cloudflare ساخته و آزمایش شده است.
- عبور XHTTP، WSS یا Hysteria2 از واسطه؛ واسطه فقط Reality را عبور می‌دهد و مسیرهای دیگر روی خروجی می‌مانند.
- ساخت تونل از طریق سرویس‌های تماس یا پیام‌رسان شخص ثالث.

## رفع مشکلات

### تداخل پورت

ممکن است سرویس دیگری پورت واسطه را گرفته باشد. با `ss -tlnp sport = :443` بررسی کنید و آن سرویس را متوقف کنید، یا با `--port 8443` پورت دیگری انتخاب کنید.

### مسدود بودن در فایروال

مطمئن شوید پورت واسطه علاوه بر UFW در فایروال یا گروه امنیتی میزبان ابری هم باز است.

### خروجی در دسترس نیست

واسطه باید به پورت Reality خروجی برسد. یک ابر روسی ممکن است مسیرش به VPS خارجی را از دست بدهد، در حالی که آدرس داخلی خودش همچنان باز است. کاربر می‌بیند «متصل است، اما چیزی باز نمی‌شود»: دسترسی به واسطه فقط سالم بودن گام اول را ثابت می‌کند.

از کامپیوتر مدیریت هر دو سرور را بررسی کنید، سپس ترافیک را از شبکهٔ دچار مشکل آزمایش کنید:

```bash
meridian check 203.0.113.10  # سرویس‌های واسطه و مسیر به خروجی
meridian check 198.51.100.10  # سرویس‌های خروجی، هدف استتار و DNS
meridian test 203.0.113.10  # ترافیک واقعی از مسیر واسطه
meridian test 198.51.100.10  # ترافیک واقعی مستقیم به خروجی
```

اگر خروجی بررسی‌ها را می‌گذراند و اتصال مستقیم هم کار می‌کند، اما بررسی گام بعدی از واسطه ناموفق است، مسیر خارجی یا فایروال میزبان واسطه را بررسی کنید. اگر سرویس‌ها یا DNS خود خروجی مشکل دارند، ابتدا خروجی را بازیابی کنید. اتصال مستقیم در شبکه‌ای که به واسطه نیاز دارد ممکن است خودش مسدود باشد؛ محل قطع مسیر را با نتایج بررسی گام‌ها از روی سرورها پیدا کنید. یک واسطهٔ دوم در شبکه‌ای دیگر یا خروجی دومی که از واسطه‌ها در دسترس است اضافه کنید تا قطع یک مسیر خارجی همهٔ مسیرها را از کار نیندازد.

### سرویس واسطه اجرا نمی‌شود

روی سرور واسطه، سرویس‌های هدایت ترافیک و گزارش‌هایشان را بررسی کنید. نام‌ها خنثی هستند: سرویس‌های `netfwd-*` و تنظیمات `/etc/netfwd/` به Meridian، Realm یا نقش واسطه اشاره نمی‌کنند.

```bash
systemctl list-units 'netfwd-*'
journalctl -u 'netfwd-*' --no-pager -n 20
```
