این راهنما تمام گزینه‌های `meridian deploy` را پوشش می‌دهد. اگر این استقرار اول شما است، با [Getting Started](/fa/getting-started/) شروع کنید.

## استقرار بنیادی

```
meridian deploy 198.51.100.10
```

یک سرور هم سرور کنترل (اجراکنندهٔ سرویس کنترل Meridian) و هم exit می‌شود که ترافیک را حمل می‌کند. Meridian همان توپولوژی بازبینی‌شده‌ای را می‌سازد که [`meridian setup`](/fa/cli-reference/#meridian-setup) تولید می‌کند و آن را با checkpoint اعمال می‌کند. پیش از چاپ «Done»، ترافیک واقعی را از طریق اشتراک تحویل‌شده عبور می‌دهد.

`meridian deploy` را بدون IP اجرا کنید و آن برای شما درخواست می‌کند. برای رد کردن تأیید‌ها `--yes` اضافه کنید:

```
meridian deploy 198.51.100.10 --client-name alice --yes
```

## سرورهای فقط با گذرواژه

Meridian با کلید SSH وارد می‌شود. بسیاری از ارائه‌دهندگان VPS فقط یک گذرواژهٔ root به شما می‌دهند؛ بنابراین وقتی سرور کلیدهای شما را رد می‌کند اما گذرواژه را می‌پذیرد، `meridian deploy` تعاملی می‌پرسد:

```
→ This server accepts only a password. Create a key for Meridian and install it now? [y/N]
```

`y` را پاسخ دهید و گذرواژه را (پنهان) تایپ کنید. Meridian کلید مخصوص خودش را در `~/.config/meridian/ssh/meridian_ed25519` می‌سازد، آن را به `authorized_keys` سرور اضافه می‌کند، بررسی می‌کند که ورود با آن کار می‌کند، آن را در پروفایل سرور ذخیره می‌کند و ادامه می‌دهد. گذرواژه فقط برای همان یک فرمان استفاده می‌شود و هرگز ذخیره یا لاگ نمی‌شود. host key ابتدا تأیید می‌شود، پس گذرواژه فقط به سروری فرستاده می‌شود که fingerprint آن را پذیرفته‌اید. `meridian setup` هنگام افزودن سرور همین را پیشنهاد می‌دهد.

بدون ترمینال، با `--yes` یا با `--json`، Meridian هرگز prompt نمی‌دهد: به‌جای آن با فرمان دستی متوقف می‌شود. یک بار کلید خودتان را نصب کنید و دوباره اجرا کنید:

```
ssh-copy-id root@198.51.100.10
```

Hardening پس از deploy ورود با گذرواژه را خاموش می‌کند، پس کلید را نگه دارید: فرمان‌های بعدی به‌طور خودکار از آن استفاده می‌کنند.

## تمام پرچم‌ها

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--sni HOST` | (خودکار) | هدف camouflage. بدون آن، deploy سایتی را در زیرشبکهٔ خود سرور ترجیح می‌دهد، سپس `www.google.com`، `dl.google.com`، `www.cloudflare.com` |
| `--domain DOMAIN` | (هیچ) | دامنه شما: XHTTP به آن منتقل می‌شود و WSS اضافه می‌شود، هر دو از طریق CDN Cloudflare |
| `--self-steal` | خاموش | استتار با دامنه خودتان (`--sni`، وگرنه `--domain`) به‌جای سایت دیگران ([دامنه خودتان](#دامنه-خودتان-self-steal) را ببینید) |
| `--hysteria2/--no-hysteria2` | فعال | Hysteria2 را روی UDP/443 به عنوان آخرین fallback ارائه دهید |
| `--client-name NAME` | default | نام کلاینت اول |
| `--display-name NAME` | (هیچ) | برچسب برای صفحات اتصال (مثل "VPN علی") |
| `--icon EMOJI_OR_URL` | (هیچ) | آیکون صفحه — emoji یا URL تصویر |
| `--color PALETTE` | ocean | تم رنگ صفحه (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | root | کاربر SSH (کاربران non-root نیاز به sudo بدون رمز عبور دارند) |
| `--ssh-port PORT` | 22 | پورت SSH، اگر 22 نیست |
| `--harden / --no-harden` | فعال | ورود تنهای کلید SSH، fail2ban و firewall UFW. از `--no-harden` برای سروری که خدمات دیگری روی آن است استفاده کنید |
| `--warp / --no-warp` | غیرفعال | ترافیک خروجی را از طریق Cloudflare WARP ارسال کنید |
| `--geo-block / --no-geo-block` | فعال | IP‌های روسی و دامنه‌های روسی را روی سرور block کنید |
| `--country CC` | جست‌وجو می‌شود | کشور نمایش‌داده‌شده در نام اتصال‌ها، مثل `DE`. Meridian آن را از رجیستری آدرس پیدا می‌کند؛ اگر اشتباه بود خودتان مشخص کنید |
| `--yes` | | پرسش تأیید را رد کنید |

پرچم‌های برای اسکریپت‌ها و UI‌ها (`--json`، `--events`، `--request`، `--dry-run`) در [CLI reference](/fa/cli-reference/#meridian-deploy) توصیف شده‌اند.

## انتخاب هدف camouflage

هدف camouflage (SNI) وب‌سایتی است که سرور شما خود را جای آن جا می‌زند. معمولاً این دامنه‌ای **نیست** که مالکش باشید، بلکه یک سایت واقعی با TLS 1.3 است و هر کسی که سرور شما را probe کند گواهینامه واقعی آن سایت را می‌بیند. برای استفاده از دامنه خودتان، [دامنه خودتان](#دامنه-خودتان-self-steal) را ببینید.

بهترین هدف کنار سرور شما قرار دارد. سانسورچی SNI را همراه با IP سرور شما می‌بیند؛ وقتی DNS آن سایت واقعاً به همان شبکه اشاره می‌کند، این جفت مثل ترافیک عادی به نظر می‌رسد، در حالی که یک سایت خارجی مشهور روی آدرس VPS به چشم می‌آید.

بدون `--sni`، استقرار اول زیرشبکهٔ خود سرور را برای چنین سایت‌هایی اسکن می‌کند (حدود یک دقیقه) و فقط آن‌هایی را نگه می‌دارد که DNS‌شان به همان زیرشبکه اشاره می‌کند و بررسی TLS 1.3 و HTTP/2 در Reality را می‌گذرانند. بعد به `www.google.com`، `dl.google.com` و `www.cloudflare.com` برمی‌گردد. از اولین هدفی استفاده می‌کند که ترافیک واقعی از آن عبور کند. `meridian node add` همسایه را به همین شکل انتخاب می‌کند. هدفی که با `--sni` می‌دهید هرگز جابه‌جا نمی‌شود؛ اگر ترافیک ناموفق باشد، استقرار متوقف می‌شود و گزارش می‌دهد. بازاستقرار هدف ذخیره‌شده را نگه می‌دارد.

برای دیدن خودتان نامزدها، محله IPv4 سرور را اسکن کنید:

```
meridian scan 198.51.100.10
```

اسکن یک build ثابت و checksum‌بررسی‌شده RealiTLScanner را روی سرور اجرا می‌کند و دامنه‌های گواهینامه‌ای که پیدا کرده را فهرست می‌کند. سپس با انتخاب خود استقرار کنید:

```
meridian deploy 198.51.100.10 --sni dl.google.com
```

برای بررسی دستی یک هدف، `meridian check 198.51.100.10 --sni HOST` را اجرا کنید. از `apple.com` و `icloud.com` پرهیز کنید — شبکه‌های آن‌ها با دیتاسنترهای VPS همخوانی ندارند.

### تغییر هدف در آینده

وقتی `meridian test --probe` گزارش می‌دهد SNI استتار مسدود است، exit را بدون استقرار دوباره به هدف دیگری ببرید. Meridian نام‌های `apple.com`، `icloud.com` و `www.microsoft.com` (گواهی آن برای Reality بیش از حد بزرگ است) را رد می‌کند، بررسی می‌کند که exit با TLS 1.3 و HTTP/2 به سایت جدید می‌رسد، بررسی را نشان می‌دهد و اعمال می‌کند. نام قدیمی بی‌درنگ جایگزین می‌شود و کنار نام جدید نمی‌ماند، چون یک شنوندهٔ Reality دقیقاً یک سایت را تقلید می‌کند. برنامه‌ها در تازه‌سازی بعدی اشتراک (هر 6 ساعت) یا وقتی کاربر اشتراک را تازه کند جابه‌جا می‌شوند. برای relay از `meridian relay sni RELAY NEW_SNI` استفاده کنید.

```
meridian node sni 198.51.100.10 www.cloudflare.com
```

### دامنه خودتان (self-steal)

سرور می‌تواند به‌جای قرض گرفتن سایت دیگران، دامنه‌ای را که مالکش هستید تقلید کند. یک رکورد A فقط DNS (ابر خاکستری در Cloudflare، بدون پراکسی) به سرور بسازید و سپس با `--self-steal` مستقر کنید:

```
meridian deploy 198.51.100.10 --sni www.example.com --self-steal
```

Meridian برای این نام گواهی Let's Encrypt صادر می‌کند و آن را از خود سرور ارائه می‌دهد. بررسی بدون کلید Reality، یا با هر SNI ناشناخته‌ای، همین گواهی و صفحه 404 پیش‌فرض nginx را می‌بیند، مثل هر سرور nginx که هنوز چیزی روی آن منتشر نشده است. نام به همین سرور ترجمه می‌شود و گواهی‌اش واقعی است، پس ناهمخوانی‌ای برای دیدن نیست، و سایت بیرونی‌ای هم نیست که از کار بیفتد، گواهی‌اش را عوض کند یا جداگانه مسدود شود.

Meridian پیش از هر تغییری از روی سرور بررسی می‌کند که نام به کجا اشاره می‌کند. اگر نام ترجمه نشود متوقف می‌شود (Let's Encrypt نمی‌تواند گواهی صادر کند)، و اگر به جای دیگری مثل پراکسی Cloudflare اشاره کند هشدار می‌دهد.

با `--domain` و بدون `--sni`، دامنه هر دو کار را انجام می‌دهد: Reality آن را تقلید می‌کند و XHTTP و WSS پشت آن کار می‌کنند. اما دامنه‌ای که از Cloudflare پراکسی می‌شود به Cloudflare ترجمه می‌شود، پس برای self-steal همراه با CDN از دو نام استفاده کنید: یکی فقط DNS برای `--sni` و یکی پراکسی‌شده برای `--domain`. `meridian node add` و `meridian node sni` هم `--self-steal` را می‌پذیرند. relayهایی که SNI خودشان را دارند همچنان سایت دیگران را قرض می‌گیرند.

### هدف camouflage در مقابل دامنه

- **هدف camouflage** (`--sni`) — یک وب‌سایت محبوب که **مالک آن نیستید** و Reality خود را جای آن جا می‌زند؛ یا با `--self-steal`، نامی که مالکش هستید و به همین سرور اشاره می‌کند.
- **دامنه** (`--domain`) — دامنه‌ای که **مالک آن هستید**، که به سرور شما اشاره می‌کند. XHTTP و Hysteria2 به آن منتقل می‌شوند، و آن مسیر WSS را از طریق CDN Cloudflare اضافه می‌کند. [Domain mode](/fa/domain-mode/) را ببینید.

## Hysteria2

```
meridian deploy 198.51.100.10 --no-hysteria2
```

هر deploy Hysteria2 را روی UDP/443 با گواهینامه دامنه شما یا IP گواهینامه بدون دامنه ارائه می‌دهد. ترافیک آن در obfuscation salamander بسته‌بندی می‌شود، پس سانسورگرها UDP تصادفی را می‌بینند نه QUIC. در شبکه‌های lossy یا پرتاخیری کمک می‌کند؛ جایی که UDP مسدود است، برنامه‌ها به روش‌های TCP که قبل از آن ذکر شده‌اند برمی‌گردند. `--no-hysteria2` آن را خاموش می‌کند. Hysteria2 از relay عبور نمی‌کند.

## برندسازی

صفحات اتصال را شخصی‌سازی کنید تا دریافت‌کنندگان بدانند چه کسی VPN خود را راه‌اندازی کرده:

```
meridian deploy 198.51.100.10 --display-name "VPN علی" --icon 🚀 --color sunset
```

- **`--display-name`** — در سرتیتر و عنوان صفحه نمایش داده می‌شود
- **`--icon`** — emoji یا URL تصویر در بالای صفحه نمایش داده می‌شود
- **`--color`** — پالت رنگی: `ocean` (پیش‌فرض)، `sunset`، `forest`، `lavender`، `rose`، `slate`

برندسازی در `cluster.yml` ذخیره می‌شود و برای صفحه اتصال هر کلاینت اعمال می‌شود.

## بازاستقرار

برای بازاستقرار، دستور را دوباره اجرا کنید. Meridian مسیرها، کلیدها و کاربران ذخیره‌شده را نگه می‌دارد، بنابراین لینک‌های موجود کار می‌کند. بازاستقرار بدون `--sni` هدف camouflage ذخیره‌شده را نگه می‌دارد.

در انتهای هر استقرار، Meridian دستور بازاستقرار دقیق را با تنظیمات فعلی شما چاپ می‌کند. با دستورات متفاوت دوباره اجرا آن سرور را تغییر می‌دهد: اضافه‌کردن یا حذف `--domain` یا `--no-hysteria2` این مسیرها را اضافه یا حذف می‌کند.

`meridian deploy` فقط سروری را بازاستقرار می‌کند که قبلاً exit در ناوگان شما است. برای اضافه کردن سرور دیگر، از `meridian node add NEW_IP` استفاده کنید. اگر ناوگان هنوز روی پنل Remnawave اجرا می‌شود، deploy ابتدا پیشنهاد می‌کند آن را به سرویس کنترل منتقل کند (ببینید [انتقال از Remnawave](#انتقال-از-remnawave)).

## ویرایش ناوگان با یک فایل

برای تغییر چند چیز با هم، یا نگه‌داشتن چیدمان ناوگان در کنترل نسخه، آن را صادر کنید، ویرایش کنید و دوباره وارد کنید:

```bash
meridian fleet export > fleet.yml
$EDITOR fleet.yml
meridian fleet import fleet.yml
```

وارد کردن پیش از هر کاری هر تغییر را نشان می‌دهد:

```
  + client carol
  ~ exit-2 sni www.example.com -> www.example.org
  → اعمال شود؟ [y/N]
```

فایل سرورها را با نام ذخیره‌شده‌شان می‌آورد و هیچ کلید، اطلاعات ورود، پیوند یا مسیر انتقالی ندارد، پس نگه‌داشتنش در مخزن امن است. سرورهایی که نام می‌برد باید از قبل ذخیره شده باشند (`meridian server add`). آنچه رد می‌شود در [`fleet import`](/fa/cli-reference/#meridian-fleet) آمده است.

## بررسی پیش از نصب

مطمئن نیستید که سرور مناسب است؟

```
meridian check 198.51.100.10
```

هدف استتار، آزاد بودن پورت 443 و دسترسی به آن از بیرون، DNS دامنه (در صورت وجود)، سیستم‌عامل، فضای دیسک و اختلاف ساعت را بدون نصب هیچ برنامه‌ای بررسی می‌کند.

## استقرار non-root

```
meridian deploy 198.51.100.10 --user ubuntu
```

دستورات از طریق `sudo` اجرا می‌شوند، بنابراین کاربر به sudo بدون رمز عبور نیاز دارد.

## استقرار محلی

اگر به سرور به عنوان root وارد شده‌اید:

```
meridian deploy local
```

این SSH را رد می‌کند. `check local`، `scan local` و `doctor local` به همین شکل کار می‌کنند و بعد از استقرار، دستورات بعدی روی سرور نیز به صورت محلی اجرا می‌شود. اجرای Meridian از ماشین خود همچنان توصیه می‌شود، زیرا `meridian test` نیاز به نقطه نظر بیرونی است.

## Cloudflare WARP

WARP ترافیک خروجی سرور شما را از طریق Cloudflare ارسال می‌کند، بنابراین وب‌سایت‌ها به جای IP VPS شما آدرس Cloudflare را می‌بینند.

```
meridian deploy 198.51.100.10 --warp
```

**زمانی که WARP کمک می‌کند:** سایت‌هایی که محدوده IP datacenter را مسدود می‌کنند، یا زمانی که می‌خواهید آدرس VPS را از سایت‌های مقصد مخفی کنید.

**زمانی که نیاز ندارید:** اکثر سایت‌ها بدون آن خوب کار می‌کنند، و یک hop اضافه می‌کند (VPS → Cloudflare → مقصد).

Meridian کلاینت `cloudflare-warp` را در حالت proxy نصب می‌کند (SOCKS5 روی `127.0.0.1:40000`) و آن را outbound Xray می‌سازد. اتصالات ورودی تحت تأثیر قرار نمی‌گیرند. WARP رایگان است و به حساب Cloudflare نیاز ندارد.

### WARP تنها برای برخی سایت‌ها

برای ارسال تنها سایت‌های انتخاب‌شده از طریق WARP و نگه داشتن بقیه مستقیم، یک route روی exit اضافه کنید بجای روشن کردن WARP برای تمام ترافیک. Meridian WARP را بر روی exit برای اولین بار که یک route نیاز دارد تنظیم می‌کند:

```
meridian route add exit-1 --via warp chatgpt.com netflix.com
meridian route add exit-1 --via block geosite:category-ads-all
meridian route list
meridian route remove exit-1 warp
```

مقادیر دامنه‌ها (subdomain‌ها شامل)، لیست‌های `geosite:NAME` یا لیست‌های `geoip:NAME` از فایل‌های v2fly stock هستند؛ یک route تک نوع را نگه می‌دارد. `--via direct` برعکس بر روی exit WARP انجام می‌دهد: آن مقاصد WARP را skip می‌کنند. Routes به ترتیبی که آن‌ها را اضافه کردید اعمال می‌شوند، پیش از egress پیش‌فرض exit و پیش از geo-blocking. این routes روی سرور قرار دارند؛ آن‌ها جدا از قوانین سمت client هستند که سایت‌های روسی مستقیم را در دستگاه کاربر ارسال می‌کند، و جدا از قانون‌های دروازه مسیریابی که می‌توانند ترافیک را مستقیم از یک دروازه داخلی بیرون بفرستند ([Split routing](/fa/split-routing/#از-طریق-دروازه-مسیریابی)).

### سرویس‌های هوش مصنوعی

سرویس‌های هوش مصنوعی (ChatGPT، Claude، Gemini، Cursor و دیگران) برخی آدرس‌های هاستینگ را رد می‌کنند، و نشستی که آدرسش بین کشورها جابه‌جا شود یا لحظه‌ای اتصال خانگی را نشان دهد ممکن است به خروج از حساب یا تعلیق آن ختم شود. یک route همه آن‌ها را از طریق WARP می‌فرستد:

```
meridian route add exit-1 --preset ai
```

این preset یک route با نام `ai` است که `geosite:category-ai-!cn`، `anthropic`، `openai`، `cursor` و `google-gemini` را پوشش می‌دهد؛ با `--via direct` آن‌ها روی آدرس خود exit می‌مانند. WARP در منطقه exit به اینترنت می‌رسد، پس کاربران هوش مصنوعی را روی exitهای یک کشور نگه دارید. route سمت سرور ترافیکی را که دستگاه بیرون از VPN می‌فرستد نمی‌گیرد: در macOS، برنامه Happ ممکن است پس از باز کردن درب لپ‌تاپ لحظه‌ای ترافیک را مستقیم بفرستد. اگر سرویس‌های Google همچنان شما را در کشور دیگری می‌بینند، درخواست «تغییر کشور مرتبط با حساب» در راهنمای حساب Google معمولاً ظرف چند ساعت مشکل را حل می‌کند.

## مسدودسازی جغرافیایی

به‌طور پیش‌فرض، سرور دامنه‌های روسی (`geosite:category-ru`) و محدوده‌های IP روسی (`geoip:ru`) را از طریق proxy مسدود می‌کند. این IP VPS شما را از لاگ‌های خدمات روسی دور می‌کند، که احتمال یافتن و مسدود کردن آن را کاهش می‌دهد.

اگر کاربران شما نیاز به آن سایت‌ها از طریق Meridian دارند، آن را خاموش کنید:

```
meridian deploy 198.51.100.10 --no-geo-block
```

برای راهی برای باز کردن سایت‌های روسی بطور مستقیم در حالی‌که مسدودسازی را نگه می‌دارید، [Split routing](/fa/split-routing/) را ببینید.

## نشانی کلاینت‌ها

سرویس کنترل هرگز ثبت نمی‌کند کاربران شما از کجا وصل می‌شوند. هر اتصال TCP از طریق nginx روی سرور به Xray می‌رسد و سرویس فقط مجموع ترافیک هر نفر را نگه می‌دارد، نه نشانی و نه لاگ اتصال.

## افزودن relay

پس از اجرای exit، یک relay روی سرور داخلی اضافه کنید تا کاربران زمانی‌که IP خروج مسدود می‌شود راه ورودی داشته باشند. [راهنمای Relay](/fa/relay/) را ببینید.

```
meridian relay add 203.0.113.10 --exit 198.51.100.10
```

## کنسول وب

سرویس کنترل یک کنسول وب برای یک مالک دارد: شما. این کنسول روی یک مسیر مخفی تصادفی، جدا از مسیر صفحهٔ اتصال، قرار دارد، پس لینک‌هایی که به اشتراک می‌گذارید هرگز آن را فاش نمی‌کنند. `meridian panel` نشانی آن را چاپ می‌کند و تا وقتی کنسول مالک ندارد، یک لینک راه‌اندازی یک‌بارمصرف هم می‌دهد:

```
  Meridian console
  URL         https://198.51.100.10/<secret-path>/
  Setup link  https://198.51.100.10/<secret-path>/#setup=…
              Works once, for 15 minutes. Open it to choose the owner's password.
```

پس از انتخاب رمز عبور، می‌توانید کد ورود از یک برنامهٔ احراز هویت را روشن کنید. در کنسول افراد را اضافه می‌کنید، لینک و QR آن‌ها را به اشتراک می‌گذارید، محدودیت و تاریخ انقضا تعیین می‌کنید و توکن API می‌سازید؛ سرورها، revisionها و عنوان اشتراک فقط‌خواندنی نشان داده می‌شوند، همراه با دستور `meridian` که آن‌ها را تغییر می‌دهد. ببینید [کنسول وب](/fa/client-management/#کنسول-وب).

با نشانی کنسول مثل رمز عبور رفتار کنید. اگر رمز عبور یا برنامهٔ احراز هویت را از دست دادید، `meridian panel --setup-link` یک لینک بازنشانی چاپ می‌کند: رمز عبور تازه‌ای تعیین می‌کند، کد ورود را خاموش می‌کند و همهٔ دستگاه‌ها را از حساب خارج می‌کند.

## پشتیبان

در پایان اولین deploy، Meridian یک بار کلید بازیابی را نشان می‌دهد:

```
  Recovery key (shown once; Meridian keeps no copy)

    AGE-SECRET-KEY-1…

  Write it down or print it, and keep it offline, away from this computer.
```

آن را آفلاین و دور از ماشین‌هایی که ناوگان را مدیریت می‌کنند نگه دارید. پس از هر تغییر، Meridian یک snapshot رمزنگاری‌شده از سرویس کنترل روی ماشین شما ذخیره می‌کند که با کلید خود ماشین یا کلید بازیابی خوانده می‌شود. اگر روزی سرور کنترل از دست برود، [`meridian restore`](/fa/recovery/#سرور-کنترل-از-دست-رفت) آن را از تازه‌ترین snapshot روی سرور جدیدی بازسازی می‌کند.

## ارتقا

سرویس کنترل و agent گره همراه Meridian عرضه می‌شوند. پس از `meridian update`، `meridian fleet upgrade` را اجرا کنید: نشان می‌دهد چه چیزی تغییر می‌کند، سپس سرویس کنترل را به نسخهٔ جدید می‌برد و هر agent را در جا ارتقا می‌دهد و هویت هر گره را حفظ می‌کند. همچنین relayها را بدون انتظار برای به‌روزرسانی Meridian به جدیدترین نسخهٔ Realm می‌برد. هر `meridian apply` هم سرویس کنترل و agentها را با نسخهٔ نصب‌شدهٔ Meridian هم‌سطح می‌کند.

## انتقال از Remnawave

ناوگانی که با نسخه‌ای قدیمی‌تر از Meridian 4 deploy شده روی پنل Remnawave اجرا می‌شود. `meridian migrate` آن را در جا، روی همان سرورها، به سرویس کنترل منتقل می‌کند:

```
meridian migrate
```

این دستور از پایگاه دادهٔ پنل نسخهٔ پشتیبان می‌گیرد (روی ماشین شما و روی سرور کنترل)، هر کلاینت را با کلیدها، وضعیت، محدودیت‌ها، تاریخ انقضا و ترافیکش منتقل می‌کند، کانتینر هر گره را با agent جایگزین می‌کند و پیش از حذف Remnawave بررسی می‌کند که هیچ لینک اشتراکی تغییر نکرده باشد. کلاینت‌ها لینک‌های خود را نگه می‌دارند و متوجه چیزی نمی‌شوند. داده‌هایی که فقط در پنل بودند، مثل فهرست دستگاه‌های HWID، تاریخچهٔ مصرف روزانه و تنظیمات پلاگین‌ها، منتقل نمی‌شوند و انتقال IP کلاینت‌ها (که برای محدودیت IP هر کاربر در پنل بود) خاموش می‌شود؛ بازبینی پیش از شروع آن‌ها را فهرست می‌کند. انتقال قابل ادامه است: اگر متوقف شد، دوباره `meridian migrate` را اجرا کنید. ببینید [`meridian migrate`](/fa/cli-reference/#meridian-migrate).
