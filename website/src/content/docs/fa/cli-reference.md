## دستورات

### meridian deploy

یک سرور مستقر کنید و لینک اتصالی قابل اشتراک دریافت کنید. سرور هم سرور کنترل (اجراکنندهٔ سرویس کنترل Meridian) و هم exit می‌شود. Deploy همان توپولوژی بازبینی‌شدهٔ `meridian setup` را می‌سازد، آن را با checkpoint اعمال می‌کند، ترافیک واقعی را از طریق اشتراک تحویل‌شده تأیید می‌کند و صفحهٔ اتصال و URL اشتراک را چاپ می‌کند. اجرای دوبارهٔ همان دستور، استقرار قطع‌شده را ادامه می‌دهد یا سرور را با حفظ مسیرها، کلیدها و کاربران بازاستقرار می‌کند. اولین deploy ناوگان در پایان کلید بازیابی آن را یک بار نشان می‌دهد (ببینید [meridian backup](#meridian-backup)).

```
meridian deploy [SERVER] [flags]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--sni HOST` | (خودکار) | هدف camouflage. بدون آن، استقرار اول ابتدا سایت‌هایی را در زیرشبکهٔ خود سرور امتحان می‌کند، سپس `www.google.com`، `dl.google.com`، `www.cloudflare.com` را، و از اولین موردی که ترافیک از آن عبور می‌کند استفاده می‌کند؛ بازاستقرار هدف ذخیره‌شده را نگه می‌دارد. `--sni` صریح هرگز جابه‌جا نمی‌شود |
| `--domain DOMAIN` | (هیچ) | دامنه شما: XHTTP به آن منتقل می‌شود و WSS اضافه می‌شود، هر دو از طریق CDN Cloudflare (XHTTP بدون دامنه هم روی IP کار می‌کند). سرویس کنترل و صفحات اتصال روی گواهینامه IP می‌مانند |
| `--self-steal` | خاموش | استتار با دامنه خودتان (`--sni`، وگرنه `--domain`) که با رکورد فقط DNS به سرور اشاره می‌کند: Meridian گواهی Let's Encrypt آن را صادر می‌کند و سرور خودش با صفحه 404 پیش‌فرض nginx به بررسی‌ها پاسخ می‌دهد. deploy ابتدا بررسی می‌کند نام به کجا ترجمه می‌شود: اگر ترجمه نشود متوقف می‌شود و اگر به جای دیگری اشاره کند هشدار می‌دهد. بازاستقرار آن را نگه می‌دارد؛ `--sni` جدید بدون این پرچم به سایت قرضی برمی‌گردد |
| `--hysteria2/--no-hysteria2` | فعال | ارائهٔ Hysteria2 روی UDP/443 با مبهم‌سازی salamander به‌عنوان آخرین مسیر پشتیبان. از گواهی دامنه یا در نبود آن از گواهی IP استفاده می‌کند |
| `--fingerprint NAME` | chrome | اثر انگشت TLS که کلاینت‌ها در Reality، XHTTP و WSS نشان می‌دهند (`chrome`، `firefox`، `safari`، `ios`، `android`، `edge`، `random`، `randomized`). اگر منطقه شما شروع به پرچم‌گذاری کردن آن کند تغییر دهید؛ بازاستقرار مقدار ذخیره‌شده را نگه می‌دارد |
| `--client-name NAME` | default | نام کلاینت اول |
| `--display-name NAME` | (هیچ) | برچسب برای صفحات اتصال |
| `--icon EMOJI_OR_URL` | (هیچ) | آیکون صفحه — emoji یا URL تصویر |
| `--color PALETTE` | ocean | تم رنگ صفحه (ocean/sunset/forest/lavender/rose/slate) |
| `--user USER` | ذخیره‌شده، وگرنه root | کاربر SSH (non-root نیاز به sudo بدون رمز عبور دارد) |
| `--ssh-port PORT` | ذخیره‌شده، وگرنه 22 | پورت SSH |
| `--harden / --no-harden` | فعال | ورود تنهای کلید SSH، fail2ban و firewall UFW. `--no-harden` برای سروری که سرویس‌های دیگری روی آن دارند است |
| `--warp / --no-warp` | خاموش | ترافیک خروجی را از طریق Cloudflare WARP ارسال کنید |
| `--geo-block / --no-geo-block` | فعال | دامنه‌های روسی و IP‌های روسی را در exit block کنید (`geosite:category-ru` + `geoip:ru`). اشتراک‌های Xray JSON و Mihomo قبلاً آن‌ها را مستقیم از دستگاه ارسال می‌کنند |
| `--country CC` | رجیستری آدرس | کشور دو‌حرفی که در نام اتصال‌ها و در فهرست سرورهای کنسول نمایش داده می‌شود. بدون آن، در اولین استقرار از رجیستری اینترنتی منطقه‌ای (RIR) آدرس سرور پرسیده می‌شود (از طریق RDAP bootstrap مربوط به IANA، بدون سرویس geo-IP)؛ در بازاستقرار، کشور ذخیره‌شده حفظ می‌شود |
| `--yes` | | پرسش تأیید را رد کنید |
| `--json` | | نتیجه deploy نهایی را به عنوان پاکت `meridian.output/v1` ارسال کنید |
| `--events=jsonl` | | رویدادهای تعریف‌شده پیشرفت را به عنوان JSONL روی stderr جریان دهید |
| `--request FILE` | | پیوند JSON `deploy-request` را از فایل بخوانید؛ از `-` برای stdin استفاده کنید |
| `--dry-run` | | deploy را بدون SSH یا تغییرات محلی compile و پیش‌نمایش کنید |

بدون IP، دستور `deploy` آن را از شما می‌پرسد. `local` روی همان ماشینی که دستور را اجرا می‌کنید مستقر می‌کند. `deploy` فقط سروری را بازاستقرار می‌کند که از قبل یک exit در ناوگان شما باشد؛ سرورهای دیگر را با `meridian node add` اضافه کنید. اگر ناوگان هنوز روی پنل Remnawave اجرا می‌شود، `deploy` ابتدا پیشنهاد می‌کند [`meridian migrate`](#meridian-migrate) اجرا شود. اجرای دوباره با پرچم‌های متفاوت همان خروجی را مطابق پرچم‌های جدید به‌روز می‌کند (مثلاً افزودن یا حذف `--domain` یا `--no-hysteria2`) و سایر خروجی‌ها، relayها، دروازه‌ها و کلاینت‌ها را حفظ می‌کند.

**جریان Machine/UI**: `meridian api workflow deploy --json` قرارداد wizard renderable برمی‌گرداند. UI آن فیلدها را جمع‌آوری می‌کند، آن‌ها را برای `deploy-request` تأیید می‌کند، سپس `meridian deploy --request deploy.json --json --events=jsonl` را اجرا می‌کند. Machine deploys غیرتعاملی هستند: درخواست باید بعد از تأیید کاربر `yes: true` داشته باشد. `--dry-run --json` `deploy-plan` را تحت `data` برمی‌گرداند، بنابراین UI می‌تواند حالت، پورت‌ها و مسیرهای تولید‌شده را پیش‌نمایش کند قبل از باز کردن SSH.

### meridian setup

یک wizard راهنمایی resumable برای یک یا بسیاری سرور: exits، Realm relays، routing gateways با failover pools و users. این برای افرادی نوشته شده است که هرگز VPN را تنظیم نکرده‌اند: هر سؤال از اصطلاح واقعی (exit، relay، SNI) استفاده می‌کند و آن را در یک جملهٔ ساده با پیش‌فرض ایمن توضیح می‌دهد که می‌توانید با فشار دادن Enter بپذیرید.

```
meridian setup [--intent FILE|-] [--restart] [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--intent FILE` | (هیچ) | از بررسی توپولوژی کامل JSON شروع کنید؛ از `-` برای stdin استفاده کنید |
| `--restart` | | پیشرفت setup ذخیره‌شده را قبل از شروع دور کنید |
| `--devices N\|default` | سقف مجموعه | سقف هر فرد، 1–100 (`client add`، `client set`)؛ `default` سقف مجموعه را دنبال می‌کند |
| `--remove ID` | | فراموش‌کردن یک ثبت (`client devices`)؛ در تازه‌سازی بعدی می‌تواند دوباره ثبت شود |
| `--clear` | | فراموش‌کردن همهٔ ثبت‌ها (`client devices`)؛ هم‌زمان با `--remove` مجاز نیست |
| `--yes`, `-y` | | بررسی و اعمال را بدون پرسش تأیید کنید |

اولین سؤال زبان است (English, Русский, فارسی, 中文)، از ترمینال شما پیش‌انتخاب‌شده و در `~/.config/meridian/preferences.json` به‌خاطر سپرده می‌شود؛ `--lang` یا `MERIDIAN_LANG` آن را رد می‌کنند. سپس wizard از طریق سروری (یک IP، `user@IP:port` یا `local` برای این ماشین)، آنچه که هر سرور انجام می‌دهد، روش‌های اتصال، مسیریابی (تنها زمانی پرسیده می‌شود که routing gateway داشته باشید: هر قانون ترافیک منطبق را به یک خروجی یا pool، مستقیم از دروازه، یا به هیچ‌جا می‌فرستد)، users، خلاصهٔ ساده‌زبان و اعمال راه‌اندازی می‌شود. گزینه‌ها فهرست هستند: با کلیدهای جهت‌دار حرکت کنید (یا شمارهٔ گزینه را بزنید)، موارد چک‌لیست را با Space علامت بزنید، برای جزئیات `?` را بزنید، با Enter تأیید کنید، با Esc به عقب برگردید و با Ctrl+C خارج شوید. هر جا که فهرستی «مورد دیگر» را پیشنهاد می‌دهد، می‌توانید مقدار دلخواه خود را تایپ کنید. در فیلدهای متنی نیز می‌توانید `back`، `details`، `save` یا `quit` تایپ کنید (یا همان کلمات به زبان شما). برای «سایت برای پنهان‌سازی»، wizard ابتدا شبکهٔ خود exit را اسکن می‌کند (حدود یک دقیقه) و آن سایت‌ها را پیش از سایت‌های شناخته‌شده فهرست می‌کند. برای prompt‌های شماره‌دار `MERIDIAN_PLAIN_PROMPTS=1` را تنظیم کنید (وقتی ترمینال نتواند فهرست‌ها را رسم کند، به‌طور خودکار استفاده می‌شوند). اجرای `meridian` بدون فرمان در یک ترمینال، قبل از آن‌که VPN موجود باشد، برای شروع wizard پیشنهاد می‌دهد. پیشرفت بعد از هر مرحله در `~/.config/meridian/setup.json` ذخیره می‌شود، بنابراین `meridian setup` دوباره اجرا resume می‌شود؛ رمزهای عبور و کلیدهای خصوصی هرگز در آنجا ذخیره نمی‌شوند. `--intent` draft موجود را جایگزین نمی‌کند مگر `--restart` همچنین داده شود. هنگامی‌که اعمال موفق باشد، setup هر گره و اشتراک را تأیید کرده و صفحه اتصال هر کاربر را چاپ می‌کند.

### meridian plan

نشان می‌دهد که `meridian apply` چه چیزی را تغییر خواهد داد و توپولوژی موجود در `~/.config/meridian/cluster.yml` را با سرورهای فعال و سرویس کنترل مقایسه می‌کند. هیچ چیزی تغییر نمی‌کند.

```
meridian plan [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--json` | | برنامه را به عنوان پاکت `meridian.output/v1` برای CI و UI clients ارسال کنید |

خروجی hash برنامه، تعداد منابع روی نوع و هر منابعی که نیاز به تعمیر دارد یا نتوانست مشاهده شود را نشان می‌دهد. JSON `data` شامل `plan_hash`، `converged`، `resources[]`، `drifted_resources[]`، `observation_errors[]` و `state_changes[]` است.

**کدهای خروج**:
- `0` — همگرا شده، کاری نمانده است
- `1` — چیزی برای برنامه‌ریزی نیست (هنوز ناوگانی وجود ندارد، یا وضعیت محلی قابل استفاده نیست)
- `2` — تغییرات در انتظار اعمال (`meridian apply` را اجرا کنید)
- `3` — شواهد لازم (سرویس کنترل، SSH، وضعیت محلی) در دسترس نبود

topology را در `cluster.yml` دستی ویرایش نکنید. آن را با `meridian setup`، `deploy`، `client add`، `node add` یا `relay add` تغییر دهید.

### meridian apply

توپولوژی بررسی‌شده در `cluster.yml` را برای سروری شما اعمال کنید. Apply hash برنامه و تعداد منابع را نشان می‌دهد، برای تأیید درخواست می‌کند، سپس دقیقاً برنامه را اعمال می‌کند که نشان داده، با checkpoints. استقرار قطع‌شده جایی‌که متوقف شد از سر می‌گیرد.

```
meridian apply [--yes] [--forget-unreachable] [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--yes`, `-y` | | تأیید را رد کنید |
| `--forget-unreachable` | | آنچه روی سرورِ حذف‌شده مستقر شده را فراموش کن اگر از طریق SSH پاسخ نمی‌دهد (مسدود یا حذف شده)، به جای شکست در پاک‌سازی؛ تا وقتی حذفش نکنید به کاربران قبلی‌اش سرویس می‌دهد |
| `--json` | | نتیجه نهایی اعمال را به عنوان پاکت `meridian.output/v1` ارسال کنید |

JSON `data` شامل `plan_hash`، `generation` و `actions[]` با `status: "converged" | "applied" | "failed" | "unknown" | "skipped"` است. JSON mode هرگز پرسش نمی‌کند: بدون `--yes` `MERIDIAN_CONFIRMATION_REQUIRED` را با hash برنامه بازگردانده و exit `2` می‌شود. منابع شکسته exit `3`؛ علت را رفع کنید و اعمال را دوباره اجرا کنید. اگر وضعیت محلی نتوانست بعد از تغییرات راه دور ذخیره شود، اعمال exit `3` و می‌گوید؛ `~/.config/meridian` permissions را تعمیر کنید، سپس `plan` و `apply` را دوباره اجرا کنید.

حذف‌ها نیز اعمال می‌شوند: هر چیزی که topology را ترک کرده (کاربران، مسیرهای پروتکل، exitها، relayها، routing gatewayها) بعد از اینکه همه چیزی که در برنامه باقی است همگرا شود حذف می‌شود، و `plan` آن را اول فهرست می‌کند. سرور کنترل فقط با `meridian teardown` حذف می‌شود یا با `meridian restore` جابه‌جا می‌شود.

هر apply در سرویس کنترل به‌عنوان یک revision ثبت می‌شود (ببینید `meridian fleet history`) و در طول اجرا یک lease آنجا نگه می‌دارد، پس دو ماشین هرگز هم‌زمان apply نمی‌کنند.

### meridian client

افرادی را که متصل می‌شوند مدیریت کنید.

```
meridian client add NAME [NAME...] [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N|default] [--json]
meridian client show NAME [--connections] [--json]
meridian client preview NAME --user-agent UA [--accept TYPE] [--suffix SUFFIX] [--json]
meridian client usage NAME [--days N] [--json]
meridian client list [--attention] [--tag TAG|none] [--json]
meridian client set NAME [--limit SIZE] [--reset PERIOD] [--expires DATE] [--devices N|default] [--note TEXT] [--tag TAG|none] [--language en|ru|fa|zh|default] [--json]
meridian client reset-traffic NAME [--json]
meridian client extend NAME --days N [--json]
meridian client devices NAME [--remove ID | --clear] [--json]
meridian client enable NAME [--json]
meridian client disable NAME [--json]
meridian client reissue NAME [--cut-off] [--yes] [--json]
meridian client remove NAME [--cut-off] [--yes] [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--days N` | 30 | روزهای UTC برای `client usage` یا `fleet usage`، بین 1–730 و در محدودهٔ مدت نگهداری ذخیره‌شده |
| `--json` | | نتیجه را به عنوان پاکت `meridian.output/v1` ارسال کنید (تمام دستورات client) |
| `--attention` | خاموش | `client list`: فقط افراد نیازمند توجه، همراه با دلیل |
| `--limit SIZE` | بدون سقف | سقف ترافیک (`client add`، `client set`): `500MB`، `50GB`، `1.5TB`؛ `none` یا `0` آن را برمی‌دارد. واحدها دودویی‌اند (1 GB = 1024³ بایت)، همان‌طور که سرویس کنترل می‌شمارد |
| `--reset PERIOD` | never | ترافیک مصرف‌شده کی دوباره از صفر شروع شود: `day`، `week`، `month` یا `never`، بر پایهٔ روز، هفته یا ماه تقویمی |
| `--expires DATE` | never | دسترسی کی تمام شود: `YYYY-MM-DD` (پایان همان روز به وقت UTC)، یک زمان ISO مانند `2026-12-31T18:00:00+03:00` (زمانِ بدون اختلاف ساعت، UTC حساب می‌شود) یا `never`. باید در آینده باشد |
| `--yes`, `-y` | | تأیید `client reissue` یا `client remove`؛ با `--json` الزامی است |

**`client add`** — یک یا چند نفر را به topology اضافه می‌کند، آن را اعمال می‌کند و صفحهٔ اتصال و URL اشتراک هر فرد را چاپ می‌کند. صفحه از اشتراک واقعی آن‌ها ساخته می‌شود، پس relayها و Hysteria2 در صورت وجود نمایش داده می‌شوند. نام‌هایی که از قبل در topology یا در سرویس کنترل هستند رد می‌شوند. نام‌ها می‌توانند به هر خطی نوشته شوند (`client add Биба 王小明`): صفحه‌ها و خروجی آن‌ها را همان‌طور که تایپ شده‌اند نشان می‌دهند، اما سرویس کنترل که فقط حروف لاتین، ارقام، `.`، `-` و `_` را می‌پذیرد، یک نام کاربری ترانویسی‌شده (`biba`، `wangxiaoming`) دریافت می‌کند. سایر دستورهای client هر دو شکل را می‌پذیرند. اگر لینک اشتراک کلاینت ساخته نشود، کلاینت همچنان اضافه می‌شود و دستور با کد `3` خارج می‌شود. `--limit`، `--reset`، `--expires` و `--devices` در طرح بررسی‌شده قرار می‌گیرند و همراه هر حساب در یک تراکنش ثبت می‌شوند. اعمال ناموفق لینکی چاپ نمی‌کند؛ برای تکمیل، `meridian apply` را دوباره اجرا کنید. اعمال بعدی تغییرات مدیر را حفظ می‌کنند.

**`client show`** — صفحهٔ اتصال، URL اشتراک، وضعیت، ترافیک در برابر سقف همراه با دورهٔ صفرشدن، تاریخ انقضا و زمان آخرین اتصال را چاپ می‌کند. **URL اشتراک برای هر فرد همان نشانی صفحهٔ اتصال است.**

گزینهٔ `--connections` نام، پروتکل و URI دارای اطلاعات دسترسی هر اتصال را به ترتیب اشتراک نشان می‌دهد و سپس پیوندهای Xray JSON، Mihomo و sing-box را چاپ می‌کند. در JSON این بخش در `data.connections` قرار دارد؛ اطلاعات دسترسی فقط در خروجی نهایی همین فرمان آشکار می‌شود. این پیوندها و تصاویر QR را در گزارش‌های عمومی یا لاگ‌ها قرار ندهید.

نخستین ترافیک ثبت‌شده و آخرین گره گزارش‌دهنده از افزایش پذیرفته‌شدهٔ شمارنده‌ها به دست می‌آیند (`first_traffic_at` و `last_traffic_node` در JSON). زمان نخستین استفاده پیش از ارتقا ممکن است نامشخص باشد؛ این داده‌ها تجمیعی‌اند و هیچ نشست یا نشانی کاربری ثبت نمی‌شود.

**`client list`** — کلاینت‌ها را همراه با وضعیت، ترافیک، تاریخ انقضا و آخرین اتصال فهرست می‌کند، از جمله افرادی که در کنسول وب اضافه شده‌اند (`declared: false` در JSON). با `--json`، شمارنده‌های `data.summary` و `data.clients[]` را برمی‌گرداند.

`client list --attention` فقط افرادی را نشان می‌دهد که دسترسی‌شان تا هفت روز آینده منقضی می‌شود (شامل همین لحظه)، دست‌کم ۸۰٪ سهمیه را مصرف کرده‌اند، یا بیش از سه روز از ایجاد حسابشان گذشته و هنوز هیچ ترافیکی ندارند. دلیل در ستونی جداگانه آمده است؛ JSON شامل `clients[].attention_reasons` است و شمارش خلاصه فقط افراد نمایش‌داده‌شده را در بر می‌گیرد. ترافیک واردشده بدون تاریخ دقیق و بازنشانی دوره به معنی استفاده‌نشدن نیست.

`GET /api/attention` به سطح `read` نیاز دارد و برای مالک واردشده نیز قابل دسترسی است. پاسخ شامل `observed_at`، `thresholds`، `people[]` با نام کاربری و دلیل، و `nodes[]` با شناسهٔ گره و دلیل است. گره‌های قطع‌شده یا هنوز دیده‌نشده، منابعی که اعمالشان ناموفق بوده، و سلامت گزارش‌شدهٔ `degraded` یا `unhealthy` بررسی می‌شوند. پارامترهای اختیاری: `expiry_days` (۱–۳۰، پیش‌فرض ۷)، `quota_percent` (۱–۱۰۰، پیش‌فرض ۸۰) و `unused_days` (۱–۳۶۵، پیش‌فرض ۳). این فهرست بدون ذخیرهٔ پرچم، نشست، نشانی یا دادهٔ دستگاه محاسبه می‌شود.

**`client set`** — سقف ترافیک، دورهٔ صفرشدن یا تاریخ انقضای کلاینت را تغییر می‌دهد؛ فقط گزینه‌هایی که می‌دهید تغییر می‌کنند و دست‌کم یکی لازم است. کلاینتی که سقف یا انقضا قطعش کرده (وضعیت `limited` یا `expired`) به‌محض اینکه مقادیر جدید اجازه دهند دوباره وصل می‌شود. تغییرها فوراً اعمال می‌شوند و apply هرگز به آن‌ها دست نمی‌زند. مقدار نادرست پیش از آنکه Meridian به جایی وصل شود با کد `2` خارج می‌شود. با `--json`، کلاینت را همان‌طور که اکنون در سرویس کنترل است در `data.client` برمی‌گرداند، از جمله `traffic_limit_bytes`، `traffic_reset` و `expires_at` (خالی یعنی بدون انقضا).

**`client reset-traffic`** — ترافیک مصرف‌شدهٔ کلاینت را از صفر شروع می‌کند، همان کاری که دورهٔ جدید می‌کرد؛ کلاینتی که سقف قطعش کرده دوباره می‌تواند وصل شود.

**`client extend`** — از زمان فعلی یا تاریخ انقضای حساب، هر کدام دیرتر باشد، ۱ تا ۳۶۵۰ روز کامل اضافه می‌کند. اگر حساب انقضا ندارد، مدت از اکنون حساب می‌شود. `--days N` الزامی است. محاسبه و اجرای محدودیت‌ها در یک تراکنش سرویس انجام می‌شوند، پس تمدیدهای هم‌زمان هر دو حساب می‌شوند. دسترسی منقضی‌شده دوباره برقرار می‌شود، ولی غیرفعال‌سازی مدیر و سقف ترافیک حفظ می‌شوند. JSON وضعیت و انقضای مؤثر را در `data.client` برمی‌گرداند.

**`client enable` / `client disable`** — کلاینت را فوراً فعال یا تعلیق کنید. کلاینت تعلیق‌شده تا وقتی `client enable` را اجرا نکنید غیرفعال می‌ماند؛ apply (از جمله بازاستقرار و `client add`، `node add`، `relay add`) وضعیت کلاینت را تغییر نمی‌دهد.

**`client reissue`** — لینک‌های کلاینت را پس از لو رفتن جایگزین می‌کند. سرویس کنترل شناسه اشتراک و کلیدهای جدید صادر می‌کند، پس نشانی اشتراک، صفحه اتصال و لینک‌های قبلی از کار می‌افتند. Meridian URL اشتراک تازه را چاپ می‌کند که همان صفحهٔ اتصال تازه را هم باز می‌کند. وضعیت، سقف‌ها و تاریخ انقضا همان‌طور که بودند می‌مانند. تأیید می‌خواهد مگر `--yes`، و نام‌هایی را که جزو کلاینت‌های شما نیستند رد می‌کند.

**`client remove`** — کلاینت را از topology حذف می‌کند و حساب او را در سرویس کنترل پاک می‌کند؛ اشتراک و صفحهٔ اتصال او دیگر پاسخ نمی‌دهند. تأیید می‌خواهد مگر `--yes`. آخرین کلاینت نمی‌تواند حذف شود. افرادی که در کنسول وب اضافه شده‌اند همان‌جا حذف می‌شوند.

**`client usage`** — بایت‌های آپلود، دانلود و مجموع روزانه را برای هر فرد سرویس، از جمله افراد کنسول، نشان می‌دهد. تاریخچه باید در [حریم خصوصی](/fa/privacy/) روشن باشد؛ وگرنه با کد `2` و راهنمای فعال کردن خارج می‌شود. `client show` هنگام روشن بودن تاریخچه هفت روز اخیر UTC را اضافه می‌کند (`data.usage` در JSON و `null` وقتی خاموش است). روز خالی یعنی مصرفی ثبت نشده است؛ مصرف گذشته بازسازی نمی‌شود.

**`client devices`** — در private تعداد و در full اطلاعات دستگاه‌ها را نشان می‌دهد؛ off هیچ دستگاهی را نمی‌خواند. `--json` فیلدهای `username`، `level`، `count`، سقف مؤثر `limit`، `devices` و `removed` را برمی‌گرداند. `--remove ID` یا `--clear` ثبت‌ها را بدون لغو اعتبارنامه فراموش می‌کند؛ تکرار آن صفر حذف گزارش می‌دهد. ثبت‌های افراد کنسول را هم می‌توان از CLI مشاهده و حذف کرد. `client set --devices N` سقف را تعیین و `--devices default` سقف مجموعه را انتخاب می‌کند. بخش [سقف دستگاه‌ها](/fa/client-management/#سقف-دستگاهها) را ببینید. صدور لینک جدید همهٔ ثبت‌ها را پاک می‌کند و سقف را نگه می‌دارد.

فرمان‌های تغییر اطلاعات فرد در سرویس (`client enable`، `disable`، `set`، `reset-traffic` و حذف ثبت دستگاه‌ها) برای افراد کنسول هم کار می‌کنند. نام کاربری دقیق اولویت دارد؛ تطبیق بدون توجه به بزرگی حروف یا با نام نمایشی باید فقط یک فرد را مشخص کند. در صورت ابهام، نام دقیقِ `client list` را وارد کنید. حذف فرد، صدور دوبارهٔ اطلاعات اتصال و انتشار صفحه همچنان فقط برای افراد تعریف‌شده در توپولوژی است.

نشست‌های باز VLESS ممکن است پس از لغو کلیدها هم ادامه یابند. **`--cut-off`** در `client remove` یا `client reissue` منتظر می‌ماند تا هر سرورِ مربوط نسخهٔ بدون کلیدهای قدیمی را اعمال کند، سپس ورودی‌های مربوط را بازنشانی می‌کند. همهٔ نشست‌های آن ورودی‌ها، حتی نشست‌های دیگر کاربران، بسته می‌شوند و کاربران برای لحظه‌ای دوباره وصل می‌شوند. اگر API ورودی کار نکند، Xray راه‌اندازی مجدد می‌شود و همهٔ نشست‌های آن در همان سرور بسته می‌شوند. این گزینه پیش‌فرض نیست و برای لینک فاش‌شده توصیه می‌شود. JSON نتیجهٔ هر سرور را در `data.cut_off` با وضعیت `done`، `core_restart`، `failed` یا `timed_out` نشان می‌دهد. انتظار حداکثر پنج دقیقه است؛ شکست با کد `4` و پایان زمان انتظار با کد `3` گزارش می‌شود. هنگام حذف فردی که در کنسول اضافه شده، همین گزینه در کنسول هم وجود دارد.

فیلدهای خصوصی: `client set NAME --note TEXT --tag TAG` فقط مقدارهای واردشده را تغییر می‌دهد. یادداشت حداکثر ۵۰۰ نویسهٔ متن ساده با امکان چند خط دارد؛ `--note ""` آن را پاک می‌کند. برچسب ۱ تا ۱۶ حرف بزرگ A–Z، رقم یا زیرخط دارد؛ `--tag none` آن را پاک می‌کند. `client show` هر دو فیلد را نشان می‌دهد و `client list --tag TAG` ستون برچسب را فیلتر می‌کند (`none` افراد بدون برچسب را انتخاب می‌کند). خواندن و ویرایش به دسترسی people/admin نیاز دارد. کنسول همین فیلدها را ویرایش می‌کند؛ اعمال پیکربندی آن‌ها را حفظ می‌کند و پشتیبان‌های رمزگذاری‌شده آن‌ها را منتقل می‌کنند. [یادداشت‌ها و برچسب‌های خصوصی](/fa/client-management/).

`client preview NAME --user-agent UA [--accept TYPE] [--suffix SUFFIX]` انتخاب قالب و حذف گزینه‌ها را بدون اطلاعات محرمانه توضیح می‌دهد. User-Agent حداکثر ۵۱۲ نویسهٔ Unicode و Accept حداکثر ۲۵۶ نویسه دارند؛ هرکدام یک خط و موقت‌اند. `--suffix` یکی از پسوندهای فعلی نشانی قالب را تحمیل می‌کند. JSON خروجی `subscription-preview` دارد؛ API، `POST /api/subscription/preview` با دسترسی read است.

### meridian privacy

اطلاعاتی را که سرویس کنترل نگه می‌دارد انتخاب کنید. محدودیت دستگاه و تاریخچهٔ روزانه به‌صورت پیش‌فرض خاموش‌اند؛ اعمال تنظیمات سرورها این انتخاب‌ها را تغییر نمی‌دهد. توضیح افشای اطلاعات و پیامد تصرف سرور را در [حریم خصوصی](/fa/privacy/) بخوانید.

```bash
meridian privacy [--json]
meridian privacy show [--json]
meridian privacy set [--devices off|private|full] [--device-limit N] [--history off|daily] [--history-days N] [--yes] [--json]
```

| گزینه | پیش‌فرض | توضیح |
| --- | --- | --- |
| `--devices LEVEL` | بدون تغییر | `off`، اثر انگشت کلیددار `private` یا جزئیات دستگاه `full` |
| `--device-limit N` | بدون تغییر (ابتدا 3) | سقف پیش‌فرض افراد بدون سقف اختصاصی، بین 1–100 |
| `--history LEVEL` | بدون تغییر | `off`: مجموع مصرف و آخرین فعالیت؛ `daily`: مجموع افراد و سرورها در هر روز UTC |
| `--history-days N` | بدون تغییر (ابتدا 90) | نگهداری 7–730 روز UTC، شامل امروز |
| `--yes`, `-y` | | رد کردن پرسش تأیید؛ برای تغییر در JSON لازم است |
| `--json` | | خروجی envelope از نوع `meridian.output/v1` |

`privacy` بدون زیردستور همان `privacy show` است: تنظیمات، توضیح افشای اطلاعات و 50 تغییر آخر. `set` فقط گزینه‌های داده‌شده را تغییر می‌دهد، اطلاعات ذخیره‌شده در سطح بالاتر و حذف‌شده در سطح پایین‌تر را توضیح می‌دهد و تأیید می‌گیرد. مقادیر یکسان تغییری ایجاد نمی‌کنند. `data` در JSON تنظیمات و تغییرات را دارد؛ `set` تعداد رکوردهای حذف‌شده در `deleted` و تبدیل‌شده در `rekeyed_devices` را نیز می‌دهد. نام توکن، `owner` یا `root`، زمان و مقادیر قبل/بعد ثبت می‌شوند. رکوردهای خصوصی دستگاه پس از بازیابی پاک می‌شوند، چون کلید اثر انگشت هرگز در اسنپ‌شات نیست.

### meridian server

سروری SSH ذخیره‌شده مدیریت کنید (`~/.config/meridian/servers.json`).

```
meridian server add [USER@]IP[:PORT]|local [--name NAME] [--user USER] [--ssh-port PORT]
meridian server list [--json]
meridian server set NAME [--allowance SIZE] [--reset-day DAY] [--provider TEXT] [--pay-on DATE] [--pay-every month|year|none] [--dry-run] [--yes] [--json]
meridian server remove NAME_OR_IP [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--name NAME` | (هیچ) | نام نمایشی برای سرور |
| `--user/-u USER` | root | کاربر SSH |
| `--ssh-port PORT` | 22 | پورت SSH |
| `--yes`, `-y` | | تأیید حذف را رد کنید (`server remove`) |

`server add local` ماشینی را که روی آن هستید ذخیره می‌کند؛ دستورهای بعدی به‌جای SSH مستقیم روی همین ماشین اجرا می‌شوند. نام‌ها و آدرس‌ها باید یکتا باشند؛ `server add` در صورت تکرار خطا می‌دهد و سرور موجود را بازنویسی نمی‌کند. `server remove` فقط پروفایل ذخیره‌شده را حذف می‌کند و تا زمانی که سرور در توپولوژی نقشی دارد آن را رد می‌کند.

**سهمیه و تاریخ پرداخت** برای سرورهای خروجی، سرورهای واسط، دروازه‌ها و سرور کنترل در توپولوژی بازبینی‌شده ذخیره می‌شوند. `server set NAME` نام ذخیره‌شده، شناسهٔ پروفایل یا آدرس سرور را می‌پذیرد. گزینه‌های مشخص‌نشده مقدار قبلی را حفظ می‌کنند؛ دستور بدون گزینه آن‌ها را می‌خواند. `server list --json` پروفایل‌های ذخیره‌شده را همراه `metadata` و تاریخ محاسبه‌شدهٔ پرداخت بعدی برمی‌گرداند.

| تنظیم سرور | پیش‌فرض | معنا |
|---|---|---|
| `--allowance SIZE` | تعیین نشده | حجم ماهانه مانند 20TB یا 50GiB؛ `none` آن را پاک می‌کند. GB/TB مانند سهمیهٔ کاربران نام‌های دیگر واحدهای دودویی GiB/TiB هستند |
| `--reset-day DAY` | 1 | نیمه‌شب UTC در روز 1 تا 31؛ در ماه کوتاه، آخرین روز ماه |
| `--provider TEXT` | خالی | متن ساده در یک خط، حداکثر 80 نویسه؛ `none` نام را پاک می‌کند |
| `--pay-on DATE` | تعیین نشده | YYYY-MM-DD، از جمله تاریخ گذشته برای پرداخت یک‌باره؛ `none` تاریخ و تکرار را پاک می‌کند |
| `--pay-every PERIOD` | none | `month`، `year` یا `none`؛ تکرار به تاریخ پرداخت نیاز دارد |
| `--dry-run` | | بازبینی تغییرات بدون اعمال |
| `--yes`، `-y` | | اعمال تغییر بازبینی‌شده بدون تأیید؛ در حالت JSON یا بدون ترمینال الزامی است |
| `--json` | | خروجی `meridian.output/v1` برای `server list` یا `server set` |

```bash
meridian server set edge --allowance 20TB --reset-day 15 --provider "ارائه‌دهنده نمونه" --pay-on 2026-11-15 --pay-every month --dry-run --json
meridian server set edge --allowance 20TB --reset-day 15 --yes
meridian server set edge --allowance none --pay-on none --yes
```

با فعال کردن سهمیه یا تغییر روز بازنشانی، شمارش هنگام دریافت تغییرات توسط سرویس شروع می‌شود؛ مصرف پیشین دورهٔ فعلی مشخص نیست. تغییر صرفاً حجم سهمیه، ارائه‌دهنده یا تاریخ پرداخت، مصرف دوره را حفظ می‌کند. تاریخ‌های ماهانه و سالانه هنگام خواندن محاسبه می‌شوند: پس از گذشت تاریخ به وقت UTC، نوبت بعدی انتخاب می‌شود و روز مبنا پس از ماه کوتاه یا سال کبیسه حفظ می‌شود. تاریخ یک‌باره پس از گذشتن همچنان عقب‌افتاده است. `fleet export`، بخش `server_metadata` را با نام ذخیره‌شدهٔ سرورها به‌عنوان کلید صادر می‌کند و `fleet import` آن را از مسیر معمول بازبینی و اعمال می‌کند. حذف آخرین نقش سرور اطلاعاتش را حذف می‌کند؛ با جابه‌جایی خروجی، اطلاعات با سرور فیزیکی می‌ماند. سهمیه و یادآوری جنبهٔ اطلاعاتی دارند و ترافیک را مسدود نمی‌کنند.

### meridian node

سروری exit را مدیریت کنید. سرور اول با `meridian deploy` استقرار می‌یابد (یا `meridian setup`)؛ با `meridian node add` exit دیگر اضافه کنید.

```
meridian node add [USER@]IP[:PORT] [flags]
meridian node list [--json]
meridian node restart NAME [--core|--all] [--yes] [--json]
meridian node remove NAME_OR_IP [--yes] [--force] [--forget-unreachable]
meridian node replace EXIT [USER@]NEW_IP[:PORT] [--name NAME] [--yes] [--forget-unreachable]
meridian node sni EXIT NEW_SNI [--self-steal] [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--name NAME` | (خودکار) | نام دوستانه برای گره |
| `--user USER` | ذخیره‌شده، وگرنه root | کاربر SSH روی گره |
| `--ssh-port PORT` | ذخیره‌شده، وگرنه 22 | پورت SSH روی گره (`node add`, `node replace`) |
| `--sni HOST` | (خودکار) | هدف استتار Reality برای این گره (بدون آن، ابتدا سایتی در زیرشبکهٔ خود گره ترجیح داده می‌شود، وگرنه `www.google.com`) |
| `--domain DOMAIN` | (هیچ) | دامنه گره: XHTTP به آن منتقل می‌شود و WSS اضافه می‌شود، هر دو از طریق CDN Cloudflare؛ Hysteria2 از گواهینامه آن استفاده می‌کند |
| `--self-steal` | خاموش | `node add`: استتار با دامنه خودتان (`--sni`، وگرنه `--domain`) که به گره اشاره می‌کند. `node sni`: `NEW_SNI` دامنه خود شماست |
| `--country CC` | رجیستری آدرس | کشور نمایش‌داده‌شده در نام اتصال‌ها؛ وقتی رجیستری اشتباه است (anycast یا بازه‌های اجاره‌ای) آن را مشخص کنید |
| `--harden / --no-harden` | فعال | مقاوم‌سازی سیستم‌عامل، SSH و firewall. سرورهای ناوگان همیشه آن را نگه می‌دارند؛ `--no-harden` رد می‌شود |
| `--yes` | | پرسش تأیید را رد کنید |
| `--forget-unreachable` | | `node remove`, `node replace`: آنچه روی سرورِ حذف‌شده مستقر شده را فراموش کن اگر از طریق SSH پاسخ نمی‌دهد (مسدود یا حذف شده)، به جای شکست در پاک‌سازی؛ تا وقتی حذفش نکنید به کاربران قبلی‌اش سرویس می‌دهد |
| `--force` | | `node remove`: همچنین زنجیرهای relay که به این exit مسیریابی می‌کنند را بردارید |
| `--json` | | `node list` / `node restart` را به عنوان پاکت `meridian.output/v1` ارسال کنید |

**`node add`** — از طریق SSH متصل شده، سرور را به عنوان exit در topology شما اضافه کرده و برنامه بررسی‌شده را اعمال می‌کند (hardening، agent گره و Xray، ثبت در سرویس کنترل). کلاینت‌های موجود exit جدید را در تازه‌سازی بعدی اشتراک دریافت می‌کنند.

**`node list`** — گره‌ها را با وضعیت لحظه‌ای agent آن‌ها، نسخه و ترافیک فهرست می‌کند. اگر سرویس کنترل در دسترس نباشد، گره‌های پیکربندی‌شده به عنوان `unknown` نشان داده می‌شوند و دستور با کد `3` خارج می‌شود.

**`node restart`** — فرمانی امضاشده به عامل سرور می‌فرستد و منتظر آماده شدن سرویس می‌ماند. به‌صورت پیش‌فرض و با `--core`، Xray (`netcore`) راه‌اندازی مجدد می‌شود؛ `--all` همهٔ سرویس‌های فعالِ تحت مدیریت سند فعلی سرور را یکی‌یکی راه‌اندازی مجدد می‌کند. هنگام راه‌اندازی مجدد هر سرویس، اتصال‌های فعال آن قطع می‌شوند. `--core` و `--all` هم‌زمان قابل استفاده نیستند؛ `--json` به `--yes` نیاز دارد. JSON فرمان‌ها و نتیجهٔ هر سرور را در `data.nodes[]` با وضعیت `done`، `failed` یا `timed_out` نگه می‌دارد. شکست با کد `4` و پایان پنج دقیقه انتظار با کد `3` گزارش می‌شود. در بخش سرورهای کنسول، دکمهٔ **راه‌اندازی مجدد Xray** با همان توضیحِ اتصال مجدد و نمایش نتایج وجود دارد.

**`node remove`** — یک exit یا دروازهٔ مسیریابی را از topology شما حذف می‌کند. همهٔ منابعی را که حذف خواهند شد فهرست می‌کند (رکورد و سند گره، agent و Xray آن، قوانین firewall، نقاط اتصال کلاینت)، تأیید می‌خواهد و دقیقاً همان بازبینی را اعمال می‌کند؛ سرور در سرورهای ذخیره‌شده باقی می‌ماند. این دستور برای سرور کنترل (از `meridian teardown` استفاده کنید)، تا وقتی relayها هنوز به این exit مسیریابی می‌کنند (ابتدا آن‌ها را حذف کنید یا `--force` بدهید)، تا وقتی یک دروازهٔ مسیریابی از طریق آن وارد ناوگان می‌شود، و وقتی نتیجه topology را می‌شکند (مثلاً خالی شدن استخر egress یا حذف egress پیش‌فرض) اجرا نمی‌شود. قوانین مسیریابی محدود به دروازهٔ حذف‌شده همراه آن حذف می‌شوند.

**`node replace`** — یک exit را به سرور دیگری منتقل می‌کند. `EXIT` شناسهٔ exit یا نام ذخیره‌شده یا IP سرور آن است؛ سرور جدید از همان نحو هدف `node add` استفاده می‌کند (نام ذخیره‌شده یا `local` هم کار می‌کند) و مانند `server add` ذخیره می‌شود. exit شناسه، کلیدهای Reality، مسیرهای پروتکل، SNI، تنظیمات WARP و geo، و هر relay را که به آن اشاره می‌کند حفظ می‌کند، بنابراین کاربران relay بدون قطعی کار می‌کنند و کاربران مستقیم نشانی جدید را در تازه‌سازی بعدی اشتراک می‌گیرند. بازبینی، آنچه روی سرور جدید مستقر خواهد شد و همهٔ منابعی را که روی سرور قدیم پاک‌سازی می‌شوند (agent و Xray، فایل‌های nginx، قوانین firewall و گواهینامه‌ها) فهرست می‌کند؛ سرور ذخیره‌شده باقی می‌ماند. برای سرور کنترل (جابه‌جایی آن هر URL اشتراک را تغییر می‌دهد؛ اگر از دست رفته، از `meridian restore` استفاده کنید) و برای سرور جدیدی که از قبل نقش دارد رد می‌شود.

**`node sni`** — برای مسیر Reality یک exit، SNI استتار جدیدی تنظیم می‌کند. `EXIT` ID exit یا نام ذخیره‌شده یا IP سرور آن است. نام‌های `apple.com` و `icloud.com` و `www.microsoft.com` را رد می‌کند، از طریق SSH بررسی می‌کند که exit با TLS 1.3 و HTTP/2 به سایت جدید می‌رسد، بررسی را نشان می‌دهد (relayهایی که از SNI exit پیروی می‌کنند، relayهایی که SNI خود را نگه می‌دارند، دروازه‌های مسیریابی ساخته‌شده بر این مسیر، و آنچه پاک می‌شود)، تأیید می‌گیرد و اعمال می‌کند. نام قدیمی جایگزین می‌شود، نه اینکه کنار نام جدید بماند: برنامه‌ها در تازه‌سازی بعدی اشتراک (هر 6 ساعت) یا تازه‌سازی دستی جابه‌جا می‌شوند و تا آن زمان نمی‌توانند از طریق Reality وصل شوند. XHTTP، WSS و Hysteria2 تغییر نمی‌کنند. وقتی `meridian test --probe` گزارش می‌دهد SNI استتار مسدود است از آن استفاده کنید. با `--self-steal`، `NEW_SNI` دامنه‌ای است که مالکش هستید: به‌جای بررسی دسترسی، بررسی می‌کند که نام به exit ترجمه شود (اگر ترجمه نشود متوقف می‌شود و اگر به جای دیگری اشاره کند هشدار می‌دهد)، و exit برای آن گواهی Let's Encrypt می‌گیرد و خودش به بررسی‌ها پاسخ می‌دهد.


### meridian relay

relayها را مدیریت کنید — فورواردرهای TCP مبتنی بر Realm که به کاربران نقطهٔ ورود داخلی به یک سرور خروجی در خارج می‌دهند. relayها ترافیک Reality را حمل می‌کنند.

```
meridian relay add [USER@]RELAY_IP[:PORT] --exit EXIT [flags]
meridian relay list [--exit EXIT] [--json]
meridian relay remove RELAY [--exit EXIT] [--yes] [--forget-unreachable]
meridian relay sni RELAY NEW_SNI [--exit EXIT] [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--exit/-e EXIT` | (الزامی برای add) | IP یا نام سرور exit |
| `--name NAME` | (خودکار) | نام دوستانه برای relay (مثل "ru-moscow") |
| `--port/-p PORT` | 443 | پورت گوش دهی روی سرور relay |
| `--sni HOST` | هدف exit | هدف camouflage Reality برای این relay؛ برای استفاده از exit حذف کنید |
| `--user/-u USER` | ذخیره‌شده، وگرنه root | کاربر SSH روی relay |
| `--ssh-port PORT` | ذخیره‌شده، وگرنه 22 | پورت SSH روی سرور relay (`relay add`) |
| `--yes/-y` | | پرسش تأیید را رد کنید |
| `--forget-unreachable` | | `relay remove`: آنچه روی سرورِ حذف‌شده مستقر شده را فراموش کن اگر از طریق SSH پاسخ نمی‌دهد (مسدود یا حذف شده)، به جای شکست در پاک‌سازی؛ تا وقتی حذفش نکنید به کاربران قبلی‌اش سرویس می‌دهد |
| `--json` | | `relay list` (`data.relays[]`) را به عنوان پاکت `meridian.output/v1` ارسال کنید |

**`relay add`** — relay تک‌hop را به topology شما اضافه کرده و آن را اعمال می‌کند. کلاینت‌ها آن را در بعدی تازه‌سازی اشتراک دریافت می‌کنند. برای زنجیری با بیش از یک hop، از `meridian setup` استفاده کنید.

**`relay remove`** — `RELAY` یک IP سرور relay یا نام ذخیره‌شده یا ID زنجیره relay است. هر زنجیره‌ای را از طریق آن سرور می‌اندازد (آن را با `--exit` محدود کنید)، فهرست می‌کند که چه چیزی حذف خواهد شد (واحدهای Realm، قوانین firewall، شنونده سمت exit، نقاط اتصال کلاینت)، تأیید می‌کند و حذف بررسی‌شده را اعمال می‌کند. سرورها در سرورهای ذخیره‌شده باقی می‌مانند.

**`relay sni`** — برای زنجیره‌های relay از طریق یک سرور (یا یک زنجیره با ID؛ با `--exit` محدود کنید) SNI استتار جدیدی تنظیم می‌کند. همان نام‌های `node sni` را رد می‌کند، بررسی می‌کند که exit به سایت می‌رسد (نام خود relay را یک شنوندهٔ Reality روی exit سرو می‌کند)، بررسی را نشان می‌دهد، تأیید می‌گیرد و اعمال می‌کند. دادن SNI خود exit باعث می‌شود relay دوباره از exit پیروی کند. برنامه‌ها در تازه‌سازی بعدی اشتراک جابه‌جا می‌شوند.

برای بررسی hopهای relay، از `meridian check RELAY` استفاده کنید.

### meridian route

مقاصد انتخاب‌شده را از exit از طریق Cloudflare WARP، مستقیم، یا هیچ‌کدام ارسال کنید، پیش از egress پیش‌فرض exit.

```
meridian route add EXIT VALUE... --via warp|direct|block [--name ID] [--json]
meridian route add EXIT --preset ai [--via warp|direct|block] [--name ID] [--json]
meridian route list [EXIT] [--json]
meridian route remove EXIT ROUTE [--yes] [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--via ACTION` | `warp` همراه `--preset`، وگرنه الزامی برای add | `warp`، `direct` یا `block` |
| `--preset NAME` | | مجموعه نام‌دار مقصدها به جای `VALUE`: `ai` (سرویس‌های هوش مصنوعی) |
| `--name ID` | نام preset، یا action شماره‌دار | Route ID نشان داده‌شده توسط `route list` و استفاده شده توسط `route remove` |
| `--yes/-y` | | تأیید حذف را رد کنید (با `--json` الزامی است) |
| `--json` | | پاکت `meridian.output/v1` ارسال کنید (`data.override` برای add/remove، `data.exits[]` برای list) |

`EXIT` ID exit، نام سرور ذخیره‌شده یا IP است. هر `VALUE` دامنه (subdomains شامل)، `geosite:NAME` یا `geoip:NAME` است؛ یک route یک نوع را نگاه می‌دارد.

**`route add`** — مسیر (route) را به exit در توپولوژی شما اضافه می‌کند و آن را اعمال می‌کند. مسیرها به ترتیبی که اضافه شده‌اند بررسی می‌شوند. یک مسیر `warp` روی سروری که WARP ندارد، WARP را فقط برای همان مسیر راه‌اندازی می‌کند؛ سایر ترافیک مستقیم می‌ماند.

**`route list`** — هر exit's egress پیش‌فرض و routes آن را به ترتیب match نشان می‌دهد.

**`route remove`** — یک route را حذف کرده و تغییر را اعمال می‌کند؛ مقاصد آن egress پیش‌فرض exit را دنبال می‌کند دوباره. WARP روی سرور نصب شده باقی می‌ماند اما هیچ چیزی را حمل نمی‌کند تا route یا `--warp` آن را استفاده کند.

### meridian fleet

سلامت و موجودی ناوگان از سرویس کنترل زنده، تاریخچهٔ applyها، ارتقاها و ناوگان به‌صورت فایل قابل ویرایش.

```
meridian fleet status [--json]
meridian fleet inventory [--json]
meridian fleet history [--json]
meridian fleet events [--since ID] [--limit N] [--json]
meridian fleet usage [--days N] [--json]
meridian fleet routing [ru-split|full] [--dry-run] [--yes] [--json]
meridian fleet contact [--text TEXT] [--link LINK|none] [--dry-run] [--yes] [--json]
meridian fleet notice show [--for NAME] [--json]
meridian fleet notice set TEXT [--until WHEN] [--for NAME] [--yes] [--json]
meridian fleet notice clear [--yes] [--json]
meridian fleet language [en|ru|fa|zh] [--json]
meridian fleet upgrade [--tested] [--yes]
meridian fleet export [--json]
meridian fleet import FILE [--dry-run] [--yes] [--forget-unreachable] [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--since ID` | 0 | `fleet events`: رویدادهای پس از این شناسه |
| `--limit N` | 100 | `fleet events`: بازگرداندن ۱ تا ۲۰۰۰ رویداد |
| `--days N` | 30 | روزهای UTC برای `client usage` یا `fleet usage`، بین 1–730 و در محدودهٔ مدت نگهداری ذخیره‌شده |
| `--json` | | نتیجه را در قالب `meridian.output/v1` برگردانید (`status`، `inventory`، `history`، `routing`، `export`، `import`، `usage`) |
| `--tested` | | `fleet upgrade`: از GitHub نمی‌پرسد؛ Realm روی نسخهٔ تست‌شده یا نسخه‌ای که قبلاً به آن ارتقا داده‌اید می‌ماند |
| `--yes`, `-y` | | `fleet upgrade`، `fleet routing`، `fleet import`: بدون پرسش تأیید اعمال کنید |
| `--dry-run` | | `fleet routing`، `fleet import`: تغییرات و طرح بازبینی را بدون اعمال نشان دهید |
| `--forget-unreachable` | | `fleet import`: آنچه روی سرور حذف‌شده‌ای که درگاه SSH آن پاسخ نمی‌دهد مستقر شده فراموش می‌شود |

**`fleet status`** — سلامت سرویس کنترل، آخرین گزارش هر agent و اینکه پیکربندی فعلی را اعمال کرده یا نه، relay listeners و تعداد کلاینت. کلاینت‌های اعلام‌شده missing سلامتی را کاهش می‌دهند؛ کلاینت‌های غیرفعال، محدود یا منقضی شده شمرده می‌شوند اما انتخاب شما هستند، نه خرابی. relay listener قابل دسترس فقط TCP را ثابت می‌کند، پس مسیر relay غیر‌تأیید‌شده سلامتی را `unknown` نگه می‌دارد؛ از `meridian test` برای بررسی مسیر کامل استفاده کنید. Exit `0` سلامت، `4` کاهش و `3` نامعلوم است.

ستون `active` تعداد افرادی را نشان می‌دهد که در آخرین گزارش افزایش ترافیک داشته‌اند؛ زمان جمع‌آوری گزارش زیر جدول آمده است. گزارش قدیمیِ دیررس جای داده‌های جدیدتر را نمی‌گیرد. مجموع ترافیک گره با تغییر دورهٔ شمارنده حفظ می‌شود؛ `traffic_counting_since` آغاز شمارش کامل و پایدار را مشخص می‌کند و تنها شواهد باقی‌ماندهٔ پیش از ارتقا بازیابی می‌شوند.

`GET /api/nodes/NODE` مجموع پایدار `traffic_bytes`، بازهٔ آخرین گزارش فعالیت و آغاز شمارش کامل را برمی‌گرداند؛ قرارداد آن با `meridian api schema service-node-status` در دسترس است.

**`fleet inventory`** — سرورها، نقش‌ها، گره‌ها و relayهای پیکربندی‌شدهٔ شما را همراه با وضعیت لحظه‌ای، وقتی سرویس کنترل در دسترس است، نشان می‌دهد. هرگز توکن‌های API یا مسیرهای مخفی را چاپ نمی‌کند. اگر وضعیت لحظه‌ای در دسترس نباشد، موجودی پیکربندی‌شده همچنان همراه با هشدار نشان داده می‌شود و دستور با کد `3` خارج می‌شود. از `plan --json` برای بررسی اینکه آیا `apply` کاری برای انجام دارد استفاده کنید.

**`fleet history`** — هر apply بازبینی‌شده‌ای که سرویس کنترل ثبت کرده، از جدیدترین: شماره، زمان، نویسنده (نام توکن ماشین؛ `root` برای توکن خود CLI و `owner` برای کنسول)، وضعیت (`proposed`، `approved`، `applied` یا `failed`) و ابتدای hash طرح. `--json` فهرست `data.revisions[]` را برمی‌گرداند.

**`fleet events`** — تغییرات محلی کاربران، توکن‌ها و حریم خصوصی، همراه با قطع ارتباط گره‌ها و بازیابی آن. رویدادها پس از `--since ID`، از قدیمی به جدید، نمایش داده می‌شوند (پیش‌فرض `0`). `--limit N` بین ۱ تا ۲۰۰۰ رویداد برمی‌گرداند؛ پیش‌فرض ۱۰۰ است. JSON شامل `data.events[]`، `next_cursor` و `has_more` است؛ برای ادامه از شناسهٔ برگشتی استفاده کنید. هر رویداد زمان UTC، نوع، انجام‌دهنده (نام توکن، `root`، `owner` یا `system`)، موضوع و جزئیاتی کوتاه مانند نام فیلدهای تغییرکرده، سطح دسترسی توکن یا شناسهٔ ثبت تغییر حریم خصوصی دارد. اطلاعات اتصال، متن خام خطاها، نشانی کاربران و داده‌های دستگاه ثبت نمی‌شوند. حداکثر ۲۰۰۰ رویداد از ۱۸۰ روز گذشته نگهداری می‌شود و در نسخه‌های پشتیبان قرار می‌گیرد. `GET /api/events?after=ID&limit=N` به سطح `read` نیاز دارد و برای مالک واردشده نیز قابل دسترسی است.

**`fleet upgrade`** — ناوگان را با یک apply بازبینی‌شده به‌روز می‌کند. سرویس کنترل و هر agent گره به buildی می‌روند که همراه این نسخهٔ Meridian عرضه می‌شود و هر agent در جا ارتقا می‌یابد و هویت گره‌اش را حفظ می‌کند؛ برای نسخه‌های تازه‌تر، ابتدا `meridian update` را اجرا کنید. relayها بدون انتظار برای به‌روزرسانی Meridian به جدیدترین نسخهٔ Realm می‌روند: جدیدترین نسخهٔ GitHub در همان major تست‌شده، همراه با sha256 که GitHub برای هر آرشیو منتشر می‌کند در `cluster.yml` ثبت می‌شود و هر relay پیش از نصب آن را بررسی می‌کند. آنچه روی هر سرور اجرا می‌شود را با `current` یا `upgrade` نشان می‌دهد، سپس پس از تأیید شما طرح بازبینی‌شده را اعمال می‌کند و `meridian check` را روی هر سرور اجرا می‌کند. نسخه‌ای که خوانده نشود دستور را پیش از هر تغییری با کد `3` متوقف می‌کند.

**`fleet routing`** — حالت مسیریابی دستگاه‌ها را از توپولوژی محلی می‌خواند و هر دو گزینه را توضیح می‌دهد. `ru-split` (پیش‌فرض) مقصدهای روسی منطبق با قوانین، بازه‌های خصوصی و شبکهٔ محلی را مستقیم می‌فرستد؛ `full` ترافیک اینترنت، از جمله مقصدهای روسی، را از VPN عبور می‌دهد و بازه‌های خصوصی و شبکهٔ محلی را مستقیم نگه می‌دارد. هر دو حالت مسدودسازی QUIC و قانون اتصال مستقیم به همتایان شناسایی‌شدهٔ BitTorrent در Xray JSON را حفظ می‌کنند تا شکایت‌های کمتری متوجه سرورهای خروجی شود. با دادن نام حالت، توپولوژی ویرایش می‌شود و پس از بازبینی و تأیید، دقیقاً همان طرح اعمال می‌شود. بدون ترمینال یا با `--json`، تغییر به `--yes` نیاز دارد؛ `--dry-run` طرح را بدون اعمال نشان می‌دهد. JSON مقدارهای `data.client_routing` و `choices[]` و در صورت وجود، نتایج بازبینی و اعمال را برمی‌گرداند. برنامه‌ها حالت را در تازه‌سازی بعدی اشتراک یا پس از تازه‌سازی دستی دریافت می‌کنند. کنسول آن را در بخش تنظیمات فقط برای خواندن نشان می‌دهد. مسدودسازی جغرافیایی روی خروجی جداگانه تنظیم می‌شود؛ پیوندهای Base64 قانون مسیریابی ندارند. محدودیت قالب‌ها و اجازهٔ دسترسی به مقصدهای روسی روی خروجی در [مسیریابی دستگاه‌ها](/fa/split-routing/) توضیح داده شده است.

**`fleet export`** — توپولوژی بازبینی‌شدهٔ ناوگان شما را به شکل یک فایل YAML قابل ویرایش چاپ می‌کند: خروجی‌ها و مسیرهای پروتکل آن‌ها، relayها، دروازه‌ها، استخرهای خروجی، قواعد مسیریابی، routeها، کاربران و تنظیمات ناوگان. سرورها با نام ذخیره‌شده‌شان (یا نشانی، اگر نامی ندارند) می‌آیند، نه با شناسهٔ داخلی، و فایل با `schema: meridian.fleet/v1` شروع می‌شود. کلیدهای Reality، توکن‌های API، پیوندهای کاربران و مسیرهای انتقال XHTTP و WSS در Meridian می‌مانند و در فایل نیستند. `--json` همین سند را زیر `data.document` برمی‌گرداند.

**`fleet import`** — فایل ویرایش‌شده (یا `-` برای ورودی استاندارد) را می‌خواند و تغییرات آن را هر کدام در یک خط نشان می‌دهد: `+` افزودن، `-` حذف و `~` تغییر یک فیلد (`~ exit-2 sni www.example.com -> www.example.org`). سپس هر منبعی را که تغییر حذف می‌کند و هش بازبینی را فهرست می‌کند، تأیید می‌خواهد و دقیقاً همان بازبینی را مانند `apply` اعمال می‌کند. فایلی بدون ویرایش «تغییری نیست» چاپ می‌کند. حذف یک کاربر از `access.users` او را مانند `client remove` حذف می‌کند: URL اشتراک و صفحهٔ اتصالش دیگر پاسخ نمی‌دهند. افزودن کاربر او را مانند `client add` می‌سازد و سرویس صفحهٔ اتصالش را به‌طور خودکار ارائه می‌کند؛ `client show NAME` پیوندها را چاپ می‌کند. SNIهای استتار تازه همان بررسی‌های `node sni` را می‌گذرانند. وارد کردن این‌ها را رد می‌کند: `schema` دیگر، سروری که ذخیره نکرده‌اید (با `meridian server add` ذخیره‌اش کنید)، مسیرهای انتقال در فایل، تغییر سرور کنترل، دامنه یا بک‌اند آن، حذف یا تغییر نام خروجیِ روی سرور کنترل، و انتقال یک خروجی به سرور دیگر (از `node replace` استفاده کنید). کلیدها و اطلاعات ورود همان‌طور می‌مانند. بدون ترمینال `--yes` بدهید؛ `--dry-run` تغییرات و بازبینی را بدون اعمال نشان می‌دهد.

**`fleet usage`** — مجموع بایت‌های هر سرور را در هر روز UTC، شامل مصرف باقی‌ماندهٔ سرورهای حذف‌شده، نشان می‌دهد. `--days N` بین 1–730 روز در محدودهٔ مدت نگهداری انتخاب می‌کند. تاریخچه باید روشن باشد؛ JSON مجموع مجموعه و `nodes[].daily` را در `data` برمی‌گرداند.

**`fleet contact`** — تماس عمومی مالک را نشان می‌دهد یا برای بررسی آماده می‌کند. `--text TEXT` یک خط متن ساده با حداکثر ۱۲۰ نویسه و `--link LINK` یک پیوند استاندارد `https:`، `tg:` یا `mailto:` تعیین می‌کند. فیلدهای واردنشده حفظ می‌شوند؛ `--text ""` و `--link none` آن‌ها را پاک می‌کنند. `--dry-run` نتیجهٔ بررسی را برمی‌گرداند؛ تغییر بدون ترمینال یا با `--json` به `--yes` نیاز دارد. JSON شامل `data.owner_contact`، بررسی و نتیجهٔ اعمال است. کنسول تماس را فقط برای مشاهده نشان می‌دهد و خروجی/ورودی سرورها `delivery.owner_contact` را منتقل می‌کنند. صفحه‌ها راهنما و پیوندی را نشان می‌دهند که کاربر خودش باز می‌کند؛ برنامه‌ها از آن برای دکمهٔ پشتیبانی استفاده می‌کنند. [تماس مالک](/fa/client-management/).
**سهمیهٔ سرورها** — `fleet status` و صفحهٔ فقط‌خواندنی «سرورها» در کنسول، مصرف دوره، ارائه‌دهنده، روز بازنشانی، پرداخت بعدی و هشدارهای سرور را نشان می‌دهند. مصرف، برآورد ترافیک پذیرفته‌شدهٔ کاربران است (ارسال + دریافت)؛ سربار پروتکل، دریافت‌های خود سرور و ترافیک عبوری سرورهای واسط را شامل نمی‌شود. هر گزارش در دورهٔ دریافتش به وقت UTC شمارش می‌شود؛ بنابراین گزارش دیررس می‌تواند مصرف دورهٔ بعدی را افزایش دهد. برای سرورهای واسط و سرور کنترل بدون عامل، عبارت **اندازه‌گیری نمی‌شود** نمایش داده می‌شود و عدد مصرفی وجود ندارد. کنسول دستور `meridian server set NAME` را برای تغییر نشان می‌دهد.

`GET /api/servers` به دسترسی read نیاز دارد و قرارداد `server-usage` را برمی‌گرداند: اطلاعات سرور، مرزهای دوره به وقت UTC، بایت‌های شمارش‌شده، آغاز شمارش، پرداخت بعدی و محدودهٔ اندازه‌گیری. `GET /api/attention` بخش `servers[]` را اضافه می‌کند: `allowance_near` در 80٪، `allowance_exceeded` در 100٪، `payment_due` تا 7 روز پیش از پرداخت و `payment_overdue` برای تاریخ گذشتهٔ یک‌باره. آستانه‌های `allowance_percent` و `allowance_exceeded_percent` در درخواست، بین 1 تا 100 هستند و اولی نباید از دومی بیشتر باشد؛ `payment_days` بین 1 تا 30 است. هشدارهای سهمیه و پرداخت، `summary.needs_attention` را فعال می‌کنند؛ وضعیت مجموعه و کدهای خروج همچنان وضعیت اجرای سرویس‌ها را توصیف می‌کنند.

پیام متعلق به مدیر سرویس است. `fleet notice set` پیش‌نمایش را قبل از تأیید نشان می‌دهد؛ `--until WHEN` پایان اعتبار را تعیین می‌کند و `--for NAME` اطلاعات حساب را جای‌گذاری می‌کند. تغییر در حالت JSON نیاز به `--yes` دارد. `fleet notice show` پیام را می‌خواند و `fleet notice clear` حذف را تأیید می‌کند. به [مدیریت کاربران](/fa/client-management/) مراجعه کنید.

پیام‌های وضعیت اشتراک از زبان صریح سرویس استفاده می‌کنند: `en`، `ru`، `fa` یا `zh`. `fleet language` تنظیم را می‌خواند و `fleet language CODE` آن را ذخیره می‌کند. `client set NAME --language CODE` زبان فرد را تعیین می‌کند و `--language default` آن را پاک می‌کند. کد وضعیت‌ها انگلیسی می‌ماند. این تنظیمات در اعمال بررسی‌شده و نسخه‌های پشتیبان رمزگذاری‌شده حفظ می‌شوند.

### meridian context

چند ناوگان جدا را روی یک دستگاه نگه دارید، مثلاً یکی برای خانواده و یکی برای کار، و انتخاب کنید دستورات روی کدام کار کنند.

```
meridian context list [--json]
meridian context use NAME
meridian context rename OLD NEW
meridian context remove NAME [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--json` | | `context list`: یک پاکت `meridian.output/v1` چاپ می‌کند |
| `--yes`, `-y` | | `context remove`: زمینه‌ای را که ناوگانش هنوز سرور دارد بدون پرسش حذف می‌کند |

**`context list`** — همهٔ زمینه‌ها با سرور کنترل و تعداد سرورهای خروجی، رله‌ها و دروازه‌های مسیریابی هر کدام، فقط از روی همین دستگاه؛ `*` زمینهٔ فعلی را نشان می‌دهد:

```
  * default   198.51.100.10    2 exits, 1 relay
    family    198.51.100.40    1 exit
```

**`context use`** — NAME را ناوگانی می‌کند که همهٔ دستورات بعدی روی آن کار می‌کنند. `meridian deploy IP --context NAME` زمینهٔ تازه می‌سازد و هر دستوری `--context NAME` را می‌پذیرد تا یک بار روی ناوگان دیگری کار کند.

**`context rename`** — نام زمینه را تغییر می‌دهد؛ به ناوگان و سرورها دست نمی‌زند.

**`context remove`** — فایل‌های زمینه را از این دستگاه پاک می‌کند و هرگز به سروری وصل نمی‌شود: سرورها به کار ادامه می‌دهند، اما این دستگاه دیگر نمی‌تواند آن‌ها را مدیریت کند. زمینهٔ فعلی را حذف نمی‌کند و تا وقتی ناوگان سرور دارد اول می‌پرسد (`--yes` پرسش را رد می‌کند). زمینهٔ `default` خودِ دایرکتوری خانگی Meridian است، پس تغییر نام نمی‌دهد و فقط وقتی حذف می‌شود که زمینهٔ دیگری ناوگانش را تحویل گرفته باشد. چنین نسخه‌ای در `context list` جایگزین‌شده نشان داده می‌شود و هیچ تغییری را نمی‌پذیرد؛ حذف `default` در این حالت فقط فایل‌های ناوگان را پاک می‌کند و کلید SSH و ترجیحات می‌مانند.

### meridian check

سلامت سرور را بررسی کنید، یا اینکه آیا یک سرور جدید می‌تواند Meridian را اجرا کند. آنچه اجرا می‌شود به نقش سرور در ناوگان شما بستگی دارد:

- **هنوز در ناوگان نیست** — بررسی‌های پیش‌استقرار: در دسترس بودن هدف استتار و DNS، آزاد بودن و دسترسی خارجی پورت 443، DNS دامنه، سیستم‌عامل، دیسک و ساعت. هیچ چیزی نصب نمی‌شود؛ زمانی که پورت 443 آزاد باشد، یک شنوندهٔ کوتاه‌مدت فایروال را آزمایش می‌کند. DNS از resolver خود سرور استفاده می‌کند.
- **سرور کنترل، exit یا routing gateway** — سرویس کنترل (پاسخ می‌دهد، متعلق به همین ناوگان است و نسخهٔ سازگار دارد)، agent هر گره (آنلاین، پیکربندی فعلی را اعمال کرده، build فعلی)، SSH (یا دسترسی محلی)، هر پورت عمومی و داخلی کامپایل‌شده، گواهینامه‌های TLS و فضای دیسک. اگر از دستگاه دیگری اجرا کنید، سرور کنترل بررسی جریان داده را هم دریافت می‌کند: دانلود ~50 کیلوبایتی که اگر پس از حدود 16 تا 24 کیلوبایت متوقف شود هشدار می‌دهد (محدودسازی سرعت، اندازه‌گیری‌شده از شبکهٔ شما).
- **Relay** — هر گام Realm روی سرور: سرویس فعال است و می‌تواند به گام بعدی برسد، و ورودی عمومی زنجیره اتصال TCP را از دستگاه شما می‌پذیرد.

بدون سرور، هر سرور در ناوگان بررسی می‌شود.

```
meridian check [SERVER] [--domain NAME] [--sni HOST] [--user USER]
               [--ssh-port PORT] [--ai] [--json]
```

`--domain` و `--sni` برای سروری که هنوز deploy نشده اعمال می‌شوند: بررسی می‌کنند که دامنه به سرور ترجمه شود و هدف استتار مشخص‌شده در دسترس باشد. `--user` و `--ssh-port` کاربر و پورت ذخیره‌شدهٔ SSH را بازنویسی می‌کنند. `--ai` یک پرامپت تشخیصی آمادهٔ AI را در clipboard کپی می‌کند. `--json` یک پاکت `meridian.output/v1` شامل گزارش هر سرور و دامنهٔ بررسی چاپ می‌کند.

نبودن شواهد هرگز به‌عنوان موفقیت تلقی نمی‌شود. کد خروج `0` یعنی همهٔ بررسی‌ها موفق بوده‌اند، `4` یعنی مشکلاتی پیدا شده، `3` یعنی شواهد لازم در دسترس نبوده، و `2` یعنی ورودی نامعتبر است. هر خطا راه‌حل خود را هم چاپ می‌کند. برای عبور دادن ترافیک واقعی از کل مسیر، از `meridian test` استفاده کنید.

### meridian scan

با استفاده از pinned RealiTLScanner release روی شبکه خود سرور هدف‌های camouflage پیدا کنید. Meridian قبل از اجرا SHA-256 checksum آن را تأیید می‌کند و workspace راه دور را بعد از آن حذف می‌کند.

```
meridian scan [SERVER] [--user USER] [--ssh-port PORT]
```

RealiTLScanner محدوده IPv4 را اسکن می‌کند؛ سرور IPv6-only exit `3` می‌شود. انتخاب نتیجه دستور را برای استفاده آن چاپ می‌کند — topology استقرار‌یافته را تغییر نمی‌دهد. رد کردن exit `0`، انتخاب نامعتبر exit `2`، بدون هدف مناسب exit `4` و scanner یا دانلود failures exit `3`.

### meridian test

ترافیک پراکسی تحویل‌شده را از دستگاه خودتان آزمایش کنید. نیازی به SSH نیست.

آزمایش کامل یک کلاینت فعال را انتخاب می‌کند، دقیقاً همان Xray JSONی را که سرویس کنترل تحویل می‌دهد می‌گیرد و ترافیک واقعی را از مسیر جایگزینی خودکار و از تک‌تک مسیرهای سرور هدف عبور می‌دهد. اولین اجرا ممکن است تا 120 ثانیه صرف دانلود و بررسی نسخهٔ پین‌شدهٔ Xray کند. بررسی‌های ترافیک چند سرویس مستقل تشخیص IP را می‌چرخانند و با درخواست مستقیم مقایسه می‌کنند، بنابراین در دسترس نبودنِ سرویس تشخیص IP نامشخص (inconclusive) اعلام می‌شود، نه خطای کاذب. `MERIDIAN_CONNECT_TEST_URL` سرویس تشخیص IP را برای محیط‌های کنترل‌شده تغییر می‌دهد.

هر مسیر زمان رسیدن به اولین بایت را گزارش می‌دهد. وقتی مسیری ناموفق باشد، Meridian یک اتصال سادهٔ TCP به نقطهٔ پایانی باز می‌کند تا مشخص کند آیا **متصل می‌شود اما ترافیکی عبور نمی‌کند** (سرور پاسخ می‌دهد اما نشست پراکسی چیزی جابه‌جا نمی‌کند: کلید نادرست یا قطع شدن نشست) یا **غیرقابل دسترس است** (هیچ پاسخی روی آن پورت نمی‌آید). با `--json`، فیلد `data.transports` نتیجهٔ هر مسیر (`ok`، `no_traffic`، `unreachable`، `failed`، `egress_mismatch`، `inconclusive`، `invalid`) و `first_byte_ms` را فهرست می‌کند.

در دسترس نبودن سرویس کنترل، خطای HTTP `429` یا `5xx` باعث می‌شود اشتراک در دسترس نباشد و دستور با کد `3` خارج شود. هر خطای دیگر اشتراک مانند `400` یا `422` شکست قطعی محسوب می‌شود و با کد `4` خارج می‌شود.

```
meridian test [SERVER|DOMAIN] [--domain NAME] [--sni NAME]
              [--client NAME] [--basic] [--probe] [--timeout SECONDS] [--json]
```

بدون هدف، `test` سرور ذخیره‌شده‌ای را که روی آن اجرا می‌شود یا تنها سرور ذخیره‌شدهٔ شما را تست می‌کند. اگر چند سرور باشد، هر نقطهٔ ورود عمومی ناوگان شما را به‌ترتیب تست می‌کند (هر exit، سپس نقطهٔ ورود هر relay) و با بدترین نتیجه خارج می‌شود؛ در این حالت `--json` برای هر سرور یک نتیجه در `data.results` برمی‌گرداند.

`--client` کلاینت فعال مشخصی را آزمایش می‌کند. `--basic` فقط بررسی‌های شبکه و TLS را بدون دانلود Xray اجرا می‌کند و نمی‌تواند مسیرهای فقط UDP را تأیید کند؛ ترکیب آن با `--client` مجاز نیست (خروج `2`). `--timeout` (پیش‌فرض `5`، بازهٔ `1` تا `30`) زمان هر عملیات شبکه را جدا از دانلود اولیهٔ Xray محدود می‌کند.

خروج `0` یعنی همهٔ بررسی‌ها موفق بوده‌اند، `4` یعنی مشکل پیدا شده، و `3` یعنی شواهد لازم در دسترس نبوده است. `--json` یک پاکت `meridian.output/v1` شامل همهٔ بررسی‌ها و یافته‌ها چاپ می‌کند.

#### نقطه نظر سانسورکننده: `meridian test --probe`

`--probe` به‌جای ارسال ترافیک، سرور را همان‌طور که یک کاوشگر فعال سانسورچی بررسی می‌کند می‌سنجد تا ببیند آیا استقرار خودش را لو می‌دهد یا نه. روی هر IP یا دامنه‌ای کار می‌کند و وقتی هدف متعلق به توپولوژی ذخیره‌شدهٔ شما باشد بررسی‌های سخت‌گیرانه‌تری اعمال می‌کند.

بررسی‌ها مطابق استقرار واقعی انجام می‌شوند: پورت‌های باز عمومی و داخلی، رفتار HTTP/TLS، سازگاری و استتار SNI، مسیرهای رایج پراکسی و پنل‌های مدیریت، ارتقای WebSocket،‏ reverse DNS،‏ HTTP/2، نسخه‌های قدیمی TLS و دامنه‌های پیکربندی‌شده. `--sni` مقدار SNI را برای کاوش‌های عمومی TLS بازنویسی می‌کند. برای شنونده‌های فقط UDP به‌جای حدس زدن اعلام می‌شود که نیاز به اجرای کامل `meridian test` دارند.

`--probe` همچنین به سؤال «چه چیزی مسدود است؟» پاسخ می‌دهد. اتصال TLS را با SNI استتار سرور باز می‌کند؛ اگر ناموفق بود، بدون SNI دوباره تلاش می‌کند و سایت استتار واقعی را هم مستقیماً باز می‌کند، سپس گزارش می‌دهد که آیا **IP سرور** یا **SNI استتار** مسدود به نظر می‌رسد. اگر دسترسی مستقیم به سایت واقعی هم ممکن نباشد، نتیجه نامشخص اعلام می‌شود نه خطا. در حالت استتار self-steal، سایت واقعی همان سرور شماست و معیار مستقلی برای مقایسه وجود ندارد: وقتی هیچ اتصالی برقرار نشود، نتیجه نامشخص است. روی سرور کنترل، اسکریپت ~50 کیلوبایتی صفحهٔ اتصال را هم دانلود می‌کند و بررسی می‌کند که آیا انتقال پس از حدود 16 تا 24 کیلوبایت متوقف می‌شود یا نه — که رفتار رایج روی IPهای خارجیِ محدودشده (throttled) است. وقتی مسیر WSS از CDN عبور کند، همین دانلود از طریق CDN هم انجام می‌شود. این نتایج تنها زمانی معنا دارند که دستور را از داخل شبکهٔ سانسورشده اجرا کنید. `--probe` را نمی‌توان با `--basic`، `--client` یا `--domain` ترکیب کرد. کدهای خروج مانند `test` هستند؛ بررسی‌های ردشده (skipped) هرگز موفق گزارش نمی‌شوند.

`meridian probe [SERVER|DOMAIN] [--sni NAME] [--timeout SECONDS] [--json]` همان `meridian test IP --probe` است.

### meridian doctor

جمع‌آوری تشخیص سیستم برای bug reports.

```
meridian doctor [SERVER] [--sni HOST] [--user USER] [--ssh-port PORT] [--ai]
```

`--sni` هدف camouflage را برای تشخیص انتخاب می‌کند، `--user` و `--ssh-port` کاربر SSH ذخیره‌شده و پورت را جایگزین می‌کنند و `--ai` گزارش redacted، آماده‌شده برای AI را به clipboard کپی می‌کند بجای چاپ issue template.

Doctor از نقش‌های سرور پیروی می‌کند: سرور relay-only به عنوان exit تشخیص نمی‌شود، و routing gateways به طور جداگانه برچسب‌گذاری می‌شوند. ابزارهای missing یا اتصال SSH گم گزارش را inconclusive می‌کند (exit `3`)؛ بخش‌های قبلاً جمع‌آوری‌شده همچنان نشان داده می‌شوند.

### meridian logs

لاگ‌های اخیر یک سرور را، redacted و بدون ورود به آن، نشان دهید.

```
meridian logs [SERVER] [--lines N] [--grep TEXT] [--component NAME]
              [--user USER] [--ssh-port PORT]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--lines`, `-n N` | `100` | تعداد خطوطی که از هر لاگ نشان داده می‌شود (`1`–`10000`) |
| `--grep`, `-g TEXT` | | فقط خطوط حاوی این متن؛ بدون حساسیت به حروف بزرگ و کوچک و به‌صورت لفظی تطبیق داده می‌شود، نه به‌عنوان regex |
| `--component`, `-c NAME` | همه | فقط `node`، `panel`، `nginx` یا `relay`؛ برای انتخاب چند مورد تکرار کنید |

`logs` همان چیزی را می‌خواند که نقش‌های سرور اجرا می‌کنند: exitها و routing gatewayها agent (`netagent`) و Xray (`netcore`) را زیر `node` نشان می‌دهند، سرور کنترل سرویس کنترل (`ctld`) را زیر `panel` نشان می‌دهد، هر دو لاگ خطای nginx را نشان می‌دهند و relayها ژورنال unitهای Realm خود را. `--user` و `--ssh-port` کاربر SSH ذخیره‌شده و پورت را جایگزین می‌کنند.

هر خط از همان redaction دستور `meridian doctor` عبور می‌کند: توکن‌ها، رمزهای عبور، کلیدها، UUIDها، شناسه‌های اشتراک و مسیرهای مخفی سرویس کنترل و صفحهٔ اتصال با `[REDACTED]` جایگزین می‌شوند، پس خروجی را می‌توان با اطمینان در گزارش باگ چسباند. خطوط به‌صورت متن ساده چاپ می‌شوند و کاراکترهای کنترلی ترمینال حذف شده‌اند.

سروری بدون نقش در ناوگان، یا `--component` که اجرا نمی‌کند، پیش از اتصال با کد `2` خارج می‌شود. لاگی که خوانده نشود (سرویس جاافتاده، قطع شدن اتصال SSH) به‌صورت غیرقابل دسترس نشان داده می‌شود و دستور با کد `3` خارج می‌شود.

### meridian panel

نشانی کنسول وب را نشان می‌دهد و تا وقتی کنسول مالک ندارد، یک لینک راه‌اندازی یک‌بارمصرف هم می‌دهد.

```
meridian panel [--setup-link]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--setup-link` | | حتی اگر کنسول مالک دارد، یک لینک بازنشانی چاپ می‌کند: رمز عبور تازه‌ای تعیین می‌کند، کد ورود را خاموش می‌کند و همهٔ دستگاه‌ها را از حساب خارج می‌کند |

لینک راه‌اندازی یک بار و به مدت ۱۵ دقیقه کار می‌کند؛ آن را باز کنید تا رمز عبور مالک را انتخاب کنید. وقتی کنسول مالک دارد، `panel` نشانی و روشن یا خاموش بودن کد ورود را چاپ می‌کند. هم با نشانی و هم با لینک راه‌اندازی مثل رمز عبور رفتار کنید. در کنسول افراد و توکن‌های API را مدیریت می‌کنید؛ سرورها، revisionها و عنوان اشتراک آنجا فقط‌خواندنی هستند. ببینید [کنسول وب](/fa/client-management/#کنسول-وب).

### meridian teardown

Meridian را از سرور حذف کنید.

```
meridian teardown [SERVER] [--user USER] [--ssh-port PORT] [--yes]
```

در یک استقرار تک‌سروری، `teardown` هر چیزی را که Meridian ساخته حذف می‌کند: سرویس کنترل و پایگاه داده‌اش، agent و Xray، پیکربندی nginx، گواهینامه‌ها، relay و قوانین firewall روی سرور، و سپس `cluster.yml` محلی و پروفایل سرور ذخیره‌شده. بسته‌های سیستمی، سخت‌سازی SSH و fail2ban باقی می‌مانند، و اگر nginx هنوز سایت‌های خود شما را سرو کند، به کار ادامه می‌دهد. همچنین 3x-ui مربوط به Meridian 3.x را حذف می‌کند. در ناوگان چندسروری، `teardown` سروری را که هنوز در توپولوژی نقشی دارد رد می‌کند.

`--yes` تأیید را رد می‌کند؛ بررسی‌های نقش همچنان اول اجرا می‌شوند. رد کردن exit `1` می‌شود. نام سرور نامعلوم، یا صفر یا چندین هدف ممکن، exit `2` بجای prompt.

### meridian backup

snapshotهای رمزنگاری‌شدهٔ وضعیت سرویس کنترل، ماشین‌هایی که آن‌ها را دریافت می‌کنند و کلید بازیابی.

```
meridian backup pull [--name NAME]
meridian backup recovery-key [--yes]
meridian backup devices
meridian backup revoke ID
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--name NAME` | نام میزبان این کامپیوتر | `backup pull`: نامی که کلید این ماشین در اولین ثبت می‌گیرد |
| `--yes`, `-y` | | `backup recovery-key`: کلید بازیابی موجود را بدون پرسش جایگزین می‌کند |

پس از هر دستوری که ناوگان را تغییر می‌دهد، Meridian تازه‌ترین snapshot سرویس کنترل را در `snapshots/` کنار `cluster.yml` ذخیره می‌کند (چند مورد آخر نگه داشته می‌شوند). snapshot شامل کاربران، محدودیت‌ها، ترافیک، revisionها، توکن‌های API و نسخه‌ای از `cluster.yml` و `servers.json` این ماشین است، پس می‌تواند ناوگان را روی ماشینی که هیچ چیز دیگری ندارد بازسازی کند. برای کلید هر ماشین ثبت‌شده و برای کلید بازیابی رمزنگاری می‌شود و هرگز کلید امضا، نشست یا رمز کنسول را در بر ندارد. ذخیره‌سازی ناموفق فقط هشدار می‌دهد و هرگز دستوری را که آن را به راه انداخته شکست نمی‌دهد.

**`backup pull`** — همین حالا یک snapshot ذخیره می‌کند. اولین pull روی هر ماشین کلید آن را می‌سازد (`device.key`، فقط برای شما قابل خواندن) و آن را در سرویس کنترل ثبت می‌کند.

**`backup recovery-key`** — کلید بازیابی ناوگان را می‌سازد، یا پس از پرسش کلید موجود را جایگزین می‌کند، و آن را یک بار نشان می‌دهد. Meridian فقط بخش عمومی آن را نگه می‌دارد، پس آن را بنویسید یا چاپ کنید و آفلاین نگه دارید. اولین deploy ناوگان از قبل یکی نشان می‌دهد. با `--json` در دسترس نیست.

**`backup devices`** — ماشین‌هایی را که snapshotها برای کلیدشان رمزنگاری می‌شوند، با شناسه و زمان ثبت هر کدام، و اینکه ناوگان کلید بازیابی دارد یا نه فهرست می‌کند.

**`backup revoke`** — رمزنگاری snapshotهای تازه برای کلید یک ماشین، مثلاً لپ‌تاپی گم‌شده، را متوقف می‌کند. snapshotهایی که از قبل دارد همچنان با کلیدش خوانده می‌شوند؛ پیش از آنکه snapshot تازه‌ای بگیرد آن را لغو کنید.

### meridian restore

سرور کنترل از دست رفته یا توقیف‌شده را از یک snapshot روی سرور دیگری بازسازی می‌کند.

```
meridian restore --to SERVER [--snapshot FILE] [--recovery-key] [--force]
                 [--name NAME] [--user USER] [--ssh-port PORT] [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--to SERVER` | (الزامی) | سرور کنترل جدید: IP، `user@IP:port` یا نام ذخیره‌شده |
| `--snapshot FILE` | تازه‌ترین ذخیره‌شده | snapshotی که بازیابی می‌شود |
| `--recovery-key` | | snapshot را به‌جای کلید این ماشین با کلید بازیابی باز می‌کند؛ کلید (به‌صورت پنهان) پرسیده می‌شود یا یک خط از ورودی استاندارد خوانده می‌شود |
| `--force` | | حتی اگر سرویس کنترل قدیم هنوز پاسخ می‌دهد بازیابی می‌کند |
| `--name NAME` | (هیچ) | نام سرور جدید |
| `--user/-u USER` | root | کاربر SSH روی سرور جدید |
| `--ssh-port PORT` | 22 | پورت SSH روی سرور جدید |
| `--yes`, `-y` | | تأیید را رد می‌کند |

restore snapshot را باز می‌کند، کارهایی را که انجام خواهد داد برای بازبینی نشان می‌دهد و تأیید می‌خواهد. سپس سرویس کنترل را از snapshot روی سرور جدید نصب می‌کند، سرور کنترل (و exit سرور قدیم، اگر داشت) را در توپولوژی شما به نشانی جدید منتقل می‌کند و apply بازبینی‌شدهٔ معمول را اجرا می‌کند. سرویس بازیابی‌شده مرجع صدور گواهی، کلیدهای امضا و توکن API تازه می‌گیرد، پس هر agent دوباره ثبت می‌شود و سرور توقیف‌شده نمی‌تواند چیزی امضا کند که گره‌های شما بپذیرند. کاربران حساب، محدودیت‌ها و ترافیک خود را نگه می‌دارند. مالک کنسول با لینکی از `meridian panel` رمز عبور تازه‌ای انتخاب می‌کند.

روی IP خالی، نشانی سرور کنترل بخشی از هر URL اشتراک است، پس همهٔ لینک‌ها عوض می‌شوند: بازبینی این را می‌گوید و در پایان لینک جدید هر کلاینت چاپ می‌شود. با دامنه، لینک‌ها همان می‌مانند، به محض اینکه رکورد DNS آن به سرور جدید اشاره کند؛ بازبینی نام این رکوردها را می‌آورد.

تا وقتی سرور کنترل قدیم پاسخ می‌دهد، restore اجرا نمی‌شود، چون دو سرویس کنترل ناوگان را دو تکه می‌کنند؛ `--force` این را نادیده می‌گیرد، مثلاً وقتی سرور قدیم توقیف شده است. اگر `--snapshot` به فایلی قدیمی‌تر از تازه‌ترین snapshot ذخیره‌شده اشاره کند هشدار می‌دهد: snapshot قدیمی‌تر توکن‌ها، ماشین‌ها و افرادی را که از آن زمان حذف کرده‌اید برمی‌گرداند. restore متوقف‌شده را می‌توان دوباره اجرا کرد و از همان جا ادامه می‌دهد.

روی ماشینی که ناوگان را ندارد، فایل snapshot و `--recovery-key` را بدهید: ابتدا نسخهٔ فایل‌های ناوگان که درون خود snapshot است بازیابی می‌شود. اگر نسخهٔ این ماشین قدیمی‌تر از نسخهٔ snapshot باشد، restore ناوگان را در یک زمینهٔ جدید قرار می‌دهد و پس از بازبینی‌ای که آن را نام می‌برد، ناوگان را از زمینهٔ قدیمی تحویل می‌گیرد؛ آن زمینه به‌عنوان جایگزین‌شده علامت می‌خورد و تا وقتی با `meridian context remove` حذفش نکنید هر تغییری را رد می‌کند.

### meridian migrate

ناوگانی را که روی پنل Remnawave اجرا می‌شود در جا و با حفظ همهٔ لینک‌ها به سرویس کنترل Meridian منتقل می‌کند.

```
meridian migrate [--yes]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--yes`, `-y` | | تأیید را رد می‌کند |

migrate ابتدا انتقال را برای بازبینی نشان می‌دهد: کلاینت‌هایی که منتقل می‌شوند، هر چیزی دربارهٔ یک کلاینت که نمی‌تواند حفظ شود، و داده‌های پنل که هیچ‌کس نگه نمی‌دارد (حساب مدیر و توکن‌های API پنل، تاریخچهٔ مصرف روزانه، ثبت دستگاه‌های HWID، پلاگین‌های پنل و قوانین پاسخی که Meridian تعیین نکرده، انتقال IP کلاینت‌ها (که برای محدودیت IP هر کاربر در پنل بود)، و صفحهٔ اشتراک Remnawave؛ صفحه‌های اتصال خود Meridian می‌مانند). پس از تأیید شما:

1. از پایگاه دادهٔ پنل، همراه با فایل‌های ناوگان، در `backups/` روی ماشین شما و در `/var/backups/meridian-migration/` روی سرور کنترل نسخهٔ پشتیبان می‌گیرد
2. سرویس کنترل را کنار پنل نصب می‌کند و هر کلاینت را با همان کلیدها، شناسهٔ اشتراک، وضعیت، محدودیت‌ها، تاریخ انقضا و ترافیک وارد می‌کند
3. پنل را متوقف می‌کند (داده‌هایش می‌مانند) و کانتینر هر گره را حذف می‌کند
4. ناوگان را apply می‌کند: هر exit یک agent ثبت‌شده در سرویس کنترل می‌گیرد
5. بررسی می‌کند که لینک اشتراک هر کلاینت دقیقاً همان قبلی باشد
6. Remnawave را حذف می‌کند

بازگشتی وجود ندارد؛ راه بازگشت همان نسخهٔ پشتیبان است. هر مرحله ذخیره می‌شود، پس انتقال متوقف‌شده با اجرای دوباره ادامه پیدا می‌کند و انتقال تمام‌شده کاری انجام نمی‌دهد. اگر بررسی لینک‌ها شکست بخورد، Remnawave سر جایش (متوقف) می‌ماند و دستور با خطا تمام می‌شود. بدون ترمینال `--yes` را بدهید؛ در غیر این صورت migrate پس از بازبینی متوقف می‌شود. `meridian deploy` وقتی ناوگانی روی Remnawave پیدا کند انتقال را پیشنهاد می‌دهد.

### meridian update

CLI را به آخرین release نسخه اصلی خود روی PyPI به‌روزرسانی کنید. نسخه اصلی جدید فقط اعلام می‌شود؛ `--major` بعد از خواندن یادداشت‌های release برای آن جابه‌جا می‌شود. نسخه beta نسخه‌های beta جدیدتر نسخه اصلی خود را دنبال می‌کند و سپس release پایدار. Meridian uv، pipx و pip را امتحان می‌کند، و فقط موفقیت را گزارش می‌کند زمانی‌که دستور `meridian` فعال نسخه جدید را نشان می‌دهد. Exit `0` قبلاً جاری یا به‌روزرسانی‌شده؛ `3` به‌روزرسانی یا تأیید آن ناموفق بود. به‌روزرسانی CLI سروری شما را تغییر نمی‌دهد.

```
meridian update [--major]
```

### meridian studio

Meridian Studio، یک browser UI تجربی را با Engine API محلی آن باز کنید. سرور فقط به `127.0.0.1` bind می‌شود.

```
meridian studio [--port PORT] [--assets-dir DIRECTORY] [--no-open]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--port PORT` | 7391 | پورت localhost از 0 تا 65535؛ `0` هر پورت آزادی را انتخاب می‌کند |
| `--assets-dir DIRECTORY` | bundled assets | Built Studio asset directory را بجای کپی package استفاده کنید |
| `--no-open` | | URL محلی را بدون باز کردن مرورگر چاپ کنید |

Studio نشانی‌ای مانند `http://127.0.0.1:7391/studio/#k=…` را چاپ می‌کند و باز می‌کند. بخش بعد از `#k=` کلیدی است که در هر اجرا عوض می‌شود. فقط تبِ مرورگری که با همین نشانی باز شده باشد می‌تواند از Engine استفاده کند، پس برنامه‌های دیگر و کاربران دیگرِ همان رایانه نمی‌توانند. آن را خصوصی نگه دارید. بعد از راه‌اندازی دوباره Studio، نشانی جدیدی را که چاپ می‌کند باز کنید.

بدون `--port`، Studio از پورت 7391 یا در صورت اشغال بودن، از پورت آزاد بعدی تا 7400 استفاده می‌کند؛ به این ترتیب پیش‌نویسی که مرورگر شما برای Studio ذخیره کرده بار بعد هم سر جایش است. اگر `--port` صریحی که داده‌اید اشغال باشد، Studio با خطای روشن متوقف می‌شود؛ نبودنِ فایل‌های رابط هم همین‌طور. پوشهٔ فایل‌های رابطی که صریحاً مشخص می‌کنید باید `studio/index.html` را داشته باشد.

### meridian serve

سرویس کنترل را اجرا می‌کند. Meridian آن را روی سرور کنترل به‌صورت واحد systemd ‏`ctld` نصب می‌کند که همین دستور را اجرا می‌کند؛ لازم نیست خودتان آن را اجرا کنید.

```
meridian serve [--config FILE]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--config FILE` | `/etc/ctld/config.json` | پیکربندی سرویس که Meridian می‌نویسد |

سرویس روی `127.0.0.1:3000` پشت nginx گوش می‌دهد و وضعیتش را در یک فایل SQLite زیر `/var/lib/ctld/` نگه می‌دارد. هیچ درخواستی را ثبت نمی‌کند، پس شناسه‌های اشتراک و مسیرهای مخفی هرگز به ژورنال نمی‌رسند. `meridian logs SERVER -c panel` لاگ آن را نشان می‌دهد.

### meridian api

قرارداد machine-readable پشت JSON output را برای اسکریپت‌ها و UI clients بازرسی کنید.

```
meridian api schemas [--json] [--include-schemas]
meridian api commands [--json] [--include-schemas]
meridian api schema NAME [--envelope|--json]
meridian api workflow NAME [--json]
```

| پرچم | پیش‌فرض | توضیح |
|------|---------|-------------|
| `--json` | | کاتالوگ را به عنوان پاکت `meridian.output/v1` ارسال کنید |
| `--include-schemas` | | JSON Schemas کامل را شامل کنید (JSON output را نتیجه می‌دهد) برای `api schemas` یا `api commands` |
| `--envelope`, `--json` | | `api schema NAME` را در پاکت `meridian.output/v1` wrap کنید بجای چاپ schema خام |

**`api schemas`** — نام‌های schema مثل `output-envelope`، `deploy-request`، `deploy-result`، `deploy-plan`، `plan-envelope`، `apply-envelope`، `client-list-envelope`، `fleet-status-envelope` و `event` را فهرست می‌کند.

**`api commands`** — قرارداد دستورها را فهرست می‌کند: argv، schema envelope و data، statusها و outcomeهای ممکن، معانی کد خروج، همه گزینه‌هایی که دستور می‌پذیرد (`machine_flags`) و `interrupt_behavior`. آرگومان‌ها، گزینه‌ها و توضیحات از خود CLI خوانده می‌شوند. Ctrl-C بدون JSON envelope با کد `130` خارج می‌شود (`interrupt_behavior: "exit_130_without_envelope"`).

**`api schema NAME`** — یک JSON Schema چاپ می‌کند، مثل `meridian api schema output-envelope`.

**`api workflow NAME`** — workflow UI-renderable چاپ می‌کند، مثل `meridian api workflow deploy --json`.

### meridian help

Meridian را به یک عامل هوش مصنوعی معرفی می‌کند، یا راهنمای یک دستور را نشان می‌دهد.

```
meridian help [agents | COMMAND...]
```

**`meridian help agents`** یک راهنمای Markdown برای عامل‌های هوش مصنوعی چاپ می‌کند: Meridian چه کاری انجام می‌دهد، ناوگان و توپولوژی بازبینی‌شده‌اش چطور به هم مربوط‌اند، وضعیت کجا نگه‌داری می‌شود، قواعد اجرای امن CLI (پرچم‌های غیرتعاملی، پاکت‌های JSON، plan پیش از apply، تأیید پیش از حذف، لینک‌ها به‌عنوان رمز)، کدهای خروج و کارهای رایج. خروجی همیشه Markdown ساده است، پس عامل می‌تواند آن را از pipe بخواند.

**`meridian help COMMAND`** همان راهنمای `meridian COMMAND --help` را نشان می‌دهد، مثلاً `meridian help node add`. بدون آرگومان، راهنمای سطح بالا را چاپ می‌کند. موضوع ناشناخته با کد `2` خارج می‌شود.

## گزینه‌های سراسری

گزینه‌های سراسری قبل دستور می‌روند، مثل `meridian --quiet doctor`. گزینه‌های دستور مثل `test --json` بعد از آن می‌روند.

| پرچم | توضیح |
|------|-------------|
| `--version`, `-v` | نسخه CLI را نشان داده و خروج کنید |
| `--verbose` | فعال کردن debug logging |
| `--quiet`, `-q` | output پیشرفت را suppress کنید |
| `--context NAME` | کار روی ناوگان دیگر ([meridian context](#meridian-context))؛ پیش‌فرض: `MERIDIAN_CONTEXT`، وگرنه زمینهٔ فعلی. بعد از دستور هم پذیرفته می‌شود، مثل `meridian deploy 203.0.113.5 --context work` |
| `--lang CODE` | زبان برای wizard setup: `en`, `ru`, `fa` یا `zh` (پیش‌فرض: انتخاب ذخیره‌شده، وگرنه پرسیده می‌شود) |
| `--json` | درخواست JSON envelope از دستور که آن را پشتیبانی می‌کند؛ دستورات دیگر صریح ناموفق می‌شوند |
| `--install-completion` | shell completion برای shell فعلی نصب کنید |
| `--show-completion` | completion script برای shell فعلی چاپ کنید |

JSON output پاکت `meridian.output/v1` را استفاده می‌کند (`schema`، `command`، `operation_id`، `status`، `summary`، `data`، `warnings`، `errors`). هر دستوری که `--json` دارد از آن پشتیبانی می‌کند: deploy، plan، apply، check، test، probe، تمام client و route commands، fleet status/inventory/history/export/import، node/relay list و api commands. `--json` سراسری و `--json` خود دستور به‌جای هم قابل استفاده‌اند. اسرار قبل از JSON خروج process redacted می‌شوند. `meridian api commands --json` را برای اکتشاف قرارداد اجرا کنید.

## گزینه‌های سرور معمول

این گزینه‌ها در دستورات عود می‌آیند؛ هر دستور فقط گزینه‌های فهرست‌شده در بخش خود را قبول می‌کند.

| پرچم | استفاده‌شده توسط |
|------|---------|
| `SERVER` argument | deploy، check، scan، test، doctor، logs، teardown، node add، relay add، server add |
| `--user`, `-u USER` | deploy، check، node add، relay add، server add، scan، doctor، logs، teardown، restore |
| `--ssh-port PORT` | deploy، check، node add، relay add، server add، scan، doctor، logs، teardown، restore |
| `--sni HOST` | deploy، check، node add، relay add، test، doctor |
| `--domain DOMAIN` | deploy، check، node add، test |
| `--self-steal` | deploy، node add، node sni |

دستورات client مستقیم از API سرویس کنترل استفاده می‌کنند و سرور نمی‌گیرند. `test` از دستگاه شما اجرا می‌شود و SSH استفاده نمی‌کند.

## تفکیک سرور

سرور را مانند `ssh` اول بنویسید: یک IP، یک نام ذخیره‌شده، `user@host:port` یا `local` برای اجرا روی همین ماشین بدون SSH. `--user` و `--ssh-port` بخش‌هایی را که در هدف نیامده کامل می‌کنند و نباید با آن تناقض داشته باشند. کاربر یا پورت خالی یعنی مقدار ذخیره‌شده، و اگر نباشد `root` و `22`. بدون سرور، Meridian از حالت محلی (هنگام اجرا روی سرور مستقرشده) یا تنها سرور ذخیره‌شده استفاده می‌کند. اگر هیچ نامزدی نباشد یا چند نامزد باشد، فرمان به‌جای پرسیدن با کد `2` خارج می‌شود.
