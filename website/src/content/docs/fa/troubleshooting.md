## کدام ابزار را استفاده کنید

```
قبل از نصب                   → meridian check IP
  "آیا این سرور برای Meridian مناسب است؟"
  بررسی‌ها: در دسترس بودن SNI، پورت 443، DNS، سیستم‌عامل، فضای دیسک.

بعد از نصب، آیا سالم است؟   → meridian check
  "آیا سرویس کنترل، agentها، relayها، پورت‌ها و گواهی‌ها سالم هستند؟"
  هر سرور در ناوگان را بر اساس نقش آن از طریق SSH بررسی می‌کند.

بعد از نصب، وصل نمی‌شود     → meridian test IP
  "آیا VPN از شبکه‌ای که الان در آن هستم در دسترس است؟"
  بررسی‌ها: پورت‌های پیکربندی‌شده، TLS/SNI، اشتراک تحویل‌شده و ترافیک واقعی VPN.
  بدون نیاز به SSH — از دستگاه کلاینت اجرا می‌شود.

بعد از نصب، بررسی لو رفتن   → meridian test IP --probe
  "آیا این سرور نشانی از VPN یا پنل مدیریت لو می‌دهد؟"
  بررسی‌ها: پورت‌های عمومی، رفتار TLS/HTTP، مسیرها، SNI، DNS و سیاست توپولوژی.
  بدون نیاز به SSH — از دستگاه کلاینت اجرا می‌شود.

بعد از نصب، چیزی خراب شده   → meridian doctor IP
  "جمع‌آوری همهٔ اطلاعات برای عیب‌یابی."
  جمع‌آوری: سیستم‌عامل سرور، سرویس‌های Meridian، لاگ‌های agent و nginx، پورت‌ها، فایروال، SNI، DNS.
```

`--ai` را به check یا doctor برای یک prompt تشخیصی آماده AI اضافه کنید.

## نمی‌تواند اصلاً اتصال برقرار کند

### پورت 443 در دسترس نیست

**علت‌ها:**
1. firewall ارائه‌دهندهٔ ابری / security group پورت 443 ورودی را مسدود می‌کند
2. ISP یا شبکه کل IP سرور را مسدود می‌کند
3. سرور خاموش است یا سرویس‌های VPN اجرا نمی‌شوند
4. UFW روی سرور پورت 443 را مجاز نکرده است

**راه‌حل‌ها:**
1. کنسول ارائه‌دهندهٔ ابری را بررسی کنید — مطمئن شوید پورت 443/TCP ورودی باز است
2. از شبکهٔ دیگری امتحان کنید (اینترنت موبایل، Wi-Fi دیگر)
3. با SSH وصل شوید و بررسی کنید: `systemctl status ctld netagent netcore nginx` (آیا همه فعال‌اند؟)، `ss -tlnp sport = :443`
4. UFW را بررسی کنید: `ufw status` — باید 443/tcp ALLOW را نشان دهد

### خطا در handshake مربوط به TLS

**علت‌ها:**
1. Xray (`netcore`) اجرا نمی‌شود
2. پورت 443 توسط سرویس دیگری اشغال شده است
3. هدف SNI در Reality از روی سرور در دسترس نیست

**راه‌حل‌ها:**
1. Xray را بررسی کنید: `meridian logs IP -c node -n 20`
2. پورت را بررسی کنید: `ss -tlnp sport = :443` — باید nginx باشد
3. SNI را آزمایش کنید: `meridian check IP --sni HOST`

### دامنه قابل رسیدن نیست

**علت‌ها:**
1. DNS به IP سرور اشاره نمی‌کند
2. nginx اجرا نمی‌شود یا TLS certificate دریافت نکرد
3. nginx مسیریابی SNI domain را درست انجام نمی‌دهد

**راه‌حل‌ها:**
1. DNS را بررسی کنید: `dig +short yourdomain.com @8.8.8.8`
2. nginx را بررسی کنید: `systemctl status nginx`
3. فایل‌های nginx routing را بررسی کنید: `ls /etc/nginx/stream.d/ /etc/nginx/sites-enabled/` (فایل‌های Meridian `meridian-v4-` شروع می‌شوند) و `nginx -t`

## اتصال پس از چند ثانیه قطع می‌شود

**علت‌ها:**
1. مسائل MTU در مسیر شبکه
2. ISP قطع کردن جلسات TLS طولانی

**راه‌حل‌ها:**
1. شبکه دیگری امتحان کنید
2. مسیر XHTTP یا WSS استفاده کنید (حالت domain)

## Deploy ناموفق

### "ترافیک هیچ از طریق آن عبور نمی‌کند"

سرور deploy شد اما ترافیک واقعی از طریق هدف پنهان‌سازی انتخاب‌شده با `--sni` جریان نیفتاد. هدف دیگری انتخاب کنید — `meridian scan IP` در شبکه سرور خود موارد را پیدا می‌کند — و دستور deploy را دوباره با `--sni` جدید اجرا کنید. بدون `--sni`، Meridian قبلاً `www.google.com`، `dl.google.com` و `www.cloudflare.com` را به ترتیب امتحان می‌کند.

### "سرور نمی‌تواند به هدف پنهان‌سازی Reality برسد"

سرور HTTPS outbound کار نمی‌کند به هدف پیش‌فرض. firewall outbound provider را بررسی کنید یا هدف قابل دسترس را با `--sni` پاس دهید.

### Deploy قطع‌شده یا ناموفق

Deploys و applies checkpoint شده‌اند. علت گزارش‌شده را برطرف کنید و دستور یکسان را دوباره اجرا کنید؛ مراحل تمام شده پرش می‌شوند.

### تداخل پورت 443

سرویس دیگری (Apache، nginx) از پورت 443 استفاده می‌کند. آن را متوقف کنید یا از سروری تمیز استفاده کنید. `meridian check IP` نشان می‌دهد چه سرویسی پورت را در اختیار دارد.

### انتقال از Remnawave متوقف می‌شود

`meridian migrate` پس از هر مرحله پیشرفت خود را ذخیره می‌کند. علت گزارش‌شده را برطرف کنید و دوباره اجرا کنید؛ از همان جایی که متوقف شده ادامه می‌دهد و انتقال تمام‌شده کاری انجام نمی‌دهد. پیش از هر تغییری، از پایگاه دادهٔ پنل در `~/.config/meridian/backups/` و در `/var/backups/meridian-migration/` روی سرور کنترل نسخهٔ پشتیبان گرفته می‌شود. اگر پس از apply بررسی لینک‌ها شکست بخورد، Remnawave سر جایش (متوقف) می‌ماند و دستور این را اعلام می‌کند: این یک باگ است، پس با خروجی `meridian doctor` یک [issue باز کنید](https://github.com/getmeridian/meridian/issues).

### خطاهای اتصال SSH

اتصال SSH را دستی آزمایش کنید: `ssh root@SERVER_IP`. مطمئن شوید دسترسی مبتنی بر کلید دارید. اگر کاربر شما `root` نیست، از پرچم `--user` استفاده کنید. اگر سرور فقط گذرواژه می‌پذیرد، `meridian deploy` را در یک ترمینال و بدون `--yes` اجرا کنید تا کلید را نصب کند (ببینید [سرورهای فقط با گذرواژه](/fa/deploy/#سرورهای-فقط-با-گذرواژه))، یا یک بار `ssh-copy-id root@SERVER_IP` را اجرا کنید.

### agent گره آفلاین است یا پیکربندی را اعمال نمی‌کند

لاگ‌ها را بررسی کنید: `meridian logs IP -c node -n 50` agent (`netagent`) و Xray (`netcore`) را نشان می‌دهد. علت‌های معمول تداخل پورت روی میزبان (Xray پورت‌های توپولوژی شما را مستقیم می‌گیرد، پس باید آزاد باشند) یا exitی است که از طریق TCP 443 به سرور کنترل نمی‌رسد (agent خودش به آن وصل می‌شود؛ فایروال خروجی ارائه‌دهنده را بررسی کنید).

**راه‌حل:** `meridian check IP` را اجرا کنید و راه‌حل‌های آن را دنبال کنید، سپس `meridian apply`: agentی را که هویتش را از دست داده دوباره ثبت می‌کند و agentی را که build قدیمی دارد ارتقا می‌دهد. `meridian fleet status` نشان می‌دهد هر agent آنلاین است و پیکربندی فعلی را اعمال کرده یا نه؛ صفحهٔ **Servers** در پنل وب هم همین را نشان می‌دهد.

### فضای دیسک ناکافی

کمتر از 2GB آزاد. فضا خالی کنید: `journalctl --vacuum-time=1d`، `apt-get clean`، `/var/log/` را بررسی کنید.

### DNS resolution ناموفق (حالت domain)

certificate برای دامنه شما تنها زمانی می‌تواند صادر شود که رکورد A دامنه به سرور اشاره کند (ابر خاکستری در حین deploy). رکورد را به‌روز کنید، برای تکثیر انتظار دهید (معمولاً 5–15 دقیقه)، سپس دستور deploy یکسان را دوباره اجرا کنید. `meridian check IP --domain DOMAIN` این را قبل از deploy بررسی می‌کند.

## کار می‌کرد، اکنون متوقف شد

**بیشترین علت معمول:** IP سرور مسدود شد. `meridian test IP` را اجرا کنید؛ یافته‌های آن قابلیت رسیدن شبکه را از TLS، اشتراک و شکست‌های تونل تمایز می‌کند. شکست TCP می‌تواند فایروال ابری یا سرور آفلاین هم باشد.

[راهنمای بازیابی IP مسدود](/fa/recovery/) را برای گزینه‌های بازیابی (خروجی جایگزین، relay، fallback CDN) ببینید.

علت‌های دیگر:
- سرور reboot شد و سرویس‌ها شروع نشدند → `meridian plan` نشان می‌دهد چه چیز خاموش است و `meridian apply` تعمیر می‌کند. دستی: `systemctl restart ctld netagent nginx`
- دیسک پر — `df -h /`، `journalctl --vacuum-time=1d`
- سرور کنترل برای همیشه از دست رفته — آن را با `meridian restore` از یک snapshot بازسازی کنید ([سرور کنترل از دست رفت](/fa/recovery/#سرور-کنترل-از-دست-رفت))
- اتصال برقرار است اما سایت‌ها با نام باز نمی‌شوند (با نشانی IP باز می‌شوند) — سرور خروجی به هیچ‌یک از resolverهای DNS رمزگذاری‌شده‌اش نمی‌رسد. `meridian check` آن‌ها را زیر **Encrypted DNS** نام می‌برد؛ TCP 443 خروجی به آن نشانی‌ها را در فایروال ارائه‌دهنده باز کنید

## سرعت کم

1. سرور جغرافیایی نزدیک‌تر انتخاب کنید (فنلاند، هلند، سوئد برای اروپا/خاورمیانه)
2. بار سرور را بررسی کنید: `htop` یا `uptime`
3. مسیر XHTTP یا WSS را امتحان کنید (حالت domain) — مسیریابی از طریق Cloudflare گاهی بهتر است
4. تأیید BBR فعال است: `sysctl net.ipv4.tcp_congestion_control`

**هرگز** پروتکل‌های دیگر (OpenVPN, WireGuard) را روی سرور یکسان اجرا نکنید — IP را flag می‌کند.

## تفسیر خروجی preflight

| بررسی | آنچه آزمایش می‌کند | اگر ناموفق باشد |
|-------|--------------|-------------|
| Camouflage target | آیا سرور می‌تواند به سایت استتار دسترسی پیدا کند؟ | ترافیک خروجی سرور محدود است. با `--sni` هدف دیگری امتحان کنید |
| Camouflage target DNS | آیا سایت استتار از طریق DNS سرور ترجمه می‌شود؟ | تنظیمات DNS سرور را اصلاح کنید یا سایت استتار دیگری انتخاب کنید |
| Port 443 | آیا پورت 443 آزاد است یا در اختیار Meridian است؟ | سرویس دیگری روی پورت 443 است. آن را متوقف کنید یا از سرور تمیز استفاده کنید |
| Port 443 from outside | آیا پورت 443 از بیرون قابل دسترسی است؟ | فایروال ابری آن را بسته است. پورت ورودی 443/TCP را باز کنید |
| Domain DNS | آیا دامنه به IP سرور اشاره می‌کند؟ | رکورد A در DNS را به‌روز کنید |
| Server OS | آیا سیستم‌عامل Ubuntu یا Debian است؟ | سیستم‌های بدون apt (CentOS، Fedora، Alpine) خطا می‌دهند؛ Ubuntu یا Debian نصب کنید |
| Disk space | آیا حداقل 2GB فضای خالی وجود دارد؟ | فضای دیسک را خالی کنید |
| Clock sync | آیا اختلاف ساعت کلاینت و سرور کمتر از یک دقیقه است؟ | یکی از دو طرف زمان را همگام نمی‌کند. NTP و ساعت خودکار را روی هر دو دستگاه فعال کنید |

## تفسیر خروجی doctor

| بخش | چه چیزی را بررسی کنید |
|---------|-----------------|
| Local Machine | سازگاری سیستم‌عامل محلی |
| Server | نسخهٔ سیستم‌عامل، زمان روشن بودن (reboot اخیر؟)، مصرف دیسک و حافظه |
| Services | آیا `ctld` (سرویس کنترل)، `netagent` (agent) و `netcore` (Xray) فعال هستند؟ |
| Exit node Logs | خطاهای راه‌اندازی agent و Xray، پیام‌های "failed to start"، مشکلات گواهی |
| Listening Ports | پورت 443 باید nginx را نشان دهد. اگر نبود، nginx در حال اجرا نیست |
| Firewall (UFW) | پورت 443/tcp باید ALLOW باشد. اگر در فهرست نبود، بسته است |
| Camouflage Target | باید CONNECTED را همراه با زنجیرهٔ گواهی نشان دهد |
| Domain DNS | باید به IP سرور ترجمه شود |

## تفسیر خروجی test

| بررسی | موفق | ناموفق یا ردشده |
|-------|------|-----------------|
| قابلیت رسیدن TCP | هر listener عمومی TCP پیکربندی‌شده در دسترس است | firewall، مسدودسازی ISP، خاموش بودن سرور یا توپولوژی نادرست |
| استتار TLS/SNI | هدف هویت استتار مورد انتظار را نشان می‌دهد | عدم تطابق مسیریابی TLS، گواهی، DNS یا SNI |
| ریشهٔ دامنه | پاسخ مقاوم‌سازی‌شدهٔ `403`/`404` در دسترس است | خطای DNS/nginx یا محتوای عمومی ناخواسته |
| اشتراک | سرویس کنترل یک Xray JSON معتبر برای کلاینت فعال تحویل داد | نبودن یا غیرفعال بودن کلاینت، یا در دسترس نبودن سرویس کنترل |
| جایگزینی خودکار | سیاست تحویل‌شده ترافیک واقعی را عبور داد | خطای balancer، مسیریابی، اعتبارنامه یا نقطهٔ پایانی |
| بررسی‌های پروتکل | هر مسیر خروجیِ هدف ترافیک واقعی را عبور داد | خطای listener پروتکل، فایروال یا پیکربندی تحویل‌شده |

آزمایش کامل چند سرویس مستقل تشخیص IP عمومی را می‌چرخاند و همان سرویس‌ها را مستقیم هم بررسی می‌کند. اگر نه تونل VPN و نه مسیر مستقیم نتوانند IP را دریافت کنند، نتیجه به‌جای خطای کاذبِ پروتکل، نامشخص (inconclusive) اعلام می‌شود. متغیر `MERIDIAN_CONNECT_TEST_URL` را فقط زمانی تنظیم کنید که خودتان یک سرویس تشخیص IP شناخته‌شده دارید.

اولین اجرای کامل ممکن است تا 120 ثانیه صرف دانلود و بررسی نسخهٔ پین‌شدهٔ Xray از GitHub کند. پس از آن، `--timeout` (پیش‌فرض `5`، بازهٔ `1` تا `30`) روی تک‌تک عملیات شبکه اعمال می‌شود. کد خروج `0` یعنی موفقیت، `4` یعنی یافتن مشکل، و `3` یعنی نتیجهٔ نامشخص به‌دلیل نبود شواهد لازم. حالت `--basic` نمی‌تواند ترافیک Hysteria2 را که فقط روی UDP است تأیید کند.

اگر همهٔ بررسی‌ها موفق بود اما برنامهٔ VPN هنوز وصل نمی‌شود: کد QR را دوباره اسکن کنید، مطمئن شوید تاریخ و ساعت دستگاه روی حالت خودکار است، یا یکی دیگر از برنامه‌های پیشنهادی (Happ، FlClashX، Clash Mi، یا Throne روی دسکتاپ) را امتحان کنید.
